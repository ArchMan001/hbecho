本轮重组已把领域语言、产品路线、数据底座、访问控制、规则和指标拆到正确层次；`CONTEXT.md` 未混入表、SQL、框架或任务，下游也未重建平行 Staff、账号、归属、组织或媒资主档。旧表名、Dealer 错误路径和统一 `async=false` 在现行文档中只作为反例或证据限制出现。四个 fixture 的关键事实自洽：抖音 profile 为 `HITACHI1`，列表 20 条（19 条 `HITACHI1`、1 条 `HITACHI2023`）且 cursor 为 integer；小红书 profile 为 `49328995493`，21 条作者均为 `5decba2300000000010007e1` 且 cursor 为 string。**confirmed** 阻断点集中在高权威 v2 与 tracer 合同无法同时成立，以及一份 archive 文件仍宣称自己可实施。

## High-level view

领域边界已经收敛，历史模块稿和两份域 E 材料也大多有明确的禁止用途头；**confirmed** 例外是 `database-design-v1.md`，它仍以“P0 可实施基线”开篇。

tracer 三份文档覆盖了目标行为，但 **confirmed** v2 的物理合同装不下 R10 checkpoint 元数据，Discovery 唯一键也与 R9 occurrence 语义冲突。**confirmed** v2 同时把首次列表写成 `<=20`，并把详情/评论列入“tracer flow”，与当前 21 条 fixture 和 Feature 非目标相反。

tracer design 要求发送前 capture request，v2 却从收到响应后才开始落地；**confirmed** 这留下远端已收费、本地没有 durable intent 的窗口。**confirmed** 总纲中的“resolve_account 是否复用 media_user_info”也未进入 tracer P0 或任务，导致一次或两次付费请求都符合当前文字。

下游 draft 的主要缺口在 owner 和生命周期：**confirmed** `AttributionSnapshot` 同时被列为 Rule-owned 和 P0 未定 owner，Metrics 同时定义显式 `activate()` 与 build 自动激活。**confirmed** INDEX 未编目 always-included steering，而 steering 与 INDEX 对历史文档存放位置又给出不同规则。

## `database-design-v1` 仍在 archive 中自称可实施

**Blocking — confirmed.** [`HBECHO设计方案/archive/data-foundation/database-design-v1.md:1-8`](../data-foundation/database-design-v1.md) 没有 archived/superseded、替代文档或禁止用途头，反而声明“文档状态：P0 可实施基线”。这与 [`HBECHO设计方案/INDEX.md` §8.1](../../INDEX.md) 将其标成 archived，以及 [`.kiro/steering/structure.md`](../../../.kiro/steering/structure.md) 要求被替代文件文首标明状态、替代文档和禁止用途直接冲突。应在正文前加入 archive banner，指向 v2，并明确旧 DDL、状态与假设不得实施；历史正文可原样保留。

## `sync_checkpoints` 无法承载 R10 的原子 effect

**Blocking — confirmed.** R10、tracer design §11.4 和 task 6 要求 checkpoint 原子固定 cursor 值及类型、`has_more`、page ordinal、processed count、ProviderCall、Adapter version、completedAt 和 fence。v2 [`database-design-v2.md` §9.4](../../domains/data-foundation/database-design-v2.md) 只有 cursor envelope/hash、task/batch 引用、continuity 状态、version 和 `updated_at`；page/count/`has_more` 位于一年期 task，ProviderCall 和 Adapter version 也不在 checkpoint，清理后引用会置空。应让 v2 直接承载所需长期字段，或在 R10 明确哪些 lineage 一年后允许丢失；task 6 不能自行创建平行结构。

## Discovery 唯一键会吞掉同一列表的重复 occurrence

**Blocking — confirmed.** R9.3 要求多个 entry 指向同一内容时保留每个 qualifying `ContentDiscovery`，task 6 也覆盖 duplicate entry 和 same content multiple discoveries。v2 [`database-design-v2.md:627-631`](../../domains/data-foundation/database-design-v2.md) 的 `UQ(batch_id, assignment_id, content_id)` 禁止同一 assignment/batch 的第二次出现，即使 page、position 和 ProviderCall 不同。必须先决定 Discovery 是去重事实还是列表 occurrence；前者需修改 R9/task 6，后者需把 occurrence 维度加入唯一键或拆表。

## ProviderCall durable intent 建立得太晚

**Blocking — confirmed.** tracer design §8.3 在发送前 capture exact request bytes，R14.5 又要求恢复不重复已完成付费 effect；v2 §12.4 却从“收到响应后”才上传 request/response 并插入 call/payload。供应商已接收请求、但本地提交前崩溃时，系统既不知道是否计费，也没有可恢复 intent。v2 应明确发送前持久化 logical call intent 和 request bytes，网络期间不持事务，之后再落 response/error；结果不明的调用进入可审计 ambiguous/reconcile 状态。

## `<=20` 不能表达完整 21 条首屏

**Major — confirmed.** R9.2/R9.5 规定 local limit 只在页边界生效；实测小红书第一页为 21 条。v2 §9.1、§9.4 和 §12.2 分别写 `initial_content_limit` 仅 1–20、“首次采集最多取”以及“首次列表（<=20）”，容易被实现成数组切片，尽管 v2 另一处要求整页处理。20 可以保留为续页目标，但 v2 应删除返回条目上限语义，并把 21-entry fixture 纳入验收。

## v2 把详情和评论留在当前 tracer 范围

**Major — confirmed.** tracer requirements §2.2/design §3.2 排除内容详情、评论和完整后续分页，v2 §19 第 10 步却把详情、评论列入“tracer flow”。由于 v2 权威更高，“完成 tracer”现在有两个验收边界。应将该步骤收窄到当前首屏/封面 slice，并把详情、评论放入后续 Spec；另一选择是同步扩充 requirements/design/tasks。

## TracerRoot/TracerCommand 没有 v2 persistence mapping

**Major — confirmed.** tracer 要保存 canonical command、`actor + idempotency_key`、payload hash、root/stage、cancel、logical-effect keys 和审计事件，并以 `root_task_id` 查询；v2 只提供 batch/task 的通用 key 和 `task_parameters`，没有说明 root 映射到 batch、resolve task 还是新事实。tracer 还说 namespace 名称实现前锁定，而 v2 §6.3 已指定 `xiaohongshu.profile.user_id` 与 `xiaohongshu.content.user_id`。设计应逐项映射到 v2；如需新表/列，必须先改基线，不能藏进无约束 JSON。

## `resolve_account` 是否复用 profile payload 未下沉

**Major — confirmed.** [`prd-platform.md` §12.1(2)](../../prd-platform.md) 将复用 `media_user_info` 还是第二次付费请求列为 P0，tracer Open Decisions/tasks 却没有该项，也没有 ProviderCall 数量断言。两种实现的成本、幂等恢复和 lineage 不同。应把决定加入 P0/task 1；未决时 fail closed，而不是默认多付一次。

## 主导作者规则在唯一最高与 plausibility gate 间冲突

**Major — confirmed.** R6.1 规定唯一最高时 SHALL bind，R6.2 又规定未通过 configured plausibility checks 时 SHALL NOT bind；design §10.3/Open Decision 7 尚未决定绝对多数或最低占比。4/3/3 之类分布因此没有唯一结果，task 5 也只覆盖全 21 条同作者和 tie。实现前应冻结版本化 policy，或把 R6.1 改为“唯一最高且通过 policy”，再测试低占比、空作者和异常分布并保留 evidence counts。

## 强制失败路径没有明确任务 owner

**Major — likely.** Requirements 引用虽覆盖 R2/R3/R4/R7/R15，但 task 4 只实现抖音 Home locator 和无冲突 Assignment，task 5 未写小红书解析/平台错配/三次失败；assignment conflict 只在最终验收出现。R2.6 一年 expiry/cleanup 没有 task acceptance，R15.4 redaction 也缺少针对 secret、raw body、完整 ODS key、临时 URL 和越权 ID 的负向断言。应把这些路径分配到 task 3/4/5，并增加离线故障注入或 redaction snapshot。

## Capability 证据等级与生产启用混在一个开关

**Major — confirmed.** task 1 要“启用证据支持的 tuple”，`CapabilityProfile` 却只有 `verifiedAt`/`enabled`；raw3 能证明同步响应形态，但不能证明 raw capture，认证也仍需批准 smoke。task 8 只明确异步生产禁用，v2 §17 还把“25 个捕获包络 → ProviderCall + OSS payload”写成“覆盖”。应区分 fixture-observed、supplier-declared、smoke-verified、production-enabled 和环境，并要求批准 smoke 才能提升生产 tuple；v2 矩阵应改成“字段形态覆盖，raw-before-parse 未验证”。

## INDEX 的唯一权威入口仍是双轨

**Major — confirmed.** 三份 [`.kiro/steering`](../../../.kiro/steering/) 都是 `inclusion: always`，却不在 INDEX 的导航、状态矩阵或权威顺序中；若它们只是派生镜像，INDEX 也未定义来源和漂移处理。structure steering 要求 superseded/archived 文件进入 `HBECHO设计方案/archive/`，INDEX §4/§8.2 却长期保留 `HBECHO设计方案/archive/legacy/项目历史文档/` 和根目录域 E 作为第二历史位置。应登记 steering 的派生地位并统一 archive 位置，或在 structure 中写出受控例外。

## AttributionSnapshot owner 与授权权威未闭合

**Major — confirmed.** Rule §4.1 把 `AttributionSnapshot` 列为 Rule-owned，同一行/Open Decision 13 又说 owner 未定；Metrics §8.3 强制 outcome 携带它，同时仍把 owner 作为 P0；Access Control 也保留同一 P0。Rule §2 还未列 Access Control，尽管后文使用 DataScope、异步范围和 Capability。应先把该概念标为 unresolved cross-domain contract，决定 owner/schema/freeze time 后再归域，并把 Access Control 加入 Rule 的授权语义权威链。

## CampaignProjection 同时显式和自动激活

**Major — confirmed.** Metrics §5.2 暴露 `build/getStatus/activate`，§9.2 sequence 却在 `write candidate` 后立即 `atomic activate projection`。两者对强制激活审计、重复事件和旧 projection 保留有不同语义。若自动激活，应删除公开 `activate`；若显式激活，build 应停在 ready candidate，由带权限和理由的命令切换，并补状态/验收。

## 空 Access Control requirements 制造假完备

**Minor — confirmed.** `.kiro/specs/access-control/requirements.md` 为 0 字节，而 INDEX/design 将该模块定义为 design-only draft。应删除空占位，或写明 `not started / non-authoritative`；文件存在本身不能替代需求合同。
