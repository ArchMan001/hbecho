## R3 · D 域判定语义（最重要，影响 D、E 两个 spec）

这一章的问题不是文字不一致，而是按现在的规则，业务配不出常见的考核，或者会算出错误的结论。改动会连带 E 域，建议在写 `d-rule-engine` 的 requirements 之前定下来。

### R3-01 三层漏斗按「专员」推进还是按「内容」推进

> **2026-11-04**：用户选 A′；内容集合逐层传递，不保留分项率。见 §8.4 / §8.7。

- **位置**：D-D01、D-D06、D-D07；D §2.0.2；D §2.0.1；D §2.1；D §2.2 开头。
- **现状**：文档里有两种说法。
  - 按专员：D-D01「三层按专员推进」；§2.0.2「同层所有考核项全部通过，才进入下一层」「到达该层 = 通过前面所有层全部考核项的专员」；§2.0.1 第 2 页「对到达本层的专员内容执行比对」。
  - 按内容：§2.0.1 第 1 页「点击确认 → 返回圈定条数」；§2.1「候选规模：千级 → 百级 → 十级」；§2.2「把活动范围内的全部内容，缩到值得继续看的一批」；A §7.5「活动规则先用不花钱的条件过滤」。
- **核实**：准确，是本文档里最重要的一处歧义。
- **背景**：两种读法结果不同。业务最常见的要求是「发 ≥ 3 条**带 #618 且封面合规**的视频」。
  - 按专员推进：#618 是第 1 层一个考核项，封面是第 2 层一个考核项，各自按专员聚合。专员 A 发了 3 条带 #618 但封面不对的视频，又发了 3 条封面对但没带话题的视频，会**两项都通过**。D-D07 又规定不做跨考核项组合，所以这个要求配不出来。
  - 第 2 层还会对「到达本层的专员」的**全部内容**做比对，包括第 1 层没圈中的内容，比对数量和 ASR 费用都会变大。
- **选项**：
  - A（推荐）：**内容漏斗 + 最后按专员聚合**。
    - 第 1 层：圈定内容。计划级公共条件 + 第 1 层条件，同一条内容必须全部满足（AND）。
    - 第 2、3 层：只对上一层留下的内容做比对和理解，同一条内容仍是 AND。
    - 最后：每个专员数一下「通过全部层的内容」有几条，用**一个**专员级达标方式（至少 N 条 / 全部 / 任一 / 比例）判定。
    - 账号级考核项（头像、背景匹配）单独判，和内容结果 AND 合成计划总结果。
  - B：保留现在的按专员推进，另外增加「跨层同一内容」的组合项。
- **建议**：选 A。理由：
  1. 和业务说法一致（「带话题且封面合规的视频」）；
  2. 比对和 ASR 只做圈中的内容，费用最低；
  3. 规则更少：不需要「同层多个考核项全部通过才进下一层」「到达该层的专员数」这些概念，一个计划只有一个达标方式；
  4. 三值逻辑（D-D05）照用，只是作用在「通过全部层的内容条数」上。
- **代价**：E-D15～E-D22 里的「分项完成率（分母 = 到达该层人数）」要改。最省事的改法是：分项只在专员明细和导出里显示「各层通过的内容条数」，不再算分项完成率。这其实也减少了 E 的工作量。
- **改动范围**：D-D01～D-D07、D §2.0.1～§2.2、D §6 验收；E-D16、E-D17、E-D19、E-D20、E §3.5、§4.1、§4.4、§5.4；CONTEXT「考核项」定义（R2-04）。建议你先选，再让我起草具体文字。
- [x] 2026-11-04

- **背景**：这是安全项里唯一建议改的，因为它直接产生费用，而且 B 的「待激活账号提示与密码错误一致」意味着系统不会告诉对方号码是否存在，那就更不能先验证号码再发。
- **建议**：只加两条，不加图形验证码以外的东西：
  1. 发送短信前，手机号必须是系统里「待激活或有效」的用户；不是的话返回和成功一样的提示，但实际不发。这一条就能挡住大部分轮换号码的刷法，而且不增加用户操作。
  2. 全局每日短信上限（配置项，归 I 域预算），超过时告警并暂停发送。
  - 如果第 1 条和「不暴露账号是否存在」冲突，那就加图形验证码，二选一即可。
- **改动范围**：B §4.2、B §14 验收；I 域预算项。
- [x] 2026-11-04

### 8.1 R2-01 详细说明：内容快照按账号还是跨账号

**一句话**：同一条平台作品出现在两个被监控账号的列表里时，系统是存一条「合并内容」，还是每个账号各存一条「这个账号看到的内容」。

**两种模型**：

| | A 按账号各存一条（D-23、A §9.2） | B 跨账号合并（CONTEXT:130、宪法 C10） |
|---|---|---|
| 内容主档 | 同一作品在每个被观察账号下各一条 | 同一作品全平台一条 |
| 快照 | 每个账号每个批次一份 | 每批次一份，汇集所有账号的列表结果 |
| 归属 | 每条内容事实带当时的账号 / 门店 / 专员归属 | 归属只能选一个，或另建关系 |
| 计数 | 同一作品在两个账号出现算两次，重复计数已知可接受 | 算一次 |
| 评论 / 媒资 | 按账号内容事实分别关联；媒资按 SHA-256 共享 | 一份关联 |
| 已落地 | A §3.4、§9.2；E §6.3；tracer requirements §1.2 第 2 项 | CONTEXT:130；宪法 C10；v2 `content_snapshots` 唯一键 `(batch, content)` |

**具体例子**：一条抖音视频 V 同时出现在账号 A（张三）和账号 B（李四）的列表里。

- 按 A：库里两条内容事实，`V@A` 和 `V@B`；张三的完成率只看 `V@A`，李四只看 `V@B`；V 的封面 / 视频字节按 SHA-256 只存一份。张三和李四各自「发过这条」的事实都保留。
- 按 B：库里一条 V；「这条内容算谁的」没有单一答案。强行归给一个账号，另一个账号的列表事实就丢了；不归，张三 / 李四的内容数都少一条。

**为什么现在会冲突**：`CONTEXT.md:124` 的 Content 已经写「按被观察的账号分别保存，不跨账号合并」，但同一份文件 `:130` 的 ContentSnapshot 又写「必须先汇集本批次全部列表来源」，宪法 C10 也是后者。D-23（2026-10-27）明确选了 A，A §9.2 与 E §6.3 都按 A 落地。因为 CONTEXT 是权威顺序第 1 位，模型严格按 CONTEXT 会选 B，结果与 A / E / tracer 全部对不上，而且不会报错。

**选 A 改什么**：

- tracer 只验收单账号，不受影响。

**v2 约束建议**（待 v2 修订时确认）：

```sql
-- 2026-11-04 复审修正：归属是当前单一事实（D-16 / D-28），没有 valid_to；
-- 外部监控账号 staff_id 为 NULL，MySQL 唯一键允许多个 NULL，不需要生成列。
staff_account_assignments
+ platform_id BIGINT NOT NULL
+ FOREIGN KEY (account_id, platform_id)
    REFERENCES external_accounts(account_id, platform_id)
+ slot_released_at DATETIME(6) NULL      -- 账号确认已删除时释放名额，见 §9.3
+ active_staff_platform BIGINT GENERATED ALWAYS AS (
    CASE WHEN slot_released_at IS NULL THEN staff_id END) STORED
+ UNIQUE KEY UQ(active_staff_platform, platform_id)
```

**对 R3-04 原问题的影响**：

- 原问题「一专员两个账号一个合格一个不合格」仍存在，但只发生在**跨平台**（例如抖音头像合规、快手封面不合规）。
- 账号级考核项的判定对象因此可以按平台唯一确定。建议规则：
  - 账号级考核项配置时绑定平台与对象（头像 / 背景 / 封面）；
  - 专员在该平台有账号 → 判这个账号；
  - 专员在该平台没有账号 → `not_applicable` 或「未参与」，按计划口径处理；
  - 计划有多个平台的账号级项 → 三值 AND，不达标优先。
- 这比「任一账号通过 / 全部账号通过」更简单，也更符合「同平台一个账号」的新规则。

### 8.3 R6-01 旧系统 Excel 核查：lxk-BigSpard 用 exceljs

**结论**：旧系统主链路用 **exceljs 4.4.0 在 Node 侧导出**，不是 Python。建议 R6-01 改选 **方案 A（Node + exceljs，仅写入）**，不采用原建议的 B（Python + XlsxWriter）。

**证据**：

| 文件 | 用途 |
|---|---|
| `lxk-BigSpard/web/package.json:15` | `"exceljs": "^4.4.0"` |
| `lxk-BigSpard/scraper/package.json:16` | 同样 `exceljs ^4.4.0` |
| `web/src/routes/export.js:459` | `addWorksheet('点检表', { views: [{ state: 'frozen', ySplit: 3 }] })`：冻结行列 |
| `export.js:472` 起 | `mergeCells`、多层表头、单元格样式 |
| `export.js:709-716` | `wb.addImage({ buffer, extension })` + `ws.addImage(...)`：从 OSS 取图并嵌入 |
| `export.js:878-967` | 多 sheet：经销商与专员 / 视频明细 / 汇总 |
| `export.js:730` 左右 | `wb.xlsx.write(res)`：流式写响应 |
| `web/src/routes/import.js:5,82`；`web/run_import_618.js:11,173` | 也用 exceljs **读** xlsx；这部分**不要照搬**，hbecho 导入仍用 CSV（D-08 / ADR-0005） |
| `generate_excel_full.py`、`generate_bg_report.py`、`write_import_result.py`、`scraper/scripts/export_*.py` | Python 的 openpyxl，多为一次性报表 / 脚本，不是主链路 |

**为什么选 A 而不是 B**：

1. 旧系统已经用 exceljs 做过 E6 需要的能力（合并表头、冻结、样式、嵌图、多 sheet、流式写），是已验证的做法；沿用比新引入 Python 报表渲染简单。
2. 不把「报表渲染」加进 Python 能力服务，保持 Python 只做图像 / 音视频 / 文档解析；不新增跨进程传数据和取图的链路。
3. 导入仍是 CSV，exceljs 只用于写自己的数据，不解析外部 xlsx；ADR-0005 否决 exceljs 的主要理由（解析不可信 xlsx、原型污染、压缩炸弹）不适用于这条路径。

**风险控制（必须写进 ADR）**：

- 只用 exceljs 的写入 API；代码里禁止 `wb.xlsx.readFile` / `load` 读取外部文件；导入路径继续用 CSV。
- 锁定 `4.4.0`，不加 `^`；CI 依赖审计；导出 Worker 单独进程 / 容器，限制行数、图片数、单图大小、文件大小与运行时长（E §8.5 已有上限要求）。
- 在 ADR-0005 的「已知坑」补一行，或新写 ADR-0011「报表导出用 exceljs（仅写入）」，写明「不用它做什么」：不读取任何外部 xlsx，不承担导入。
- 如果后续 exceljs 的写路径出现未修 CVE，再评估维护中的 fork 或 Python XlsxWriter；现在不为此提前引入第二套运行时。

**对 R6-01 的结论**：方案 A；不需要 Python 服务；需要一份短 ADR（或 ADR-0005 增补）记录「导出例外」。

### 9.3 需补的规则（在对应批次落地）

1. **计划恢复后账号怎么重新开采（R2-06，批次 2）**。暂停/归档不算引用，暂停超过 15 天，账号会被自动停采。计划转回「采集中」时，现在的联动表里没有「重新打开」这一条：恢复不是导入，A §11.5 的四条联动规则都不覆盖它。结果是计划恢复了但账号不采。
   - 建议在 A §11.5 联动表加一行：「活动计划恢复为采集中 → 名单中『因 15 天无引用而自动停采』的账号重新打开；人工关闭与上级关闭的不受影响」。
   - 这要求账号记下「关闭原因」（自动 / 人工）。R4-01 选 B 后本来不需要这个字段，现在因为这条又需要了。只是一个原因字段，不增加流程。

2. **A′ 下「未获取成功」的内容怎么逐层传递（R3-01，批次 3）**。A′ 写了「C1 → C2 → C3 逐层 AND」，但没写某条内容在第 2 层缺素材时怎么办。这会同时影响结果和费用：
   - 建议：某层结果为「未获取成功」的内容**不进入下一层**（不对它发起 ASR 等付费调用），最终按 D-D05 的三值阈值计为「未获取」。
   - 例：至少 3 条；2 条通过全部层，1 条在第 2 层缺封面 → 已知通过 2 + 未获取 1 = 3，可能达标 → 记「未获取成功」，而不是「不达标」。

3. **A′ 下专员明细仍保留各层通过条数（R3-01，批次 3）**。A′ 去掉了分项完成率，这是对的。但业务被判不达标时，第一个问题就是「卡在哪一层」。建议 E 的专员明细与导出保留「第 1 / 2 / 3 层通过内容条数」三列。这只是计数，不需要分母，也不进点检表。门禁 5「某考核项的完成率」在批次 3 改为「某监控判定计划的完成率」。

4. **R3-04 的判定规则可以更简单（批次 3）**。A §11.1 规定一个活动计划只有一个平台，监控判定计划挂在活动计划下，名单里的专员必然在这个平台有账号；再加上一专员一平台一账号，**一个计划里每个专员只对应一个账号**。所以 §8.2 末尾的「专员在该平台没有账号 → not_applicable」「计划有多个平台的账号级项 → 三值 AND」两种情况不会出现，不用写进 D。D 只需写一句：「账号级考核项判定该专员在计划平台上的那个账号，使用执行时最新的已终态主页快照」。E §6.2「多账号合并为一行」在计划内同样不会出现，可以保留为跨计划的说明。

5. **一平台一账号的名额什么时候释放（R3-04，批次 2）**。专员的旧账号被注销后，运营会把它标「已删除」。按 CONTEXT 不变量 5，归属不物理删除，旧归属还在，于是这位专员在该平台永远无法再录入新账号。
   - 建议：账号被人工确认为「已删除」，或被改绑给他人时，释放该专员在该平台的名额；归属记录保留供历史查询。
   - A §5.3、§5.5 各补一句；v2 用 `slot_released_at` 表达，见 §8.2 的 SQL。

6. **exceljs 导出的内存（R6-01，批次 4）**。旧系统 `export.js` 用的是 `wb.xlsx.write(res)`，即先在内存里建完整工作簿再写出，不是流式写入器。万行级、带图的点检表在这种写法下内存占用会很高。ADR-0011 里要写两件事：
   - 带图导出受 E §8.5 的硬上限约束（行数、图片数、单图大小），超限降级为链接；
   - 不带图的大表是否改用 exceljs 的流式写入器（`stream.xlsx.WorkbookWriter`），在 `e-metrics` spec 里实测后定。exceljs 的流式写入器对图片的支持我没有核实，不要预先假定它能嵌图。

**几处我按「最小改动」自己定的实现细节，请过目**：

1. **v2 的按账号内容**：没有改快照唯一键，而是让 `contents` 本身带 `account_id`（同一作品在两个账号下是两条内容）。这样 current 指针、快照、评论都不用改结构，跨账号 fan-in 规则直接删掉。tracer design 写的「快照按 (batch, account, content) 唯一」与此等价，已在 tracer requirements 登记。
2. **撤回 v2 待修订第 ② 项**（取消 `content_discoveries`）：CONTEXT 的 ContentDiscovery 与不变量 19 仍要求保留列表出现与当时归属快照，CONTEXT 权威更高。
3. **名额释放**：只有「确认已删除」需要写 `slot_released_at`；改绑本身是更新归属行的 `staff_id`，原专员的名额自然释放。
4. **配了评论要求的快手计划在保存时拒绝**（D §2.0.2）：A 已定快手不采评论，提前拒绝比执行后全部「未获取成功」更清楚。
5. **A′ 下「全部通过」要求 T > 0**：零内容按 D-D14 修订后的规则走，不会因为空集被判成通过。
