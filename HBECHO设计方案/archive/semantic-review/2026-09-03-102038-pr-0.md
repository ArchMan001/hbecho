# Tracer 四项合同修复第二次定向回归

> **状态**：`archived`（2026-09-03 设计评审证据；不构成当前实现合同，见 `HBECHO设计方案/INDEX.md` §8.3）

本轮仅以 [`2026-09-03-095959-pr-0.md`](2026-09-03-095959-pr-0.md) 为基线，在无 Git/diff 的当前快照中复核其 4 个 confirmed Major 和原五项边界。Expected/actual action、reconciliation 证明和 `initial_content_limit` P0 冲突已经关闭；两条 JCS 向量也能按文档 bytes 重算，但 command 修复新引入了一个 schema 身份冲突。原基线五项按各自原始边界均为 CLOSED，canonical command 的物理字段和 dominant-author 的一年后长期载体都已建立。本轮仅保留这一个 Major，没有另列 Minor。

Watch for: **confirmed** `data-foundation-tracer-command.v1` 同时被定义为两字段 task-parameters closed schema 和五字段 digest closed schema，单一版本化 validator 无法同时满足两处合同。

**Verdict**: NEEDS_CHANGES

## High-level view

四项定向回归结论为：**#1 CLOSED · #2 CLOSED · #3 CLOSED · #4 OPEN（Major）**。ProviderCall 已将 requested、expected、captured actual action 分列；ambiguous 终态化也要求同一 logical effect 的 distinct captured terminal call 和版本化 outcome mapping。Design P0 不再把 limit 默认值或上限列为未决。

RFC 8785 JCS、exact-text/no-normalization 和两条 digest vector 都已写入 v2；直接重算也与发布摘要一致。阻塞点不是 canonicalization 算法，而是同一个 command schema 名称在 §5.5 要求五字段全必有、在 §9.3 又只允许两字段，导致 closed-schema 校验对象不唯一。

原基线五项结论为：**#1 CLOSED · #2 CLOSED · #3 CLOSED · #4 CLOSED · #5 CLOSED**。原 #2 要求的 root SyncTask 物理映射与 limit 冲突均已修复；原 #5 的 accepted evidence 留在长期 identifier + SyncBatch，rejected evidence 留在长期 quality issue + SyncBatch，不依赖一年期 task/call/ODS。

## 四个 confirmed Major 的逐项结论

### 1. Expected 与 actual response action 独立持久化 — CLOSED

**Confirmed.** [`database-design-v2.md` §9.5](../../domains/data-foundation/database-design-v2.md) 在 `ods_provider_calls` 分别定义 `requested_action NOT NULL`、`expected_response_action NOT NULL` 和 `response_action NULL`；expected 在 `prepared` 时写入并不可变，actual 只能来自完整 captured response，mismatch 保留两值并归为 `invalid_response`。[`requirements.md` R2.2](../../../.kiro/specs/data-foundation-tracer/requirements.md)、[`design.md` §9.1](../../../.kiro/specs/data-foundation-tracer/design.md) 与 [`tasks.md` task 1/3](../../../.kiro/specs/data-foundation-tracer/tasks.md) 分别要求逐 call 记录、三者分列和 mismatch 离线验收，合同一致。

### 2. Reconciliation 的 captured terminal 证明 — CLOSED

**Confirmed.** v2 §9.5 的受限事务锁定原调用和非自身目标调用，要求相同 `sync_task_id/provider_id/platform_id`、至少一个 exact correlation、目标已 terminal、`terminal_captured_at` 非空且完整 response payload 通过完整性校验；版本化 `reconciliation_method` 还必须从该 payload 解出同一 remote effect 的明确 success/failure，并唯一映射至 reconciled outcome。同节显式拒绝 correlation-only、self、unrelated logical effect、pending、invalid 和缺少完整 terminal payload 的证据；Requirements R14.3、Design §8.3、Tasks task 3/8 使用相同正反边界。

### 3. `initial_content_limit` 默认值与上限不再列为 P0 — CLOSED

**Confirmed.** v2 §9.1 固定默认 20、范围 1～20，§9.3 将显式值或冻结 setting 复制为 effective value 并纳入 command hash。Design §18 P0(7) 现在只询问本 Feature 是否在首屏验收之外请求第二页，不再把 default/maximum 标为未决；Requirements R1/R9、Design §4.3/§11.2 和 task 2/6 仍采用同一页边界语义。

### 4. JCS bytes 与 digest vector — OPEN（Major, confirmed）

v2 §5.5 已规定 closed schema、RFC 8785 JCS、UTF-8 无 BOM、完整 SHA-256，以及 exact Unicode code point sequence 不执行 NFC/NFD、大小写、空白、URL 或数字文本 normalization。内部 BIGINT/batch 使用 decimal string，外部 ID/locator 保留 exact string，limit/count 使用受限 integer。§9.3 和 §8.2 分别把规则接到 command 与 dominant-author evidence；Design §4.3/§10.3、Tasks task 2/5 要求 TypeScript、Python、SQL fixture 一致。

对 §5.5 展示的一行 exact bytes 直接重算，结果均匹配文档：

```text
command v1  = 7dcf255d17be6de663a23e92310bb0f835e00b6cb223d46a9a2c8abd0bf8ec36
evidence v1 = 2ecbbeebd4d015bb5685d288c0230ab92646f1d0cba08a0937b2a5def673b36d
```

**Major — confirmed.** §5.5 同时称 `data-foundation-tracer-command.v1` 是五字段 closed schema，并明确“5 个字段全部必有且非 null”；§9.3 又要求根任务 `task_parameters` 通过同名 schema，但其“当前只允许”的对象只有 `schema_version` 与 `effective_initial_content_limit` 两个字段。Design §4.3 和 task 2 继续沿用同一名称，未定义这是两个不同 schema 或 aggregate 的受限 projection。实现若注册五字段 validator，会拒绝持久化的两字段 parameters；注册两字段 validator，则无法验证 digest vector 的五字段对象。应拆分 schema ID，或显式定义五字段 command aggregate 与两字段 persistence projection 的不同版本化合同后再关闭本项。

## 原基线五项的逐项结论

### 1. ProviderCall 状态、时间、payload 与转换矩阵 — CLOSED

**Confirmed.** v2 §9.5 对 `prepared`、`in_flight`、`terminal/not_sent`、完整响应、known non-delivery `transport_error`、`ambiguous` 和 reconciled terminal 定义字段/nullability、payload role 与合法转换；§9.6 固定三类 ODS payload。Requirements R14.6、Design §8.3/§9.2 和 task 3 使用同一故障边界。

### 2. Canonical TracerCommand 物理映射 — CLOSED

**Confirmed.** v2 §9.3 将提交映射为 manual SyncBatch + 根 `resolve_account` SyncTask，显式保存 platform、`subject_type='media_staff'`、staff subject ID、原始 locator、effective limit、caller-key digest 和 canonical digest；Design §4.3 与 task 2 同步，limit P0 冲突也已关闭。上面的 schema 命名冲突是本轮新发现，未否定这些原问题要求的物理字段已经落位。

### 3. Root 幂等与 status 的一年窗口 — CLOSED

**Confirmed.** Requirements R1.2/R1.3/R1.7 将 same-payload reuse、different-payload conflict 和旧 status 承诺限制在一年窗口，R15.5 对 unknown/expired/out-of-scope 返回 non-disclosing 结果；v2 §9.3、Design §4.3/§6.2 和 task 2 的 fake clock 采用同一边界。

### 4. 已捕获 profile payload 强制复用 — CLOSED

**Confirmed.** Requirements R3.6、[`prd-platform.md` §12.1(2)](../../prd-platform.md)、Design §18 P0(5) 和 Tasks task 1/4/5 都要求复用 locator 阶段已有的 captured terminal `media_user_info`；只有未产生该 payload 的 strategy 才允许一次独立 profile fetch。

### 5. Dominant-author 一年以上长期载体 — CLOSED

**Confirmed.** v2 §8.2 将 accepted 决策的 policy、canonical evidence、digest 和长期 `evidence_batch_id` 保存于 `external_account_identifiers`，batch FK 为 `ON DELETE RESTRICT` 且首次证据不可覆盖；rejected 决策用同一 evidence schema保存于长期 `data_quality_issues.detail + batch_id`。v2 §5.3/§12.7 仅置空长期表对一年 call/task 的来源 FK，再显式清理 payload → call → task；Design §4.3/§10.3 与 task 5 的 fake-clock 验收要求 operational lineage 到期后两条决策路径仍能仅凭长期 evidence + batch 解释。
