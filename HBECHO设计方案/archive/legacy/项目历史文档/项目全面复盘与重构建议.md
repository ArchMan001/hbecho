## 零、五个根因模式

重构时如果只带走一样东西，带走这五条。项目里几乎每个数据事故都能归到其中之一。

### 模式 1：静默错误 —— "成功"不代表"对"

这是本项目最大的系统性风险。典型链条是：链接指向错误账号 → 爬虫正常访问、正常返回数据 → `scrape_logs.status='success'` → 看板照常出数 → **没有任何一环报错**。

已发生的实例：
- 专员换号后 `home_url` 未更新，爬虫长期采集别人的账号（`importCampaignMembers.js:258-266` 的事故注释）
- 抖音登录号的 profile 被当成目标账号，29 个不同门店的昵称变成同一个陌生小号
- 导出的视频明细从 26478 条塌缩到 283 条，界面无提示（`export.js:797-808`）
- `dashboard.js` 全部聚合依赖已停写的 `videos.matched_keywords`，新数据上恒为 0，但接口返回 200

**重构原则**：
- 每个数据写入点都要能回答"我凭什么认为这条数据属于这个主体"。答不上来就不要写。
- 状态要三态而非两态：`success` / `failed` / **`succeeded_but_unverified`**。第三态是这个项目最缺的东西。
- 关键指标必须有**独立口径的交叉校验**，且校验结果要落库、要能报警。不能只打 stdout。

### 模式 2：字段语义漂移 —— 同一列在不同上下文含义不同

- `total_favorited`：抖音 = 获赞数；小红书 = 获赞+收藏合计（`xiaohongshu.js:168`）。而 `account_snapshots` 直接复用这一列做趋势，跨平台 SUM 必错。
- `videos.aweme_id`：承载抖音 aweme_id、小红书 note_id，唯一键 `uq_aweme_id` 是**全局单列**，两个平台的 id 空间在同一命名空间裸奔。
- `douyin_created_at`：承载所有平台的发布时间。`database-design.md:324` 已自认"字段名历史遗留，可视为通用的 published_at"。
- `note_content`：小红书语义的字段名，被抖音用来存 `share_desc + hashtag`（`scraper.js:656-665`）。
- `bg_match_standard = NULL` 有两个含义：「未比对」（`init.sql:51` 注释）和「待比对队列」（`bg_comparator.py:292` 用它当 WHERE 条件）。

**重构原则**：字段名必须平台中立；一个字段一个含义；跨平台指标先定义**语义层**再落库。

### 模式 3：口径分裂 —— 同一个业务问题有多个答案

「这个专员算不算完成活动」当前有三套口径同时存在：

| 口径 | 出处 | 现状 |
|---|---|---|
| `video_type_matches` 有记录 | `export.js` 的 Sheet2/Sheet3、点检表 | 权威表，实时写入 |
| `staff_campaign_membership.qualified_video_count` | `export.js:917` Sheet1「活动命中数」 | 只在爬虫里重算，改关键词后不刷新 |
| `videos.matched_keywords LIKE ...` | `dashboard.js` 全部聚合、`campaigns.js:249,294` | **字段已停写，新数据恒 0** |

导致的实际现象：同一份 Excel 里 Sheet1 命中合计 1872、Sheet3 命中合计 46。

同类分裂还有：
- 互动量：导出算五项（含 forward、collected），看板算三项（`dashboard.js:20`）
- 活动日期窗上界：`rematch` 用 `<= end_date`（漏最后一天，`keywords.js:307`）、导出/爬虫用 `< end_date+1天`、看板**完全没有日期窗**
- 分母：点检表用「认证通过的参与专员数」，看板 `total_members` 用「参与账号数」（不要求认证）

**重构原则**：每个指标只允许有**一个**计算实现，其它地方只能引用。指标定义进代码（或配置），不散落在 SQL 里。

### 模式 4：配置改了，历史数据不回溯

- 改关键词 → 必须手工点「重新匹配」，且该操作**不更新** `qualified_video_count`（`keywords.js:211-345` 全程未碰 `staff_campaign_membership`）
- 改活动日期 → 什么都不重算（`campaigns.js:96-113` 只 UPDATE 日期就返回）
- 换背景图标准图 → 只能全库重比，且会覆盖历史活动的结论
- 三者都没有版本号、没有审计、没有"复现上周那张报表"的能力

**重构原则**：判定结果要带**判定依据的版本**（规则版本号 / 标准图 hash / 阈值）。改配置产生新版本，历史判定保留。报表指定版本即可复现。

### 模式 5：约束在代码注释里，不在数据库里

代码在三处提到三个不同的唯一约束名，DDL 里只有一个，实库里又是另外两个：

```
importCampaignMembers.js:553  注释说 (dealer_id, contact_name, platform)
importCampaignMembers.js:651  注释说 (dealer_id, platform, home_url)
import.js:342                 注释说 uq_dealer_contact_platform / uq_platform_url
mysql/init.sql:69             只建了 uq_ds_platform_home_url (platform, home_url(200))
实库 SHOW CREATE TABLE        uq_dealer_contact_platform (dealer_id, contact_name, platform)
                              uq_ds_dealer_platform_home_url (dealer_id, platform, home_url(200))
```

所有 `ER_DUP_ENTRY` 兜底分支都是在对着**想象中的约束**编程。

更麻烦的是漂移是**双向**的 —— 有的地方实库超前于 init.sql，有的地方 init.sql 超前于实库：

| 对象 | `init.sql` | 实库 | 谁对 |
|---|---|---|---|
| `dealer_staff` 唯一键 | 1 个 `(platform, home_url)` | 2 个，且都含 `dealer_id` | 实库超前 |
| `campaign_type_keywords` | `(video_type_id, keyword)` | `(video_type_id, keyword, rule_group)` | 实库超前 |
| `video_type_matches` | `(video_id, video_type_id)` | `(video_id, campaign_id, video_type_id)` | 实库超前 |
| `videos` 索引名 | `idx_videos_staff_id` / `idx_videos_created_at` | `idx_staff_id` / 无 created_at 索引 | 混杂 |
| `campaign_video_types` 唯一键 | 无 | 无 | 都缺（实库已有重复数据） |

**后果**：按 `init.sql` 建的新环境，`video_type_matches` 会让同一视频在不同活动间互相覆盖命中记录，`campaign_type_keywords` 会禁止同词进不同规则组 —— 而这两条恰好是业务需要的能力。也就是说**现在无法从零搭出一套和生产行为一致的环境**。

**重构原则**：schema 只有一个来源（迁移文件），禁止手改生产库。CI 里加一条"实库 schema 与迁移产物 diff 必须为空"。

## 一、录入经销商数据与链接

### 1.1 踩过的坑

#### 数据源本身的坑（Excel/CSV）

| 坑 | 实例 | 现有应对 |
|---|---|---|
| 列名不统一 | 全角/半角括号、「平台id」vs「抖音id」、「平台主页链接」vs「抖音主页链接」 | 别名表 + 去空格小写化（`importCampaignMembers.js:84-101`） |
| 表头行被当数据导入 | `staff_id=753` 的 `home_url` 字面就是「抖音主页链接」 | 无防护 |
| 链接里混着整段分享文案 | `https://v.douyin.com/xxx/3@7.com:3pm` | `cleanCandidateUrl` 按"路径后跟非路径字符"截断（`:123-149`） |
| 贴的是视频链接不是主页 | — | 判失败，记 `video_url_not_profile`（`:325-332`） |
| 贴的是 `/user/self` | 那是"登录用户自己的主页" | 特判（`:174`） |
| Excel 超链接单元格 vs 富文本 | 三种取值形态 | `extractCellText` 分三种情况处理（`import.js:673-707`）—— **这段写得好，重构要保留** |
| 同一账号被登记给多人 | 已确认存在（595/602 共用同一账号） | 唯一键冲突时告警交人工（`:651-668`） |
| 同一条链接被录到两个门店 | 已确认（710 与 3474 共用短链） | 无防护，事后才发现 |

#### 多平台的坑（这是重构必须先解决的）

现状：**只有 1.5 个平台**。实库 `platform` 分布 1336 行全是 `douyin`，小红书在生产环境从未跑通。

1. **`platform` 是自由 VARCHAR，取值全集散落在 10 处**，无一处权威：

| 位置 | 内容 |
|---|---|
| `init.sql:38` | `VARCHAR(20) DEFAULT 'douyin'`（非 ENUM，DB 不校验） |
| `importAccounts.js:101` | `SUPPORTED_PLATFORMS = ['douyin','wechat_video','xiaohongshu']` ← 全仓唯一白名单，只被这个 CLI 用 |
| `index.js:50-53` | `detectPlatform`：非小红书**一律返回 douyin** |
| `import.js:657-662` | `normalizePlatform`：默认 douyin |
| `run_import_618.js:102` | 同上，复制粘贴的第二份 |
| `accounts.js:78` | `req.query.platform \|\| 'douyin'` |
| `app.js:38` | 未知平台 badge fallback 成 douyin |
| `scrape.js:212` | `platform != 'xiaohongshu'` ← **反向排除**，新平台会被自动纳入背景图比对 |

后三处的共同特点是：**不改也不报错，只是行为悄悄错了**。

2. **主力导入 CLI 完全不支持非抖音，而且是静默的**。`importCampaignMembers.js` 解析了「平台」列（`:87`）却**从不使用**；`resolveHomeProfile` 三个正则全是 `douyin.com`（`:334-337`）。小红书链接进去 → 三个过滤器全不命中 → 返回 `shortlink_unresolved` → 插入一条 **`platform='douyin'`、`home_url=NULL`** 的僵尸行（`:679` 硬编码字面量）。

3. **`videos` 表被小红书直接复用**，字段名全是抖音语义，唯一键 `uq_aweme_id` 是全局单列。

4. **小红书实现有一处致命 bug 导致它 100% 失败**：

```js
// xiaohongshu.js:289-292
await db.query(
  `UPDATE social_accounts SET video_total_count = ?, keyword_video_count = 0 WHERE id = ?`,
  [videoCount, accountId]);
```

`social_accounts` 表在实库里**不存在**（26 张表里没有它）。这句在 try 块内 → 抛错被 catch 吃掉 → **每次小红书采集都返回 `success:false`**，尽管 `dealer_staff` / `videos` / 快照都已写成功。数据是对的、状态永远是错的。这是"第二个平台已经烂在半路"最硬的证据。

5. `account_identifier` 的格式假设写死在 5 个文件里，且小红书 id 有**两套互不兼容的正则**：
   - `xiaohongshu.js:44`：`[a-f0-9]{24}` 严格 24 位 hex
   - `import.js:653`：`[A-Za-z0-9]{10,}` 宽松

### 1.2 为什么会踩

根本原因是**抖音是"隐式默认"而非"一个平台选项"**。项目从单平台起步，`platform` 字段是后加的，加了之后没有任何一处强制它必须被显式处理 —— 默认值、fallback、反向排除三种写法都在放大这个问题。

### 1.3 重构建议

#### 建模：把"平台账号"抽成一等实体

```
dealer（门店）
  └── staff（专员，人）
        └── platform_account（平台账号）   ← 新增这一层
              ├── platform          ENUM，DB 层强约束
              ├── platform_uid      平台内唯一 id（抖音 sec_uid / 小红书 user_id / 快手 eid…）
              ├── canonical_url     标准化主页地址（由 platform + platform_uid 派生，不手写）
              ├── raw_input         原始录入文本（证据链，永不覆盖）
              └── resolve_state     解析状态机
```

关键约束（**必须建在 DB 层**）：

```sql
UNIQUE (platform, platform_uid)        -- 一个平台账号全局只有一条记录
UNIQUE (staff_id, platform)            -- 一个人在一个平台只有一个账号（若允许多个则去掉）
```

注意当前 `(dealer_id, platform, home_url(200))` 的两个问题，重构别再犯：
- 用了 `home_url` 前缀索引（200 字符）。小红书带 `?xsec_token=...` 的长链接前 200 字符可能相同 → 误判冲突。**要约束的是 uid，不是 URL**。
- `home_url` 允许 NULL，MySQL 唯一索引不约束多 NULL → 所有解析失败的行不受任何唯一保护。这正是 pending 分支必须手工查重的原因。

#### 「一个账号对应多个门店」要显式建模

已确认现实中存在（旧编码/新编码并存、多店共用一个号）。当前是靠"把记录在门店间搬来搬去"处理的，这是所有 `ER_DUP_ENTRY` 兜底的来源。重构应该用关联表：

```
platform_account ──< account_dealer_binding >── dealer
                       ├── is_primary
                       └── valid_from / valid_to
```

#### 平台适配层

```
PlatformAdapter 接口（每个平台实现一份）
  ├── detect(url)              -> platform | null      ← 认不出就返回 null，不要 fallback
  ├── parseUid(url)            -> uid | null
  ├── resolveShortLink(url)    -> uid | null
  ├── buildProfileUrl(uid)     -> string
  ├── buildContentUrl(id)      -> string
  ├── validateUid(uid)         -> bool                 ← 格式校验只在这里，不散落
  └── normalizeMetrics(raw)    -> 统一语义的指标对象     ← 语义映射只在这里
```

`detect` 认不出必须返回 null 并让导入行判失败。当前 `detectPlatform` 对快手链接返回 `'douyin'`，然后一路走到最内层才以"链接格式错误"的名义失败 —— 错误信息与真实原因完全不符，排查时极易误判。

#### 导入流程：三阶段，而不是一把梭

```
阶段1 解析（只读，可反复重跑）
   原始文本 → 平台识别 → uid 解析 → 输出「解析报告」
   不写业务表，只写一张 import_staging 表
   ↓ 人工看报告：识别失败 N 条、跨门店冲突 N 条、同账号多人 N 条
阶段2 确认
   人工处理完冲突后，显式点"应用"
阶段3 落库（事务，幂等）
   staging → 业务表
```

现在是解析和落库混在一个循环里，出问题时一半数据已经写进去了。三阶段的好处是**冲突在落库前就暴露**，而不是靠 `ER_DUP_ENTRY` 事后补救。

#### 前置动作清单（照做即可规避大部分坑）

导入前：
1. **模板下载 + 服务端校验模板版本号**。不接受任意表头的文件。
2. 表头映射结果**回显给用户确认**（"我把第 3 列当成了『门店编码』，对吗"）。识别不到必填列直接拒绝。
3. 首行数据做**表头相似度检测** —— 值等于列名就是表头行重复，拒绝（能挡住 753 那种情况）。
4. 平台列**必填且校验白名单**，不给默认值。

导入时：
5. **只做解析，不写业务表**，输出报告。
6. 报告必须包含四类：解析失败、跨门店链接冲突、同一账号多人持有、疑似表头/示例行。
7. 短链解析要**限速 + 缓存 + 失败可重试**（当前是 400ms sleep + 6 跳，可保留）。

导入后：
8. 自动跑一致性巡检（当前有，但只打 stdout，重构应落库 + 可视化）。
9. 巡检结果里**"无法判定"必须与"一致"区分开**。当前 `pct()` 在分母为 0 时返回 null，和真实 0% 混在一起。

## 二、更新经销商数据与链接

### 2.1 踩过的坑

这是本项目**踩得最狠**的环节。`importCampaignMembers.js:258-266` 的注释是全仓最重要的一段事故复盘：

> 背景（这是一个曾导致长期静默错误采集的问题）：
> 历史实现里两个字段的写入保护级别不一致 —— account_identifier 与 home_url 都用
> COALESCE(旧值, 新值) 保护，而 raw_home_url 用新值覆盖。结果是专员换号、
> 重新导入新链接后，raw_home_url 更新了，爬虫真正访问的 home_url 却停留在旧号。
> 爬虫照常「采集成功」，但抓的是别人的账号，表面无任何报错。

具体坑：

| 坑 | 后果 | 现有应对 |
|---|---|---|
| 三个链接字段保护级别不一致 | 换号后爬虫长期采集旧号 | `decideLinkUpdate` 成对覆盖（`:279-308`） |
| 换号后旧号的历史 videos 仍挂在该账号下 | 统计口径混入别人的数据 | 只打印"建议重新采集"，**不自动处理** |
| 两位专员的链接录反了 | — | 检测到冲突不覆盖，交人工（`:651-668`） |
| 短链没解析成功的行无人接管 | 僵尸行永久 pending | `resolvePendingHomeUrls.js`，但**只处理 `platform='douyin'`**（`:176`），小红书 xhslink 行永远无人管 |
| 解析器有两份且已漂移 | 同一链接在导入端能过、补解析端过不了 | 无 |
| `account_identifier` 也可能是错的 | 本次实测：710 的 ident 指向别人门店的号 | 无（本次新增了 `fix_stale_home_url.js` 的 dry-run 提示） |

**本次实操中新发现的一个结构性盲点**（值得单独说）：

`staff_id=752` 的 `home_url` 是从未解析的原始文案，`expectedSecUid` 抽不出来 → 退回用 `account_identifier`；而 `account_identifier` 当初是 NULL、被 `COALESCE` 填入了**污染值本身**。于是"采到的"和"登记的"自我一致，**所有身份校验都发现不了**。

这说明：**用"库里登记的值"做兜底基准，等于让错误自证清白**。

### 2.2 重构建议

#### 链接变更走事件流，不做原地覆盖

```
account_link_event（append-only）
  ├── platform_account_id
  ├── event_type      ENUM('created','switched','corrected','disputed')
  ├── old_uid / new_uid
  ├── source          ENUM('import','manual','resolver')
  ├── evidence        原始文本 / 解析链路 / 操作人
  └── created_at
```

`platform_account.platform_uid` 是这张表的**投影**，不是权威。好处：
- "这个号什么时候换的、谁改的、依据是什么"永远可查
- 换号时能自动判定"旧号的历史数据要不要归档"
- 出现争议（如 710）时可以标 `disputed` 并挂起，而不是二选一硬改

#### 身份校验的基准必须是外部事实

三条规则：
1. **绝不用库里的值做兜底基准**。基准只能是"本次从平台实际取回的 uid"与"本次从原始链接解析出的 uid"。
2. 解析不出 uid 的账号**不进采集队列**。当前是带着坏链接去爬，爬出脏数据再事后清理。本次已加的形状校验（`scraper.js:326`）是对的，重构应该前移到入队前。
3. 校验失败要落库成状态，不能只 warn。当前 `scrape_logs` 里 `status='success'` 涵盖了"抓的是别人的号"这种情况。

#### 多平台下的换号

每个平台的"换号"语义不同，重构要在适配层显式声明：

| 平台 | uid 稳定性 | 换号识别方式 |
|---|---|---|
| 抖音 | `sec_uid` 稳定 | uid 变化 |
| 小红书 | `user_id` 稳定，但短链每次不同 | 必须解析到 uid 才能比 |
| 快手 | 待确认（`eid` vs `userId` 两套体系） | — |
| 视频号 | 无公开稳定 id，可能只能靠名称+主体 | **重构前必须先调研，否则这一层设计会返工** |

视频号这条要特别注意：如果它没有稳定 uid，整个"以 uid 为身份锚点"的模型对它不成立，需要单独的身份策略（比如以"认证主体 + 账号名"做软匹配 + 人工确认）。**建议在动手前先把视频号的 API 能力摸清**。

## 三、改用商用 API 采集（账号、视频、评论）

你后面要换成商用 API。这会消掉爬虫的一大类问题（反爬、翻页、DOM 变化），但会**引入一批新的坑**，而且其中几个和本项目已经踩过的是同构的。

### 3.1 会消失的坑

- 反爬节奏（批次、随机延迟、换 context、cookie 维护）
- DOM 结构变化（内层滚动容器、懒加载触发）
- profile 串号污染（API 按 uid 请求，不会混入登录号）
- XHR 超时（15s→30s 那类问题）

### 3.2 新引入的坑（按严重度排序）

#### 坑 1：身份绑定仍然是最大风险 —— 而且更隐蔽

商用 API 通常要求你传一个 id。这里有个陷阱：**API 厂商的 id 体系可能和平台原生 id 不一致**。常见形态：
- 厂商用自己的内部 id，需要先"注册/绑定"账号才能查
- 厂商接受主页链接，内部自己解析 —— **你就失去了"我在查谁"的控制权**
- 同一个账号在厂商侧有多条记录（历史改名、跨端）

**如果你传链接、厂商返回数据，你必须校验返回的 uid 与你期望的一致。** 这和本项目 profile 串号污染是同一个问题，只是换了个外壳。厂商不会保证这件事。

对策：
- 只用 uid 调用，不用链接。若厂商只吃链接，则**必须校验返回体里的 uid**。
- 返回体里没有 uid 的 API 不要用于身份敏感场景。
- 建立 `platform_uid ↔ vendor_account_id` 映射表，绑定关系变化要留事件。

#### 坑 2：字段语义与口径

这是本项目模式 2 的重演，而且更难察觉，因为你看不到厂商的计算逻辑。

必须逐字段和厂商确认清楚的：

| 字段 | 要问清的问题 |
|---|---|
| 点赞 | 是否含取消？是否实时？快照时点是什么 |
| 收藏 | 抖音"收藏"与小红书"收藏"是否同义 |
| 分享 / 转发 | 两个还是一个？站内转发算不算 |
| 评论数 | 含二级回复吗？含被删除的吗 |
| 播放量 | 口径（去重 UV / 总 PV / 完播）—— **平台间差异极大** |
| 粉丝数 | 是否去除僵尸/注销 |
| 发布时间 | 时区！是否 UTC，是否含秒 |

对策：
- 建**语义层**：`metric_definition` 表，记录每个指标在每个平台每个数据源下的定义与单位。
- 落库时**同时存原始返回体**（JSON 列或对象存储），出问题能复算。本项目现在没存原始响应，所有历史争议都无法追溯。
- 指标不要直接混合聚合。跨平台汇总必须先经语义映射，且要在报表上标注"跨平台口径已归一"。

#### 坑 3：评论数据的量级与合规

评论是本项目从未处理过的数据类型，有三个特有问题：

**量级**：一条爆款视频几万条评论。1000 个账号 × 40 条视频 × 平均 200 条评论 = 800 万行。设计时就要考虑：
- 评论表要分区（按时间或按 video_id hash）
- 不要和 `videos` 放同一个存储策略
- 全量拉还是只拉 TOP N？只拉 TOP N 的话，"评论区情感分析"的样本就是有偏的，报表要标明

**增量**：评论会**新增、删除、被作者隐藏**。所以：
- 不能只 append，要有 `last_seen_at` 和软删标记
- "评论数"这个指标有两个版本：平台返回的 `comment_count` 和你实际拉到的行数。**两者必然不等**，报表要明确用哪个（本项目 `videosFound` vs `qualified_video_count` 就是同类问题）

**合规**：评论含用户昵称、头像、可能含手机号/微信号。
- 要做 PII 脱敏策略，明确哪些字段落库、保留多久
- 导出到 Excel 时要控制 PII 外泄面
- 这块建议在设计阶段就和法务/合规确认，不要等做完再补

#### 坑 4：配额、限流、部分失败

商用 API 有配额，且失败模式比爬虫更多样：

| 失败类型 | 特点 | 对策 |
|---|---|---|
| 429 限流 | 可重试 | 指数退避 + 令牌桶 |
| 配额耗尽 | 当天不可恢复 | **必须有配额预算与降级策略**，否则月底数据断档 |
| 单账号无权限 | 只这个账号失败 | 记录状态，不影响批次 |
| 返回部分字段缺失 | 最危险 —— 看起来成功了 | **字段级校验**：缺关键字段视为失败 |
| 数据延迟 | 返回的是几小时前的快照 | 记录 `data_as_of` 时间戳，不要用请求时间当数据时间 |

第 4 项和第 5 项是重点。本项目"表面成功"的教训在这里同样适用：**厂商返回 200 + 一半字段是 null，如果你不做字段级校验，就会静默写入残缺数据**。

`data_as_of` 这个字段必须有。本项目 `account_snapshots` 用 `CURDATE()` 当快照日期（`scraper.js:568`），实际数据可能是平台几小时前的状态 —— 商用 API 的延迟通常更长且不固定。

#### 坑 5：快照与幂等（本项目已踩，会重演）

`account_snapshots` 用 `INSERT IGNORE` + `UNIQUE(staff_id, snapshot_date)`，导致**同一天第二次采集被完全丢弃**，无论新值是否更准。本次事故中当天被污染的快照，当天重爬也修不回来，必须手工 DELETE。

换成 API 后这个问题更突出，因为你可能一天调多次。

对策：
- 快照表用 `ON DUPLICATE KEY UPDATE` 而非 `INSERT IGNORE`，并记录 `updated_at` 和 `source`
- 或者改成 append-only 的事实表，聚合时取当日最后一条
- **推荐后者**：能保留"同一天数值变化过"的信息，对排查极有价值

#### 坑 6：对账

商用 API 最大的隐患是**你无法验证它对不对**。爬虫时代你至少能点开主页人工核对。

必须建立对账机制：
- 抽样人工核对（每批固定抽 N 个账号，人工看主页）
- 跨源交叉校验（若有两个数据源，定期比对差异率）
- 自比对：`profile.video_count`（平台声称的作品数）vs 实际拉到的视频数，差异过大要告警。本项目已有这两个字段（`video_count` / `video_total_count`）但**从未用来做校验**

### 3.3 重构建议：采集层的形状

```
采集编排层（不关心数据源）
  ├── 任务定义：采什么（账号/视频/评论）、采谁、什么口径
  ├── 配额与限流管理
  └── 结果校验与状态机（success / partial / failed / unverified）
       ↓
数据源适配层（每个源一份实现）
  ├── VendorApiAdapter（商用 API）
  ├── ScraperAdapter（保留兜底能力，别全删）
  └── 统一输出：RawResponse + NormalizedFacts
       ↓
落库层
  ├── raw_response（原始 JSON，可回溯）      ← 本项目最缺的
  └── 事实表（已归一语义）
```

三点建议：
1. **保留爬虫作为兜底**。商用 API 会涨价、会下线、会改口径。适配层设计好，切换成本很低。
2. **原始响应必须落盘**。存储很便宜，但"当时厂商到底返回了什么"这个问题在出争议时价值极高。
3. **先用小批量做一轮对账再全量切换**。同一批账号同时用爬虫和 API 采一遍，比对差异，把口径差异摸清楚再切。

### 4.1 活动规则：关键词匹配

#### 踩过的坑

| rematch 的日期上界仍是 `<= end_date` | `keywords.js:307` | **活动最后一天发布的视频全部漏计**。爬虫和导出已修成 `< end_date+1天`，这条路径没改 |
| rematch 不更新 `qualified_video_count` | 全程未碰该表 | 改完关键词点了重新匹配，命中表变了、Sheet1 的数字还是旧的 |

| 无版本、无审计 | `campaign_type_keywords` 无 created_by/updated_at | 无法复现历史报表 |

#### 重构建议

**规则要版本化**：

```
rule_set（规则集，一个活动可以有多个版本）
  ├── campaign_id
  ├── version           自增
  ├── effective_from    生效时间
  ├── created_by
  └── status            draft / active / archived
      └── rule_group ──< rule_keyword
```

`video_type_matches` 上加 `rule_set_version`。好处：
- 改规则 = 建新版本，历史判定不动
- 报表可以指定"按 v3 规则看"，能复现任何时点的数字
- 能回答"这条视频为什么算命中"（哪个版本、哪个组、哪个词）

**唯一键要建对**：

```sql
UNIQUE (campaign_id, type_name)                        -- campaign_video_types
UNIQUE (video_type_id, rule_group, keyword)            -- 允许同词进不同组
UNIQUE (video_id, campaign_id, video_type_id)          -- 补上 campaign_id
```

**匹配要抽成纯函数 + 单测**。当前同一套 OR-of-AND 逻辑在两个地方各写一遍（`scraper.js:194-235` 和 `keywords.js:299-320`），而且**日期窗上界两处不一致** —— 这正是重复实现的必然结果。

**关键词规范化管道**（写入和匹配用同一个）：

```
原文 → NFKC 归一（全半角）→ 去零宽字符 → 折叠大小写 → trim → 折叠连续空格
      → [可选] 繁简转换 → 存 normalized 列，匹配只用这一列
```

同时保留原文供展示。

**重算要幂等、事务化、可指定范围**：
- 作用域：该活动参与账号的视频，而非全库
- 单事务或分批 + 断点续跑
- **重算完必须连带刷新所有派生统计**（`qualified_video_count` 及任何缓存表）
- 改活动日期也要触发重算

### 4.2 活动规则：背景图匹配

#### 踩过的坑

| 坑 | 位置 | 说明 |
|---|---|---|
| 阈值是 SIFT good-match 的**绝对个数** | `bg_comparator.py:68`（默认 200）、`:265`（Lowe 0.75 硬编码） | 不归一化 → 阈值与标准图分辨率/纹理强绑定。**换一张标准图就得重调阈值，且历史 `bg_match_score` 与新阈值不可比** |
| 标准图存在 `settings` 表 base64，靠 **key 命名约定**分流 | `standard_bg_image_<code>_<sector>` → `_<code>` → 全局 | 三级降级是**静默的**（`:147-165`），报表上看不出这个分公司用的是别的活动的标准图 |
| 缺标准图 → 跳过，`bg_match_standard` 保持 NULL | `:430-436` | 点检表把"装修完成"算作 `=1`，跳过的账号在报表里等于"未完成"，**与"没配标准图"无法区分** |
| 缺 `failure_bg_image` → 占位图被判成 `0` | `:392-393` | **下载失败伪装成"没装修"** |
| 判定结果不记录依据 | 只写 `bg_match_standard` + `bg_match_score` | 用的哪张标准图、什么阈值、什么时间，全都不记 → 结论不可审计、不可复现 |
| `bg_match_standard=1` 会跳过下次背景图下载 | `scraper.js:546-560` | 一旦污染就被**固化**（本次事故中 26 个账号的背景图是登录号的图，且 `bg_match_standard=1`，等于点检结果是假的） |
| bg-rematch 跨品牌全库置 NULL | `scrape.js:209-224` | 历史活动的结论被新标准图覆盖，且按"账号参与的最新活动"解析标准图 → 旧活动被用新标准图重判 |
| 进度解析正则与 Python 日志不匹配 | `scrape.js:245` 期望 `std_score=`，`bg_comparator.py:466` 实际输出 `std=` | **每一行都落进 errLines，前端进度与统计恒为 0**。这个 bug 一直没被发现，因为没人对着日志核对过 |
| `--ids=` 拼进单个 argv | `scrape.js:236-239` | 上千 id 会撞 ARG_MAX |
| 无人工复核入口 | routes 里没有任何写 `bg_match_standard` 的接口 | 运营认为机器判错了只能直连数据库改 |

#### 重构建议

- **标准图升级为实体**，不用 settings key 约定：

```
standard_image
  ├── campaign_id / sector      （NULL 表示通用）
  ├── image_hash                内容 hash，作为版本标识
  ├── storage_key
  ├── algorithm + params        存 JSON：{"algo":"sift","threshold":200,"lowe":0.75}
  └── uploaded_by / uploaded_at
```

- **比对结果记录完整依据**：

```
bg_match_result
  ├── platform_account_id
  ├── standard_image_id + image_hash    ← 用的哪张
  ├── algorithm_params                  ← 什么阈值
  ├── raw_score
  ├── verdict         ENUM('matched','custom','download_failed','no_standard','error')
  ├── matched_at
  └── reviewed_by / review_verdict      ← 人工复核入口
```

注意 verdict 要有 **`no_standard`** 这个态。当前"没配标准图"和"未比对"都是 NULL，在报表里都表现为"未完成"，这是错的。

- **分数要归一化**。用 good-match 数 / 标准图特征点总数，或直接改用更稳定的方法（pHash + 结构相似度组合）。归一化之后阈值才有跨图可比性。

- **改标准图不覆盖历史**。新标准图 = 新 `standard_image` 行 + 新 hash，历史 `bg_match_result` 保留。要重判就产生新结果行。

- **进度协议要约定死**。当前 Node 用正则解析 Python 的人类可读日志，字段名一改就静默失效。改成 Python 输出**结构化 JSON 行**（NDJSON），Node 直接 parse。

| 同步构建 + 硬上限 | `LIMIT 50000` / `100000`，无分页无流式 | 全部进内存 → ExcelJS 建表 → 一次性写出。大活动会打爆堆 |
| 图片嵌入无上限保护 | `export.js:695`（CONCURRENCY 30） | 5 万行 × 2 图 = 10 万次 OSS 往返，全部 buffer 常驻内存，无超时无取消无进度 |
| 图片失败静默留空 | `export.js:75-78` | 文件里不标注"图片缺失" |
| `campaign_id` 不校验归属 | 所有导出 | `campaign_events` 无 brand 列 → 传别品牌活动 id 会拿到一份全 0 的表且无提示 |

#### 重构建议

- **导出 = 异步任务**，不是同步响应。下单 → 后台生成 → 通知下载。当前的同步模式在数据量上去后必然出问题。
- **口径元数据随文件走**。每份导出第一个 sheet 固定是"口径说明"：数据范围、分母定义、规则版本、生成时间、数据截止时间。本次已在汇总页加了采集范围说明，重构应该制度化。
- **0 和 null 必须区分**。0 就写 0，无数据写"—"或留空并在图例说明。
- **维度取自数据，不硬编码**。大区/分公司从 `dealers` 聚合，缺数据显式标"无数据"，不静默丢弃。
- **列定义配置化**。点检表 14 列现在硬编码在代码里，改一列要发版。
- 图片导出单独走一个"含图版"任务，有行数上限和明确的时间预期。

**品牌隔离缺失（安全问题，重点）**：

`req.brand` 在 `server.js:236-239` 注入，但**每个路由要自己手写 `AND d.brand = ?`**。漏写的：

| 路由 | 风险 |
|---|---|
| `keywords.js` **全部接口**（无 brand、无 requireAdmin） | **最危险**：可改任意品牌活动的考核规则；`POST /rematch` 可对任意活动 `DELETE FROM video_type_matches` |
| `campaigns.js` 全部接口 | 列全部品牌活动；`POST /:id/members/batch` 可给别品牌门店打标（**写操作越权**） |
| `snapshots.js` 全部接口 | 改 `accountId` 就能读别品牌账号趋势 |
| `ai.js` 全部接口 | 可对任意品牌视频跑 ASR/分析并写回 `videos.ai_*`（跨品牌写） |
| `videos.js` `GET /type-stats` | 跨品牌类型汇总外泄 |

另外 session 是内存 `Map`（`server.js:16`），进程重启即失效、多实例不共享。

#### 重构建议

- **数据范围在数据访问层强制注入**，不靠每个路由手写。所有查询走一个带 tenant/brand 上下文的 DAO，漏写就查不到数据而不是查到全部。这是 `HBECHO设计方案/hbecho-设计大纲.md:38` 已有的结论，重构必须落实。
- **`campaign_events` 加 `brand` 字段**，并在所有以 campaign_id 为入参的接口校验归属。
- **指标层独立**。定义一次，看板/导出/API 共用：

```
metric_definition
  ├── code                 如 'campaign_completion_rate'
  ├── numerator_sql        或表达式
  ├── denominator_sql
  ├── scope                brand / campaign / branch / staff
  └── version
```

- **建事实表 + 预聚合**。当前每次查询都全表扫 videos。建议：
  - `fact_content`（内容事实，含平台归一后的指标）
  - `fact_account_daily`（账号日快照，append-only）
  - `agg_campaign_branch_daily`（活动×分公司×日，预聚合）

  最后一张能同时解决"看板慢"和"没有活动维度趋势"两个问题。

- **报表要有数据新鲜度标记**。每个数字旁边能看到"数据截止 X 时间"。商用 API 有延迟，这个更重要。

## 六、几条来自本次实操的经验

这些不是代码问题，是流程经验，但对重构同样重要。

**dry-run 挡下了三次数据损坏。** 本次修复过程中：
1. "按 `account_identifier` 无差别改 `home_url`" —— dry-run 发现 710 的 ident 指向别人门店的号，方案本身是错的
2. "清理串号污染" —— 第一版检测规则会误清 15 个链接错配账号的**真实**资料
3. "清理污染快照" —— 第一版会误删 31 个账号的**合法**快照（它们只是 bg 残留，profile 数值是真的）

三次都是在 dry-run 阶段发现的。**任何批量写库操作默认 dry-run，这条应该写进开发规范。**

**"改一处、验一处"比"改完再验"有效得多。** 每个补丁打完立刻用真实账号跑一遍，337 那次重爬直接证明了两个补丁都按预期工作。

**区分"数据错"和"链接错"花了最多时间。** 两者现象相似（都是"这个账号的数据不对"），但处理方式完全相反：前者要清空等重采，后者要保留数据只改链接。重构时应该在**数据模型层面**就把这两种状态区分开，而不是靠事后写脚本区分。

**注释里的事故复盘极有价值。** 这个项目的代码注释质量很高，很多"为什么这么写"都记录在案（比如 `importCampaignMembers.js:258-266`、`scraper.js:317-333`）。本次排查大量依赖这些注释。重构时请保持这个习惯：**凡是因为踩坑才写成这样的代码，都要在注释里写清踩的是什么坑。**
