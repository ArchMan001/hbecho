## 一、这个域管什么

### 1.1 四个问题

```
看到什么字     → 标题、正文里的话题（@、POI、链接 2.0）
图长什么样     → 主页背景 / 头像 / 封面与标准图像不像
算过没有       → 哪条内容、哪一版能力、什么时候算的
算不出来怎么办 → 没这个字段、本来不适用、算失败了、算得太旧
```

### 1.2 不管什么

| 事情 | 归谁 |
|---|---|
| 内容、主页、评论、媒资怎么采、怎么存 | A 数据底座 |
| 这个信号算不算命中、阈值定多少 | D 规则与考核 |
| 完成率怎么算、点检表怎么排 | E 指标与看板 |
| 谁能触发重算、谁能看证据 | B 访问控制 |
| 标准图 / 元素图存什么、与哪个监控判定计划版本绑定 | C 的监控段（D 只引用，不写图） |
| OCR、图片/视频理解 | 2.0 |
| 以图搜图 | 不做（C5 明确不做） |
| 页面长什么样 | F 业务应用 |

### 1.3 一条主线

```
A 把内容和图片存成不可变的事实
→ C 从中抽出可判定的测量值，同时记下用的是哪一版能力、什么时候算的
→ D 的规则只读测量值做判定，绝不自己调识别
→ 信号不够时 D 提需求，C 只对规则圈定的候选补算
→ 能力升级后只重算受影响的信号，不重判全部历史
```

**C 的职责到「可判定的测量值」为止。** 它不回答「这条内容有没有达标」，只回答「这条内容的封面与这张标准图的匹配度是 8.3」。

## 二、用户与场景

### 2.1 谁在用

| 使用者 | 来这个域做什么 | 频率 |
|---|---|---|
| 平台运营 | 查某条内容有哪些信号、哪一版、什么时候算的 | 每周 |
| 总部/分公司运营 | 看到「这条内容为什么没命中」时，顺着证据追到信号 | 每月 |
| D 规则与考核（系统） | 按规则声明的依赖信号读取测量值；缺信号时提需求 | 持续 |
| 研发 | 注册新信号、升能力版本、触发受控重算 | 按发版 |

**业务用户不直接操作 C。** 他们看到的是规则判定与证据；C 只在证据下钻时露出。

### 2.2 三条真实路径

| # | 场景 | 走哪条链路 |
|---|---|---|
| 1 | 每周同步后，新内容入库，0 档信号自动就位 | 文本信号抽取（第四章） |
| 2 | 某活动要求「主页背景与标准图一致」，规则圈定候选后跑比对 | 模板匹配（第五章） |
| 3 | 模板匹配算法升级，要知道哪些历史结果过期、要不要重算 | 能力版本与重算（第七章） |

### 2.3 规模

| 参数 | 数值 | 状态 |
|---|---|---|
| 被监控账号 | 6,000 | 已确认（D-02、D-30） |
| 支持平台（1.0） | 抖音、小红书、快手 | 已确认（D-47） |
| 内容增量假设 | 每账号每天 1 条 → 约 218 万条/年 | **沿用旧总纲假设，待实测** |
| 特征表规模 | 一条内容一行 → 与内容表同量级 | 估算 |
| 模板匹配调用量 | 进入第 2 层时对该活动圈定范围全量执行，按候选约占 10% 估算 → 约 22 万次/年 | 估算，取决于活动与规则 |

> 旧总纲的容量测算是按 3,000 账号算的；D-30 把被监控账号改为 6,000 后，内容与特征表的年增量大约翻倍。**这不是精确预算，只用来判断「不需要大数据栈、需要按候选集控制识别调用」这个结论仍然成立。**

### 2.4 1.0 的边界

- 1.0 做 **C1 文本信号、C2 模板匹配（图片是否一致）、C3 音频 ASR + 大模型判定、C4 特征存储**（§7.1）；
- 2.0 增加 **C2 的 OCR**（图中文字）、**C3 的图片 / 视频理解**与多轮对话配置（§5.9）；
- **不做** pHash 作为独立能力或判同依据；~~pHash 只用于档 1 特征匹配的内部预筛（§5.2），不产出信号、不单独计费~~ —— 由刘学奎于 2026-11-12 修订（C-D16）：1.0 不做 pHash 预筛，档 1 直接 SIFT / ORB；不得作为媒资判同依据（不继承清单第 7 条）；
- **不做** 分镜、机型识别等独立能力——它们由视频理解的标准化输出覆盖，不单列模块；
- **C5 向量与相似检索、C2 档 4 图像向量化明确不做**——1.0 与 2.0 都不做（2026-10-28 决策，见第十三章 13.8）；
- **不做** 任何「业务判定」——阈值、命中、达标都在 D；
- **1.0 只产出会被算子消费的信号**：@ 提及、POI、外链、账号昵称/签名等暂无算子的 C1 信号不抽取、不落库，标 2.0（C-D06）。
- 覆盖抖音、小红书、快手；视频号 2.0。快手的 C1 文本信号与封面模板匹配可用；快手主页没有头像与背景，`account.bg_*` / `account.avatar_*` 对快手一律 `not_applicable`；**小红书同理**（由刘学奎于 2026-11-12 修订，C-D18）。

## 三、概念

### 3.1 什么算信号

**信号是从原始事实或素材中抽出的、可被规则直接比较的测量值。**

它不是原始字段的复制。原始字段归 A（标题、正文、时长、互动数都在内容快照里）；信号是经过解析与归一化、能被规则稳定引用的那一层。

| 例子 | 是信号吗 | 原因 |
|---|---|---|
| `published_at` | 否（是 A 的事实） | 平台返回的时间原样存着 |
| `hashtags = [#618, #海信中央空调]` | 是 | 从正文里解析、去重、归一化后得到 |
| `cover_template_score = 8.3` | 是 | 一次比对算出的测量值 |
| `is_618_campaign = true` | 否 | 这是判定，归 D |

### 3.2 两类信号：结构化与派生

| 类别 | 从哪来 | 存储 | 成本 | 1.0 例子 |
|---|---|---|---|---|
| **结构化信号** | 从 A 的字段解析 | 能走索引的列或 JSON 列 | 0 档 | 话题、正文归一化文本 |
| **派生信号** | 需要算法计算 | 特征表的信号 JSON | 档 1（本地算法） | 模板匹配得分 |

分工的理由：结构化信号要作为 0 档算子做 SQL 预过滤（把几千条剪到几百条），必须能走索引；派生信号只在候选集内存中比较，候选集已经很小。

> 结构化信号存在哪张表、用列还是 JSON，由 C 域 spec 决定；本文只要求「0 档信号必须可索引、可下推」。

### 3.3 一个信号的五态

规则只看到「命中 / 不命中 / 不知道」三值；C 内部必须把「不知道」拆细，否则运营无法判断该补采、该重算还是该改规则。

| 状态 | 含义 | 典型原因 | 规则看到 |
|---|---|---|---|
| `valid` | 算出来了 | — | 参与比较 |
| `missing` | 该有但还没有 | 还没跑、依赖的素材没归档 | unknown |
| `not_applicable` | 本来就不适用 | 图文笔记没有时长；无封面 | not_applicable |
| `failed` | 算了但失败 | 图片损坏、算法异常、超时 | unknown |
| `stale` | 有旧值，但能力已升级 | 算法版本落后于当前版本 | 默认使用旧值并标 `stale`；计划可配置为 unknown（C-D05） |

**`missing` 与 `failed` 不能合并成 null**，`not_applicable` 不能当成 `missing`——后者会触发无意义的识别任务。

### 3.4 信号版本与时间

每个信号值必须同时带着三件事：

```
value        测量值本身
capability   产出它的能力标识与版本（如 template-match@1）
produced_at  实际产出的时间（UTC），不是内容发布时间
```

**版本要精确到单个信号，不是整张特征表。** 升级模板匹配不应让文本信号一起失效。

### 3.5 信号不是判定

- 模板匹配返回**匹配度**（0.0–10.0 的得分 + 证据），不返回「算不算达标」；
- **阈值是规则参数**，写在 D 的算子实例里，随规则版本冻结（13.2 已关闭：阈值归 D）；
- 因此同一次匹配结果可以被两条规则用不同阈值复用，不需要重算。

### 3.6 缓存与复用

一次识别结果的复用键是四元组：

```
素材指纹（SHA-256）+ 能力标识 + 能力版本 + 参数指纹
```

- 参数指纹包含算法参数与标准图/元素图指纹；**标准图换了就是新的参数指纹**，必须重算；
- **素材指纹按对象类型定义**（C-D12）：内容 = 快照原始标题/正文或图片字节；账号 = 主页快照；评论 = 评论记录；平台解析差异进能力标识。上线后不改；
- 同一个标准图被多个监控判定计划引用时**共享结果**；不同标准图各存一份，互不覆盖；
- 监控判定计划 ID 与版本只作为血缘记录，不进入复用键；
- 只按素材指纹缓存会让不同标准图读到彼此的结果（设计大纲 C2 注意点 1）；
- 复用键一旦上线再改等于历史缓存全部作废，必须在 C 域 spec 开工前定稿。

## 四、C1 文本信号

### 4.1 抽什么

| 信号 | 从哪抽 | 1.0 |
|---|---|---|
| 话题标签 | 正文与标题中的 `#话题` | ✅ |
| 归一化标题与正文 | 全半角、空白、不可见字符、平台专有占位符 | ✅ |
| ~~@ 提及~~ | `@昵称` | ❌ 1.0 不产出（暂无算子，2.0，C-D06） |
| ~~POI / 位置~~ | 平台返回的地点或正文中的位置标记 | ❌ 1.0 不产出（暂无算子，2.0，C-D06） |
| ~~外链~~ | 正文中的 URL | ❌ 1.0 不产出（暂无算子，2.0，C-D06） |
| ~~分词与关键短语~~ | 正文分词、短语抽取 | ❌ 1.0 不做（13.1），用子串匹配 |

**不做情感、不做实体识别、不做摘要。** 这些是 2.0 或 H 域的事。

### 4.2 归一化规则

同一活动的话题，业务和专员写法不会一致；不归一化就会出现「配了 #618 却漏掉 #618大促」的假阴性。

| 情况 | 处理 |
|---|---|
| 全角 `＃` 与半角 `#` | 统一为半角 |
| 话题大小写 | 英文统一小写，中文不受影响 |
| 前后空白、连续空白 | 去除 / 合并为单个 |
| 中文标点与英文标点 | ~~统一为中文标点（用于文本匹配）~~ —— 由刘学奎于 2026-11-12 修订（C-D17）：按 NFKC 方向统一（全角标点折叠为 ASCII），另补 `。`→`.`、`、`→`,`；`text.regex` 的正则须按归一化后的形态书写 |
| emoji 与不可见字符 | 保留原文，另存归一化副本 |
| 平台专有占位（@好友、话题跳转符） | 按平台适配器剥离，不进入正文 |

**原文永远保留。** 归一化只产生「用于匹配的那一份」，不覆盖 A 存的原始字段。

### 4.3 何时抽

- ~~内容快照 **finalized 之后立即抽**~~ —— 由刘学奎于 2026-11-12 修订（C-D15）：内容 **current 指针推进后**抽取，0 档、免费、不阻塞同步落库；评论正文在评论入库后立即抽；
- **模板与元素匹配分不在入库时算**：在计划进入第 2 层、每次判定执行（只补缺失值）或显式重算时按计划范围算（C-D09）；
- 抽取失败不回滚内容入库——内容事实已经成立，信号状态记为 `failed`；
- 同一内容重复入库不重复抽（~~按 content + snapshot + capability 幂等~~ —— 由刘学奎于 2026-11-12 修订（C-D15）：按素材指纹 + 能力版本幂等，文本没变的新快照只前移所持快照，不重抽）。

### 4.4 抽不出来怎么办

| 情况 | 表现 |
|---|---|
| 平台没有标题字段 | 标题信号为 `not_applicable`，不是空字符串 |
| 正文为空 | 归一化文本为 `valid` 的空值，话题为空数组 |
| 评论 `content_text` 为 `NULL` | 与空串一样读 `valid` 的空值，但素材指纹区分二者；A 日后给评论正文加值状态时改读 `missing`（C-D20，由刘学奎于 2026-11-12 修订） |
| 解析器遇到未识别格式 | 该信号 `failed`，记录原始片段，其余信号照常 |

### 4.5 平台差异

抖音与小红书的话题在返回结构里位置不同，**解析规则按平台版本化**，不写成一个 if 分支堆；2.0 恢复 @、POI、外链时同样按平台版本化。两平台的表现差异必须能在信号目录里看出来（哪个平台支持哪类信号）。

## 五、C2 素材比对与 C3 理解能力

### 5.1 三个业务问法（不区分图像对象）

2026-10-28 决策（刘学奎）：素材比对按**业务问法**定义能力，不按图像对象（主页背景 / 头像 / 封面 / 图文图片）拆分。同一能力可用于任一图像，由调用方指定对象。

| 业务问法 | 输入 | 技术手段 | 成本档 | 1.0 |
|---|---|---|---|---|
| 这张图和标准图是不是同一张 | 标准图 | 特征匹配（~~pHash 预筛 + ~~SIFT / ORB 精匹配；由刘学奎于 2026-11-12 修订，C-D16：1.0 不做预筛） | 1 | ✅ |
| 图里有没有某个元素 | 元素图（业务提供） | 局部特征匹配（SIFT / ORB + 单应性校验） | 1 | ✅ |
| 图里有没有某些字 | 要求出现的文字 | OCR + 字符串匹配 | 2 | ❌ 2.0 |

**三种做法统一输出 0–10 分与 11 个整数档**，每档配一张真实被测评图，供业务判断阈值。

**不做类别识别**（2026-10-28 决策）：业务不会说"要有空调外机"这种没有具体图的要求；所有元素判断都走"提供元素图 + 特征匹配"。因此视觉大模型不用于第 2 层的元素判断，只用于第 3 层的图片/视频理解。

**元素图匹配的适用边界**：它找的是"这一张具体的图"——同一设计稿、同一素材、外形基本一致时才找得到。元素要有足够纹理、在画面中不能太小、不能被大面积遮挡；纯色 logo、文字类元素特征点少，匹配不稳定，这类需求应改用文字识别。

**四类做法的成本差异很大**，实施与计费必须分开看：模板匹配是本地算法（~0），OCR 是低额外部调用，视觉大模型是中高额调用。

### 5.2 技术档位映射

| 档 | 能力 | 对应业务问法 | 1.0 |
|---|---|---|---|
| 0 | 感知哈希 pHash / dHash | ~~档 1 的内部预筛；不产出信号、不单独计费~~ —— 由刘学奎于 2026-11-12 修订（C-D16）：1.0 不使用 | ❌ 1.0 不做 |
| **1** | **特征匹配 SIFT / ORB** | **图片是否一致、元素图是否出现** | ✅ |
| 2 | OCR | **图中是否包含指定文字** | ❌ 2.0 |
| 3 | 视觉大模型 | 第 3 层的图片理解与视频理解 | ❌ 2.0 |

### 5.3 分数标准化与阈值选择

- C 把原始相似度**标准化为 0.0–10.0 分**，原始值与算法参数保留在证据里；
- **存储与规则比较用连续 0.0–10.0（含小数）**；0–10 共 11 个整数档只用于界面选阈值与展示样例（C-D08）；
- **不同做法的 0–10 分含义不同**（整图匹配分 / 元素图匹配分 / 文字命中度），阈值不可互换，也不能跨做法复用同一套分数；
- **文字检测的分数定义**：要求出现 N 个字或词，识别到 M 个，得分 `round(M ÷ N × 10)`；全部命中为 10 分。要求只有一个词时，命中即 10、未命中即 0；
- 阈值本身属于 D 的规则参数，C 只提供分值。

### 5.4 模板匹配做什么

输入两张图：**标准图**与**待比对图**。输出：

| 输出 | 说明 |
|---|---|
| 标准化得分 | 0.0–10.0 |
| 证据 | 原始相似度、匹配点数量、内点率、预处理尺寸、耗时 |
| 能力版本 | 算法与参数版本 |
| 状态 | `valid` / `failed` / `not_applicable`（无图） |

**不输出「匹配 / 不匹配」。** 阈值由 D 的算子实例决定。

**1.0 的适用范围**：同一张标准图与同一张待比对图的整体相似度。不做局部区域匹配、不做多标准图选优、不做旋转/透视校正之外的复杂变换。

### 5.5 输入从哪来

```
标准图  ← 每个监控判定计划、每个图像对象一张（封面 / 背景 / 头像），归 C 的监控段；D 只引用
元素图  ← 业务为「图里有没有某元素」提供的那张图，按元素条件各一张
待比对图 ← A 的正式媒资（verified + archived），C 只读字节、不触发新的采集下载
```

- **同一计划内每个图像对象只允许一张标准图**（封面 / 背景 / 头像最多三张），不做同一对象的多标准图组（C-D01）；
- 标准图存 OSS，按「监控判定计划 ID + 计划版本 + 图像对象 + 图片 SHA-256」定位，旧版本不覆盖（C-D02）；活动计划本身不版本化；C 只按「一张可从 OSS 读取的图 + 稳定指纹」对待；
- 标准图 / 元素图由 C 的监控段管理，D 只引用、不写图（C-D01）；
- 标准图变更 = 参数指纹变更 = 必须重算，不复用旧结果；
- **不允许使用 `carried_forward` 素材做「当前图匹配」**：它证明不了本轮当前图没变（规则引擎 design §8.2 第 8 条）。

### 5.6 什么时候跑

2026-10-28 决策（刘学奎）：业务进入第 2 层筛定时上传标准图或元素图，后台对**该活动圈定范围内的全量对象**执行比对，不等到规则发布。

1. **进入第 2 层时**：对圈定范围全量跑，产出每个对象的分值，供业务看分值分布并定阈值；
2. **受控重算**：能力升级或标准图变更后，由有权限的人指定范围补算。

3. **每次判定执行时**：对执行范围内缺失的匹配分自动补算（例如第一次进入第 2 层之后新入库的内容），已有分数不重算（2026-11-04 补）。

匹配分不在内容入库时算（C-D09）；第 1 层与全局文本信号不依赖标准图，不受此限制。

**仍没有「入库即全量算」。** 比对范围是「该活动圈定的候选」，不是全部历史内容。

### 5.7 输出什么

一次比对的结果落到特征表，带五态、得分、证据、能力版本、产出时间。**同一 (素材, 能力, 版本, 参数) 只算一次**；再请求直接复用。

### 5.8 陈旧素材

待比对图是上一轮 `carried_forward` 的，或素材文件已不可读时：

- 状态记 `missing`（本轮没有新的 verified 素材）或 `failed`（文件不可读），不返回得分；
- `stale` 只用于「有旧值但能力版本落后」，不用于素材陈旧（C-D05）；
- 业务侧统一展示为「未获取成功」，不等待、也不判不达标（D 域 §1.4）。

### 5.9 C3 理解能力：三类

2026-10-28 决策（刘学奎）：C3 按输入形态分三类，不再按「语音与视频」笼统定义。

| 类型 | 输入 | 处理 | 输出 | 1.0 |
|---|---|---|---|---|
| **音频理解** | 视频音轨 | ASR + 固定提示词 + 表单标准 → 大模型判定 | 转写文本 + 结构化判定（结论 / 理由 / 模型 / 提示词版本） | ✅ |
| **图片理解** | 封面、主页背景、图文图片 | 视觉大模型 + 系统提示词 | 标准化结构化描述 | ❌ 2.0 |
| **视频理解** | 视频（关键帧或整段） | 视觉大模型 + 系统提示词 | 标准化结构化描述 | ❌ 2.0 |

**1.0 只开放音频**（C-D14）：标准由 D 的表单以一段自然语言提供；每计划最多一个 ASR 考核项；`asr_judgement` 按标准/提示词/模型参数化；ASR 与大模型能力必须 smoke 验证后启用，未验证时该层 disabled。图片/视频理解与多轮对话 2.0。

音频最直接：调 ASR 拿到文本。图片与视频需要**系统提示词约束输出格式**，不允许自由文本（2.0）。

### 5.10 标准化输出与落库

- 每个理解能力有一套固定的**系统提示词与输出 schema**；
- **1.0 的 ASR 判定**输出结构化结论（结论 / 理由 / 模型版本 / 提示词版本），按「标准 + 提示词 + 模型」参数化；
- **2.0 的图片 / 视频理解**输出必须是结构化 JSON（不是散文），落到特征表，带能力版本与产出时间；
- 下游判定读取这些结构化结果，**不重新读原始素材**；
- schema 变更 = 能力版本变更，旧结果标 `stale`。

### 5.11 业务与对话大模型协作定标准

2026-10-28 方向（细节待 D 域设计）：业务不再只靠表单配阈值，可以与大模型对话描述标准（如「封面里要有活动主视觉，且不能出现竞品」），由大模型把标准转成可执行的判定条件。

**1.0 不做**：随第 3 层（2.0）或 H 域规则辅助一起做；C 只提供信号目录与结构化输出，不定义对话流程（C-D11）。

约束：**对话产生的标准必须落成可复核的结构化条件**，不能只存在于对话历史里；否则无法解释、无法重算、无法审计。

## 六、C4 特征存储

### 6.1 一个对象一行

一条内容 / 一个账号的主表只保留**一行当前值**，信号放在结构化字段或 JSON 里，每个信号自带版本与时间；旧版本值进独立的历史 / 证据表，按 §6.4 保留（C-D13）。

理由：按信号拆行会让行数上一个数量级（约 218 万内容 × 十来个信号），而查询永远是「读这个对象的全部信号」。

### 6.2 每个信号自带版本与时间

```text
{
  "hashtags":       { "v": ["618", "海信中央空调"], "cap": "text@1",     "at": "..." },
  "cover_template": { "v": 8.3, "ev": {...},          "cap": "template@1", "at": "..." }
}
```

升某一个能力时只重算该信号的条目，不动其他条目。

### 6.3 复用键

见 §3.6。特征表按复用键判重，**重复请求不产生第二次计算**。

### 6.4 保留与失效

| 项 | 规则 |
|---|---|
| 判定结果（达标 / 不达标 / 未获取成功） | **长期保留**，作为成绩档案 |
| 判定证据与被判定引用过的特征 | **3 个月**（申诉期，2026-10-28 决策） |
| 未被任何判定引用的特征 | **1 年**，随 ODS 一起清理 |
| 旧能力版本的特征 | 确认无判定引用后清理 |
| 失败的记录 | 3 个月，供运营判断是否补采素材 |
| 重算的可行性 | 重算读的是 A 的正式媒资（长期保留），不读 ODS；证据删除后可通过重算重建（OCR 与视觉有费用，模板匹配免费） |

> 旧值可用于新判定，前提是仍在保留期内；超过保留期被清理后，信号变 `missing`，D 显示 unknown / 未获取成功（C-D05）。

> **可解释性的取舍**：申诉期定为 3 个月。期内判定可完整下钻到证据；超过 3 个月只保留结论，不再能解释"为什么"。这个取舍由业务接受（刘学奎，2026-10-28），不是技术默认值。

## 七、能力版本与重算

### 7.1 什么时候算「能力升级」

以下任一变化都算升级，必须是新版本：

- 抽取/匹配算法或参数变化；
- 归一化规则变化（例如话题大小写策略调整）；
- 平台解析规则变化；
- 依赖的预处理变化（图像尺寸、去水印）。

**所有信号的能力版本跟随最新**（C-D03）：升级不改变监控段的固定版本，也不产生新的计划版本（C-D04）。旧结果保留并标 `stale`，新判定默认继续使用旧值并标 `stale`，计划可配置为 unknown（C-D05）。升级不触发 D 的计划重算：已保存的判定结果不改写；需要按新能力补算时，由业务显式触发（§7.2）。

### 7.2 重算是显式操作

**C 的系统性改动（算法、解析规则、预处理）不主动重算任何历史，也不触发 D 的计划重算**；历史就是历史。重算一律由业务显式触发，且只影响触发之后的新执行。

重算不是界面上一个「重新识别」按钮。任何重算必须：

1. 指定范围（时间 / 品牌 / 活动 / 账号 / 内容）；
2. 1.0 展示预估条数；档 1 免费，不展示费用；付费重算的费用预估 2.0 仅超管可见；
3. 由 `rule.definition.manage` 持有者触发（与配置规则、上传标准图是同一个能力），记录操作者、范围、时间、能力版本；
4. 只重算该范围，不越界。

这样设计的原因：新增一个能力后，业务的第一反应必然是「把历史全部重跑」，而全量重算在 2.0 接入付费识别后就是百万级调用。

### 7.3 重算不阻塞判定

重算期间，D **默认继续使用旧值并标 `stale`**；计划可配置为把 stale 当 unknown 并等待重算。默认值是"不断档"，但 C 不替 D 决定单个计划的策略（C-D05）。

### 7.4 旧结果不删除

新版本结果写入后，旧版本记录进历史 / 证据表保留供对账：同一范围内两版得分差异、翻转的对象清单。保留期按 §6.4，不承诺永久（C-D13）。

## 八、失败与未知

### 8.1 识别失败 ≠ 未命中

~~技术失败（图片损坏、算法异常、超时、依赖未就绪）一律记 `failed`，规则看到 unknown。~~ —— 由刘学奎于 2026-11-12 修订（C-D19）：失败分两类。**确定性失败**（图片损坏、解码失败、模型拒绝、输出非法）记 `failed`；**瞬时失败**（能力服务不可用、超时、来源 5xx、依赖未就绪、能力版本不一致）重试，用尽后任务置 `dead`，**不写结果行**，信号读作 `missing` 并带原因。两类对规则都是 unknown。**绝不能把失败写成 0 分或空数组**——那会让「没算」和「算出来是零」混为一谈。

### 8.2 素材缺失

需要比对图但 A 还没有 verified 媒资时，状态是 `missing`，并向 D 暴露「需要素材」这件事（由 D 通过 A 的媒资需求链路补下载），C 不直写同步任务。

### 8.3 不适用

图文没有视频时长、内容没有封面、账号没有自定义背景图 → `not_applicable`，不是失败，也不触发识别任务。

### 8.4 过期与不可重算

媒资文件缺失、损坏或从未归档 → 标记不可重算，保留原结果与原因。**ODS 过期不影响重算**，因为重算读的是长期保留的正式媒资。

## 九、谁能做什么

C 没有独立界面。它的操作入口都在相邻域，权限由 B 统一发放：

| 动作 | 典型 Capability | 说明 |
|---|---|---|
| 查看某对象的信号与证据 | 随对象的读取权限（内容/账号） | 没有内容读权限就看不到证据 |
| 触发受控重算 | 复用 `rule.definition.manage`（能配置规则与标准图的人就能重算） | 不单独设能力；必须带范围与预估 |
| 注册新能力 / 升版本 | 研发发版，不走业务界面 | 记录变更 |
| 信号目录与覆盖率 | 不单独开放界面 | 平台不支持的信号在规则配置里直接不可选 |

**未注册的信号默认不可用**；规则引用一个未注册或未启用的信号时，保存即拒绝，而不是运行时返回空。

**信号删除**（C-D10）：C 删除一个信号后，引用它的**已发布计划标「不可执行」**，下一次执行记未获取成功并提示原因；保存或发布新版本时直接拒绝。不自动从计划里移除信号，避免静默改变判定语义。

## 十一、与相邻域的契约

| 对方 | C 要什么 | C 给什么 |
|---|---|---|
| **A 数据底座** | finalized 的内容快照、verified 的媒资、平台与内容类型 | 特征记录（独立于 A 的表） |
| **D 规则与考核** | 依赖信号清单、候选集、信号集合与标准图引用 | 测量值 + 证据 + 五态 + 版本；缺素材时回报需求 |
| **B 访问控制** | 触发重算的授权判断 | 操作记录（谁、何时、什么范围、哪版能力） |
| **E 指标与看板** | — | 不直接对接；指标只读 D 的判定 |
| **I 运维与成本** | 部署、资源与计量（常驻小服务，D-35） | 单次与批量耗时、失败率、信号覆盖率 |

**C 不写 A 的表，D 不写 C 的表。** 跨域只通过「读事实 / 提需求 / 回结果」这三个动作。

### 11.1 与 D 的分工规则

**谁调用模型，谁产信号；谁定阈值，谁出结论。**

- 第 3 层由 C 调用模型，产出 `*.judgement` 信号，带结论、理由、模型版本与提示词版本；C 仍不回答「这个考核项是否达标」。
- D 只做组合与达标：读 C 的判据信号，加上自己配的阈值与逻辑，产出成功 / 不达标 / 未获取成功。
- C 不读 D 的规则表；D 把标准图引用、阈值、标准文本作为**参数**传给 C，不写 C 的表。
- 第 3 层的 ASR 与大模型调用**全部经 H1**（2026-11-04）：C 拥有信号语义与提示词内容，H1 负责 Key、成本、审计与降级。
- D 的第 2、3 层能力目录**引用** C 的信号目录，不重复定义参数；C 增删信号，D 的可选集跟着变。
- 两种重算分开：C 的能力升级重算由 `rule.definition.manage` 持有者按范围显式触发；D 的计划回退只让计划版本失效，不自动触发 C 重算。

**监控段归 C、由 D 驱动**（C-D10）：监控段（信号集合、标准图 / 元素图）由 C 拥有；D 建计划时同步建 C 段，D 改信号集合或图时 C 段同版本更新；C 与 D 各持一张 1:1 记录、通过计划 ID 关联。C 不写判定段，D 不写监控段。

**能力版本不进监控段固定**（C-D03）：每次执行把实际能力版本写进信号与判定证据；计划版本只由配置变化产生（C-D04）。

> 计划作为消费侧统一入口、常态采集与按需采集的分工，见 `prd-platform.md` §6.11。
