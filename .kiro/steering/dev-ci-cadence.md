# 开发节奏：本机验证、推送批次、CI 等待与合并

2026-10-25 建立。数字来自 hbecho 当前实际：仓库里还没有应用代码，CI 只跑文档与密钥门禁，因此**本条不写任何未实测的耗时**。应用代码落地后补测并替换。

## 本机

1. **每个 task 边界跑一次 `./scripts/verify.sh`**，不 push。它当前覆盖：密钥扫描（工作区 + git 历史）、Markdown 相对链接、文档登记与 spec 结构。应用代码落地后，该命令扩展为 typecheck + 测试 + 静态门禁，**在此之前不要声称"测试通过"**。
2. 同一时刻只跑一个会清库的测试进程。本机测试共用同一个库时并发会互相清表，报出来是一片不相干的失败。
3. 测试造数据不要对争抢同一行锁的发布类操作使用 `Promise.all`；顺序 `await`。

## 推送

4. **一个 spec 一条分支**（如 `a-data-foundation-tracer`），**不按批次开新分支**；一次性修复用 `fix/<主题>`。`main` 永远保持 CI 全绿、可部署。
5. **一个 spec 推两次**：① 建表/迁移那批做完之后（尽早在干净库上跑一次 migrate + 全量 verify，同时把工作推到远端做异地备份）；② 收尾（全部 task 做完、验收文档就绪）。中间不推。
6. 只改文档的 push 同样会跑 CI；它不会构建镜像，也不会产生付费调用。
6a. 分支 push 改了应用路径时，`image` job 会构建并做生产配置冒烟，但**不推 ACR**（2026-11-12）；`main` 才推。需要测试 ECS 拉某个分支的镜像时，手动 `gh workflow run ci.yml --ref <分支>`。合并前等的是 `verify` 与 image 的构建 + 冒烟，不用等推送。
7. push 之后**不要停下来等**，继续写下一个 task。只有**合并前**那一次需要等。
8. 在一个你打算合并的 run 结束之前，不要再往同一分支 push；新的 push 会取消上一个 run（`cancel-in-progress`）。

## 等 CI

9. 用 `gh run watch <run-id> --exit-status`，超时设大。**不要 `sleep` 轮询**，也不要 `2>/dev/null` 吞 stderr——那会把「打错 run id」伪装成「还在运行」。

## 合并

10. 从 `main` 切分支；**CI 绿**才合 `main`。合并提交说明写：run id、本机 `verify.sh` 结果；涉及测试机验证的再写通过数与耗时。
11. 合并用 `--no-ff` 语义的合并提交。工作区里不属于本任务的未提交文件，不提交、不改动。

## 小改动批（fix 批次）

2026-11-16 建立，决策人：刘学奎。目标：一批小改动只做一次验证、推送、CI、合并，部署也只做一次，不是每个按钮都走一遍。

**怎么定「一批还是几批」**：不用硬性清单。刘学奎提出改动需求和范围，AI 给出「一次 / 两次 / 拆出去走 spec」的建议和理由，由刘学奎定。AI 判断时看三件事：

1. **能不能整批回滚**：这批有没有迁移？有的话是不是只加表加列（旧代码仍能跑）？只加不删，就可以和别的改动一起合并、一起部署，但部署前要做逻辑备份。
2. **安全面**：改了 Capability、角色或 DataScope 的话，要补对应的授权测试，并在合并说明里单独点出来。数量不是问题，漏测才是。
3. **是否与在途 spec 混合**：**不与在途 spec 放进同一次 CI 和合并**（出问题时分不清是谁引入的）；两者可以共用一次部署窗口，分别合并到 `main` 后再一次部署。

拿不准的单项（改动本身是完整功能、或要先单独观察的）：拆出去走 spec 或单独的 `fix/<主题>`。

**节奏**

1. 一批一条分支：`fix/<主题>-<日期>`（例：`fix/ui-batch-2026-11-16`），不按项开分支；多个提交，每个提交说明逐条列出改动，便于单独 revert。
2. 本机 `./scripts/verify.sh` 只跑一次（批次边界），UI 改动在预览 3202 上看过、截过图（见 `ui-workflow.md`）。
3. 推送一次，等 CI 绿；`--no-ff` 合并一次，合并说明写 run id 与 verify 结果。
4. 部署一次（先说明、得到同意，见 `server-access.md`），部署后按 `ui-workflow.md` §4 第 8 步走查。
5. **文档与运维记录不单独推送**：只改文档的 push 同样要跑完整 verify（见下），附在下一批里；紧急修复除外，可单独走。
6. 批次内每一项在对应 spec 的 tasks / acceptance 里登记（谁提的、改了什么、怎么验的）。

**CI 的实际耗时**（2026-11-16 四次运行）：`verify` 9.6 ~ 19 分钟（含只改文档的一次，16 分钟）；`image` 约 2 分钟；部署本身（拉镜像、迁移、重启）几分钟。慢在 `verify`，所以靠「攒批」少跑，不靠多买一台 ECS（正式 ECS 的价值是隔离真实用户，不是提速）。
