# 界面协作：原型（4100）、完整应用（4400）与 ECS

2026-11-16 建立，决策人：刘学奎。**2026-11-18 端口改为 4100（原型）/ 4400（完整应用），决策人：刘学奎**，与 hbdam 的 3100 / 3400 同一套记法；旧文档里的 4175 / 3202 是历史写法，以本文为准。解决的问题：UI 预览散在多个目录、多个端口，AI（Claude / DeepSeek 等）各自生成预览，看到的内容与线上不一致，不知道哪个是准的。

**权威关系**：视觉与交互以 [`ui-foundation.md`](../../HBECHO设计方案/ui/ui-foundation.md) 为准（本文件不改它）；带页面的 spec 的「界面确认闸门」仍按 `structure.md`。本文件只规定**预览怎么跑、改动怎么分类、从原型到线上怎么流转**。本机的启动命令、账号、已知坑在 [`ui-lab/LOCAL-UI.md`](../../ui-lab/LOCAL-UI.md)。

## 1. 四个地方，各管一件事

| 地方 | 是什么 | 代码与数据 | 用来做什么 |
|---|---|---|---|
| **4100** 可点击原型 | 静态 HTML / JS，没有后端 | `ui-lab/`（当前预览工作树里的那份），数据写死在 JS 里 | **做新页面或复杂流程的设计、让刘学奎确认**；不是线上页面的镜像 |
| **4400** 完整应用 | 真实的 Next 应用（与线上同一套代码），假短信、假的 C 端口 | 预览工作树当前分支的 `src/`；数据由 `tests/demo/preview.ts` 造，每次启动重置成同一份 | **确认真实页面的样子与行为**；代码写完后的本地验收 |
| **ECS**（测试机） | 部署出去的镜像 | `main` 合并后 CI 构建的镜像；真实数据、真短信、capability 门控 | 最终环境；部署后只查「与 4400 不一致的地方」 |
| **截图存档** | `ui-lab/<spec>/shots` 或 `app-shots` | 每次发版 / 定稿时拍 | 记录「当时的样子」，用来对比，不用来同步 |

4100 和 4400 **来自同一个工作树**，所以永远是同一份代码、同一个分支；其它端口（3201、3411 等）一律不再使用。

## 2. 一个预览工作树

- 所有 UI 工作（无论谁做）都在预览工作树里做：`~/Documents/hbecho-preview`，分支是当前批次分支（`fix/ui-batch-<日期>`）或当前 spec 分支。
- 启动：`./scripts/preview.sh`（前台运行，Ctrl-C 退出）。它同时提供 4100 与 4400，并把一次性 MySQL 容器和静态服务一起清理。
- 同一时间只有一个工具在这个工作树里改文件（`AGENTS.md` 已有此规定）；换工具前先提交或说明未提交的内容。
- 主目录 `~/Documents/hbecho` 始终停在 `main`，是 `main` 的**只读镜像**（见 [`dev-ci-cadence.md`](dev-ci-cadence.md)「一个事实来源与收尾」）：不在里面改文件、**不用来做 UI**；合并后由 AI 把它拉取到最新。
- 开始新一批之前先对齐：`git fetch && git rev-list --count HEAD..origin/main`，要为 0（或先合并 `main`）。否则 4400 和 ECS 的差别，一半来自代码版本。

## 3. 每次改动先分类

| 类型 | 举例 | 做法 |
|---|---|---|
| **A 新页面 / 复杂流程** | 判定计划三页向导、点检表 | 先在 4100 做静态原型 → 刘学奎确认 → 写代码 → 4400 验收。确认记录写进该 spec 的「N.6 界面设计确认」 |
| **B 已有页面上的小改** | 按钮、筛选、字段、文案、布局微调 | **跳过静态原型**，直接在真实页面上改，在 4400 看、截图、确认 |
| **C 带迁移的完整功能** | 学习平台两级标签 | 走 spec（要原型就先原型），不与别的改动混在同一次验证里；迁移与回滚按 `dev-test-deploy-workflow.md` 的「扩展 → 部署 → 收缩」 |

分类拿不准就问；刘学奎提需求和范围，AI 给出「这是 A / B / C」「一批还是两批」的建议和理由，由刘学奎定。一批小改动怎么走 CI 见 [`dev-ci-cadence.md`](dev-ci-cadence.md)「小改动批」。

## 4. 从想法到线上

1. **提需求**：刘学奎说要改什么、范围多大；AI 分类（§3）并给出批次建议。
2. **设计**：A 类在 4100 做原型（`ui-lab/<spec>/`，按 `ui-lab/README.md`）；B 类直接改真实页面。
3. **确认**：刘学奎在 4100 / 4400 上看，明确说「确认」。AI 不把「没反对」当作确认；超出已确认范围要重新确认。
4. **实现**：A 类确认后才写 tasks 与页面代码；B 类确认的改法直接提交。
5. **本地验收**：4400 上走一遍，对照 `ui-foundation.md` §9 的清单；本机 `./scripts/verify.sh` 一次。
6. **推送与合并**：按批次推一次、CI 绿后合并一次。
7. **部署**：从 `main` 部署到 ECS（Workbench，先说明再得到同意，见 `server-access.md`）。
8. **部署后走查**：在 ECS 上只查两件事——① 页面版本与 4400 是同一版（见 §6）；② 真实数据、真短信、capability 带来的差异。结论写进批次说明。

## 5. 原型与真实页面：单向，不做双向同步

- 方向只有一个：**原型 → 代码**。页面落地并部署后，**以真实页面（4400 与 ECS）为准**，4100 里对应的原型标成「已实现，归档」（在 `ui-lab/README.md` 的状态表里登记），不再维护。
- 以后要大改某个页面：从真实页面的当前样子出发，复制成新的原型再改，不要从旧原型出发。
- 小改（B 类）不回写原型。截图存档记录当时的样子。
- 为什么不双向同步：原型是静态 JS，真实应用是 Next，两份文件手工保持一致就是漂移的来源。

## 6. 4400 与 ECS 一致意味着什么

- **代码一致**：ECS 部署的镜像对应 `main` 的某个提交；4400 跑的是预览工作树当前提交。页面页脚和 `/api/health` 的 `build` 字段都显示提交号（预览环境末尾带「+未提交改动」表示有没提交的修改），两边一对就知道是不是同一版。
- **数据不会一致**：ECS 是真实数据，4400 是造的数据。
- **环境不同、且必须不同**：ECS 是真短信、https、production 的 capability 门控、真实的 C（含未接通的图像比对）；4400 是假短信、http、假的 C 端口。预览验收**不能代替**对这些的验证。
- 发现不一致时，先对提交号；提交号一致才去查环境差异。

## 7. 边界

- 不改 ECS、不碰 `~/.workbench` 与任何 `.env` / 凭证；预览不连任何真实数据库、不发任何真实采集 / 识别 / 付费调用。
- 不提交、不删除别的会话的未提交文件；要合并它们，先列清单给刘学奎。
- 新的原型目录先改 `ui-lab/README.md` 的状态表（含「已确认 / 待确认 / 已实现归档」），再放文件。
- 预览造数脚本只在 `tests/demo/` 与 `scripts/preview.sh`，不进 CI、不进镜像。
