# 爬虫四环节问题复盘与解法

> 覆盖范围：录入经销商链接 → 更新经销商链接 → 爬取经销商账号 → 爬取经销商视频信息
> 最后更新：2026-08-19
> 代码基线：`scraper/src/scraper.js` 745 行、`importCampaignMembers.js` 812 行、`resolvePendingHomeUrls.js` 273 行、`bgRescraper.js` 470 行

## 为什么需要这份文档

这条链路上绝大多数故障有一个共同特征：**表面「采集成功」，实际抓的是别人的账号，没有任何报错**。
它们不会让程序崩溃，只会让看板上的数字悄悄变错。所以排查这条链路时，
「跑完了、没报错」不能作为正确性依据 —— 必须用独立口径去交叉验证。

代码里已经沉淀了不少事故注释，凡是带「曾导致」「静默」「极难察觉」「否则」字样的地方，
都是踩过的坑，改动时请先读注释再动手。

## 一、贯穿全局的三个字段

理解这条链路，先理解 `dealer_staff` 上这三个字段的关系。几乎所有链接类问题都源于它们互相错位。

| 字段 | 含义 | 谁在写 |
|---|---|---|
| `raw_home_url` | 商家/专员提供的**原始**链接或整段分享文案 | 导入时用新值覆盖 |
| `home_url` | **爬虫真正访问**的标准化主页地址 | 导入 / 补解析 |
| `account_identifier` | 账号身份标识（sec_uid） | 导入 / 补解析；爬虫只在为空时补 |

三者本应始终指向同一个账号。一旦不一致，就意味着**可能正在采集错误账号**。

### 权威性判断（重要）

不要假设某个字段一定可信：

- `home_url` 与 `account_identifier` 历史上**都**用 `COALESCE` 保护，所以两者都可能是旧值
- `raw_home_url` 是最新导入的，但**它本身可能是错录的**
- 已确认反例：`staff_id=710`（洛阳欣荣/刘大通）的 `raw_home_url` 与 `staff_id=3474`（淇县昱驰/马必威）
  是同一条短链 `v.douyin.com/D0aPVjtRn2s/`。此时 `account_identifier` 指向淇县店，
  反倒是被判成「旧号」的 `home_url` 才与洛阳门店吻合。

**结论：批量按某个字段无差别修复 `home_url` 是危险的。** 必须逐条拿到两个候选账号的昵称，
与门店名/经销商名/专员姓名比对后人工定夺。工具见文末「工具箱」。

## 三、环节二：更新经销商链接（专员换号）

这是踩得最狠的环节。`importCampaignMembers.js:258-278` 的注释是全仓最重要的一段事故复盘：

> 背景（这是一个曾导致长期静默错误采集的问题）：
> 历史实现里两个字段的写入保护级别不一致 —— account_identifier 与 home_url 都用
> COALESCE(旧值, 新值) 保护，而 raw_home_url 用新值覆盖。结果是专员换号、
> 重新导入新链接后，raw_home_url 更新了，爬虫真正访问的 home_url 却停留在旧号。
> 爬虫照常「采集成功」，但抓的是别人的账号，表面无任何报错。

| 问题 | 解法 | 位置 |
|---|---|---|
| 三个链接字段保护级别不一致，互相错位 | `decideLinkUpdate` **成对覆盖**：解析出 sec_uid 则 `home_url` + `account_identifier` 一起写；解析不出则两者都保留原值 | `:279-308` |
| 换号 vs secuid 错配修正无法区分 | 区分 `kind: 'switched' \| 'fixed'`，分别计数并打印新旧对照 | 同上 |
| 换号后旧号的历史 videos 仍挂在该账号下 | 汇总打印「换号明细（这些账号建议重新采集）」，需人工判断是否清理 | ≈`:753-770` |
| 导入时短链没解析成功的账号无人管 | `resolvePendingHomeUrls.js` 离线补解析；状态机 `pending → done`，失败只记 `resolve_error` 保持 pending 可反复重跑 | 全文 |
| 补解析器也曾无条件覆盖 `home_url` | 同样改为成对写入，且只处理 `home_url IS NULL` 的行 | `:215-231` |
| 存量错配无从发现 | `scripts/audit_home_url.js` 只读核查：重新联网解析 `raw_home_url`，与 `home_url` / `account_identifier` 三方比对 | 全文 |

**成对覆盖是这一环的核心原则**：两个字段必须始终来自同一次解析，否则又会互相错位。

### 已知技术债

`resolvePendingHomeUrls.js` 里的链接解析器是 `importCampaignMembers.js` 的**复制版**，
且已经漂移 —— 少了 `v.douyin.com` 垃圾后缀截断和视频链接判定。两份实现需要收敛。

## 四、环节三：爬取经销商账号（profile）

主文件 `scraper/src/scraper.js`

| 问题 | 根因 | 解法 | 位置 |
|---|---|---|---|
| **profile 串号污染**（详见第六章专题） | 同一 API 返回多个 profile（登录号、推荐关注），历史实现无条件覆盖 | 按 sec_uid 精确认领 + 登录号直接丢弃 + `profileUsable` 闸门 | `:21-59, 330, 378, 532` |
| 身份错配漏报一批账号 | 告警条件写了 `secUid &&` 短路，profile 没采到时 `secUid` 为 null 反而不报 —— 那恰恰最该报 | 去掉短路 | `:507-530` |
| profile 不可信时污染持久留存 | `nickname` 等字段是无条件覆盖 | 不可信则只更新 `last_scraped_at`，不写 profile 字段、不落快照、不下载图片 | `:562-570` |

| 补爬背景图会污染活动点检结果 | `bgRescraper` 有同一兜底 | 身份不符**直接判失败**，保持库中原值不动 | `bgRescraper.js:149-165` |

| 抓到的是账号横幅、不是活动要求的装修图 | 字段选错 | 优先 `coverAndHeadImageInfo.profile_cover_list`，降级才用 `cover_url`；camelCase / snake_case 两种命名都兼容 | `:496-502` |
| 已验证一致的背景图被反复重下 | 无缓存 | `bg_match_standard=1` 则跳过下载 | `:546-560` |
| 污染状态被固化 | 上一条跳过逻辑的副作用 | 清理污染时必须一并重置 `bg_match_standard` | `scripts/clean_polluted_profile.js:150-152` |

### scraperBg.js 与 bgRescraper.js 的分工

| 模块 | 职责 | 取数方式 | 速度 |
|---|---|---|---|
| `scraper.js` | 完整采集（profile + 视频列表），日常主力 | XHR | 28-35s/账号 |

### 关键词匹配口径

`OR-of-AND`：同一 `rule_group` 内关键词全部命中才算该组成立（AND），任意一组成立即命中该类型（OR）。
关键词含空格时再拆子词，子词也须全部出现。

**盲点**：匹配只用 `title`（即 `item.desc`），**不含 `note_content`**。
文案写在分享描述或 hashtag 里的内容匹配不到。是否要纳入 `note_content` 需业务决策。

### 两个容易混淆的计数

- `videosFound` = 本次实际入库条数；`scannedCount` = 本次扫到的条数
- `qualified_video_count` 是按 `video_type_matches` **重算全库历史命中**，不限本次抓到的那 40 条，
  所以 `videosFound` ≠ `qualified_video_count`

## 六、专题：「迷迷建筑师」串号污染

### 现象

多个不同门店、不同专员的 `dealer_staff.nickname` 全部变成同一个陌生小号「迷迷建筑师」（粉丝 10、作品 3）。
全库共 **37 条**受影响，其中 **29 条**源自这一个号。

### 根因

污染源 sec_uid：

```
MS4wLjABAAAA_ZcbvJIDt_MeSOT-H8Ru0z_LqcOGMMALY6UnRKq9xRiSUybN1qYrYjuhAHebUEPG
```

该 sec_uid 出现在 `cookies/douyin_cookies.json` 的 `FOLLOW_NUMBER_YELLOW_POINT_INFO`
与 `FOLLOW_LIVE_POINT_INFO` 两个 cookie 中 —— 这是抖音存放**当前登录用户自己**的 UI 状态 cookie。

**即：「迷迷建筑师」就是爬虫用来登录的那个抖音账号。**

链路是：

1. 抖音在**任意**页面都会请求登录用户自己的 profile（右上角头像、个人信息浮层），
   走的是同一个 `/aweme/v1/web/user/profile/`
2. 目标主页加载失败时，唯一到手的 profile 就是登录号
3. 历史兜底逻辑「按 sec_uid 认领失败则退回首个 profile 响应」把它当成了目标账号
4. `nickname` 等字段是无条件覆盖 → 污染持久留存

所有现象都能对上：全网只有一个登录号，所以 29 个门店变成同一个昵称；
粉丝 10、作品 3 是专门注册的爬虫小号；`staff_id=72` 的 `home_url` 是 `/user/self`，
那本身就是「登录用户自己的主页」，100% 命中。

### 修法

不用硬编码昵称（昵称随时可改，换 cookie 账号就失效），而是**自动推导登录号并永久排除**：

```js
// scraper.js:21-59
let _excludedSecUids = null;
function getExcludedSecUids() {
  // 1. 读 EXCLUDED_SEC_UIDS 环境变量（逗号分隔，手工追加）
  // 2. 从 cookie 文件中正则提取 MS4wLjABAAAA... 自动推导登录号
}
```

响应收集处，登录号**连兜底都不做**，直接丢弃：

```js
} else if (excludedSecUids.has(json.user.sec_uid)) {
  // 登录态账号/黑名单账号：连兜底都不做，直接丢弃。
  // 它是本次污染事故的唯一污染源，且永远不可能是某个经销商专员的号。
  selfProfileSeen = true;
}
```

换登录账号后自动跟着变，无需改代码。要手工追加黑名单配 `EXCLUDED_SEC_UIDS=sec1,sec2`。

### 污染识别口径（不依赖昵称）

头像/背景图是以「**实际采集到的 sec_uid**」为目录存储的，
所以 `avatar_local` / `bg_local` 路径里的 sec_uid 就是本次真正采到的账号。

判定为串号污染需**同时**满足：

```
图片目录 sec_uid ≠ account_identifier  且  图片目录 sec_uid ≠ home_url 的 sec_uid
```

⚠ **第二个条件不能省**：若图片目录 == `home_url` 的 sec_uid，说明爬虫忠实地采了
`home_url` 指向的账号，那属于**链接错配**而非串号污染，采到的数据对该账号是真实的，
必须保留。早期版本漏了这条，会误清十几个账号的真实资料。

用这个口径扫全库的结果：串号污染 37 条、链接错配 15 条，两类必须分开处理。

## 七、三张日志/统计表的口径陷阱

| 表 | 陷阱 |
|---|---|
| `scrape_logs` | `status='success'` 只代表「抓到了东西」，**不代表抓的是对的账号**。身份错配的账号在这里同样是 success，只在 stdout 告警和任务末尾汇总里出现。表里没有 mismatch 字段。 |
| `scrape_jobs` | `progress_error` 是「最终失败数」（重试成功会 `pError--`），与 `scrape_logs` 里 error 行数不相等。 |
| `account_snapshots` | **`INSERT IGNORE` + `(staff_id, snapshot_date)` 唯一键 = 同一天第二次采集被完全丢弃**，无论新值是否更准。当天先被污染，当天重爬也修不回来，必须单独清理。 |

`profile` 不可信时会显式跳过快照写入，避免把别人的粉丝/作品数写进趋势曲线。

## 十、改动这条链路时的注意事项

1. **不要把「跑完没报错」当成正确性依据。** 这条链路的典型故障就是静默错误。
2. **写库脚本一律先 dry-run + 备份。** 本次两次 dry-run 分别挡下了「按 `account_identifier`
   无差别改 `home_url`」和「误清链接错配账号的真实资料」两个会造成数据损坏的操作。
3. **`home_url` 与 `account_identifier` 必须成对写入**，且来自同一次解析。
4. **profile 与视频是两个独立 API，归属可信度不同。** profile 可能串号，视频归属明确。
   处理污染时不要把视频一起丢掉。
5. **登录态账号永远不是采集目标。** 新增任何走 profile API 的模块，都要接上排除逻辑。
6. **区分「链接错配」与「串号污染」**，处理方式完全相反：前者数据真实需保留、只改链接；
   后者数据虚假需清空。
