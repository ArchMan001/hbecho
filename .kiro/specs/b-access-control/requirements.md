## 1. 引言

### 1.1 权威顺序

冲突时按此顺序裁决，不在代码、SQL 或本 spec 里暗中选择一方：

1. [`CONTEXT.md`](../../../CONTEXT.md)：`MediaStaff`、`AccountAssignment`、组织与监控语义；
2. [`prd-domain-b-access-control.md`](../../../HBECHO设计方案/prd-domain-b-access-control.md) v1.21：B 域产品语义的唯一真相源，包括角色、Capability 矩阵、DataScope、出口、审计；
3. [`database-design-v2.md`](../../../HBECHO设计方案/domains/data-foundation/database-design-v2.md)：组织主档（品牌、分公司、门店、专员）与导入批次的物理基线；
4. [ADR-0005](../../../HBECHO设计方案/architecture/adr/0005-application-stack-and-auth.md)、[ADR-0010](../../../HBECHO设计方案/architecture/adr/0010-scope-brand-intersection.md)：技术栈与范围求交；
5. 已合并 spec（tracer、`a-master-data-import`、`a-full-sync`）与同期草案 [`a-activity-plan`](../a-activity-plan/requirements.md)：它们已经按「受限服务身份 + Capability 字符串」预留了授权接缝，本 spec 把接缝接成真实身份，**不改它们的行为**；
6. 本 spec：不得静默改写以上事实。

### 1.4 PRD 真空与本 spec 的解释

B PRD 在产品层已「待定项清零」。下列是**实现层**必须选一条、PRD 没写死的地方。「已定」表示 PRD / ADR / 已合并 spec 有结论；「本 spec 建议」表示本 spec 的解释；**2026-11-06 刘学奎已确认全部「本 spec 建议」与「待确认」项按建议采纳**。

| # | 问题 | 结论 | 性质 |
|---:|---|---|---|
| 1 | 页面 | 登录、激活、忘记密码、修改密码、用户列表 / 新建 / 批量导入 / 编辑 / 停用恢复、审计日志都**属于本 spec**，但 UI 基线 `draft`、须经刘学奎确认。**本轮交付 Module + CLI + 认证 HTTP 端点，不写页面任务**；界面一节只写草案，N.6 留空 | 本 spec 建议（`ui-foundation.md` §3 已规定页面统一在 B 之后排期） |
| 2 | Next.js 在本 spec 里要做到什么程度 | 只建**无页面的最小入口**：better-auth 的 Route Handler、一个 `authenticate(request)` 辅助、健康检查；Route Handler 是 `Request → Response` 的函数，测试直接调用，不启动 Next 服务。管理类能力（用户管理、审计读取）本轮走 Module + CLI，不暴露 HTTP | 本 spec 建议 |
| 3 | 授权数据怎么放 | better-auth 的 `user` 就是登录主体 `User`（ADR-0005：两者不得各建一套）；授权数据放本项目自有的 1:1 扩展表 `access_users`、`access_user_brands`、`access_user_branches`。**不建 Grant / RoleProfile 表**——PRD 是单角色、固定矩阵、无个人覆盖（B-D01、§12），角色到 Capability 是代码常量 | 本 spec 建议（简化旧 design 的 Grant 模型） |
| 4 | 停用用户保留原号但不占号，与插件唯一列冲突 | 授权表 `access_users.phone` 永久保存原号，并用生成列 + 唯一键保证「待激活 + 有效」内唯一（同 `media_staff.active_phone`）；认证表的登录手机号列**只在待激活 / 有效时存放真实号码**，停用时改写为不会命中任何登录的墓碑值，恢复时校验后写回。这样「登录只匹配非停用记录」由数据结构保证，不靠每个查询加条件 | 本 spec 建议（**待任务 1 验证**，通过后写 ADR-0015） |
| 5 | 用户 ID 类型 | 要求 BIGINT 自增（R7）；认证库做不到则**停下报告** | 本 spec 建议 |
| 6 | 登录失败计数的键 | 规范化手机号（不论是否存在对应用户）。这样「不存在 / 待激活 / 密码错误」的响应与计数行为一致，不暴露账号是否存在 | 本 spec 建议 |
| 7 | 密码与 OTP 的限频、锁定放在哪里 | 全部自建（B-D14）：better-auth 的请求级限流只作洪水兜底；账号锁定、短信 60 秒 / 每日 10 条 / 全局上限、输错 5 次作废都在本项目代码里，经 better-auth 的钩子或包装接入。具体钩子点任务 1 验证；插件做不到的部分，自建发送 / 校验两个端点但**仍用 better-auth 的 `verification` 存储与会话机制**，不另造会话 | 本 spec 建议 |
| 8 | 规范主体字符串 | 用户为 `user:<用户ID>`；服务身份为 `service:<名称>`。所有 `*_by_actor` 列、审计 `actor`、`created_by_actor` 都用它；`*_by_user_id` 列在 B 接入后回填，**不造假 ID** | 本 spec 建议（与 `a-activity-plan` 已写的 `service:plan-worker` 一致） |
| 9 | 审计写入失败时的行为 | 高风险（用户管理、授权变更、停用恢复、导出、原始载荷、批量导入确认）与业务写入**同一事务**，失败则整体失败（fail closed）；低风险（登录成功、普通查询）尽力写入，失败记 pino 与指标不阻塞 | 本 spec 建议（旧 design 把它列为「可配置」；这里定一个默认） |
| 10 | 用户批量导入模板 | 固定 6 列 `姓名`、`角色`、`手机号`、`品牌`、`分公司`、`门店编码`；角色写中文名；品牌写品牌名称（日立 / 海信 / 约克VRF，多个用「、」或「,」分隔）；分公司写分公司编码（多个同上）；门店编码仅 `store_staff` 填。版本 `user-import.v1`，无别名兼容 | 本 spec 建议 |
| 11 | 现有模块的 actor 适配范围 | 本 spec 提供 `toPlanActor`、`toMasterDataActor`（范围表达能直接映射）与 tracer / sync 的**全范围**适配（超管、或范围为 `all` 的主体）；非全范围主体调用 tracer / sync 的「按专员范围」命令不在本 spec 解决（它们自己的 UI spec 需要时再细化，沿用 `requireFullScope` 的「宁可拒绝」） | 本 spec 建议 |
| 12 | 每个资源的 `ScopeStrategy` 由谁写 | **B 持有注册表与「未注册即拒绝」的机制**；策略本身由资源所属域在自己的 spec 里注册。B 只自带 B 域拥有的资源（`user`、`audit_log`）与两个平台级资源（`external_account`、`raw_payload`）的策略 | 本 spec 建议 |
| 13 | 所有 Capability 谁登记 | B 持有**唯一注册表**（29 个，与 PRD §7.3 逐行一致）。别的 spec 要新增 Capability，改注册表并走 B 的评审；业务代码里出现注册表以外的 Capability 字符串，静态测试失败 | 本 spec 建议 |
| 14 | 密码最短长度 | 8 位，不做组合、弱密码和定期改密（B-D32） | 已定 |
| 15 | 一个用户一个角色 | 是（B-D01）；多角色输入被拒绝 | 已定 |
| 16 | 大区级管理范围 | 无（B-D03）。组织范围只有「全部」「若干分公司」「本人」三种 | 已定 |
| 17 | 用户导入文件的 10 MB 上限 | 实现默认值，参照 F-D12（路径 1/2 的 10 MB）；B-D12 只规定 1,000 行 | 本 spec 建议 |
| 18 | 增长型表的保留 | `access_sms_sends` 35 天；`access_login_failures` 清理 `fail_count=0` 且 7 天未更新的行与 `fail_count<5` 且 90 天未更新的陈旧计数；`access_bootstrap_tokens` 已用 / 过期 30 天后清理（design §7.10） | 本 spec 建议（**待确认**，design §14 第 13 项） |
| 19 | A 尚未实现时的适配器 | `toPlanActor` / `fromPlanAudit` 面向结构类型并以 fixture 验证，不 import A 的模块 | 本 spec 建议 |

### 1.5 范围

#### 1.5.1 范围内

- **认证基座**：better-auth 集成（手机号 + 密码、手机号 + 短信验证码）、15 天滑动会话、会话撤销（退出、改密、停用、强制下线）、Route Handler；
- **开户与激活**：单个邀请、首个超管的一次性引导、短信验证码激活并自设密码、待激活期内改手机号；
- **批量导入用户**：模板、预检、确认、回流文件、边界校验；
- **登录与短信保护**：账号锁定、短信限频与全局上限、发送前校验、输错作废、重置密码解锁与踢出其他会话；
- **用户生命周期**：停用 / 恢复（重校验）、最后一个超管保护、`MediaStaff` 联动（懒执行 + 定时补偿 + 条件恢复）、删旧建新；
- **角色与 Capability**：单角色、29 项 Capability 注册表、角色矩阵、授权入口 `authorize`、决策原因码、服务身份、资源谓词注册；
- **DataScope**：品牌 ∩ 组织、本人绑定、`ScopeStrategy` 注册表与「未注册即拒绝」、无法映射 403；
- **管理范围与授权变更**：只能授予严格低于自己的角色、`GrantBoundary` 当前 / 提案双校验、用户列表可见性、读写同源、批量逐行判断；
- **数据出口框架**：10 个出口的守卫函数、交付前复查、异步任务有效范围、撤权取消用户任务；
- **审计**：持久表、事件覆盖、系统生成的 `reason_code`、保留一年与到期清理、仅超管可读、现有三类审计的适配写入；
- **对既有模块的适配**：`AuthContext` → 各 actor、`created_by_user_id` 回填入口；
- **CLI**：`pnpm access ...`；
- **离线验证**：假短信发送器、假时钟、真实 MySQL 测试库。

#### 1.5.2 范围外

- 页面（§1.4 第 1 项）与对外暴露的管理 HTTP 接口；
- 公开注册、SSO、MFA、设备管理中心、动态角色、个人权限覆盖、高风险二次认证、Redis 会话（PRD §12）；
- 真实短信发送、短信签名与模板申请（外部）；
- 各出口的**业务实现**（导出文件、媒资下载、通知、AI 取数）：B 只交付守卫、复查与有效范围的框架和契约测试，出口由所属域实现；
- 各业务资源的 `ScopeStrategy`（除 §1.4 第 12 项列出的四个）；
- 配置中心与短信额度配置的实现（I 域），本 spec 只读取；
- 手机号变更的「改绑」方案（PRD 禁止，只做删旧建新）；
- 物理删除用户、会话以外的任何认证数据。

### 1.6 术语

| 术语 | 含义 | 来源 |
|---|---|---|
| `User` | 登录主体；= better-auth 的 user 行 + 本项目的 `access_users` 扩展行 | B §3.1、ADR-0005 |
| `RoleCode` | `platform_admin` / `hq_manager` / `branch_manager` / `store_staff`；一个用户恰好一个 | B-D01、D-22 |
| `Capability` | `resource.action` 形式的动作许可，29 项，代码常量 | B §7 |
| `DataScope` | 品牌集合 ∩ 组织范围（+ 本人 + 人员级别）；语义对象，不是 SQL | B §8、ADR-0010 |
| `ScopeStrategy` | 某资源类型如何解释 DataScope；资源域注册，未注册即拒绝 | P-R14 |
| 资源谓词 | 对「这一个对象」的条件（计划创建者、所属分公司、对象状态、监控层级） | B-D17 |
| `GrantBoundary` | 某个管理者能授予的角色等级、品牌集合、分公司集合上限 | 旧 design §9.1，缩减 |
| `AuthContext` | 一次请求里已认证主体的最小上下文：规范主体、角色、Capability 集、DataScope | 本 spec |
| 规范主体字符串 | `user:<id>` / `service:<name>`，用于所有 `*_by_actor` | §1.4 第 8 项 |
| 墓碑值 | 停用用户在认证表登录手机号列里的占位值 | §1.4 第 4 项 |
| 服务身份 | Worker / 计划任务使用的固定非用户主体，没有 Grant，权限由常量白名单限定 | B §10.3 |
| 出口 | 能把数据带出系统的 10 个位置 | B §10.1 |

## 2. 需求

### AX-1 · 认证基座与会话

**陈述**：系统 SHALL 用 better-auth 提供「手机号 + 密码」与「手机号 + 短信验证码」两种登录，会话由 better-auth 管理；授权自建（ADR-0005）。

- 会话有效期 SHALL 为 15 天，滑动续期**每个自然日至多刷新一次**（B-D13）；SHALL NOT 设绝对有效期，SHALL NOT 限制并发会话数；
- SHALL NOT 启用会话 cookie 缓存：每次请求都读会话与用户状态，使「停用后现有会话全部失效」即时生效；
- 会话 cookie SHALL 为 `HttpOnly`、`Secure`（生产）、`SameSite=Lax`；状态变更请求 SHALL 受 better-auth 的 Origin 校验保护，`trustedOrigins` 来自配置，不写死；
- 每次认证请求 SHALL 重新检查用户状态与授权（`authenticate(request)`）；`disabled` 用户无法续期；
- SHALL 提供退出登录与管理员强制下线（后者属 `user.manage` 的动作，AX-8）；
- 密码 SHALL 由用户自己设置，管理员在任何路径都不能查看或代设；仅保留最短 8 位的下限；
- better-auth 的 `adminAc` 默认包含 `set-password` 与 `impersonate`：SHALL NOT 使用它的 admin 插件角色体系；`defaultRole`、`adminRoles` 不使用（ADR-0005 已知坑 1、2）；
- SHALL 配置 better-auth 的全局请求级限流作为洪水兜底（B-D14），但账号维度的失败计数与锁定不依赖它（AX-4）；
- 修改密码或重置密码成功后 SHALL 撤销该用户的**其他**会话（已知坑 3：管理员改密不自动踢人，所以必须显式撤销）。

**验收标准**

- 用 fixture 手机号 + 密码登录得到会话；会话到期日 = 登录时间 + 15 天；同一自然日内第二次认证请求不写库，跨天后的首次请求把到期日刷新到当时 + 15 天（`FakeClock`）；
- 用户停用后，下一次 `authenticate` 返回未认证，无论会话 cookie 是否仍存在；
- 修改密码 / 重置密码后，其他会话被撤销，当前会话保留（改密）或全部失效（重置）；
- 全仓库搜索 `adminAc`、`set-password`、`impersonate`、`defaultRole`、`adminRoles` 无使用；
- 配置里没有 cookie cache；Origin 不在 `trustedOrigins` 的状态变更请求被拒绝；
- 没有任何管理员路径返回或设置用户密码。

### AX-2 · 开户与激活

**陈述**：系统 SHALL 采用邀请制：管理者创建用户，用户自己通过短信验证码激活并设置密码。

- **创建**：字段为姓名、角色、手机号、品牌集合、分公司集合；`store_staff` 另填门店编码，由「手机号 + 门店编码」定位**唯一有效 `MediaStaff`** 并绑定（B-D07）；不存在、不在该门店或已停用 → 创建失败，不建用户；
- 创建者 SHALL 通过 AX-8 的边界校验；新用户状态为「待激活」，**不发短信**（用户自己到激活入口请求验证码）；
- **系统里不存在默认管理员账号和默认密码**；
- **首个超管**：由运维执行一次性 CLI 创建，需要一次性令牌，成功后令牌失效并记审计（B-D31）；已有未停用的超管时该操作 SHALL 被拒绝；
- **激活**：待激活用户输入手机号 → 收到验证码 → 验证通过后设置密码 → 状态转「有效」。激活与找回密码共用 better-auth 的同一条「验证码重置密码」路径（已知坑 4：该路径在没有密码凭据时自动创建，所以激活不需要额外端点）；
- **待激活**不设有效期，不自动过期；管理员可在用户管理里看到「待激活天数」并批量停用（B-D04）；
- **待激活期内**管理员 MAY 直接修改手机号（尚无登录与会话）；激活后改号只能删旧建新（B-D06、D-43）；
- 待激活用户走密码登录时，响应 SHALL 与「手机号或密码错误」一致，不暴露账号是否存在。

**验收标准**

- 数据库与代码里没有默认管理员；首个超管 CLI：无令牌、令牌错误、令牌已用、已有超管四种情况各被拒绝且零写入；成功一次后同一令牌再用被拒绝；
- 创建 `store_staff`：同门店两名专员、各用自己的手机号，分别定位成功；手机号不存在 / 不在该门店 / 专员已停用 → 失败，不建用户；
- 新建用户为待激活，且没有发出任何短信；
- 待激活用户用验证码设置密码后变有效，可以密码登录；未激活用户密码登录响应与密码错误完全一致（状态码、文案、耗时量级不作区分的断言只到状态码与文案）；
- 待激活用户可改手机号；有效用户改号被拒绝并提示删旧建新；
- 待激活不会自动过期（`FakeClock` 推进 1 年后仍可激活）。

### AX-3 · 批量导入用户

**陈述**：系统 SHALL 支持用 CSV 批量创建用户，沿用两阶段（预检 → 确认）与 `a-master-data-import` 的批次、行结果、租约、回流写法（`import_kind='user_import'`）。

- 模板 `user-import.v1`：6 列固定（§1.4 第 10 项）；编码 BOM → 严格 UTF-8 → 严格 GB18030；大小 ≤ 10 MB（实现默认值，参照 F-D12，**不是** B-D12）；**数据行 ≤ 1,000**（B-D12），超过整批拒绝并提示拆分；文件级失败不建批次；
- **全部同步执行**：预检同步，确认同步写入；预检结果不过期，**确认时重新校验全部行**（B-D12）；
- 预检逐行：角色合法；**授予的角色严格低于操作者**；品牌集合 ⊆ 操作者品牌；分公司集合 ⊆ 操作者分公司；`store_staff` 的门店在操作者范围内且能定位到唯一有效专员；手机号规范化后合法；
- 手机号已被「待激活 + 有效」用户占用 → 该行错误（`phone_exists`），**不静默改角色或范围**；同文件内手机号重复 → 整组报错；
- 越权行进「跳过」清单，**不让整批失败**（B §9.2）；
- **只做新增**；不提供「一键改成新增」；
- 失败行回流为同格式文件，每行带原因码与一句指引；回流文件由**提交人本人**下载，视为导入闭环，不额外要求 `data.export`，只含本次提交的行，手机号明文（B-D12）；
- 确认写入时每个新用户 SHALL 走与单个邀请相同的创建逻辑，并逐条记审计；
- 默认测试不发起任何短信。

**验收标准**

- 1,001 行、10 MB + 1、表头不符、编码无法识别：整批拒绝，无批次；
- 总部导入含 `hq_manager`、`platform_admin` 的行：这些行进跳过清单，其余行正常；
- 分公司人员导入含他分公司门店、超出自己品牌的行：这些行被拒；
- 手机号已存在（待激活 / 有效）→ `phone_exists`；停用用户的号码不占号，可新建；
- 预检后有人先建了同号用户：确认时该行 `conflict`，不重复创建；
- 回流文件列与原文件一致并追加「结果 / 原因 / 指引」，由提交人下载；他人下载被拒；
- 重复提交同一文件：第二次全部为手机号已存在，不产生额外用户。

### AX-4 · 登录与短信保护

**陈述**：登录失败锁定与短信限频 SHALL 由本项目自建（B-D14，ADR-0005 已知坑 5）。

**登录锁定**

- 只保留**账号维度**：同一规范化手机号连续 5 次密码失败 → 锁定 15 分钟，期满自动解锁并清零计数；锁定期间正确密码也不放行；**没有 IP 维度**；
- 锁定只限制**密码登录**；短信验证码登录不受锁定影响，仍受每日 10 条上限约束（B-D15）；
- 不提供手动解锁或超管豁免；短信重置密码成功是**唯一**的提前解锁路径（B-D16）；
- 连续失败不修改业务用户状态；
- 不论手机号是否对应用户，计数与响应一致（§1.4 第 6 项）。

**短信**

- 验证码有效期 5 分钟；同一手机号 60 秒后可重发；同一手机号每天最多 10 条；连续输错 5 次作废，需重新获取；**重发使旧验证码立即失效**；
- 60 秒与每日计数只数实际处理过的请求（`sent`、`suppressed`、`failed`），**不数被限频拒绝的请求**，否则连续重试会不断续期；
- **发送前校验**（B-D37）：手机号必须是「待激活或有效」用户；不是则返回与成功一致的提示，**实际不发送**；
- **全局每日上限**（B-D38）：由 I 域配置，超限告警并暂停发送，不加图形验证码；达到上限时**密码登录不受影响**，短信登录、激活与找回密码暂停；
- 发送由 `SmsSender` 端口完成；生产实现为阿里云短信，测试为假发送器；**生产环境未显式配置发送器模式时启动失败**，不缺省为假发送器；
- 短信正文 SHALL NOT 包含密码或会话信息；日志与审计 SHALL NOT 记录验证码明文；
- `access_login_failures`、`access_sms_sends`、`access_bootstrap_tokens` SHALL 有保留期并由 `access maintain` 清理（§1.4 第 18 项），使随机手机号请求不能让表无限增长。

**验收标准**

- 5 次失败后第 6 次（含正确密码）被拒；`FakeClock` 推进 15 分钟后可登录；失败计数清零；
- 锁定期间短信登录成功；重置密码成功后立即可用密码登录（解锁）；
- 不存在的手机号与已存在手机号：5 次失败后响应与计数行为一致；
- 60 秒内重发被拒；第 11 条被拒；每 30 秒连续重试，被拒的重试不延长窗口，首次请求后 60 秒即可成功发送；重发后旧验证码失效；验证码 5 分钟过期；输错 5 次作废（第 6 次用正确码也失败）；
- 对不存在 / 停用手机号请求发送：响应与成功一致，假发送器记录为空；
- 全局上限达到：短信类请求被拒并出现一条告警事件，密码登录仍成功；
- 生产模式缺发送器配置时进程启动失败；
- 全仓库没有 IP 维度的失败封禁；密码最短 8 位，7 位被拒。

### AX-5 · 用户生命周期

**陈述**：用户状态 SHALL 为「待激活」「有效」「停用」；**不物理删除**。

- **停用**：现有会话全部失效；不能新建会话；认证表登录手机号改写为墓碑值（§1.4 第 4 项）；取消该用户触发的未完成异步任务（AX-9）；记审计；
- **手机号唯一**只约束「待激活 + 有效」；停用记录保留原号但不占号，同号可以新建用户（B-D05）；
- **恢复**：重新检查角色、品牌、分公司与关联业务身份——**无法映射的项直接去掉**（自动收窄；「不存在」在数据层由外键排除，运行时的「无法映射」经 `OrgDirectory` 端口判定），用户恢复为有效（若停用前未激活则恢复为待激活）；**品牌或组织停用不算失效**，不去掉（B-D25）；移除项在审计里记一条，不做恢复结果页；恢复前复核手机号唯一，同号已有「待激活 + 有效」用户则恢复被拒；
- **`MediaStaff` 联动**：
  - 绑定的 `MediaStaff` 停用 → 自动停用 `store_staff` 用户：**懒执行**（下次登录 / 授权时发现）并撤销会话，另有**定时补偿**任务；审计以系统身份记 `media_staff_disabled`（B-D10）；
  - `MediaStaff` 恢复 → **有条件**自动恢复：只恢复因该专员停用而自动停用的用户，人工停用的不恢复；恢复前复核手机号唯一，同号已有其他有效用户则保持停用并生成可处理问题（B-D11）；
  - 恢复时专员绑定失效（人工停用后恢复、或专员已不存在）：用户仍为有效，但本人范围拒绝，提示联系管理员（B-D08）；
- **换门店或换品牌**：删旧建新——停用旧用户，用同一手机号新建用户并绑定新专员，重新走短信激活；旧账号的学习进度与个人历史留在旧用户；不建立新旧用户的关联（B-D09、2026-10-30）；
- **最后一个可用超管**不能被停用；超管**不能停用自己**（B-D02）；这两个检查在事务内对超管行加锁；
- 采集与登录**完全解耦**（D-46）：用户的状态变化不改变任何采集；本 spec 不写监控开关。

**验收标准**

- 停用后会话失效、登录手机号为墓碑值、原号保留在授权表；同号新建用户成功；
- 恢复：构造一个品牌被删除（不存在）和一个品牌被停用（存在）的授权，恢复后前者被去掉并记审计，后者保留；
- 恢复时同号已有有效用户 → 被拒；
- 专员停用后，用户下一次 `authenticate` 被自动停用并撤销会话；定时补偿对从未登录的用户也生效；
- 专员恢复后：自动停用的恢复，人工停用的不恢复；同号冲突时保持停用并出现一条质量问题；
- 专员已不存在时恢复用户：用户有效，本人范围请求被拒绝；
- 最后一个超管、超管自停用各被拒绝；两个管理员并发停用对方（顺序交错）只有一个成功；
- 换店后新用户必须重新激活，旧用户数据不迁移；
- 全仓库没有 `DELETE` 用户或会话以外认证数据的路径。

### AX-6 · 角色、Capability 与授权入口

**陈述**：系统 SHALL 有且只有一个 Capability 注册表和一个授权入口；业务代码只检查 Capability，不写角色条件（P-R12）。

- 注册表 SHALL 含 PRD §7.3 的 **29 项** Capability 及其对四类角色的授予，与 PRD 逐行一致（design §7.1）；
- 一个用户恰好一个 `RoleCode`；多角色输入被拒绝（B-D01）；
- 授权入口 `authorize(ctx, request)` SHALL 依次检查：已认证 → 用户有效 → Capability 已注册 → 角色持有 → 资源 `ScopeStrategy` 已注册并解释 → 资源谓词；任一失败返回稳定的原因码；
- **未知 Capability、未注册资源、无法解释的范围一律拒绝**，不回退到「品牌过滤」或「全量」；
- 超管 SHALL 通过显式 Capability 与全范围表达，**没有隐藏旁路**；
- 拒绝 SHALL 不通过「返回空列表」伪装；合法的空范围（例如品牌集合为空）返回空结果；
- 对象级越权在对外表现为「未找到」，Capability 缺失表现为 403，未认证表现为 401；
- **资源谓词**（B-D17）有注册机制，B 登记清单：计划创建者、计划所属分公司、对象当前状态、监控开关层级（经销商级仅超管）；谓词由资源所属域实现，不得复制成新的 Capability，也不得由业务代码判断 `RoleCode`；
- **服务身份**（B §10.3）：只有「计划任务」与「继承提交者」两类；计划任务身份的 Capability 白名单是常量，**不含**读原始载荷、导出、改授权、改配置；Worker SHALL NOT 使用或伪造超级管理员；
- 静态护栏：业务模块（`access-control` 以外）出现 `platform_admin` / `hq_manager` / `branch_manager` / `store_staff` 字面量比较、或出现注册表以外的 Capability 字符串，测试失败。

**验收标准**

- 注册表测试：29 项逐行对照一份由 PRD §7.3 转写的 fixture，增删改任一项即失败；
- 四类角色 × 29 项的授予矩阵与 PRD 一致；
- 未知 Capability、未注册资源、停用用户、会话缺失，各返回对应原因码；
- 计划任务身份调用导出、原始载荷、授权接口被拒；
- 超管调用任何动作也先过 `authorize`（不存在 `if (admin) return true` 的旁路——静态扫描）；
- 静态护栏对一个故意违规的临时文件能报错（提交前撤掉）。

### AX-7 · DataScope 与资源策略

**陈述**：DataScope SHALL 为「组织范围 ∩ 显式品牌集合」，另含「是否仅本人」与人员级别（ADR-0010、B-D24、B-D23）。

- **品牌集合必须显式授予**，不从组织推导；组织在范围内但品牌未授予的对象不可见；大区、分公司、板块、经销商是全品牌对象，门店与账号才带品牌；
- 各角色的范围：`platform_admin` 全部品牌 × 全部组织；`hq_manager` 授权品牌 × 全部组织；`branch_manager` 授权品牌 × 授权分公司；`store_staff` 仅本人（品牌来自专员所在门店）。**不设大区级范围**（B-D03）；
- **人员级别**：`store_staff`=1、`branch_manager`=2、`hq_manager` / `platform_admin`=3，由角色映射，不新增用户字段（B-D23）；
- **「本人」绑定**：`store_staff` 与一个 `MediaStaff` 一对一；没有绑定、绑定到已停用专员、或同时绑定多条 → **拒绝本人范围**，不回退成「本门店」「本品牌」；
- `ScopeStrategy` 注册表：每个资源类型 SHALL 显式注册；**没有注册就拒绝**（P-R14）；注册表按 PRD §8.2 的资源清单维护键名；
- **可解析但为空**（合法空品牌集合）返回空结果；**无法映射**（组织 / 品牌 ID 不存在、主数据不可用）返回 403 并记可处理问题，不返回空列表、不回退（B-D26）；
- 品牌或组织**停用**不影响已授予的读范围（B-D25）；
- 外部监控账号只对 `platform_admin` 可见，总部与分公司即使持有 `data.account.read` 也看不到（B-D22）；
- 当前 Grant 决定「现在能看什么」；历史事实保存采集当时的归属快照，不因改绑或组织调整而改写；授权收缩立即缩小查询结果，但不删除历史事实；
- DataScope 在每次请求内由数据库当前状态构建，**不跨请求缓存**（B-D33：角色或范围变更不撤销现有会话，下一次请求即按新权限判断）。

**验收标准**

- 北京分公司下有海信门店 A 与日立门店 B，分公司经理品牌授权=海信：只看到 A（跨品牌分公司不泄露）；
- 品牌集合为空：合法空结果，不是全量；
- 组织 / 品牌 ID 无法映射：403 + 一条质量问题，不是空列表；
- 品牌被停用后，已授予用户仍能读到该品牌范围；恢复收窄不去掉停用对象；
- `store_staff`：绑定缺失 / 已停用 / 多条三种情况都拒绝本人范围；
- 未注册策略的资源请求被拒；删除一个已注册策略后同一请求失败；
- 外部监控账号：`hq_manager`、`branch_manager` 持有 `data.account.read` 也不可见；
- 角色变更后同一会话的下一次请求使用新范围（无需重新登录）。

### AX-8 · 管理范围与授权变更

**陈述**：管理范围 = 角色 ∩ 组织范围 ∩ 品牌；SHALL 不能授出超过自己（B §9）。

- **只能授予严格低于自己的角色**；只有超管可授予超管；超管可管理其他超管，但不能停用自己（B-D02）。可管理关系：超管 → 全部；总部 → 分公司人员、门店专员；分公司人员 → 门店专员；
- **`GrantBoundary` 双校验**：每次授权变更先做 **current 校验**（操作者当前是否有权管理目标及其现有授权），再做 **proposed 校验**（修改后的角色、品牌集合、分公司集合是否完全位于操作者边界内）；任一不过，整个变更拒绝，不部分写入；
- **用户列表只显示严格下级与自己**；同级互不可见、不可操作（B-D02）；
- **读写同源**：列表、详情、修改、停用、恢复、强制下线、批量操作使用**同一条范围判断**，杜绝「看不到但能改」；
- 批量操作逐条判断，被拒的进跳过清单，不让整批失败；
- 角色、品牌、分公司的变更 SHALL 记审计（改前、改后、`reason_code`、操作者），**不撤销现有会话**（B-D33）；
- 变更授权的事务 SHALL 同时包含用户行、品牌 / 分公司集合与审计，要么全成功要么保持旧状态；
- `store_staff` 的门店 / 品牌不能原地修改，只能删旧建新（AX-5）；改其他字段（姓名）可原地改；
- 强制下线：持有 `user.manage` 且在边界内的人可撤销目标用户的全部会话，记审计。

**验收标准**

- 总部不能创建总部或超管；分公司不能创建分公司；只有超管能创建超管；
- 同级用户在列表中不可见，直接按 ID 访问同级用户 = 未找到；分公司经理不能停用同分公司另一位经理；
- proposed 超界（给下级授予自己没有的品牌）→ 整个变更拒绝，库中无变化；
- 用户列表可见的用户集合，与「能修改」的用户集合完全相同（集合相等断言）；
- 批量变更 3 行含 1 行越权：2 行成功、1 行进跳过清单；
- 角色降级后，目标用户同一会话的下一次请求按新能力判断；
- 强制下线后目标用户的会话全部失效。

### AX-9 · 数据出口框架

**陈述**：B SHALL 为 10 个数据出口（B §10.1）提供同一套守卫与复查，并交付可被各出口复用的契约测试。各出口的**业务实现**由所属域完成。

- 每个出口 SHALL 执行「动作权限 + 数据范围」；出口 4（导出文件）、5（媒资下载）、9（通知）、10（学习资料下载）、AI 结果与签名链接另需**交付前复查**：当前范围是否仍覆盖产物；不覆盖则拒绝、删除或按新范围重建；
- **异步任务的有效范围** = 提交时范围快照 ∩ 执行时主体当前范围；后续扩权不能扩大旧任务，撤权收窄或取消；
- 用户触发任务继承提交者身份，计划任务使用固定服务身份（AX-6）；
- **停用或撤权时立即取消该用户触发的未完成异步任务**，计划任务不受影响（B-D28）。取消经 `JobCanceller` 端口：各域注册自己的任务类型，默认无注册；
- **导入失败行回流文件**不算 `data.export`：由本次提交人本人下载，只含本次提交的行；
- `data.export`（原始对象为主结构）与 `report.export`（报表产物为主结构，绑定投影）按导出物主结构划分；点检表下钻明细仍算 `report.export`；两者都走出口 4 的三次校验；
- 学习资料下载、导出、原始载荷访问、手工同步等出口 SHALL 记审计；**手机号不逐条记审计**，只在批量导出时记（B-D29）。

**验收标准**

- 契约测试（fake 出口）：提交时 / 执行时 / 交付前三个检查点，撤权发生在任一点都拒绝交付；
- 提交后扩权，旧任务有效范围不变；提交后撤权，有效范围收窄，范围为空则取消；
- 停用用户时，fake 任务注册表里该用户的未完成任务被取消，计划任务不受影响；
- 计划任务身份调用导出 / 原始载荷被拒；
- 签名链接短期有效，撤权后不能续签；
- 10 个出口各有一条「动作权限 + 范围」的守卫用例（fake 实现）。

### AX-10 · 审计

**陈述**：系统 SHALL 提供持久、追加写的审计表，覆盖 B §11.1 的事件，保留一年，1.0 仅 `platform_admin` 可读（D-41、D-44）。

- 事件至少包括：邀请、激活、登录成功 / 失败、会话撤销与强制下线；用户创建、导入、停用、恢复、角色 / 范围 / 品牌变更；主数据与活动名单导入的确认写入、预检 / 回流文件下载；敏感字段与原始载荷访问、手工同步；规则发布与重算、指标与模板变更；活动计划与监控判定计划的创建 / 删除 / 恢复 / 期满清除；导出提交 / 执行 / 取消 / 交付；高成本操作的授权与拒绝；
- 每条至少含：谁（规范主体）、对谁、什么动作、什么结果、什么时候、范围摘要、**系统生成的稳定 `reason_code`**（B-D30，不要求手填说明）；
- **不记录**密码、令牌、Cookie、验证码；手机号按明文记录（D-42、B-D29 例外为不逐条记查看）；
- 追加写：不提供修改或单条删除；重复事件按幂等键去重；
- **到期清理**：按时间窗口批量删除超过 365 天的记录，删除动作以系统身份记一条审计；不提供单条或界面删除（B §11.3）；
- 读取需要 `audit.read`，1.0 仅超管；
- 高风险事件与业务写入同一事务（§1.4 第 9 项）；低风险尽力写入；
- **适配器**：为现有三类审计回调（tracer `tracer.command`、sync `sync.command`、master-data 的 `event_type`）以及 `a-activity-plan` 的审计事件提供写入 `audit_events` 的适配，调用方代码不变；适配后的事件含规范主体与映射后的 `reason_code`。

**验收标准**

- 登录、授权变更、敏感读取、导出、高成本操作都有一条记录；
- 审计与日志里没有密码、令牌、Cookie、验证码（对全部事件夹具做字符串扫描）；
- 同一幂等键重复写入只落一条；表上没有 UPDATE / 单条 DELETE 路径（静态扫描 + 数据库权限说明）；
- 清理：构造 366 天前 / 364 天前的记录，只删前者，并产生一条系统审计；
- 非超管读取审计被拒；
- 用户管理操作的审计写入失败 → 业务写入一并回滚；登录成功的审计写入失败 → 登录成功，pino 有记录；
- 三类现有审计事件经适配器落库后可按 actor / 对象 / 批次查询。

### AX-11 · 对既有模块的接入

**陈述**：B SHALL 提供 `AuthContext` 到各模块 actor 的适配器，使这些模块在 B 落地后无需改动业务逻辑。

- **规范主体字符串**：`user:<id>` / `service:<name>`；各模块 `*_by_actor`、`created_by_actor` 使用它；
- `toPlanActor(ctx)`：品牌编码集合、分公司 ID 集合、`platformAdmin`、`capabilities`；
- `toMasterDataActor(ctx)`：品牌编码集合（`all` 仅平台级）；
- `toTracerActor(ctx)`：仅在范围为全平台、全专员时产生（超管，或范围为 `all` 的主体）；其余范围的主体调用 tracer / sync 的按范围命令 → 保持 `requireFullScope` 的拒绝（§1.4 第 11 项）；
- **回填入口**：提供 `backfillUserId(table, actor)` 的约定与测试，使 `uploaded_by_user_id`、`confirmed_by_user_id`、`created_by_user_id` 等列在 B 接入后用真实用户 ID 写入；**不为历史行造假用户**；
- 现有环境变量声明的受限服务身份（`HBECHO_MD_*`、`HBECHO_AP_*`、`HBECHO_ACTOR_*`）SHALL 继续可用于运维 CLI；它们被映射为 `service:<名称>`，范围不超过其声明；
- 所有已有代码里使用的 Capability 字符串 SHALL 属于注册表（静态测试）。

**验收标准**

- `toPlanActor` 对四类角色的输出与 `a-activity-plan` 的 `assert` 期望一致（契约 fixture）；
- `toTracerActor` 对分公司人员返回「不可适配」，不降级成全范围；
- 注册表覆盖仓库中全部已用 Capability 字符串（`data.sync.trigger`、`data.account.manage`、`data.monitoring.manage`、`monitor.external.manage`、`data.master_data.import` / `structure`、`activity_plan.*`）；
- 用户 ID 回填：用户触发的导入批次 `uploaded_by_user_id` 为真实 ID，CLI 触发的为 NULL。

### AX-12 · Web 入口骨架与 CLI

**陈述**：系统 SHALL 提供无页面的最小 Web 入口与运维 CLI。

- Next.js 16 App Router 骨架：`src/app/api/auth/[...all]/route.ts`（better-auth 处理器）、`src/app/api/health/route.ts`；`src/app` 只做入口与参数校验，不直接写 SQL（ADR-0013）；
- `authenticate(request): Promise<AuthContext | Unauthenticated>`：模块函数，Route Handler 与将来的页面共用；
- CLI `pnpm access ...`：`token create`、`bootstrap-superadmin`、`user invite|list|show|change|disable|restore|force-logout`、`user import precheck|confirm|batches|batch|rows|report`、`maintain`（定时补偿 + 审计清理）、`audit list`；输出 JSON、BIGINT 十进制字符串、退出码沿用 master-data 约定；影响多个对象的命令默认只预览，`--apply` 才写入；**没有 `--force` / `--skip-auth`**；
- CLI 身份来自环境变量，缺任一启动失败，不缺省为全部；
- 本轮**没有**对外的管理 HTTP 接口；
- `.env` 与密钥不出现在仓库、日志与回复里（`server-access.md`）。

**验收标准**

- 直接调用 `GET`/`POST` 处理器（构造 `Request`）完成登录、读会话、退出；
- `health` 返回 200 且不依赖数据库写；
- CLI 缺环境变量启动失败；写命令不带 `--apply` 时库中无变化；
- 全仓库搜索 `src/app` 下无 SQL / 直接 `db.insert`；
- `pnpm typecheck` 通过（含 Next 类型）。

### AX-13 · 默认验证离线、可重复；真实短信需批准

**陈述**：默认测试 SHALL NOT 发起任何网络请求；SHALL 使用真实 better-auth 库对真实 MySQL 测试库、假短信发送器、`FakeClock`。

- 纯函数（手机号规范化、角色矩阵、边界计算、锁定窗口、模板解析、注册表对照）为 `unit`；
- 认证流程、会话、锁定、短信规则、用户生命周期、`MediaStaff` 联动、用户导入、审计、作用域为 `*.db.test.ts`；
- 数据库测试里对争抢同一行锁的操作顺序 `await`，并发用例用显式闸门；
- **真实短信发送不属于自动验收**：需要人工批准、显式开关、固定条数与审计摘要；批准前生产不得启用真实发送器；
- 任务 1 的库兼容性验证本身也是离线测试，结论写入 design §6.5 与 ADR-0015。

**验收标准**

- 测试进程启动时网络 socket 被禁止；
- 同一 fixture 连续运行 3 次结果一致；
- 迁移在空库上成功并幂等，`drizzle-kit generate` 不产生新迁移；better-auth 的表结构与手写迁移一致；
- 测试库名以 `_test` 结尾；
- `./scripts/verify.sh` 通过；Python 侧未验证时明确写出，不声称通过。

## 4. 需求级完成边界

- 完成全部 AX 需求**不自动代表**真实用户可以使用：页面本轮不交付（§1.4 第 1 项）；短信签名与模板尚未申请；生产短信发送器未启用；各业务资源的 `ScopeStrategy` 要由各自的 spec 注册，**注册前这些资源对非超管请求一律拒绝**（这是设计，不是缺陷）；
- 本 spec 的「完成」指：真实 better-auth 对测试库完成登录 / 激活 / 重置 / 锁定 / 撤销全流程；29 项 Capability 与四类角色矩阵与 PRD 逐行一致；DataScope 与资源策略注册表「未注册即拒绝」可验证；用户管理、导入、生命周期、`MediaStaff` 联动、审计、出口守卫都有离线测试；到现有模块的适配器有契约测试；
- 本 spec 不关闭 §1.4 中标「本 spec 建议」的各项；它们的结论由刘学奎在评审时给出，给出前相应条目保持 `draft`；
- 未获评审批准前不开始写实现代码（见 [`tasks.md`](tasks.md)）。
