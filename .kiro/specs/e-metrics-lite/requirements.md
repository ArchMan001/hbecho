## 1. 引言

### 1.1 为什么有这个 spec

完整的 `e-metrics`（指标字典、活动级投影、点检表、看板、下载中心，15 张表，任务 0–13 与 P1–P6）还没有开工，而业务现在就要看到数据：旧系统每次采集后导出「全量明细」Excel（视频明细 + 账号汇总），业务靠它核对。刘学奎 2026-11-19 的决定是：**1.0 不需要看板系统，只需要把全量数据展示出来**。

本 spec 交付两件事，范围刻意很小：

1. **线上浏览**：选一个判定计划的一次已完成执行，浏览两张表——**视频明细**（该执行圈定时间范围内的全部视频 / 图文，含头像、封面、主页背景图）与**账号维度**（每个参与账号一行，含判定计划里每个能力的结果）；
2. **Excel 导出**：同样两张表，两个 sheet，**不含图片**。

「每个能力一列」是核心：判定计划里设了什么条件，就多什么列，列头是能力别名或默认名。

### 1.2 与 `e-metrics` 的关系

| 项 | `e-metrics`（完整版） | `e-metrics-lite`（本 spec） |
|---|---|---|
| 状态 | spec 已写，未开工 | 新 spec |
| 对象 | 活动级冻结投影、指标字典、点检表、看板 | **一次判定执行**的原始结果，不聚合、不投影 |
| 内容明细 | 只有「命中内容」（通过全部层），不含未命中（E-D02、E-D09） | **全量**（含未命中、未获取成功、未被选中） |
| 导出 | 5 类、异步、下载中心、嵌封面图 | 2 个 sheet、无图（U1 待确认是否同步） |
| 新表 | 15 张 | 0 张 |

两者**并存**。`e-metrics` 之后开工时，本 spec 的读口与授权策略注册可被它复用（`report` 策略「先查再注册」，见 design §8）；`e-metrics` 的点检表与专员明细仍遵守 E-D16 / E-D17（不按能力分列），本 spec 的「按能力分列」只出现在本 spec 的两张表里。

### 1.3 权威顺序

1. [`CONTEXT.md`](../../../CONTEXT.md)：不变量 14（ValueState 四态）、19（技术失败不得转成业务空值）；

## 2. 范围边界

### 2.1 做什么

| # | 能力 | 说明 |

| 1 | 导航「活动计划判定结果」+ 页面 `/reports/<判定计划>` | 导航落地页选判定计划；页面两个标签：视频明细、账号维度；可切换该计划的历史执行；筛选；分页 |

## 3. 术语

沿用 [`CONTEXT.md`](../../../CONTEXT.md)。本 spec 新增：

| 术语 | 含义 |
|---|---|
| 执行（execution） | D 的一次 `completed` 的 `run_kind='execution'` 运行。不含圈定与试跑 |
| 条件（condition） | 判定计划配置里的一个可展示单元，一个条件对应表里的一列：第 1 层的一条文本关键词、一条话题、时长；第 2 层的一个能力（对象为封面 / 头像 / 主页背景）；第 3 层的语音判定；评论要求。D 给每个条件一个稳定 `key`（design §4.2） |
| 能力列 | 一个条件在表里的一列。内容层条件出现在视频明细与账号维度；账号层条件（头像、主页背景）只出现在账号维度 |
| 账号结果四态 | 通过 / 不通过 / 获取失败 / 前置条件未满足，不进行计算。对应 D 的 `success` / `not_met` / `unobtained` 与本 spec 要求 D 新增的 `skipped` |

## 4. 需求

### EL-1 · 对象、入口与前置条件

**陈述**：页面与导出 SHALL 以「一个判定计划的一次已完成执行」为对象。默认取该判定计划最近一次 `completed` 的执行；页面 MAY 列出该计划的历史执行供切换。

- 判定计划没有任何 `completed` 的执行时，页面 SHALL 显示空态（「还没有完成的执行」，附指向判定计划的链接），**导出入口置灰，读口抛 `no_completed_execution`**。系统 SHALL NOT 在没有执行时用 A 的数据拼出一份只有基础列的表。
- 活动计划在回收站里时，D 读口对该计划的执行不可见（D 已有规则），页面显示「计划已删除」，不泄露存在性。
- 入口（刘学奎 2026-11-19）：左侧导航新增**「活动计划判定结果」，四个角色都有**（含门店专员；权限 `report.read`），点进去先选判定计划，再进入本页；D 现有的 `/judgement/results/[runId]` 占位页 SHALL 改为跳转到本页（design §10.1）。**命名（刘学奎 2026-11-19）：导航与页面标题都是「活动计划判定结果」，导出文件名保留「全量明细」**；不在 D 的判定计划详情与执行记录页加「全量明细」按钮，只改占位页跳转（最小改动，避免重复入口）。

**验收标准**
- 无已完成执行 → 空态与 `no_completed_execution`，不发出任何导出；
- 有多次执行 → 默认最近一次（按 `completed_at`，并列取执行 ID 大者），切换历史执行后表头与数据都对应那一次；
- 被保留期清理内容级行的执行（EL-10）选中时，视频明细标签显示说明，账号维度仍可用。

### EL-2 · 视频明细：行范围

**陈述**：视频明细 SHALL 对所选执行的 `run_contents` 一行一条列出**全部**行，即判定计划圈定时间范围内、内容形态符合的全部视频 / 图文，不论是否被第 1 层选中、是否通过、是否获取成功。

- 行集 = D 读口返回的该执行内容行（经 DataScope 约束后）；本 spec SHALL NOT 自己重新圈定。
- 发布时间缺失的内容（D 记为 `l0 = unobtained`）与形态未知的内容照常列出，并在能力列里体现原因，不隐藏。
- 一条内容在 D 里按账号各存一条（同一作品在两个账号下是两行），本 spec 保持一行一条。
- 默认排序：品牌、大区、分公司、板块、门店、专员的冻结组织顺序，再按发布时间倒序、内容 ID。服务端分页，每页 50 行。
- 筛选（均为 D 读口的组织过滤，不做本地全表扫描）：大区、分公司、板块、门店（级联下拉）与专员（按姓名 / 编码搜索，解析为专员 ID）。

**验收标准**
- 视频明细行数 = D 读口对该执行与同一范围约束返回的内容行数（`contentTotal` 在无约束时与之相等）；
- `skipped`（未被第 1 层选中）、`unobtained`、`fail`、`pass` 的行都在；
- 非总部角色看不到范围外的行，也看不到范围外的总数。

### EL-3 · 视频明细：固定列

**陈述**：视频明细的固定列 SHALL 按下表顺序、以下表头出现（表头以刘学奎 2026-11-19 给定为准），其后依次接能力列（EL-4）。

| # | 表头 | 来源与规则 |
|---:|---|---|
| 1 | 品牌 | 冻结组织链的品牌名 |
| 2 | 大区 | 冻结组织链的大区名 |
| 3 | 分公司 | 冻结组织链的分公司名 |
| 4 | 板块 | 冻结组织链的板块名 |
| 5 | 经销商名称 | 冻结组织链的经销商名 |
| 6 | 门店名称 | 冻结组织链的门店名 |
| 7 | 门店编码 | 门店编码（文本，不转数字） |
| 8 | 专员姓名 | 冻结的专员姓名 |
| 9 | 平台 | 执行描述的平台名（一个判定计划只有一个平台） |
| 10 | 昵称 | 表头为「<平台>昵称」（抖音为「抖音昵称」，见 U4）；取执行数据截止时点前最新主页快照的昵称 |
| 11 | 主页链接 | 账号当前归属的主页入口，仅 `http` / `https` 才输出，否则留空 |
| 12 | 类型(视频/图文) | `video` → 视频；`image`、`text` → 图文；`unknown` → 未知 |
| 13 | 视频/图文标题 | 执行冻结的内容快照的标题 |
| 14 | 发布时间 | 冻结快照的发布时间，**北京时间** `YYYY-MM-DD HH:mm`；缺失留空 |
| 15 | 视频/图文链接 | 冻结快照的分享链接，仅 `http` / `https`；否则留空 |
| 16 | 视频/图文唯一ID | 平台内容 ID 的**原文**，导出时写成文本单元格（19 位 ID 不得被转成数字） |
| 17 | 点赞 | 冻结快照互动值，见下 |
| 18 | 评论 | 同上 |
| 19 | 分享 | 同上 |
| 20 | 收藏 | 同上 |
| 21 | 采集时间 | 冻结快照的 `snapshot_at`，北京时间 `YYYY-MM-DD HH:mm` |

- 互动值按 ValueState 展示：`value` → 数字（真实 `0` 显示 `0`）；`missing` / `explicit_null` → 空；`invalid` → 「无效」。系统 SHALL NOT 把缺失显示成 `0`。
- 数据用 D 冻结的内容快照（`run_contents.content_snapshot_id`），**不读 `contents.current_snapshot_id`**，使同一次执行重复查看结果一致。

**验收标准**
- 表头文本与顺序逐字等于上表；
- 19 位内容 ID 经页面与 Excel 往返不丢位；
- 点赞为 `value` 且值 0 的行显示 `0`；`missing` 的行显示空；
- 取同一执行两次，数据一致（即使其间采集到了新快照）。

### EL-4 · 能力列：列头与单元格

**陈述**：判定计划（该执行所用版本）里每个条件 SHALL 对应一列，位置在固定列之后，顺序按**层序**：第 1 层（文本、话题、时长，按配置顺序）→ 第 2 层（按配置顺序，封面、头像、主页背景混排）→ 第 3 层语音判定 → 评论要求。视频明细只含内容类条件（封面）；头像、主页背景条件只在账号维度出现，并按配置顺序留在第 2 层的位置上（EL-5）。

**列头规则**（视频明细与账号维度共用同一份，保证两表一致）：
1. 有别名 → 用别名（取**该执行所用版本**的别名，不取最新版本）；
2. 无别名 → 默认名：文本 `文本关键词`、话题 `话题`、时长 `时长`、整张图片对比 `整图对比·<对象>`、图片元素对比 `元素对比·<对象>`、语音判定 `语音判定`、评论要求 `评论要求`；对象为 `封面` / `头像` / `主页背景`；
3. 同一表里出现相同名字（含别名撞默认名、别名撞别名）→ 对**每一个**重名列在名字后追加 ` #序号`，序号按配置顺序从 1 起（如 `话题 #1`、`话题 #2`）；
4. 名字与固定列表头相同 → 追加 `（能力）`。

**单元格规则**（每条内容、每个条件一个值）：

| 条件 | 通过 / 不通过 | 获取失败 | 未被评估 |
|---|---|---|---|
| 文本关键词、话题 | 命中词，用「、」连接；不通过且没有命中词 → `未命中` | 原因码 | 前置条件未满足，不进行计算 |
| 时长 | 秒数（保留 D 的原值） | 原因码 | 同上 |
| 整图 / 元素对比（封面） | **分数**（`0.00`–`10.00`，D 的两位小数文本） | 原因码 | 同上 |
| 语音判定 | `达标` / `不达标` | 原因码 | 同上 |
| 评论要求 | `命中 x / 共 y 条`（该内容的评论命中数与评论数；只有走完第 2 层的内容才有评论数） | 原因码（更早的层获取失败时同样写该行原因码） | 同上 |

- 「未被评估」= 该内容没走到这个条件所在的层：没被第 1 层选中，或被更早的层判定不通过而停层。统一显示 `前置条件未满足，不进行计算`（刘学奎 2026-11-19）。
- 例外：该行更早的层是**获取失败**而停下（如发布时间缺失、形态未知，D 记 `l0 = unobtained`）时，这不是「条件没满足」而是「没拿到」，后面各层的能力列显示该行的原因码（获取失败），不显示「前置条件未满足」。
- 「获取失败」写 D 的原因码文本（如 `dependency_timeout`），**不写 `0`、不留空**（D「不把没拿到写成 0」）。
- 页面与 Excel 按状态给单元格文字着色：通过 → 绿，不通过 → 红，获取失败 → 灰，未评估 → 浅灰。颜色只是辅助，不是信息的唯一载体（文字本身可读）。
- 一个内容层条件在 D 里没有对应证据（旧执行）→ 显示空，不当作未评估。

**验收标准**
- 列头规则四条各有一例：别名、默认名、重名加序号、撞固定列；
- 同一计划同一执行，视频明细与账号维度同一条件的列头完全相同；
- 改别名后再次执行，新执行用新别名，旧执行仍显示旧别名；
- 图片类单元格显示分数而不是状态；未被选中的内容显示「前置条件未满足，不进行计算」，而不是空或 `0`。

### EL-5 · 账号维度

**陈述**：账号维度 SHALL 对所选执行的 `run_participants` 一个参与账号一行，列依次为：

固定列（表头以刘学奎 2026-11-19 给定为准）：品牌、大区、分公司、板块、经销商名称、门店名称、门店编码、专员姓名、平台、`<平台>昵称`、主页链接、粉丝数、总获赞、平台作品数、已采集视频数、主页是否采集成功、主页采集时间、视频列表是否采集成功、视频列表采集时间；

其后：**能力列**（每个条件一列，含头像、主页背景；顺序同 EL-4，头像、主页背景按配置顺序留在第 2 层的位置上，不排到最后）；最后一列 **判定结果**（D 的 `plan_result`：`success` → 通过、`not_met` → 不通过、`unobtained` → 获取失败）。

- 粉丝数、总获赞、平台作品数取执行数据截止时点前最新的主页快照；值按 ValueState 展示（同 EL-3）；
- **已采集视频数** = 该账号截至执行数据截止时点已采集到的作品数（口径见 U2）；
- **主页是否采集成功 / 主页采集时间**：执行数据截止时点前，该账号最近一次**终态**的 `fetch_profile` 任务：`succeeded` / `succeeded_with_gap` → 是；`failed` / `dead` / `cancelled` → 否；没有记录（含已过一年保留期）→ `无记录`；时间 = 该任务的完成时间（北京时间）。**视频列表**同理，动作为 `fetch_content_list`；`succeeded_with_gap` 显示 `部分（有缺口）`；
- **账号能力列只有四个值**：`通过` / `不通过` / `获取失败` / `前置条件未满足，不进行计算`（EL-6）；
- 执行早于 JP-22（`ability_results` 为空）时，能力列整列显示空，页面顶部提示「该执行早于本功能，账号能力结果不可用，重新执行后可见」；`判定结果` 与固定列照常显示；
- 排序与筛选同 EL-2；分页每页 50 行。

**验收标准**
- 表头与顺序逐字等于上列；
- 行数 = D 读口对该执行与同一范围约束返回的参与账号数；
- 有一个账号「主页采集成功、视频列表失败」时，两列各自显示正确，时间各自是对应任务的完成时间。

### EL-6 · 账号能力结果规则（由 D 计算并存储）

**陈述**：每个账号的每个条件 SHALL 有一个四态结果，由 D 在执行聚合阶段**一次算好并持久化**（JP-22），本 spec 只读。规则复用 D 现有的 `at_least_n` 与零内容规则，**N = `layer1.quantity.n ?? 1`**（与内容要求同一个 N）：

1. **评估集**：
   - 第 1 层条件（文本、话题、时长）：该账号 `run_contents` 的全部行；
   - 第 2 层封面能力、第 3 层语音判定：该账号被第 1 层选中且走到该层的行；
2. 对评估集逐行取该条件的状态：`pass` 计 P，`fail` 计 F，`unobtained` 计 U；**没评估到该条件、但该行最终结果是 `unobtained` 的行也计 U**（它可能通过，与 D 的内容聚合一致）；没评估到且最终结果不是 `unobtained` 的行（被更早的层判定不通过）不计。**第 1 层条件对被数量要求截掉的行（`final = skipped`，原因 `layer1_not_selected`）同样按它保留的第 1 层证据计数**：D 的 select 阶段只改 `l2 / l3 / final`，不清第 1 层证据，所以第 1 层的能力列统计的是窗口内全部内容里该条件通过了几条（N=6、10 条命中文本时，文本列按 10 条算），这样才能看出是哪个条件拖了后腿；第 2、3 层条件的评估集仍只有被选中并走到该层的行（截掉的行没有这两层的证据，不计）；
3. 第 1 层条件：账号没有任何 `run_contents` 行 → 按零内容规则（同步完整 → 不通过，否则 → 获取失败）；有行则 `P ≥ N` → 通过；`P + U < N` → 不通过；否则 → 获取失败；
4. 第 2、3 层内容类条件：`P + U + F = 0`（没有内容走到这一层）→ **前置条件未满足，不进行计算**；否则同第 3 条的比较；
5. 头像、主页背景：沿用 D 已存的账号能力结果（`account_detail.abilities`）：通过 / 不通过 / 获取失败，不出现「前置条件未满足」；
6. 评论要求：沿用 D 的 `comment_result`；未配置评论要求则没有这一列；
7. `判定结果` 沿用 D 的 `plan_result`，不重算。

**说明（给业务的两个现象）**
- 各能力列都是「通过」，`判定结果` 仍可能是「不通过」：一条内容要同时通过全部层才算。典型是没设数量 N（N = 1）时，A 内容通过文本条件、B 内容通过话题条件，没有一条两者都过；设了 N 且被选中的条数刚好等于 N 时一般不会出现。这就是账号维度要有 `判定结果` 列的原因（原型里可看专员「马超」）；
- 第 1 层只通过了 3 条而 N 为 6 时，第 2 层能力列显示「不通过」，即使这 3 条的封面全都通过：条数没到。与账号最终结果一致。

**验收标准**
- 对 D 的纯函数穷举 (P, U, F, rows, N, 零内容) 的组合，断言结果与上述规则一致；
- 零内容账号：第 1 层条件走零内容规则，第 2、3 层条件为「前置条件未满足」；
- 每个能力列的结果与对应能力的 `pass` / `fail` / `unobtained` 内容数手工推算一致（一个固定 fixture）。

### EL-7 · 线上图片

**陈述**：页面 SHALL 显示账号头像、主页背景图与内容封面。

- 视频明细每行显示封面缩略图（取冻结内容快照的 `cover_normalized`，第 0 槽）；账号维度每行显示头像与主页背景缩略图（取执行数据截止时点前最新主页快照的 `avatar_normalized` / `background_normalized`）；
- 图片只用签名链接（TTL 沿用 `HBECHO_SQUARE_COVER_TTL_S`，默认 300 秒），**不暴露桶名与对象 key**；缺失、未归档、签名失败 → 占位图，不让整行失败；
- 点击缩略图 MAY 放大查看；放大图同样走签名链接；
- Excel 不含任何图片，也不写图片链接列。

**验收标准**
- 签名器返回失败时该行显示占位、其余行正常、页面不报错；
- 页面源码里没有桶名与对象 key；
- 导出文件里没有图片对象（离线测试扫描工作簿的 `addImage` 零调用）。

### EL-8 · Excel 导出

**陈述**：用户 SHALL 能把当前执行、当前筛选下的两张表导出为一个 `.xlsx`：**sheet 1「视频明细」、sheet 2「账号维度」**；列与单元格规则同页面（EL-3 至 EL-6）。

- Capability = `report.export`（B 已有；`store_staff` 没有，所以门店专员只能在线看，不能导出）。导出前走 B 的出口守卫（出口 4），允许与拒绝都记审计；
- 范围 = 提交人当前 DataScope ∩ 当前筛选；导出时按**提交那一刻**的范围，不放宽；
- 行数上限：视频明细 **50,000** 行、账号维度 **5,000** 行（**起始值，不是冻结值**：来自旧系统导出上限与实测前的保守取值；T5 / M3 实测后回填并定稿，U1 随导出路径确认）；超限拒绝并提示「请先用筛选缩小范围」，**不静默截断**；
- 只用 `exceljs` 的写入 API（ADR-0011）；以 `= + - @ \t \r` 开头的文本单元格加 `'` 前缀；内容 ID、门店编码写成文本单元格；时间为北京时间文本；
- 单元格着色同页面；首行冻结；列宽按表头与前 100 行估算（不遍历全表）；
- 文件名：`<活动计划名>-<判定计划别名>-<执行完成日期>-全量明细.xlsx`，非法字符替换为 `_`；
- 空 sheet 仍输出表头。账号能力结果不可用（旧执行）时，该列留空并在导出前提示。

**验收标准**
- 往返：用独立读取代码（仅测试内、不进生产）读回文件，表头与行数与页面一致；
- 以公式字符开头的昵称 / 标题被加前缀；19 位 ID 不丢位；
- 超过行数上限时拒绝，错误码 `export_row_limit`，且没有生成部分文件；
- `store_staff` 调导出被拒并记审计；
- 代码里 `xlsx.read` / `xlsx.load` 零命中。

### EL-9 · 授权与数据范围

**陈述**：本 spec SHALL 复用 B 的授权，不新增 Capability。

- 页面读：Capability `report.read`（四个角色）；导出：`report.export`；
- 资源键 `report`：本 spec 注册其范围策略（`contains`：范围非空，且判定计划的品牌 ∈ 范围品牌、所属活动计划的某个已加入分公司 ∈ 范围分公司；`constraint`：`constraintOf`）。已注册则不重复注册（同 D 的 `registerJudgementAuthz` 写法）；
- 范围约束 `constraintOf(ctx.scope)` 原样传给 D 读口，由 D 按**冻结的组织链**与 `self`（专员本人）过滤：总部全部、分公司只看本分公司、门店只看本人；
- 空范围 → 授权错误，不回退为全部；越范围的判定计划表现为 `not_found`，不泄露存在性；
- 页面不返回内部 ID 之外的敏感字段：不输出专员联系方式；专员姓名、门店编码属于业务已有字段，可见性同 D 的执行详情页。

**验收标准**
- 四个角色各一例：总部见全部；分公司只见本分公司的行，总数与分页也只算本范围；门店只见本人；平台管理员见全部；
- 无 `report.read` / 空范围 / 越范围判定计划各一例，均不泄露数据；
- 导出时范围收缩（提交后被撤权或缩范围）：下载 / 生成时按当前范围复核，不超出。

### EL-10 · 数据时点与保留

**陈述**
- 页面顶部 SHALL 显示：判定计划别名与版本、执行完成时间、**数据截止时间**（D 的 `cutoffAt` = 冻结时刻）、窗口（北京日期）、行数；
- 内容类数据（标题、互动、封面）取 D 冻结的内容快照；账号类数据（昵称、粉丝、头像、背景、采集状态）取**数据截止时点前**最新的主页快照与同步任务（以 `finished_at ≤ cutoff` 判定「已终态」，并按 `(logical_at, batch_id)` 取最新；与 `e-metrics` design §6 的观测规则一致）；
- D 只保留每个（判定计划，版本）最近 `HBECHO_JP_KEEP_CONTENT_RUNS` 次已完成执行的内容级行。更早的执行：**视频明细没有行**（内容级行已被清理，D 读口返回 `content_rows_pruned`），页面显示「这次执行的内容明细已过保留期」，**账号维度仍完整可用**（参与专员行长期保留）。系统 SHALL NOT 为已清理的执行重建视频明细；
- 同一判定计划之后又有新的执行时，旧执行仍可通过历史执行切换查看。

**验收标准**
- 被清理的执行：视频明细标签显示说明、导出时视频明细 sheet 不生成并提示，账号维度正常；
- 数据截止时间之后才到达的新快照不改变已有执行的展示。

### EL-11 · 失败语义

**陈述**：任何依赖失败 SHALL NOT 被写成业务空值。

| 情形 | 行为 |
|---|---|
| D 读口失败 / 超时 | 页面整体错误态 + 重试；导出失败，不产出部分文件 |
| 某行的内容快照或主页快照读不到 | 该行对应列显示空，行仍在；页面顶部汇总「N 行有缺失数据」；**不当作 `0`** |
| 签名失败 | 仅该图占位 |
| 导出过程中范围或权限变化 | 以提交时的范围执行；交付前复核，不满足则拒绝并记审计 |
| 同步任务记录不存在（过期或从未采集） | 显示 `无记录`，不是「否」 |
| 执行早于 JP-22 | 账号能力列整列空 + 提示（EL-5） |

### EL-12 · 对 D 的对齐请求（JP-22）

本 spec 需要 D 的读口在**不改变任何判定语义**的前提下补三处，细则写入 D 的 [`requirements.md`](../d-rule-engine/requirements.md) JP-22 与 [`design.md`](../d-rule-engine/design.md) §10.4 第 7–9 项，由 D 的任务 17 实施：

1. **内容行**：`ContentFact` 增加 `contentSnapshotId`、冻结的组织链与专员 ID、`evidence` 白名单（第 1 层各条件的状态与命中、第 2 层各能力的状态与分数、第 3 层状态与结论；**不含**正文、评论原文、作者、第 3 层的模型理由与依赖明细）；并提供带组织过滤与偏移分页的 `listContents` / `listParticipants`（含总数），流式读口同样接受组织过滤；另提供按判定计划列出已完成执行的 `executionsOf(planId)` 与授权引用 `planRefOf(planId)`（含 `activityPlanName`，用于导出文件名；判定计划不存在或所属活动计划在回收站时 `not_found`，**越范围由调用方的 `authorize(report.read)` 表现为 `not_found`**，`planRefOf` 本身没有调用者身份，不判断范围）；新读口与现有 `stream*` 同构，不做能力校验，由调用方负责 `report.read` 与范围约束，**不沿用 `explain` 的双能力校验**；
2. **执行描述**：`ExecutionDescriptor.config` 增加有序的条件清单（`key`、层、种类、对象、别名、序号）；
3. **账号结果**：`run_participants` 新增可空 JSON 列 `ability_results`（迁移 `0016`，只加不改不删），聚合阶段按 EL-6 写入；`ParticipantFact` 增加 `abilityResults`。

**验收标准**：见 D 的 JP-22；本 spec 的契约测试用 fake 的 `JudgementOutcomeReader` 与 D 的真实实现共用同一份 shape 测试。
