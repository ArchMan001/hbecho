## 一、这个域管什么

### 1.1 四个问题

```
你是谁            → 账号从哪来、怎么激活、怎么登录
你能做什么        → 四类角色分别能操作什么
你能看到什么      → 组织范围 ∩ 品牌
你什么时候被踢出  → 会话时长、强制下线、停用、离职
```

### 1.2 不管什么

| 事情 | 归谁 |
|---|---|
| 门店、专员、账号是什么 | A 数据底座 |
| 内容该不该被采 | A 数据底座 |
| 什么算达标 | D 规则与考核 |
| 指标怎么算 | E 指标与看板 |
| 页面长什么样 | F 业务应用 |
| 服务器与密钥怎么管 | I 运维与成本 |

### 1.3 一条主线

```
管理员开通账号 → 用户自己设密码 → 登录得到会话
→ 每个动作先问"能不能做" → 每个查询再问"能看哪些"
→ 所有出口（页面、导出、下载、Worker、AI）执行同一套判断
→ 停用或撤权后，会话失效、任务收窄、交付前再查一次
```

**B 的职责是"发许可"和"守出口"，不是"存业务数据"。**

## 二、用户与场景

### 2.1 四类角色

| RoleCode | 角色 | 典型人数 | 一句话 |
|---|---|---|---|
| `platform_admin` | 超级管理员（平台运营） | 1–3 | 管系统、管人、管全部配置 |
| `hq_manager` | 总部人员 | 20–50 | 管授权品牌的业务与配置 |
| `branch_manager` | 分公司人员 | 50–100 | 管本分公司的数据与人员 |
| `store_staff` | 经销商人员（门店专员本人） | 3,500+ | 看自己的数据、学课程 |

> 人数是规模估算，用于判断"批量导入"与"管理范围"的设计重心，**不作为验收项**。

### 2.2 三条真实路径

| # | 场景 | 走哪条链路 |
|---|---|---|
| 1 | 新一年度名单下来，要一次开通几百个账号 | 批量导入 + 激活（第四章） |
| 2 | 用户每天登录看自己的数据 | 登录与会话（第五章） |
| 3 | 门店换人、分公司调整、人员离职 | 生命周期与授权变更（第六、九章） |

### 2.3 1.0 的边界

- 无公开注册、无经销商自助入驻；
- 无 SSO、无 MFA、无设备管理中心；
- 无动态角色设计器、无个人权限覆盖；
- 无高风险动作二次认证（可以 2.0 再加）；
- 认证基于 better-auth，授权自建（ADR-0005）。

## 三、概念

### 3.1 三类身份必须分开

| 概念 | 含义 | 谁能登录 |
|---|---|---|
| `User` | 登录主体 | ✅ |
| `MediaStaff` | 某人在某门店与品牌下的业务身份 | ❌ |
| `ExternalAccount` | 平台账号 | ❌ |

**`User` 与 `MediaStaff` 不是一回事。** 总部与分公司人员只有 `User`，没有 `MediaStaff`；门店专员本人两者都有。

**一个 `User` 只持有一个 `RoleCode`**（B-D01）：四类角色取其一，1.0 不做多角色；身兼多职时按更高角色建号，不叠加能力或范围。

### 3.2 Capability 与 DataScope 正交

| 维度 | 回答 | 例子 |
|---|---|---|
| **Capability** | 能不能执行这个动作 | "能不能触发手工同步" |
| **DataScope** | 能访问哪些对象 | "能同步哪些门店的账号" |

两者必须分开判断：有动作权限的人，数据范围可能很小；数据范围大的人，未必有写权限。

| 场景 | Capability | DataScope | 实际结果 |
|---|---|---|---|
| 分公司管理员 | 有 `data.sync.trigger` | 只能访问本分公司 | 能手工同步，但只能同步本区的账号 |
| 总部分析人员 | 只有 `data.account.read`，没有 `data.sync.trigger` | 授权品牌下全部组织 | 能看全品牌的数据，但不能触发同步 |
| 门店专员 | 有 `learning.read` | 仅本人 | 能看自己的账号与课程；AI 内容辅助仅超管/总部 |
| 超管 | 全部 Capability | 全部 | 不受限，但仍走显式判断，没有隐藏旁路 |

### 3.3 管理范围

管理别人时多一个维度：

```
管理范围 = 角色 ∩ 组织范围 ∩ 品牌
```

且**不能授出超过自己**：不能给别人自己都没有的品牌、组织或能力。

### 3.4 数据出口

所有能把数据带出系统的地方，执行同一套判断。B 域负责定义出口清单与复查时机（第十章）。

## 四、B1 开户与激活

### 4.1 邀请制

- 平台运营或上级管理员创建用户，填写：姓名、角色、组织范围、品牌、手机号；`store_staff` 另填**门店编码**，由「手机号 + 门店编码」自动定位唯一有效 `MediaStaff` 并绑定（B-D07，2026-11-04 修订）；
- **只能授予严格低于自己的角色**；只有超管可以授予超管（B-D02）；
- **系统里不存在默认管理员账号和默认密码**；
- 首个超级管理员由一次性初始化操作创建，不通过界面导入：由运维执行一次性 CLI + 一次性令牌，成功后令牌失效，操作记审计（B-D31）；

### 4.2 激活

- 新用户处于"待激活"；
- 用户首次登录时**自己设置密码**；
- 运营人员在任何界面都不能设置、也不能查看用户密码；
- 激活凭证短期有效、一次性；重发使旧凭证失效。

**激活方式：短信验证码**（D-39）。用户输入手机号 → 收到验证码 → 验证通过后设置密码。与登录共用同一套短信能力，不预生成激活码、不导出文件。

**短信参数**（激活、登录、重置密码共用一套）：验证码有效期 **5 分钟**；同一手机号 **60 秒**后可重发；同一手机号每天最多 **10 条**；连续输错 **5 次**即作废，需重新获取。短信额度与费用归 I 域。

- **发送前校验**（B-D37）：手机号必须是系统中「待激活或有效」的用户；不是则返回与成功一致的提示，但实际不发送。
- **全局每日上限**（B-D38）：由 I 域配置；超过时告警并暂停发送。达到上限时密码登录不受影响，只有短信登录、激活与找回密码暂停。

- **待激活不设有效期**：不自动过期；管理员可在用户管理里看到「待激活天数」并批量停用（B-D04）；
- **未激活用户允许管理员直接改手机号**（尚未产生登录与会话）；激活后改号只能走「删旧建新」（B-D06）。

### 4.3 批量导入

- 格式 CSV（与 A 域一致）；
- **全部同步执行**：上传后同步预检、同步写入；单批最多 **1,000 行**，超过直接拒绝并提示拆分（B-D12）；
- 先预检再确认：阻断"操作者没有权限授予的角色、组织与品牌"；**预检结果不过期，确认时重新校验全部行**（B-D12）；
- **只做新增**；手机号唯一性只约束「待激活 + 有效」用户，已存在的非停用手机号标为冲突，不静默改角色或范围（B-D05）；
- 失败行回流为同格式文件，每行带原因码与一句指引：
  - 角色 / 范围不符 → 到用户管理里单独修改；
  - 手机号已存在且是换号 → 停用旧用户后新建（D-43）；
  - **不提供"一键改成新增"**，避免绕过授权校验。
- 失败行回流文件由**提交人本人**下载，视为导入闭环，不额外要求 `data.export`；文件只含本次提交的行，手机号明文（B-D12）。

### 4.4 明确不做

- 公开注册；
- 自助找回未开通的手机号；
- 导入时直接把密码写进文件。

## 五、B2 登录与会话

### 5.1 登录方式

| 方式 | 1.0 | 说明 |
|---|---|---|
| 手机号 + 密码 | ✅ | 主方式 |
| 手机号 + 短信验证码 | ✅ | 与激活、找回密码共用同一套短信能力 |

### 5.2 会话

- 登录后获得可撤销的会话；
- **有效期 15 天，滑动续期**（D-40）：
  - 第 1 天登录，有效期到第 16 天；
  - 第 10 天再次登录，有效期刷新到第 25 天；
  - 连续 15 天不登录，会话到期失效，需要重新登录；
- **滑动续期每天最多刷新一次**：同一自然日内的后续认证请求不再写库；跨天后的首次请求刷新到期时间（B-D13）；
- 每次登录都重新检查用户状态与授权，停用用户无法续期；
- 支持"退出登录"与"管理员强制下线"。
- **不设绝对有效期，也不限制并发会话数**（2026-10-29 决定）：只要持续活跃，会话可以一直续期；撤销仍通过停用、改密、强制下线三条路径完成。

### 5.3 密码

- 由用户自己设置，管理员不能查看、也不能代设；
- **不强制字符组合、不强制定期改密、不做弱密码黑名单**（D-45）；
- 仅保留一条安全下限：**最短 8 位**；
- 忘记密码走短信自助重置；
- **短信重置成功后解除该账号的登录失败锁定**；重置密码同样使该用户的其他会话全部失效（B-D16）；
- 修改密码后，该用户的其他会话全部失效。

### 5.4 登录保护

- 登录失败限流**由本域自建，不由 better-auth 承担**（ADR-0005）：better-auth 的限流按连接 IP 计请求次数，不能按账号计数，也不区分成功与失败；
- **只保留账号维度**：连续 5 次失败 → 该账号锁 15 分钟，期满自动解锁；锁定期间正确密码也不放行，不通知、不永久锁定；
- **去掉 IP 维度**：1.0 不再按 IP 封禁失败，避免公司 NAT 共享出口误伤整个办公室；请求洪水由 better-auth 的全局请求限流兜底（B-D14）；
- **锁定只限制密码登录**：短信验证码登录不受账号锁定影响，仍受每日 10 条短信上限约束（B-D15）；
- **不提供手动解锁或超管豁免**：只能等 15 分钟自动解锁；短信重置密码成功是唯一的提前解锁路径（B-D16）；
- 锁定期满后失败计数清零；
- 连续失败不修改业务用户状态；
- 待激活账号走密码登录时，提示与"手机号或密码错误"一致，不暴露账号是否存在。

## 六、B3 用户生命周期

### 6.1 三个状态

| 状态 | 含义 | 能否登录 |
|---|---|---|
| 待激活 | 已创建，未设密码 | ❌ |
| 有效 | 正常 | ✅ |
| 停用 | 禁止登录，历史保留 | ❌ |

**不物理删除。** 离职、退出试点都用停用表达。

**待激活不设有效期**（B-D04）：不会自动转停用；是否停用由管理员决定。

### 6.2 停用与恢复

- 停用：现有会话全部失效，不能新建会话；
- 恢复：重新检查角色、组织范围、品牌与关联业务身份；**已失效的项直接去掉（自动收窄），用户恢复为有效**。移除项在审计里记一条，不做单独的恢复结果页。
- 「已失效的项」指对象不存在或无法映射；**品牌或组织停用不算失效**，不从授权中去掉（B-D25）；
- **`MediaStaff` 停用 → 自动停用绑定的 `store_staff` User**：懒执行（下次登录/授权时发现）并撤销会话，另有定时任务补偿；审计以系统身份记 `media_staff_disabled`（B-D10）；
- **`MediaStaff` 恢复 → 有条件自动恢复 User**：只恢复因该 `MediaStaff` 停用而自动停用的 User，人工停用的不恢复；恢复前复核手机号唯一与授权，若同号已有其他有效 User，则保持停用并生成可处理问题（B-D11）；
- 停用不影响 A 域的数据采集；采集只看业务状态与监控开关；
- **采集与登录激活完全解耦**（D-46）：门店专员从未首次登录、`User` 一直是"待激活"或根本没有 `User`，只要该专员的业务身份已导入、监控开着，A 域照常采集该门店的账号；
- 同理，`User` 停用也不会停止采集；停采只看 A 域的业务状态与监控开关。

### 6.3 人员变动

- 换门店或换品牌：**删旧建新**——停用旧 `User`，用同一手机号新建 `User` 并绑定新的 `MediaStaff`，重新走短信激活；旧账号的学习进度与个人历史留在旧 `User`（B-D09）；
- `MediaStaff` 的创建发生在两处：活动计划名单导入时自动新建（手机号在有效专员中不存在，预检列出、确认后新建，沿用 `activity_plan.join`，记审计）；超管单条新增（A §4.2，2026-11-04 修订）；主数据导出不含专员。`MediaStaff` 的停用触发清单已由 A §5.4 补齐（离职、撤店、调岗、录错），复用 `data.master_data.import` / `correct`（总部授权品牌 / 超管），不新增 Capability；分公司只能通过名单撤出与监控开关停采，不能停用专员主档。
- 离职：停用 `User`；对应的 `MediaStaff` 按 A 域规则处理（账号停采、归属不变）；若 MediaStaff 也停用，按 B-D10 自动停用 User；
- 手机号变更：**只做"删旧建新"**（D-43）——停用旧用户，用新手机号新建用户并重新授权；停用用户不占手机号唯一性，新用户可复用旧号（B-D05）；
- 系统不支持直接修改登录手机号；
- 理由：系统无法区分"换号"与"换人"，而两者正确的处置完全不同；改绑会让新人继承旧人的全部权限；
- 若将来确需改绑，必须同时满足：新号短信验证、旧号收到通知、记审计（不要求人工填写原因，B-D30）。
- **不建立新旧用户之间的关联**（2026-10-30 决定）：审计按 `User` 维度记录，不按自然人；换号后新旧用户是两条独立记录，系统不提供"同一人"的追溯，也不要求填写原用户。

| `learning.tag.manage` | 维护课程标签集合 | — | ✅ | ❌ | ❌ | ❌ |
| `ai.content.assist` | 使用 AI 内容辅助 | 全部品牌 / 授权品牌 | ✅ | ✅ | ❌ | ❌ |
| `user.manage` | 管理用户与授权 | 角色 ∩ 组织 ∩ 品牌 | ✅ | 授权品牌 | 本分公司 | ❌ |
| `audit.read` | 查看审计日志 | 1.0 仅超管 | ✅ | ❌ | ❌ | ❌ |
| `config.manage` | 系统配置（含每周同步计划的调度参数） | — | ✅ | ❌ | ❌ | ❌ |

> **两条归属说明**：试运行复用 `rule.definition.manage`，不新开能力；`rule.run.execute` 只作用于已发布版本。每周同步计划的调度参数（执行时点、并发）归 `config.manage`（仅超管），业务侧只用 `data.monitoring.manage` 决定采不采某个对象。
>
> **活动计划的可选范围跟随 `activity_plan.create`**：只有计划创建者本人与超级管理员能选它建立监控判定计划；分公司即使加入计划也不能建。
>
> **活动计划的资源谓词**：编辑基本信息、暂停 / 归档 / 恢复 / 删除、替换负责人只对**计划创建者**与超管开放；`hq_manager` 在授权品牌内能看到计划，但不能编辑他人创建的计划（B-D17 / B-D19）。负责人本身不是权限，只作责任标记（B-D18）。
>
> **监控判定计划的读取**挂 `rule.definition.read`，可见范围 = 所属活动计划的可见范围 ∩ 规则适用品牌（B-D21）。
>
> **外部监控账号**：默认只有平台级可见；`hq_manager` 与 `branch_manager` 即使持有 `data.account.read` 也看不到，维护只归 `monitor.external.manage`（超管）（B-D22）。
>
> **人员级别**：`learning.read` 的可见性 = 课程品牌范围 ∩ 本人品牌范围 ∩ 本人级别 ≥ 课程级别；级别由角色映射（`store_staff`=1、`branch_manager`=2、`hq_manager` / `platform_admin`=3），不另建职级字段（B-D23）。
>
> **用户管理**：`user.manage` 的用户列表只显示严格下级与自己；同级互不可见、不可操作；只有超管可以管理其他超管，且不能停用自己（B-D02）。
>
> **批量导入不是 `structure` 的例外**：`import` 只做授权品牌门店的非结构字段与已有结构下新门店；新经销商 / 板块 / 分公司 / 大区、给门店换关系仍归 `structure`，仅超管（F-D08）。
>
> **全部品牌课程**：G-D08 / G-D42 允许 `hq_manager` 管理「全部品牌」课程；`learning.manage` 的范围判断把全部品牌课程视为落在授权品牌内，但 hq 仍不能逐个勾选未授权品牌。`learning.read` 对全部品牌课程按「所有品牌可见」处理（B-D35）。
>
> **AI 内容辅助 1.0 仅超管与总部**：`ai.content.assist` 只授予 `platform_admin` 与 `hq_manager`；分公司与门店不开放 H5。D 第三层的 ASR + 大模型判定由 D 的监控判定计划触发，不经 `ai.content.assist`（H-D02 / H-D05）。

### 7.4 权限变更

- 只有 `user.manage` 且在自己的管理范围内的人能改；
- 变更要记审计：改前、改后、`reason_code`、操作者；角色或范围变更不撤销现有会话，下一次请求按新权限判断（B-D33）；
- 角色变更后，现有会话可以继续，但下一次请求就按新权限判断。

## 八、B5 数据范围

### 8.1 范围构成

```
DataScope = 组织范围（子树） ∩ 品牌集合
            + 是否仅本人
```

**组织范围与品牌集合求交**（B-D24）：大区、分公司、板块、经销商是全品牌对象，门店与账号才带品牌；组织在范围内但品牌未授予的对象不可见。该决定同时关闭 ADR 未决选型 #7。

### 8.2 按资源类型的规则

| 资源 | 范围规则 | 说明 |
|---|---|---|
| 账号 / 内容 / 主页 / 媒资 | 组织子树 ∩ 品牌 | 门店专员只看本人 |
| 外部监控账号（竞品与官方号） | 默认只有平台级可见 | 无门店与专员，不落入组织范围；总部与分公司都看不到（B-D22） |
| 报表 / 点检表 | 同一投影下按当前范围过滤 | 同一张配置，不同人看到不同行 |
| 规则与指标配置 | Capability + 适用品牌 | **配置的适用范围不是授权** |
| 用户管理 | 角色 ∩ 组织 ∩ 品牌 | 读写用同一条谓词 |
| 原始载荷 | 独立高敏 Capability + 业务范围 + 审计 | 普通读数据权不自动包含 |
| 手机号 | 随所在行的范围判断（B §8.1） | 不单设字段级 Capability：能看到行就能看到手机号；不逐条记审计（B-D29） |
| 媒资下载 / 签名 URL | 继承源对象范围 | 每次短期签发 |
| 学习课程 | 品牌范围 ∩ 人员级别 | 级别由角色映射，与品牌求交（B-D23） |
| 活动计划 / 监控判定计划 | 所属分公司或授权品牌 + 资源谓词 | 创建者、负责人等条件由资源域实现（B-D17 / B-D21） |
| 审计日志 | 1.0 仅超管可见 | 其他角色一律不可见（D-41） |
| 通知 / 消息 | 接收者当前范围 | 发送前复查（B-D27） |

### 8.3 "本人"怎么绑定

- `store_staff` 的 User 与一个 `MediaStaff` 一对一绑定；
- `store_staff` 创建用户时用「手机号 + 门店编码」定位唯一有效 `MediaStaff`；不存在或不在该门店进回流，不建用户（B-D07，2026-11-04 修订）；
- 例：张三在"北京日立 001 店"是新媒体专员，他的登录账号绑定到这条 `MediaStaff` 记录；他能看到的账号与内容，就是归属到这条记录的那些；
- 如果没有绑定、绑定到已停用的 `MediaStaff`、或同时绑定多条：**拒绝本人范围**，不回退成"本门店"或"本品牌"；
- 绑定到已停用 `MediaStaff` 的 User 按 B-D10 自动停用；人工停用、或恢复后失去绑定的，保持有效但无业务范围（B-D08）；
- `hq_manager` 与 `branch_manager` 不使用"本人"范围——总部按授权品牌、分公司按本分公司子树看。

### 8.4 当前权限与历史事实

- 当前 Grant 决定"现在能看什么"；
- 历史事实（列表出现、快照）保存采集当时的归属快照，不因改绑或组织调整而改写；
- 授权收缩立即缩小查询结果，但不删除历史事实。

### 8.5 未注册默认拒绝

每个资源类型必须显式声明范围规则；**没有声明就拒绝**，不套用"品牌过滤"或"全量"。

**可解析但为空**（合法的空品牌集合）返回空结果；**无法映射**（组织/品牌 ID 不存在、主数据不可用）返回 403 并记可处理问题，不返回空列表、不回退（B-D26）。

## 九、B6 管理范围与授权

### 9.1 三维

管理范围 = 角色 ∩ 组织范围 ∩ 品牌。三类必须同时满足。

### 9.2 不能授出超过自己

- 不能给别人自己没有的角色等级、品牌、组织范围；
- 不能给别人自己没有的 Capability；
- 批量操作逐条判断；被拒的进"跳过"清单，不让整批失败。
- **角色层级**：`platform_admin` > `hq_manager` > `branch_manager` > `store_staff`；只能授予**严格低于自己**的角色；只有 `platform_admin` 可以授予 `platform_admin`（B-D02）；
- **用户列表只显示严格下级与自己**；同级互不可见、不可操作（B-D02）；
- **超管可以管理其他超管，但不能停用自己**；最后一个可用超管保护不变（B-D02）。

### 9.3 读写同源

列表、详情、修改、停用、恢复、删除、批量操作使用**同一条范围判断**，杜绝"看不到但能改"。

### 9.4 最后一个管理员

系统必须始终至少有一个可用的超级管理员；禁用或删除最后一个超管必须被拒绝。

## 十、B7 数据出口

### 10.1 出口清单（1.0）

| # | 出口 | 检查内容 |
|---|---|---|
| 1 | 页面查询 | 动作权限 + 数据范围 |
| 2 | 手工同步 | 动作权限 + 目标账号在范围内 |
| 3 | 点检表 / 报表 | 动作权限 + 当前范围过滤 |
| 4 | 导出文件 | 提交时范围 + 执行时范围 + 交付前复查 |
| 5 | 媒资下载 / 签名 URL | 源对象范围 + 短期有效 |
| 6 | 原始载荷 | 高敏 Capability + 业务范围 + 审计 |
| 7 | 后台 Worker | 使用 §10.3 定义的服务身份，不伪造超级管理员 |
| 8 | AI 工具取数 | 继承调用者范围 + 行数上限 + 审计 |
| 9 | 通知 / 消息 | 只发与接收者范围相关的摘要；发送前按当前范围复查（B-D27） |
| 10 | 学习资料下载 | 动作权限 + 品牌范围 + **下载审计**（谁、何时、哪门课、文件标识、结果） |

**`data.export` 与 `report.export` 的边界**（2026-10-29 决定）：

- `data.export`：导出物以**原始对象**为主结构——账号、内容、媒资、名单；按 DataScope 过滤行，不做口径加工；
- `report.export`：导出物以**报表产物**为主结构——点检表、看板快照、明细表；绑定 `projectionId` + `outcomeSetId`，数值与页面一致；
- 点检表下钻后导出的明细仍算 `report.export`，明细行按 DataScope 过滤；
- 两者都走出口 4 的三次校验，不因"是报表"放宽。
- **导入失败行回流文件**不算 `data.export`：由本次提交人本人下载，只含本次提交的行（B-D12）。

### 10.2 交付前复查

导出、打包、媒资、通知、AI 结果与签名链接，在**交付前**再查一次：

```
当前范围是否仍覆盖产物内容
→ 不覆盖：拒绝、删除或按新范围重建
```

只在提交时查，会在撤权后继续处理；只在交付时查，会让 Worker 内部接触到超范围数据。**两头都要查。**

- **停用或撤权时立即取消该用户触发的未完成异步任务**（导出、同步等）；计划任务不受影响（B-D28）。

### 10.3 Worker 身份

Worker 不是 `User`，没有 Grant，也不继承任何角色的默认能力。只有两种身份：

| 任务类型 | 身份 | 能做什么 | 不能做什么 |
|---|---|---|---|
| 计划任务（周期同步） | 固定服务身份 | 采集相关动作；范围覆盖全平台被监控账号 | 读原始载荷、导出、改授权、改配置 |
| 用户触发任务（`data.sync.trigger`） | 继承提交者 | 与提交者相同的 Capability | 超出提交者当前范围；交付前必须复查 |

计划任务之所以是平台级范围，是因为它要跑全量；这**不构成**越权，因为它没有任何"把数据交给某个人"的出口。用户触发任务反过来：范围来自提交者，撤权后交付前复查会拦住过期任务。

## 十一、B8 审计

### 11.1 记录什么

- 邀请、激活、登录成功/失败、强制下线、会话撤销；
- 用户创建、导入、停用、恢复、角色 / 范围 / 品牌变更；
- 主数据与活动名单导入的确认写入、预检 / 回流文件下载；
- 敏感字段查看、原始载荷访问、手工同步；
- 规则发布与重算、指标与模板变更；
- **活动计划与监控判定计划的创建、删除、恢复、30 天期满清除**（2026-10-30 决定：计划是跨域消费入口，删除与恢复必须可追溯）；
- 导出提交、执行、取消、交付；
- 高成本操作的授权与拒绝。

每条至少包含：谁、对谁、什么动作、什么结果、什么时候、范围摘要、**系统生成的 `reason_code`**。

**审计原因全部由系统自动生成**，不要求操作人手填业务说明；`reason_code` 使用稳定枚举（如 `invalid_password`、`scope_not_resolvable`、`media_staff_disabled`），便于筛选与统计（B-D30）。

**手机号不脱敏**（2026-10-29 决定，2026-10-30 明确到日志）：审计与应用日志都可以记录完整手机号；密码、Token、Cookie 永不记录。

**手机号不逐条记审计**：随行可见，只在批量导出（出口 4）时记（B-D29）。

### 11.2 谁能看

1.0 **只有 `platform_admin` 能看审计**；其他角色一律不可见。审计入口由独立的 `audit.read` 控制，1.0 只授予 `platform_admin`（D-41）。

> 后续如果业务要求总部或分公司查看本范围的审计，再单独开一条规则，不在 1.0 默认放开。

### 11.3 保留

保留 **一年**（D-44）；敏感读取的审计同样至少一年。到期清理与业务数据分开执行。

**到期清理**（2026-10-30 决定）：按时间窗口批量删除超过 365 天的记录，删除动作以系统身份记一条审计；**不提供单条删除，也不提供界面删除**。"不可覆盖"约束的是不修改历史记录，不约束按保留期清理。

## 十四、验收标准

用管理员或测试人员照着就能判断真假的语言写。

### B1 开户与激活

- [ ] `[自动]` 系统里没有默认管理员账号和默认密码
- [ ] `[自动]` 管理员在任何界面都看不到、也不能设置用户密码
- [ ] `[自动]` 新用户首次登录时自己设置密码
- [ ] `[自动]` 已存在的非停用手机号在导入时标为冲突，不静默改角色或范围
- [ ] `[自动]` 批量导入会被操作者的管理范围拦住越权授予
- [ ] `[手工]` 首批超管由一次性初始化创建；已有超管时该操作被拒绝

### B2 登录与会话

- [ ] `[自动]` 停用后现有会话全部失效
- [ ] `[自动]` 修改密码后其他会话全部失效
- [ ] `[自动]` 待激活账号走密码登录时，响应与"手机号或密码错误"一致
- [ ] `[自动]` 连续登录失败被限流，且不修改用户状态
- [ ] `[自动]` 同一账号连续 5 次失败后 15 分钟内正确密码也被拒；期满自动解锁
- [ ] `[自动]` 验证码 5 分钟过期、60 秒内不可重发、每天上限 10 条；连续输错 5 次作废
- [ ] `[自动]` 发送短信前校验手机号属于待激活/有效用户；不存在的号码返回与成功一致的提示且实际不发送
- [ ] `[自动]` 全局每日短信上限达到时告警并暂停发送

### B3 用户生命周期

- [ ] `[自动]` 停用不删除任何用户与授权历史
- [ ] `[自动]` 恢复用户时重新校验角色、范围、品牌，不是简单清除停用标记
- [ ] `[自动]` 恢复时不存在或无法映射的品牌 / 组织 / 专员绑定被去掉，停用对象保留；用户仍为有效，移除项记审计
- [ ] `[自动]` 最后一个可用超管不能被停用或删除

### B4 功能权限

- [ ] `[自动]` 四类角色的能力与第七章矩阵一致
- [ ] `[自动]` 后端每个写动作独立校验，前端隐藏按钮也挡不住越权
- [ ] `[自动]` 业务代码里没有 `if role == ...` 的判断
