# 不造轮子：成熟方案优先

在设计任何模块或编写任何代码之前，按顺序检查，停在第一个成立的层级：

1. **这个需要做吗？** → 不需要就不做（YAGNI）
2. **代码库里已有？** → 复用，不重写
3. **标准库能做？** → 用标准库
4. **平台/框架原生能力？** → 用原生的
5. **已安装的依赖能做？** → 用它
6. **有成熟开源方案？** → 用它，不自建（⬅ 本规则重点）
7. **一行能搞定？** → 写一行
8. **以上都不行** → 写最小可行方案

## 第 6 级判断标准

"成熟"的定义：

- GitHub ⭐ 5,000+（优先 10,000+）
- 近 6 个月有活跃维护（commit / release）
- 与项目技术栈兼容（当前只冻结了 MySQL / OSS / Docker，语言与框架未冻结——见 ADR-0004）
- 是**库**优于**独立服务**（不增加部署和运维负担）

触发场景：认证/鉴权、文件解析、全文检索、任务队列、数据校验、日志/审计、前端 UI 组件。

## 本项目的特殊约束

- **框架与 ORM 未冻结**：在 ADR-0004 关闭之前，不得以"某个库需要它"为理由反向锁定框架。
- **供应商调用不能靠通用 HTTP 客户端库解决**：raw-before-parse、ProviderCall 分段、ambiguous 语义、capability gate 都是本项目自己的合同，任何现成 SDK 都不认识。这里属于第 7/8 级自建，但**HTTP 传输、JSON 解析、OSS SDK、MySQL 驱动必须用成熟实现**。
- **云服务官方 SDK 不受星标限制**：阿里云 OSS / 短信等走官方 SDK 或平台原生能力。
- **不要为了用开源而引入独立服务**：例如为了一个队列引入 Redis，会新增一整套基础设施，并与 v2 的 MySQL 租约/fencing 设计冲突。

## 决策输出格式

选择自建时，必须写明：

```
自建：[模块名]
搜索过的开源方案：[方案1]（不适合原因）、[方案2]（不适合原因）
自建理由：[一句话]
```

选择开源时，必须写明：

```
采用：[开源项目名] (⭐数, 许可证)
用途：[用它做什么]
不用它做什么：[哪些部分仍然自建，为什么]
```

**「不用它做什么」是最容易省略也最重要的一栏。** 省了它，半年后没人分得清哪部分是库的责任、哪部分是自己的。

## 边界

- 安全相关模块（认证、加密、哈希）强烈倾向用开源库；自建安全代码的风险远高于功能代码。
- 业务逻辑高度定制的模块（账号身份、归属、检查点、媒资判同、capability 门控）倾向自建；通用框架反而增加适配成本。
- 任何新依赖都要先在 `HBECHO设计方案/architecture/adr/` 找有没有已覆盖的，再按上面的格式登记。
