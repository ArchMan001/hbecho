### 0.2 从旧系统提取的教训（新系统要避免的坑）

不是待修的技术债清单，是**设计约束的来源**。

| # | 旧系统的做法 | 造成的问题 | 新系统的约束 |
|---|---|---|---|
| 1 | 判定逻辑写在代码里，只有"标题关键词 OR-of-AND"和"背景图 SIFT"两种 | 业务想加判定维度就要发版；话题标签、口播、画面内容、时长统统判不了 | **规则必须是数据，判定能力必须原子化可组合**（§4 / §6.D） |
| 2 | 同一个"活动完成"有三套口径并存（`video_type_matches` / `matched_keywords <> ''` / `matched_keywords LIKE`） | 同一问题三个答案，总部与分公司数字对不上 | **指标口径唯一，一处定义全局引用**（§6.E1） |
| 3 | 大区/分公司 42 个名单、"活动视频"中文字面量、SIFT 阈值、三个固定视频类型全部硬编码在代码 | 组织或考核方式一变就发版 | **业务常量与组织结构全部数据化**（§6.A2 / A5） |
| 4 | 品牌隔离靠每个路由手写 `AND d.brand = ?`，5 个路由漏写 | 已存在跨品牌数据泄漏 | **数据范围在数据访问层强制注入**（§5 / §6.A3） |
| 5 | 装修判定结论存在账号表单字段 `bg_match_standard` | 下个活动一比对就覆盖，历史活动结论不可回溯 | **所有判定结果按「对象 × 规则版本 × 时点」存，不覆盖** |
| 6 | 判定重算走「先 DELETE 全部，再分批 INSERT」，无事务 | 中途失败即数据丢失 | **重算走新版本写入 → 校验 → 原子切换** |
| 7 | 长任务（导入/重算/下载/比对）跑在 HTTP 请求里靠 SSE 保命 | 客户端断开即中断，无任务记录、不可恢复重试 | **长任务一律入队，HTTP 只下单与订阅** |
| 8 | Web 用 `spawn python3` 调 CV 脚本，靠正则解析 stderr 还原进度 | 极其脆弱，契约靠日志格式 | **Python 能力服务化，暴露明确接口契约** |
| 9 | `viewer` 角色可建删活动、改关键词、触发全量重算 | 写操作无角色门禁 | **功能权限与数据范围两个维度都要有** |
| 10 | 前端 17 个静态 HTML 零框架，`settings.html` 2019 行含 1300 行内联 JS | 无法承载多角色 × 多模块 × 可配置看板 | **正规前端工程，配置化 UI** |
| 11 | 全平台零事务、session 存进程内存、`bcrypt.compareSync` 阻塞 | 只能单实例跑 | **无状态服务，可水平扩容** |
| 12 | 库里 26 张表但建库脚本只有 15 张，新旧两套模型并存 | schema 漂移，两代模型互相 JOIN | **迁移脚本单一来源（Prisma Migrate）** |

### 0.3 目标态容量测算

**输入参数**（业务给定）

| 参数 | 值 |
|---|---|
| 品牌 | 4 个：海信、日立、约克、**科龙** |
| 监控账号 | 约 **3,000** 个 |
| 平台 | 抖音 / 视频号 / **快手** / 小红书 |
| 数据更新频率 | **每周一次**（周末固定时点） |
| 内容产出假设 | 每账号每天 1 条 |

**推导结果**

| 项 | 测算 | 判断 |
|---|---|---|
| 内容年增量 | 3,000 × 365 = **109.5 万条/年** | |
| 内容 5 年总量 | ≈ **550 万条** | MySQL 分区后完全可控，**不需要大数据栈** |
| 内容特征表 | 一条内容一行（信号 JSON 列）→ 109.5 万行/年 | 与内容表同量级 |
| 判定结果 | 只对被规则圈定的候选集判定（约占 10%）→ 约 30 万行/年 | 可控 |
| API 调用量 | 3,000 画像 + 3,000 内容列表 = 6,000 次/周 → **31 万次/年**（已确认列表接口含全字段，无需逐条拉详情） | 配额预算基线 |
| 图片下载量 | 封面 109.5 万 + 头像 15.6 万 + 背景图 15.6 万 = **140 万次/年** | 头像与背景图每周下载但绝大部分未变，**pHash 去重后实际入库量可省 80%+**；下载流量成本仍在 |
| 图片存储 | 去重后约 115 万张 × 250KB ≈ **280GB/年** | |
| 视频源文件 | 按互动门槛/前 10% 筛选 → 11 万条/年 × 6MB ≈ **660GB/年** | 若全量存则 6.5TB/年，**筛选策略是必要的** |
| 存储年增 | ≈ **1TB/年** | 主要成本项，需生命周期分级 |

**核心判断：数据库不是瓶颈，成本瓶颈在三处** —— ① 外部 API 调用配额；② 对象存储与 CDN 流量；③ 视觉与多模态识别的调用量。这三条约束贯穿后面所有模块设计。

### 0.4 数据供给方式的关键约束 ⭐

商用 API 的行为模式：**单次调用返回该账号最近约 20 条内容**。同步策略是每周末重新拉取一次，新内容入库、仍在窗口内的旧内容互动数据覆盖更新。

这个模式有五个必须在设计里正面处理的后果：

| # | 后果 | 设计要求 |
|---|---|---|
| 1 | **窗口容量 vs 发布速度**：每天 1 条 → 每周 7 条，20 条窗口约 2.8 周缓冲，每周同步安全 | 但必须**监测窗口是否被填满**：若本次返回满 20 条且其中最早一条的发布时间晚于上次同步时间，说明窗口已溢出、可能有内容漏采 → 进稽核清单并告警 |
| 2 | **漏采不可补**：某周同步失败，若不在窗口滑走前重试，该周内容永久丢失 | 同步失败必须**当周内**告警重试，不能等下一周期；同步成功率是 P0 级监控指标 |
| 3 | **互动数据是"最后观测值"不是"最终值"**：一条内容在窗口内的 2~3 周被反复更新，滑出窗口后数值冻结 | 内容表必须记录 `metrics_observed_at`（最后观测时点）与 `metrics_frozen`（是否已滑出窗口）；**指标层要区分「最后观测互动量」与「发布后 N 天互动量」两种口径**，否则新旧内容不可比 |
| 4 | **排名类判定的可比性**：`前 10%`、`互动量 ≥ N` 这类判定若用不可比的观测值，结论会失真 | 排名与门槛类算子必须声明基准口径；视频源文件的下载筛选（前 10%）**必须作为同步完成后的独立筛选任务**执行，不能在同步过程中即时决定 |
| 5 | **历史深度只有 20 条**：新系统首次接入拿不到账号完整历史 | 旧系统的 39,346 条内容 + 5,752 条快照 + 1.6 万张素材是**不可再生的**，必须一次性导入新库并标记来源；这是唯一的机会 |

## 1. 产品定位与目标

**一句话**：面向海信 / 日立 / 约克 / 科龙四大品牌、全国分公司与近万家门店的新媒体运营赋能平台——把「数据供给 → 内容理解 → 规则判定 → 指标度量 → 看数分析 → 任务下发 → 内容赋能 → 学习成长」串成闭环，让业务自己定规则、自己配看板、自己拉数。

### 五个目标

| 目标 | 落地抓手 |
|---|---|
| 全品牌统一数据家底，周期自动更新，素材与历史永久留存 | §6.B 数据供给与资产层 |
| **判定能力原子化、规则业务自配**，改规则当天生效且可重算历史 | §6.C + §6.D 识别能力与规则引擎 |
| **指标与看板由配置驱动**，不是写死的报表 | §6.E 指标与看板层 |
| 四类角色 × 四个品牌，权责清晰、数据安全 | §5 角色与权限模型 |
| 内容赋能与能力成长闭环，好经验能下沉到一线 | §6.F 业务应用 + §6.G 学习平台 + §6.H AI 能力 |

### 三条路线基调

| # | 决定 | 含义 |
|---|---|---|
| 1 | **数据来源用商用 API，不自研爬虫** | 工程重心从"能不能拿到数据"转向"拿到的数据怎么用"。代价是引入配额、成本与窗口约束（§0.4）。当前 1 家供应商，架构上按多供应商设计，为未来接第二家留位 |
| 2 | **判定用规则引擎，不写在代码里** | 原子算子（研发提供）+ 可组合规则（业务配置）+ 版本化 + 判定快照 |
| 3 | **素材应存尽存，但视频源分级筛选** | 头像 / 封面 / 主页背景每次同步都下载存档（含历史版本）；视频源文件按互动门槛或排名前 N% 筛选后下载 |

**明确不做**：自研爬虫、引入大数据栈（Hudi / Iceberg / Spark，量级不需要）、程序化自动投流、自研大模型、跨企业 SaaS 多租户、旧系统逐步改造式迁移。

## 2. 设计原则

这九条是后续每个模块设计的评审标准。

| 原则 | 具体含义 |
|---|---|
| **1. 事实不可变，判定可重放** | API 原始响应落 ODS 后只增不改；所有"是否达标"都是可重算的派生结果，带规则版本号 |
| **2. 能力原子化，规则可组合** | 判定能力拆成参数化算子；业务规则是算子的布尔组合，存在数据库而非代码 |
| **3. 识别与判定解耦** | 昂贵的识别（视觉/ASR）结果落特征表；判定只读特征表做纯计算。规则可任意重跑而不重新识别 |
| **4. 代价感知执行** | 算子声明成本档位；执行器先跑低档算子剪枝，只对残余候选集跑高档算子。成本控制由引擎保证，不靠人自觉 |
| **5. 口径唯一** | 每个指标在指标字典定义一次，看板 / 报表 / 导出 / AI 取数全部引用同一定义，禁止在业务代码里手写聚合 |
| **6. 权限双维度且在数据层收口** | 功能权限（能不能做）与数据范围（能看哪些行）正交；范围过滤由框架强制注入 |
| **7. 长任务一律入队** | HTTP 只负责下单与订阅进度；任务有记录、可重试、可恢复、可查历史 |
| **8. 契约先行、类型贯通** | Zod schema 定义请求响应，Prisma 生成数据类型，前端 / Worker / Agent 共享 `packages/domain` |
| **9. 全链路可观测可审计** | 同步、识别、规则变更、重算、导入、AI 调用、取数全部留痕：谁、何时、用哪个版本、产出什么、花了多少配额与 token |

### 五条架构红线

1. **数据供给 / 识别 / 判定 / 应用四平面解耦**：换供应商不影响规则；识别服务挂了不影响出报表；改规则不需要重新取数。
2. **MySQL 主库是唯一事实来源**：任何子系统（AI、BI、知识库）不许自建影子业务库。
3. **昂贵调用统一走网关**：外部 API 与模型调用必须过配额守卫（预算、限流、缓存、计量、审计），业务代码不得直连。
4. **AI 工具只有受限权限**：Agent 调平台数据必须走内部服务并继承调用者的 DataScope，只读、表白名单、行数上限、字段脱敏、全量审计。**AI 不能成为越权旁路**。
5. **Python 只做 CV / 音视频 / 数据科学**，以 HTTP 服务暴露明确契约，业务逻辑不进 Python。

## 4. 分层能力模型（全文骨架）

把"从原始数据到业务结论"拆成六层，**L3 及以上全部是业务可配置的数据，不是代码分支**。

```
L6  看板 / 报表      卡片 = 指标 + 维度 + 图表 + 阈值着色 + 下钻      ← 业务配置
L5  指标 Metric      分子（达标定义）/ 分母（人群）+ 聚合粒度 + 口径说明 ← 业务配置
L4  达标定义 Criterion  带量词的判定：存在≥N条命中规则R / 全部规则均命中 ← 业务配置
L3  规则 Rule        算子的布尔组合（AND/OR/NOT），作用于单一对象      ← 业务配置
────────────────────────────────────────────────────────────────────
L2  算子 Operator    参数化原子判定能力，声明依赖信号与成本档位         ← 研发提供
L1  特征信号 Signal  从原始数据与素材抽取的可判定特征                  ← 研发提供
L0  原始事实         API 原始响应 + 归档素材（应存尽存）
```

### 一个例子串起六层

| 层 | 实例 |
|---|---|
| L0 | API 返回的某条抖音视频完整 JSON + 归档的封面图与视频源文件 |
| L1 | 抽出信号：`title`、`hashtags=[#海信中央空调,#618]`、`duration=42s`、`published_at`、`asr_text`、`cover_ocr_text`、`cover_objects=[空调室内机,人物]` |
| L2 | 算子：`published.within_window`(0档)、`hashtag.includes_any`(0档)、`text.contains_any`(0档)、`vision.content_contains`(3档) |
| L3 | 规则「618 活动视频」= `published.within_window(活动窗)` **AND** `hashtag.includes_any([#618,#海信618])` **AND** ( `text.contains_any([新风,除菌])` **OR** `vision.content_contains(空调室内机)` ) |
| L4 | 达标定义「活动视频完成」= 该专员在活动窗内**存在 ≥1 条**内容命中规则「618 活动视频」 |
| L5 | 指标「活动视频完成率」= 分子（满足上述达标的专员数）/ 分母（参与本活动且认证通过的专员数），支持大区 / 分公司 / 门店粒度 |
| L6 | 点检表的「活动视频完成人数 + 完成率」两列，按分公司分组，完成率 < 60% 标红，可下钻到未达标名单 |

### 代价感知的短路求值（成本控制的引擎机制）

上例中规则有 4 个算子，成本差异巨大。执行器**按成本档位分阶段执行**：

```
阶段0（0档，SQL/特征表，免费）  published.within_window + hashtag.includes_any + text.contains_any
                                3,000 条候选  →  剪到约 100 条
阶段3（3档，视觉模型，付费）     仅对剩余仍需判定的约 100 条执行 vision.content_contains
                                → 实际付费调用 100 次，而非 3,000 次
```

规则编排器在发布前**预估并展示「本规则将触发约 N 次高成本调用，预计费用 X」**，业务可见可控。这把你描述的"先圈定再判定"从人工纪律变成了引擎保证。

### 新增一个考核维度的完整路径

| 步骤 | 谁做 | 是否发版 |
|---|---|---|
| 1. 需要新识别能力时，注册算子 | 研发（一份参数 schema + 一个纯函数 + 一组单测） | 是（轻量） |
| 2. 配置规则（算子布尔组合） | 业务 | 否 |
| 3. 配置达标定义 | 业务 | 否 |
| 4. 配置指标 | 业务 | 否 |
| 5. 把指标拖到看板 / 报表 | 业务 | 否 |

**已有算子够用时，全流程零发版。**

### 规则表达能力边界（明确画线）

L3 只做**单个对象内的布尔组合**，L4 只做**存在量词**。以下不在表达范围内，也不计划支持（需要时走"新增专用算子"，不开放脚本沙箱）：

- 跨内容的时间序列关系（如"连续 3 周每周至少 1 条"）
- 相对自身基准的比较（如"超过该账号自己近 30 条均值的 2 倍"）
- 需要先算全体再判个体的排名（如"分公司内前 10%"——若确需，以预计算信号形式提供，即排名在 L1 就算好，L2 只做 `>=` 比较）

这条边界是刻意的：换来可视化编辑、静态分析、血缘追踪和零沙箱风险。

## 5. 角色与权限模型

权限是**两个正交维度**，必须分开建模。

### 5.1 四类角色 × 品牌

| 角色 | 品牌范围 | 组织数据范围 | 功能权限特征 |
|---|---|---|---|
| **超级管理员** | 全部 4 个品牌 | 全部 | 全部功能：系统配置、用户与组织管理、算子/规则/指标/看板/报表配置、知识库与学习内容管理 |
| **总部人员** | **限定品牌**（一个或多个） | 授权品牌下全部大区 / 分公司 / 门店 / 专员 | 业务全功能；可创建、修改授权品牌内分公司和经销商主档；可管理下级人员并查看完整手机号；可配置规则、报表与看板、审核知识库、上传学习内容、下发任务 |
| **分公司人员** | 随所属分公司的品牌 | **仅本分公司**及下属门店与专员 | 可查看同分公司工作人员基本资料但不可管理同级；可管理本区经销商人员；看数、下发本区任务；点检表与明细表只读且限本区；不可配置报表模板、看板和规则 |
| **经销商人员** | 随所属门店的品牌 | **仅本人**的账号与内容；同一时刻一人一店 | 看自己的数据与内容、接收与回报任务、学习、使用 AI 内容工具 |

### 5.2 两个维度分别怎么建模

**维度一：功能权限（Permission）** — 能不能执行某个动作

- `roles`（角色）→ `role_permissions` → `permissions`（权限点，如 `report.configure` / `rule.publish` / `campaign.create` / `knowledge.review`）
- 权限点粒度到"资源 + 动作"，前端菜单与按钮、后端接口守卫共用同一份定义
- 支持给个人叠加/剥离权限点（`user_permissions` 覆盖层），应对"某个分公司经理特批可配报表"这类例外

**维度二：数据范围（DataScope）** — 能看到哪些数据行

用户的范围 = `{ 品牌集合, 组织节点集合, 是否仅限本人 }`，在 Repository 层强制注入，越权抛 403 而非返回空集。

### 5.3 范围规则按资源类型声明（关键设计）

**DataScope 不是全局一套规则**。不同资源类型的范围语义不同：

| 资源类型 | 范围规则 | 说明 |
|---|---|---|
| 业务数据（账号 / 内容 / 判定 / 指标 / 任务） | 品牌 **AND** 组织层级 **AND**（经销商角色时）仅本人 | 标准规则 |
| **学习平台内容**（课程 / 资料 / 题库） | **仅按品牌隔离，不按组织层级下钻** | 四个角色都能访问本品牌的全部学习内容 |
| 组织与用户管理 | 超管管理全部；总部管理授权品牌内组织与下级人员；分公司可查看同分公司同级、管理本区经销商人员；经销商仅本人 | 读写边界不同，写操作还需校验 GrantBoundary |
| 系统配置 / 算子注册 | 仅超级管理员 | 不受品牌维度约束 |
| 知识库（产品 / 营销） | 按品牌 + 按知识库可见性配置 | 部分知识库可能跨品牌通用 |

实现上：每个资源类型在代码里声明自己的 `ScopeStrategy`，框架按策略生成过滤条件。**新增资源类型必须显式声明策略，缺省拒绝访问**（fail-closed），避免旧系统"忘记写 brand 过滤"那类漏洞。

### 5.4 已确认的人员与组织权限

- 总部人员可创建、修改授权品牌内的分公司和经销商主档；组织合并、停用和跨品牌操作保留给超级管理员。
- 总部人员默认可查看授权范围内完整手机号；批量导出仍使用独立权限点。
- 同一分公司的工作人员可互相查看基本资料，但不可修改、禁用、调岗、重置密码或授权同级人员。
- 总部用户可负责一个或多个品牌；DataScope 取授权品牌集合，前端同时支持单品牌查看和多品牌聚合。
- 经销商人员同一时刻严格一人一店；调店通过带生效区间的关系变更处理，不支持一人同时管理多店。
- 分公司人员对点检表和明细表只读、限本区，不可配置模板（已在指标与看板模块确认）。

## 6. 模块地图

九个模块组：A 平台底座 · B 数据供给与资产 · C 识别能力 · D 规则引擎 · E 指标与看板 · F 业务应用 · G 学习平台与成长 · H AI 能力 · I 运维治理。

每个模块的「⚠️ 设计注意点」是**已识别但留待模块细化时处理的问题**，不是待决风险。

### A. 平台底座

| 模块 | 职责 |
|---|---|
| **A1 身份认证** | 手机号 + 密码；邀请制开户（管理员批量导入手机号 + 角色 + 组织归属 → 用户设密码激活）；会话存 Redis；登录风控（IP + 账号双维度限速）；密码策略与重置 |
| **A2 组织与主数据** | 品牌（4 个）/ 大区 / 分公司 / 板块 / 门店 / 专员（人）/ 平台账号主档；层级关系与变更历史；主数据导入、合并、账号归属冲突稽核 |
| **A3 权限中心** | 功能权限（角色 × 权限点 + 个人覆盖层）与数据范围（DataScope + 按资源类型的 ScopeStrategy）双维度，见 §5 |
| **A4 审计与操作日志** | 谁在何时改了哪条规则/指标/看板、触发了什么任务、导出了什么数据、看了谁的数据；关键对象变更前后快照 |
| **A5 配置中心** | 分作用域（全局 / 品牌 / 活动）+ 类型化 + 版本化的配置项；同步频率、识别阈值、模型档位、配额预算、下载筛选门槛均可热调 |
| **A7 媒资与文件服务** | 统一抽象 OSS（图片 / 视频源 / 导出件）+ CDN（加速与图片处理样式）+ VOD（课程与样片）；私有资源签名 URL；上传 / 转码 / 回调 |
| **A8 配额与成本中心** | 外部 API 调用、视觉识别、大模型 token 的预算、限流、用量归因（按品牌 / 活动 / 模块 / 用户）、超限告警与自动降级 |

**⚠️ A2 设计注意点**

- **归属关系带生效区间且同一时刻独占**：一个专员同一时刻只归属一家门店，一个平台账号同一时刻也只归属一家门店。人员或账号关系出现区间重叠即判为数据异常并告警（旧系统实测 52 组 `sec_uid` 重叠属历史数据质量问题，导入时进 B7 稽核清单人工裁决）。
- **组织变更历史**：门店换分公司、专员离职换人、账号转交时，历史考核结果应保留在原归属下（考核的是"当时"）。所以考核归集必须按**判定时点**解析归属，不能按当前归属回溯改写历史。

**⚠️ A8 设计注意点**

- 配额守卫要区分**硬限**（超预算直接拒绝，如视觉全量回溯）与**软限**（超预算告警但放行，如日常同步），否则会误伤正常业务。

### B. 数据供给与资产层

| 模块 | 职责 |
|---|---|
| **B1 供应商适配层** | `DataProvider` 统一接口：`resolveAccount` / `fetchProfile` / `fetchContentList` / `fetchContentDetail`；字段映射与错误码归一。**当前 1 家供应商，架构按多家设计**（未来接第二家用于补齐字段、互为备份、交叉校验） |
| **B2 同步编排** | 同步计划（按品牌 / 平台 / 账号分组，周期与优先级可配，默认每周末）；BullMQ 调度 + 重试 + 断点续跑；调用前过 A8 配额守卫；同步批次与每账号结果可追溯 |
| **B3 原始层（ODS）** | 供应商响应原文 + 请求元信息（供应商 / 接口 / 参数 / 时间 / 批次）**只增不改**永久留存。这是"改规则不重取数"与"换供应商可回溯对账"的物理前提 |
| **B4 明细层（DWD）** | 归一化的平台中立模型：账号画像快照、内容明细、互动指标时序、主页装修素材记录。四平台字段差异在此收敛 |
| **B5 资产归档管道** | **头像 / 封面 / 主页背景每次同步都下载**，按 sha256 + pHash 去重，变化则新增版本（换图有痕）；**视频源文件按筛选策略下载**（见下）；资产 ↔ 内容 ↔ 账号三向关联；OSS 生命周期分级 |
| **B6 视频源筛选任务** | 同步完成后**独立执行**的筛选任务。下载条件为「**互动量门槛 或 全体排名前 N%（阈值走 A5 可配） OR 落在含 ASR 算子的考核项候选集内**」→ 下载 → 抽音轨（ffmpeg）→ 归档。需对规则引擎暴露 `requestSourceDownload(contentIds, reason, priority)` 接口 |
| **B7 数据质量与稽核** | 窗口溢出检测、同步成功率与缺口检测、账号标识一致性、停更检测、资产缺失清单、供应商数据异常（互动数倒退、字段突然为空）、多供应商冲突裁决 |
| **B8 存量数据导入** | 一次性导入旧系统的 39,346 条内容 + 5,752 条快照 + 1,294 门店 + 1,334 账号 + 1.6 万张素材，标记 `source='legacy'`；这批数据不可再生（§0.4） |
| **B9 元数据与血缘** | 表 / 字段 / 信号 / 算子 / 规则 / 指标全部注册；指标 → 达标定义 → 规则 → 算子 → 信号 → 上游表的完整血缘；供看板配置器与取数 Agent 读取语义 |

**⚠️ B2 设计注意点（来自 §0.4 的窗口约束）**

- **同步失败必须当周内重试完成**，不能等下一周期——窗口滑走后内容永久丢失。失败告警级别设为 P0。
- **窗口溢出检测**：若某账号本次返回满 20 条且其中最早一条发布时间晚于上次同步时间，判定为可能漏采，进稽核清单。这个检测要在同步时就做，不能事后补。
- 单次同步 3,000 账号需控制节奏（供应商可能有 QPS 限制），批次拆分与间隔要可配。

**⚠️ B4 设计注意点（互动数据的观测语义）**

- 内容表必须区分 `metrics_observed_at`（最后观测时点）与 `metrics_frozen`（是否已滑出窗口不再更新）。
- 互动数据不是最终值。**指标层要提供两种口径**：「最后观测互动量」（用于当期考核）与「发布后 N 天互动量」（用于跨期可比分析）。混用会导致新旧内容不可比。

**⚠️ B6 设计注意点**

- "排名前 N%"需要全体数据到位后才能算，所以下载决策**必须**是同步完成后的独立任务，不能在同步过程中即时判断。
- 排名基准要用可比口径（见 B4），否则老内容因观测周期更长而系统性占优。
- 抽出的音轨（约为源文件 1/20 体积）常驻标准存储供 ASR 反复使用；源文件可下沉到低频/归档。

#### B5 资产分级存储策略

| 资产类型 | 下载策略 | 存储策略 |
|---|---|---|
| 头像 / 主页背景 | 每周同步时全量下载并 pHash 比对 | 有变化才新增版本入 OSS 标准型，永久保留全部历史版本 |
| 内容封面 | 每条内容首次入库时下载 | OSS 标准型，永久 |
| 视频源文件 | **按 B6 筛选策略**（互动门槛 / 前 N%） | 近 90 天或在优秀内容池 → 标准型；其余 → 低频；超 1 年 → 归档型（生命周期自动流转） |
| 音轨（mp3） | 随视频源下载时抽取 | 标准型常驻（体积小、ASR 高频复用） |
| 课程与平台内播放的样片 | 人工上传或从优秀内容池晋升 | VOD（转码 / 加密 / 防盗链 / 播放器 SDK） |
| 导出件 | 用户下单生成 | OSS 临时目录，7 天生命周期自动清理 |

### C. 内容理解与识别能力层（提供 L1 信号 + L2 算子的底层能力）

| 模块 | 职责 |
|---|---|
| **C1 文本信号抽取** | 从标题 / 正文结构化抽出：话题标签（`#xxx`）、@提及、POI 定位、链接、分词与关键短语。0 档成本，入库即跑 |
| **C2 视觉识别服务** | 对任意图像提供分档识别能力（见下表），统一入参出参，结果按指纹缓存 |
| **C3 语音与视频理解** | ASR 口播转写；视频抽帧 → 关键帧视觉识别；分镜与场景标签；字幕 OCR；产品/机型识别 |
| **C4 特征存储与刷新** | 识别结果落 `content_features` / `account_features`（**一个对象一行，信号存 JSON 列**），带信号版本与产出时间；能力升级后可按范围重跑；**规则判定只读特征表，绝不直接调外部服务** |
| **C5 向量与相似检索** | 图像与文本 embedding 入向量库，支撑以图搜图（找同款背景图 / 抄袭检测）、语义相似内容聚类、RAG 检索 |

#### C2 视觉识别能力清单（分档）

| 档 | 能力 | 实现 | 典型用途 | 成本 |
|---|---|---|---|---|
| 0 | 感知哈希 pHash / dHash | Python 本地 | 素材是否变更、近似重复检测 | ~0 |
| 1 | 模板特征匹配 SIFT / ORB | Python 本地（旧系统已验证可用） | 主页背景是否与活动标准图一致；失败占位图识别 | ~0 |
| 2 | 文字识别 OCR | 云 OCR | 背景图/封面上是否有活动 slogan、指定机型、价格 | 低 |
| 3 | **目标与内容识别** | 视觉大模型 qwen-vl | **图中是否包含指定内容**（室内机 / 门头 / 品牌 logo / 人物 / 施工场景 / 竞品），开放词表，业务用自然语言描述标的 | 中高 |
| 4 | 图像向量化 | 嵌入模型 | 以图搜图、相似聚类、风格一致性 | 低 |
| 5 | 组合判定 | 编排 0~4 | 品牌规范检查（logo 位置 + 主色 + 必含元素 + 禁含元素） | 视组合 |

**⚠️ C2 设计注意点（成本控制的三个关键设计）**

1. **缓存键设计**是成本控制的第一道闸门。缓存键必须是 `图像指纹 + 能力标识 + 能力版本 + 参数指纹` 四元组：只按图像指纹缓存会导致不同标的读到错误结果；参数指纹里含自然语言标的描述，**业务把"室内机"改成"空调室内机"就是一次全量缓存击穿**——明明是同一意图却重跑全部。缓存键一旦上线再改等于历史缓存全部作废，所以要在模块设计阶段定稿。缓解方向：标的用「受控标的库」（业务从预定义标的中选，而非自由输入），标的库条目可维护同义描述。
2. **回溯重识别必须是显式的、带费用预估的操作**，不能是界面上一个"重新识别"按钮。新增算子后业务的第一反应必然是"把历史全部重跑看看"，按 §0.3 量级一次全量回溯就是百万级调用。设计上：回溯任务必须指定范围（时间 / 品牌 / 活动 / 账号）+ 展示预估调用次数与费用 + 走审批 + 走 A8 硬限。
3. **视频理解成本比图像高一个数量级**（一条视频抽 10 帧 = 10 次图像调用），必须硬限制在优秀内容池范围内，不开放全量。

**⚠️ C4 设计注意点**

- 特征表用「一个对象一行 + 信号 JSON 列」而非「一个信号一行」。按 §0.3 量级，前者 109.5 万行/年，后者上千万行/年。
- 信号版本要分能力粒度记录（`{"cover_objects": {"v": 2, "at": "..."}}`），这样升级某一个识别能力时只重跑该信号，不用全表重刷。

### D. 规则引擎 ⭐

本次设计与旧系统**思路完全不同**的部分，也是核心价值区。

| 模块 | 职责 |
|---|---|
| **D1 算子注册中心（L2）** | 每个算子声明：唯一标识、作用对象（内容 / 账号 / 专员 / 门店）、依赖信号、参数 JSON Schema、返回（命中 + 置信度 + 证据）、**成本档位**。研发新增算子只需注册，不改规则相关代码 |
| **D2 规则编排器（L3）** | 可视化编辑：算子实例 + AND/OR/NOT 嵌套表达式树（JSON DSL）；**试运行**（选真实样本看命中与证据）；**命中率预估**；**高成本调用次数与费用预估** |
| **D3 达标定义（L4）** | 带存在量词的判定：`该专员在时间窗内存在 ≥N 条内容命中规则 R` / `其主账号命中规则 B` / `指定规则集合全部命中`。这是"最终完成"这类复合判定的正式载体 |
| **D4 版本与生效管理** | 规则 / 达标定义不可变版本化（草稿 → 试运行 → 待审 → 发布 → 归档）；活动绑定具体版本；变更留审计；规则模板与跨活动复制 |
| **D5 判定执行与快照** | 批量判定 Worker：**代价感知分阶段执行**（§4）→ 写判定结果（命中 + 规则版本 + 证据明细 + 判定时点）；**证据可下钻**（业务能看到"为什么这条算达标"）；新内容入库触发增量判定 + 人工/事件触发批量重算双模 |
| **D6 重算与对账** | 重算走「新版本写入 → 校验 → 原子切换」；范围可收窄（活动 / 分公司 / 账号 / 时间段）；两版本可对账出差异清单 |

#### 首批算子清单（按作用对象分类，均为单对象布尔判定）

| 对象 | 算子 | 成本档 |
|---|---|---|
| 内容 · 时间 | `published.within_window` / `published.on_weekday` | 0 |
| 内容 · 文本 | `text.contains_all` / `contains_any` / `not_contains` / `regex`；`hashtag.includes_all` / `includes_any`（**标题带指定话题**）；`mention.includes`；`poi.in_list` | 0 |
| 内容 · 属性 | `duration.between`；`content_type.equals`（视频 / 图文）；`platform.in_list` | 0 |
| 内容 · 表现 | `metric.gte`（互动门槛）；`metric.rank_top_percent`（排名前 N%，排名在 L1 预计算） | 0~1 |
| 内容 · 视听 | `ocr.contains`（画面文字）；`speech.contains`（口播提到卖点）；`vision.content_contains`（**画面包含指定内容**）；`vision.similar_to_template`；`scene.in_list` | 2~3 |
| 账号 | `profile_bg.matches_template`（**主页装修判定**）；`profile_bg.contains_content`；`avatar.matches_template`；`nickname.matches_pattern`；`bio.contains`；`follower.gte`；`post_freq.gte` | 0~3 |
| 专员 / 门店 | `certified.is_true`；`in_campaign.is_true`；`store_tier.in_list`；`org.in_scope` | 0 |

#### 判定链路（识别与判定解耦）

```
内容入库 → 【0档信号抽取】（C1 文本信号，即时）           → 特征表
                                                            ↓
规则发布/活动开启 → 【判定任务 D5】
    阶段0：0档算子过滤（SQL + 特征表）  3,000 条 → 约 100 条候选
    阶段2：2档算子（OCR）仅对候选执行   → 结果写回特征表（可复用）
    阶段3：3档算子（视觉模型）仅对残余候选执行 → 结果写回特征表（可复用）
    → 写判定结果 + 证据
                                                            ↓
                                          指标预聚合（E2）→ 看板 / 报表
```

**这个链路是整个设计的关键**：贵的识别只对被便宜规则圈定的小集合执行，且结果永久落特征表可复用。规则改了重跑判定几乎免费——除非新规则引入了此前没算过的高档信号。

**⚠️ D2 设计注意点（规则可自配带来的新失效模式）**

旧系统里规则改动要研发发版，天然有人 review。新系统业务能自己改，就出现了一类新风险：**规则错了不会报错，只会静默产出错误的考核结果。**

真实会发生的例子：业务想配"标题含 618"，误用 `text.contains_all(['6','1','8'])` → "2018 年""618 元""1680"全部命中；或把两个关键词放进同一个 AND 组而本意是 OR → 命中数归零 → 次日全国完成率暴跌 → 分公司集体投诉。

产品设计上必须有四道防线：

1. **强制试运行**：发布前必须在真实样本上跑一遍，展示命中条数、命中率、抽样命中内容及其证据。
2. **命中率突变告警**：新版本与上一生效版本的命中率偏离超过阈值时，要求二次确认并填写原因。
3. **发布审批**：影响考核的规则（绑定到活动的）发布需审批；沙箱规则（未绑定活动）可自由试。
4. **双版本差异对账**：D6 提供"切换前后差异清单"，能看到哪些对象的达标结论发生了翻转。

**⚠️ D5 设计注意点**

- 证据（evidence）要存到能支撑申诉的粒度：命中了哪个算子、匹配到哪个词/哪个标的、置信度多少、用的哪张图。经销商对考核结果有异议时，这是唯一的对话依据。
- 判定结果按「对象 × 规则版本」存，不覆盖。旧系统把装修结论存在账号单字段导致历史不可回溯，不能重演。

### E. 指标与看板层（L5 / L6）

| 模块 | 职责 |
|---|---|
| **E1 指标字典（L5）** | 指标 = 唯一编码 + 业务口径说明 + 分子（引用 D3 达标定义 或 聚合表达式）+ 分母（人群定义）+ 支持粒度 + 单位格式 + 责任人 + 生效版本。含**分子分母同源校验** |
| **E2 预聚合引擎** | 按「活动 × 组织粒度（大区 / 分公司 / 门店 / 专员）× 周期」生成 ADS 宽表；幂等 upsert；判定完成后自动触发；重算有任务记录 |
| **E3 看板配置器（L6）** | 看板 = 卡片列表；卡片 = 指标 + 维度 + 图表类型（数值卡 / 表格 / 柱 / 折线 / 排行榜 / 热力）+ 筛选器 + 排序 + 阈值着色 + 下钻路径。看板可按角色与品牌授权、可复制为模板、可设为角色默认首页 |
| **E4 报表模板** | 点检表、内容明细表、稽核表统一为「报表模板 = 列定义（每列引用一个指标或字段）+ 分组 + 排序 + 样式 + 表头层级」；模板可版本化、可复制、可按品牌差异化 |
| **E5 自助分析** | 业务自选维度 / 指标 → 即席查询 → 保存为个人或共享看板；走语义层不写 SQL；带行数与超时上限 |
| **E6 导出中心** | 导出下单进队列 → Worker 生成 → OSS → 下载中心；含图 Excel 走同一通道；任务可查历史、可重下、有生命周期 |

**"看板不写死"的含义**：旧系统的 14 列点检表是硬编码在代码里的特殊逻辑。新系统里它就是**一个报表模板实例**——列定义引用指标字典里的指标，分组用组织维度，样式与阈值着色是配置。改一列不发版。

**⚠️ E1 设计注意点**

- **分子分母必须同源校验**。旧系统实测存在一个真实缺陷：`最终完成` 的分子条件不要求"认证通过"，但分母是"认证通过专员数"，导致比率理论上可以超过 100%。指标字典必须在保存时校验分子人群 ⊆ 分母人群，不满足则拒绝保存或强制标注。
- **口径要带观测语义**（来自 §0.4）：互动类指标必须声明用「最后观测值」还是「发布后 N 天值」。同一张报表里混用两种口径会让新旧内容不可比。
- **分母定义待业务确认**：旧系统用"认证通过专员数"，但实测认证通过率 99.6%，分母几乎等于账号总数，完成率的区分度很低。是否改为"活动参与专员数"需要业务决策。
- 指标要能标注**「派生自哪个规则版本」**，规则一改，依赖它的指标要提示"历史数据口径已变"。

**⚠️ E2 设计注意点**

- 预聚合的重算范围要能收窄到活动 + 组织节点，否则 4 品牌全量重算会成为例行负担。
- ADS 宽表要保留 `computed_at` 与 `rule_version_set`，让看板能显示"数据截至何时、基于哪版规则"。

**⚠️ E3 设计注意点**

- 看板配置权限仅超管 + 总部（§5.1），但**卡片的数据仍要过调用者的 DataScope**：同一张看板配置，分公司人员打开时只看到本区数据。配置与数据范围是两件事，不能混。

**⚠️ F2 设计注意点**

- 活动必须绑定**规则的具体版本**而非规则本身。否则规则一改，历史活动的考核结论会被静默改写。
- 参与范围的三种表达（全品牌 / 按分公司 / 按名单）要能混用与增量调整（活动中途加入门店），且范围变更要留痕——分母变了完成率就变了。

**⚠️ F6 设计注意点**

- 自动核销与人工确认要能共存：有些任务（如"更换主页背景图"）可自动判定，有些（如"参加线下培训"）只能人工。任务类型要声明核销方式。

### G. 学习平台与成长体系

独立成组，因为它有自己的内容体系、权限规则（§5.3：仅按品牌隔离，四角色均可访问）和成长机制。

| 模块 | 职责 |
|---|---|
| **G1 学习内容管理** | 课程（视频走 VOD）、图文资料、产品手册、标杆案例；按品牌 / 岗位 / 知识点 / 产品线多维分类；上传、编辑、上下架、版本管理；总部人员维护 |
| **G2 学习中心（学员端）** | 课程目录与检索；播放器（**倍速、进度记忆、断点续播**、防拖拽可选）；资料在线预览与下载控制；我的学习（在学 / 已完成 / 收藏 / 错题） |
| **G3 AI 智能出题** | 从课程视频转写与图文内容自动生成题目（单选 / 多选 / 判断 / 简答），含答案与解析；**生成结果必须经总部人工审核后才进正式题库**；支持按知识点定向出题与难度分级 |
| **G4 题库与考核** | 题库管理（人工录入 + AI 生成 + 审核）；随堂测验、章节测试、认证考试；组卷策略（随机 / 按知识点配比）；判分与错题本；补考规则 |
| **G5 成长体系** | 积分（学习时长 / 完成课程 / 通过考试 / 答题正确率 / 任务完成）；等级与称号；勋章与成就；**排行榜**（个人 / 门店 / 分公司，分品牌）；学分要求与必修课；认证证书 |
| **G6 学习任务与督学** | 总部 / 分公司下发学习任务（指定课程 + 截止时间 + 目标人群）；完成率看板；与 F6 任务闭环统一入口 |
| **G7 学习效果分析** | 学习行为与运营表现的关联分析：学过某课程的专员，其账号质量评分 / 活动完成率是否更高 → 反向指导课程优先级与必修课设置 |

**⚠️ G3 设计注意点**

- AI 出题**必须人工审核**才能进正式题库。产品知识（机型参数、能效、适用面积）一旦出错并进入考核，会造成一线知识污染，比不出题更糟。审核界面要展示题目 + 答案 + **来源片段引用**（出自哪个课程的哪一段），审核人能快速核对。
- 出题要能标注知识点，否则组卷时无法按知识点配比。

**⚠️ G5 设计注意点**

- **防刷是必须的**：挂机播放（视频后台播放不看）、连点答题、多设备同时学习。至少要有：播放心跳与焦点检测、答题最短用时校验、同一账号并发学习限制、异常行为进稽核清单。积分一旦与奖励挂钩，刷分动机就是真实的。
- 排行榜要分品牌 + 分组织层级，避免大分公司天然占优；建议同时提供绝对值榜与人均榜。

**⚠️ G7 设计注意点**

- 这是相关性分析不是因果推断，结论表述要谨慎（"学过 X 课程的专员完成率高 12%"不等于"学 X 能提升 12%"）。用于排优先级可以，用于考核归因不行。

### H. AI 能力

| 模块 | 职责 |

| **H1 AI 网关** | 统一出口：模型档位管理（Provider / 端点 / Key / 参数）、按任务路由、失败降级与重试、结果缓存、**token 与成本计量**、全量调用审计；Key 走密钥引用不落明文；与 A8 配额中心联动 |

| **H4 知识审核工作流** | 总部人员审核入库知识：待审队列、内容预览与切片查看、通过 / 驳回 / 修订、生效版本管理。自动推送的文档同样入待审队列，不直接生效 |
| **H5 脚本分析与仿写** | 亮点提炼、脚本结构还原（钩子—展开—号召）、优缺点诊断、分镜脚本 + 完整口播生成；输入复用 C3 的视听理解结果 |
| **H6 内容合规审核（RAG）** | 检索产品与营销知识库 → 校验机型参数正确性、政策口径一致性、违禁词与绝对化用语 → 输出结论 + 依据引用；**不通过则回退重生成，只有通过的才允许分发** |
| **H7 营销 Agent 对话** | 多轮对话 + 工具调用：查平台数据（指标 / 账号 / 内容 / 规则）、查知识库、生成内容、创建任务。**工具继承调用者的 DataScope**，只读、表白名单、行数上限、字段脱敏、全量审计 |
| **H8 规则辅助生成** | 业务用自然语言描述考核要求 → AI 推荐算子组合草案 → 人工确认后落为规则草稿。降低 D2 规则编排器的上手门槛 |
| **H9 评测与反馈闭环** | Prompt / 流程 / 识别能力的版本管理与离线评测集；脚本采纳率与发布后表现回流；识别准确率抽样标注与回归；用于判断"哪类脚本真有效" |

**⚠️ H1 设计注意点**

- **图像入参一律用 OSS 签名 URL，禁止传 base64**。视觉模型（qwen-vl）调用如果内联 base64 图片，图片就变成 ECS 的公网出流量（¥0.72/GB），既产生费用又挤占 §11.1 的 30Mbps 公网带宽，还拉长单次调用延迟。签名 URL 由 A7 媒资服务签发，有效期按调用超时设置。这条约定要在 AI 网关的入参校验里强制：检测到内联图片数据直接拒绝，不留"临时先这样"的口子。
- 同理，H5 脚本分析复用 C3 的视听理解结果时，传的是特征表里的结构化信号与素材引用，不是原始音视频。

**⚠️ H6 设计注意点**

- **知识库质量是审核能力的天花板**。知识库召回率不达标时上线自动审核，比不审更危险（会给错误内容盖上"已审核"的章）。上线前必须用历史脚本做抽样验证，达标前保留人工兜底。
- 审核结论必须给出**依据引用**（引自哪份文档的哪一段），否则业务无法判断该不该信，也无法申诉。

**⚠️ H7 设计注意点**

- 这是最容易出安全事故的模块。Agent 的数据工具必须是**平台内部服务调用**并强制传入调用者身份，而非让 Agent 自由生成 SQL 或调用无鉴权接口。经销商问"我们分公司谁的完成率最低"时，如果工具没继承范围，就是一次越权。
- 对话历史与工具调用链要全量留痕，用于事后审计与效果分析。

### I. 运维与治理

| 模块 | 职责 |
|---|---|
| **I1 环境与部署** | Docker Compose 单机编排（8C32G，见 §11）；配置分环境；数据库迁移单一来源（Prisma Migrate） |
| **I2 可观测性** | 结构化日志 + requestId 贯通；队列指标（等待 / 执行 / 失败 / 积压）；**同步成功率与数据鲜度看板**（P0）；外部 API 与模型的用量、失败率、成本看板；主动告警：同步失败（P0，当周必须处理）、窗口溢出、配额将超、识别失败率异常、资产归档积压 |
| **I3 备份与恢复** | MySQL 每日全备 + binlog；OSS 版本化；**ODS 原始层是重算的唯一依据，备份优先级最高**；恢复演练 |
| **I4 安全与合规** | 最小权限、手机号等敏感字段脱敏、密钥托管、全站 HTTPS；数据来源与供应商授权凭证登记，使用范围符合服务条款；操作审计留存期限 |
| **I5 数据生命周期** | OSS 分级流转规则、导出件清理、ODS 冷归档、判定结果历史版本保留策略（建议保留当前生效版 + 最近 N 个版本，更早的归档） |

## 7. 数据模型方向

不展开字段，只定关键决策。详细 schema 在建设阶段 S1 的独立文档给出。

| # | 决策 | 理由 |
|---|---|---|
| 1 | **组织主档表化**：`brands` / `regions` / `branches` / `sectors` / `dealers`，层级用外键，关系带生效区间 | 分公司人员权限要绑在实体上；组织变更时历史考核结果留在原组织 |
| 2 | **人 / 账号 / 门店三层解耦**：`staffs`（人）+ `staff_accounts`（平台账号）+ `staff_store_relations`（归属关系，**带生效区间，同一时刻独占**） | 支持一人多平台账号、门店变更与人员流动的历史追溯。业务规则是「同一专员同一时刻只归一家门店、一个账号同一时刻只归一家门店」，所以关系表要有区间重叠约束；重叠即数据异常（旧系统实测 52 组账号重叠，属数据质量问题）；考核归集按判定时点的归属解析 |
| 3 | **用户与专员分离**：`users`（登录主体）+ `user_scopes`（品牌集合 / 组织节点集合 / 是否仅本人）+ `roles` / `permissions` / `role_permissions` / `user_permissions` | §5 双维度权限的落地 |
| 4 | **内容表平台中立**：`contents`，主键业务标识用 `(platform, platform_content_id)`；`published_at`；区分内容形态（视频 / 图文笔记）；四平台字段差异在 DWD 收敛 | 四平台并存，不能用抖音专有字段名 |
| 5 | **内容表带观测语义**：`metrics_observed_at`（最后观测时点）+ `metrics_frozen`（是否已滑出 API 窗口） | §0.4 约束 3：互动数据是最后观测值不是最终值 |
| 6 | **原始层独立**：`ods_provider_payloads`（供应商 / 接口 / 请求参数 / 响应原文 / 批次 / 时间），大 payload 落 OSS 存引用 | 应存尽存；换供应商可回溯对账；是重算的唯一依据 |
| 7 | **资产表独立**：`media_assets`（类型 / sha256 / pHash / OSS key / 尺寸 / 来源 URL / 存储层级 / 首见时间）+ `asset_bindings`（资产 ↔ 账号/内容/活动，带版本序号与生效区间） | 头像与主页背景要留历史版本；去重靠指纹；视频源要管生命周期 |
| 8 | **特征表宽表化**：`content_features` / `account_features`，**一个对象一行**，`signals` JSON 列，每个信号内嵌版本与产出时间 | §0.3 量级下，一行一信号会到千万级；且升级单个能力时只重跑该信号 |
| 9 | **规则体系表**：`operators`（注册表，含成本档位）/ `rules` + `rule_versions`（表达式树 JSON）/ `criteria`（达标定义）/ `rule_bindings`（活动 ↔ 规则版本） | 规则是数据不是代码 |
| 10 | **判定结果带版本与证据**：`judgements`（对象 / 规则版本 / 命中 / 置信度 / **证据 JSON** / 判定时点），按「对象 × 规则版本」唯一，不覆盖 | 历史可回溯；证据支撑申诉；重算走新版本原子切换 |
| 11 | **装修判定按活动 × 账号存**，不存在账号单字段 | 旧系统单字段被下个活动覆盖，历史结论不可回溯 |
| 12 | **指标与看板配置表**：`metric_definitions` / `dashboards` / `dashboard_cards` / `report_templates` / `report_columns` + ADS 宽表 `ads_campaign_org_stats`（带 `computed_at` 与 `rule_version_set`） | 口径唯一 + 看板可配置 + 秒级响应 |
| 13 | **学习域独立**：`courses` / `course_sections` / `materials` / `question_bank` / `exams` / `learning_progress` / `points_ledger`（积分流水，可追溯可冲正）/ `badges` / `certificates` | 积分必须用流水账而非余额字段，否则防刷追溯与冲正无从下手 |
| 14 | **知识库域独立**：`knowledge_bases` / `documents` / `doc_chunks` / `review_records`，向量存向量库、元数据存 MySQL | 双入库路线（接口推送 + 人工上传）统一走审核队列 |
| 15 | **存量导入带来源标记**：所有从旧系统导入的记录标 `source='legacy'` + `legacy_id` | 便于区分数据可信度与排查 |
| 16 | **大表策略**：`contents`、`judgements`、`ods_provider_payloads` 按时间分区；ODS 冷归档；预留读写分离 | 5 年 550 万条内容 + 判定结果按版本累积 |

## 8. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| **仓库** | pnpm workspace Monorepo + Turborepo：`apps/web` `apps/api` `apps/worker` `services/vision`(Py) `services/media`(Py) `packages/domain` `packages/db` `packages/rules` `packages/ui` | 领域类型与**规则 DSL 定义**集中在 packages，API / 前端 / Worker / Agent 工具共享，字段与算子变更编译期暴露 |
| **前端** | Next.js（App Router）+ React + TypeScript + Tailwind + shadcn/ui + TanStack Table/Query + ECharts | 报表密集需要强表格（虚拟滚动 / 列固定 / 分组 / 多层表头）；**规则编排器与看板配置器是复杂交互组件**；AI 流式交互生态成熟 |
| **后端** | NestJS + Fastify adapter + Zod（`nestjs-zod`） | 模块极多且要"一个模块一个模块优化"，Module/DI **强制**分层边界，对独立开发 + AI 协作最省心。旧系统已证明"靠自律维持分层"在业务压力下会失守 |
| **数据访问** | Prisma（迁移 + CRUD + 类型）+ Kysely（复杂聚合的类型安全 SQL） | ORM 管模型与迁移，报表聚合走手写 SQL 但保留类型安全。**禁止在 Service 里拼字符串 SQL** |
| **规则执行** | `packages/rules`：表达式树解释器，纯 TS 无副作用，可单测；批量判定在 Worker 内按成本档位分阶段并行执行 | 规则是数据，执行器是纯函数 → 可对任意规则版本回放任意历史数据 |
| **队列** | BullMQ + Redis | 数据同步、资产归档、视频筛选下载、信号抽取、判定重算、预聚合、导入导出、AI 流水线全部入队 |
| **会话 / 缓存** | Redis | 无状态服务，可水平扩容 |
| **数据库** | MySQL 8.0（buffer pool 8G） | §0.3 已证明量级足够；窗口函数满足组织聚合。不切 PostgreSQL |
| **Python 服务** | FastAPI：`services/vision`（pHash / SIFT / OCR 编排 / 视觉模型调用 / embedding）、`services/media`（ffmpeg 抽帧与抽音轨） | 明确接口契约，取代旧系统 `spawn python3` + 正则解析 stderr |
| **数据来源** | 商用社媒数据 API（当前 1 家，架构按多家设计） | 放弃自研爬虫 |
| **模型** | 百炼 qwen-plus / qwen-vl / qwen3-asr-flash + 云 OCR；档位化配置可灰度回退 | 避免单点依赖 |
| **AI 编排与 RAG** | 见 §9 独立决策 | |
| **对象存储** | OSS + CDN（图片处理样式）+ 生命周期分级规则；私有读走签名 URL | |
| **视频** | 阿里云 VOD：课程 + 平台内播放的样片（转码 / 加密 / 防盗链 / 播放器 SDK / 进度上报）；海量原始视频源走 OSS 分级 | 支撑学习平台倍速与进度记忆；避免 OSS 直链扛视频流量 |

| **OLAP** | 不引入。触发条件：ADS 查询 P95 > 3s 或 `judgements` > 5,000 万行 | §0.3 已证明量级不需要 |
| **部署** | Docker Compose（服务边界清晰，可平滑迁 K8s）+ Nginx | |
| **质量** | Vitest + Playwright + ESLint/Prettier + Husky + CI；**规则执行器与指标口径必须有单测**（给定数据集断言命中与完成率） | 旧系统零测试，口径改动无保护 |

## 9. AI 实现路径决策（Dify / 其他开源 / 自建）

### 9.1 四类 AI 场景的差异

| 场景 | 特征 | 关键需求 |
|---|---|---|
| ① 脚本分析与仿写（H5） | 单轮或少轮 LLM，prompt 需业务频繁调优 | Prompt 版本管理、效果回流 |
| ② RAG 合规审核（H6） | 检索双知识库 → 判定 → 给依据 | **文档解析质量**、切片可视化、引用溯源、**给总部人员的知识库管理与审核 UI** |
| ③ 营销 Agent 对话（H7） | 多轮 + 工具调用（查平台数据） | **权限上下文必须贯通**、工具可测试、调用链留痕 |
| ④ 学习平台智能出题（G3） | 结构化输出（题目 JSON schema）+ 来源引用 | Schema 约束、批量生成、来源可追 |

### 9.2 候选方案评估

| 方案 | 优势 | 劣势 |
|---|---|---|
| **Dify 自托管** | 可视化编排；知识库管理 UI 现成；业务可自助改 prompt 与工作流；Agent 与工具配置化 | 自带 PostgreSQL + Redis + 向量库，8C32G 上占约 4G，是**第二套运维体系**；Agent 调平台数据要走 HTTP 工具，**权限上下文传递麻烦且易成越权旁路**（违反架构红线 4）；工作流版本管理与自动化测试弱；深度定制受限 |
| **RAGFlow** | **文档解析质量业界靠前**（复杂 PDF / PPT / 表格 / 图片）；切片可视化；引用溯源做得好；有 API 可供接口推送入库 | 只解决 RAG，不做编排与 Agent |
| **FastGPT** | 轻量；知识库 + 简单编排；国内生态与文档友好 | 编排与 Agent 工具生态弱于 Dify；解析质量一般 |
| **全自建**（TypeScript + AI SDK，需图状流程时用 LangGraph.js） | 权限天然贯通（工具就是内部 service，直接继承 DataScope）；类型安全；可单测；无额外运维；与业务模块同一套审计与配额 | **知识库管理 UI 要自己写**（文档解析、切片、标注、审核），这是成本最高的部分；文档解析质量难以短期追平专业方案 |

### 9.3 建议：按能力切分，不选单一平台

| 能力 | 方案 | 理由 |
|---|---|---|
| **知识库层**（文档解析 / 切片 / 向量化 / 检索 / 管理 UI） | **用现成，优先 RAGFlow** | 文档解析质量是 RAG 效果的天花板，产品样册大概率是复杂 PDF/PPT，自己写解析不划算。只用它的「文档入库 + 检索 API」，管理与审核 UI 直接给总部人员用。**同时天然满足两条入库路线**（API 自动推送 + 人工上传） |
| **编排与 Agent**（H2 / H5 / H6 判定逻辑 / H7 / G3） | **自建（TypeScript）** | 核心理由：营销 Agent 与取数能力必须调平台内部数据（指标 / 账号 / 内容 / 规则），这些工具的权限必须走 DataScope。放在 Dify 里等于**把权限判断搬到平台之外**，这是最容易出安全事故的地方，也直接违反架构红线 4 |
| **Prompt 管理** | **自建轻量版**（prompt 表 + 版本 + 变量 + 灰度 + 效果指标） | 业务真正需要自助的是"提示词措辞"和"知识库内容"，**不是"工作流拓扑"**——拓扑一年改不了几次，不值得为它引入并运维一整个平台 |
| **模型出口** | **自建 AI 网关（H1）** | 档位路由、降级、缓存、计量、审计、配额联动必须与平台的 A8 打通，这层不能外包 |

**不引入 Dify 的补充依据**：旧系统本机已跑着一整套 Dify 容器，但旧系统的 `ai.js` 实际是**绕过 Dify 直连 DashScope** 的——说明在真实使用中 Dify 没有承担核心链路，却一直在占用资源和运维注意力。

### 9.4 这个决策的可逆性

反悔成本是选型的重要考量：

- **先自建编排，后来想换 Dify**：AI 网关（H1）是统一出口，编排层在网关之上。替换编排层时网关、prompt 表、知识库服务、审计与配额都可保留 → **成本可控**。
- **先用 Dify，后来想迁出**：业务流程都长在 Dify 的工作流里，工具配置、变量、上下文传递逻辑都是 Dify 私有格式，迁出等于重写 → **成本高**。

**结论：先自建编排 + 用现成知识库，是可逆性更好的选择。** 待 H3 知识库服务接入后，可用一个真实场景（合规审核）验证 RAGFlow 的解析与召回是否达标，不达标再评估替换知识库方案——此时编排层不受影响。

## 10. 关键设计取舍备忘

记录容易反复纠结的决策及其理由，避免后续来回摇摆。

| 议题 | 取舍 |
|---|---|
| 规则用 JSON DSL 还是嵌入脚本（JS 沙箱 / CEL） | **JSON 表达式树 + 注册算子**。换来可视化编辑、静态分析、血缘追踪、零沙箱风险。代价是表达能力有上限（§4 边界），遇到表达不了的判定走"新增算子"，**永不开放脚本** |
| 识别在入库时全跑，还是按规则按需触发 | **分档处理**：0 档（文本信号 / pHash）入库即跑；1~2 档（SIFT / OCR）对主页背景与封面入库即跑；**3 档（视觉大模型）仅当有规则圈定该对象时按需触发**，结果永久落特征表复用 |
| 判定实时还是批量 | **双模**。新内容入库触发增量判定（保证看板新鲜）；规则发布 / 活动开启 / 人工触发走批量重算 |
| 指标预聚合还是即席查询 | **看板与报表走预聚合**（ADS 宽表，秒级）；**自助分析走即席查询**（带行数与超时上限） |
| 视频源文件全存还是筛选 | **筛选**。全存 6.5TB/年不划算且大部分内容永远不会被看；按互动门槛或排名前 N% 筛选（阈值可配），约 660GB/年。音轨全部留存（体积小、ASR 复用率高） |
| 头像与背景图每周下载是否浪费 | **不浪费，必须每周下载**——不下载无法知道有没有换。但用 pHash 去重，未变化的不新增存储，只更新"最后确认时间" |
| 旧系统的 39,346 条内容要不要导入 | **必须导入**。API 只回溯 20 条，这批历史不可再生（§0.4 约束 5），是唯一机会 |
| 旧系统的判定结果要不要导入 | **作为对照参考导入，不作为权威数据**。用于新规则引擎上线时校验"新算法算出来的结果与业务的历史直觉是否一致"，差异大要能解释 |
| 多品牌是"切换"还是"同时查看" | **两者都支持**：总部用户可授权一个或多个品牌；前端提供单品牌切换和授权品牌多选聚合，查询始终取授权集合与用户筛选的交集 |
| 排名类判定（前 N%）如何进规则 | **排名在 L1 作为预计算信号**产出，L2 只做 `>=` 比较。不在规则引擎里做聚合运算 |
| 云资源放一个地域还是分散 | **集中在华北2（北京）**，OSS 与 ECS 同地域是硬约束（§11.1）。代价是单地域单可用区无容灾，用「每日全备直传 OSS」兜底。**VOD 是唯一例外**，它无需与 ECS 同地域 |
| ECS 选新一代规格还是省钱型 | **选企业级 g9i，不用 u1 / e**。省下的钱换不回算力的确定性——§B2 的「同步失败当周内必须重试完成」是 P0 约束，共享型 CPU 争抢与 u1 的平台漂移会让周末同步窗口变成不可预期的量 |
| ECS 磁盘一块还是两块 | **两块**：100G 系统盘 + 200G 数据盘。单盘省几十块钱，代价是重装系统即数据全失、快照策略无法分离、扩容要停机 |
| 宿主机 OS 选成熟版还是新版 | **Alibaba Cloud Linux 4**（新版）。因为 §I1 是全容器化，业务依赖都封在镜像里，宿主机 OS 的生态差异（Alinux 4 不再 CentOS 兼容、1191 个组件不再提供）对本项目几乎无影响——那些缺失项是多语言包、DNF Module、OCaml、mingw 和非阿里云网卡驱动。换来的是仍在开发支持期、开箱带 Docker、cgroup v2。**且这个决定可逆**：换 OS 只需重装系统盘 + `docker compose up`，数据盘挂回即可 |

| 理由 | 权重 |

| **百炼在中国内地只有华北2（北京）**，无上海/杭州入口；北京有业务空间专属域名 `{WorkspaceId}.cn-beijing.maas.aliyuncs.com`。§8 全套模型走百炼，§0.3 把模型调用列为三大成本瓶颈之一 | 高 |

### 11.3 已识别的资源缺口：RAG 知识库服务 ⚠️

**问题**：§11.2 给 RAG 知识库服务留了 4G 内存，但 §9.3 建议的 RAGFlow 官方要求是 **内存 ≥ 16GB、磁盘 ≥ 50GB**（它一套起来是 RAGFlow 本体 + Elasticsearch/Infinity + MinIO + PostgreSQL + Redis）。差额 12G 会直接击穿 32G 预算——周末峰值本来已经是 27G / 32G。

**为什么不现在就买 64G**：S1~S5（底座、数据供给、规则引擎、指标看板、业务闭环）完全不需要 RAGFlow，而这五个阶段是路线图里最长的一段。为一年后的需求提前付一年钱不划算。注意 g 系列 8 vCPU 上限就是 32G，要 8C64G 得换到内存型 r9i.2xlarge，或升到 g9i.4xlarge（16C64G）。

**S7 开工前在三个方案中选一**：

| 方案 | 说明 | 倾向 |
|---|---|---|
| 单独加一台 4C16G 专跑 RAGFlow | 同地域同 VPC，内网直连主库；符合 §I1「服务边界清晰，可平滑迁 K8s」 | ✅ 首选 |
| 主机升配到 8C64G（r9i.2xlarge）或 16C64G（g9i.4xlarge） | 包年包月允许升配，补差价即可 | 备选 |
| 用托管的向量检索服务替代自托管 RAGFlow | 省运维，但 §9.3 选 RAGFlow 的核心理由是文档解析质量，替换前需验证 | 需验证 |

**这个缺口的验证时点**：§14 第 6 项「RAG 方案验证」时，用真实产品样册跑一遍并实测内存占用，届时再定方案。

## 12. 建设路线

全新系统，全新库。旧系统不做逐步改造，只做**存量数据一次性导入**与**口径对照参考**。

| 阶段 | 目标 | 关键交付 | 验收标准 |
|---|---|---|---|
| **S0 澄清与设计** | 把口径和模型定下来再动手 | 商用 API 字段与配额实测（含是否需逐条详情）；指标口径评审（分母定义、观测语义）；规则算子首批清单确认；数据模型详细设计 | 关键口径有书面结论；Prisma schema 评审通过 |
| **S1 平台底座** | 四类角色能登录，看到正确范围 | A1 身份 + A2 组织主数据（4 品牌）+ A3 双维度权限 + A4 审计 + A5 配置 + A8 配额骨架；Monorepo 与前端骨架；四角色工作台空壳 | 四角色各看到正确范围；越权返回 403 而非空集；新增资源类型不声明 ScopeStrategy 时默认拒绝 |
| **S2 数据供给与资产** | 数据进来了，素材存下来了 | B1 供应商适配 + B2 同步编排（含窗口溢出检测）+ B3 ODS + B4 DWD（四平台归一）+ B5 资产归档 + B6 视频筛选下载 + B7 质量稽核 + **B8 存量导入** | 一个完整周末同步跑通，3,000 账号数据与素材归档完整；窗口溢出与同步失败告警可用；存量 39,346 条内容导入完成 |

| **S4 指标与看板** | 口径唯一，看板不写死 | E1 指标字典（含同源校验）+ E2 预聚合 + E3 看板配置器 + E4 报表模板（点检表迁为模板）+ E6 导出中心 | 点检表由报表模板生成；业务能自己配一张新看板；同一看板不同角色打开数据范围正确 |

| **S7 AI 能力** | AI 产出敢下发 | H1 网关 + H2 Prompt 管理 + H3 知识库服务 + H4 知识审核 + H5 脚本分析仿写 + H6 RAG 合规审核 | 审核能拦住机型参数错误与违规用语并给出引用依据；只有通过的能分发 |
| **S8 学习平台** | 能力下沉有载体 | G1 内容管理 + G2 学习中心（VOD）+ G3 AI 出题 + G4 题库考核 + G5 成长体系 + G6 学习任务 | 经销商能看课、考试、看到积分与排名；AI 出题经审核后入库；防刷机制生效 |
| **S9 自助与智能** | 业务不再排队取数 | E5 自助分析 + B9 元数据血缘 + H7 营销 Agent + H8 规则辅助生成 | 业务自建跨维度报表；Agent 取数结果与看板一致且范围正确 |
| **S10 增强模块** | 从监控走向指导 | F7 账号质量评分 + F8 热点选题 + F9 投放记录 + G7 学习效果分析 + H9 评测闭环 | 按业务优先级排期 |
