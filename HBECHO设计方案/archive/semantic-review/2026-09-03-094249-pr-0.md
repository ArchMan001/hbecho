第二轮回归确认上一轮 15 项中 11 项已经关闭；archive、完整页、Discovery grain、checkpoint 保留边界、tracer scope、负向任务、capability、INDEX/steering 及三个 design-only Spec 的修复已经对齐。Discovery 与 checkpoint 没有通过新增平行长期结构规避 v2，21 条首屏和一年期 lineage 的边界也已一致。剩余问题都位于本轮新增合同：ProviderCall 状态矩阵、TracerRoot 命令与保留期、profile payload 复用决策，以及主导作者证据的长期落点。

## High-level view

ProviderCall 已具备发送前 request ODS 和 `prepared → in_flight` 顺序，但 **confirmed** 状态与时间字段没有唯一可实现矩阵。TracerRoot 已映射到 manual batch + root SyncTask，但 **confirmed** submitted MediaStaff、per-command limit、canonical command 原文及一年后幂等行为仍无闭合合同。

Profile payload 仍有强制复用和允许第二次调用两个答案。Dominant-author policy 已版本化并补齐负向 fixture，但 **confirmed** 成功绑定的 policy、counts 和 denominator 会随一年期 task/call/raw 一起消失。

## ProviderCall 状态没有可执行的字段矩阵

**Major — confirmed.** [`database-design-v2.md` §9.5](../../domains/data-foundation/database-design-v2.md) 定义 `prepared/in_flight/terminal/ambiguous`，但只要求 terminal 有结束与捕获时间、ambiguous 有 outcome，并以“响应与耗时字段按状态同空同非空”概括其余约束。`terminal + transport_error` 没有完整响应，不能与成功响应共享 `response_received_at` 规则；`ambiguous` 应证明已经开始发送，却未明确要求 `send_started_at`；[`requirements.md` R14.6](../../../.kiro/specs/data-foundation-tracer/requirements.md) 和 task 8 又允许 prepared 后、发送前因取消或预算截止停止，但 terminal outcome 没有 `cancelled/not_sent`。恢复器、清理器和 DDL 因而可以形成不同状态语义。

v2 需要逐状态 nullability/transition matrix：prepared 禁止 send/terminal 字段；in-flight、ambiguous 和所有已发送终态要求 `send_started_at`；只有完整响应要求 `response_received_at`；transport error 单独要求 error payload、finished/elapsed/terminal captured；发送前取消使用 retained terminal outcome，或明确由 cancelled task 永久封口 prepared intent。还需定义 ambiguous reconcile 后的合法转移。

## Canonical TracerCommand 仍没有完整物理映射

**Major — confirmed.** [`requirements.md` R1.1](../../../.kiro/specs/data-foundation-tracer/requirements.md) 要求持久化 platform、`media_staff_id`、locator、key 与 optional limit 的 canonical command。v2 §9.3 和 [`design.md` §4.3](../../../.kiro/specs/data-foundation-tracer/design.md) 只明确 `platform_id`、locator 的 `subject_key`、caller key hash 与 canonical hash；没有指定 submitted MediaStaff 是否进入 `subject_type/subject_id`，也没有指定 per-command limit 和 canonical payload 的可重建表示。仅有 hash 不能恢复命令，未定义的 `task_parameters` 又会把关键身份放进无约束 JSON。

应固定 root 字段合同，例如 `subject_type='media_staff'`、`subject_id=media_staff_id`、`subject_key=original home locator`，并给 `task_parameters` 定义版本化 canonical schema 来承载 limit 等非身份参数，再明确 hash 的规范化输入。v2 已固定 global limit 1–20，因此 design 中“默认值、最大值仍为 P0”也应收窄为是否允许 per-command override 与是否请求第二页。

## Root idempotency 承诺超过保留期

**Major — confirmed.** v2 §9.3 为所有 SyncTask 设置一年 `expires_at` 并在 §12.7 删除 task，而 tracer 把 `root_task_id`、actor/key 唯一约束和 canonical hash 全部放在 root task。[`requirements.md` R1.2–R1.3](../../../.kiro/specs/data-foundation-tracer/requirements.md) 却无期限要求相同 key 返回原 root、不同 payload 报 conflict。任务到期后，长期 SyncBatch 不含这些字段，同一 key 会被当作新命令并可能再次付费。

若幂等与 status 只保证一年，Requirements/API 必须声明窗口与到期后的 non-disclosing result；若要永久防重，则需在 v2 长期事实中保留最小 actor/key/canonical/root tombstone。

## Profile payload 复用仍同时是强制行为和 P0

**Major — confirmed.** [`requirements.md` R3.6](../../../.kiro/specs/data-foundation-tracer/requirements.md) 与 task 4 要求 locator 已产生 captured terminal `media_user_info` 时必须复用且不得重复 profile call；[`prd-platform.md` §12.1(2)](../../prd-platform.md)、[`design.md` Open Decision 5](../../../.kiro/specs/data-foundation-tracer/design.md) 和 task 1 仍把复用与第二次付费请求列为两种允许策略。task 1 可以选出一个直接违反 R3.6/task 4 的实现。

按当前安全与成本方向，最小修复是保留 R3.6，删除总纲/design/task 1 中“captured payload 仍可不复用”的分支，只把“locator 未产生 profile payload 时是否单独 fetch”留作策略。若业务确实允许重抓，则需先放宽 R3.6，再定义触发条件、调用数和幂等恢复语义。

## Dominant-author 成功绑定缺少长期证据载体

**Major — confirmed.** [`requirements.md` R6.5](../../../.kiro/specs/data-foundation-tracer/requirements.md) 与 [`design.md` §10.3](../../../.kiro/specs/data-foundation-tracer/design.md) 要求 made 或 rejected 决策都保存 policy version、exact counts、denominator 和 reason。拒绝路径可写长期 `data_quality_issues.detail`，但 v2 §8.2 的成功 identifier 只有 `binding_method`、`confidence` 与 first/last seen；task 5 也只明确为 rejection 写 DQ issue。raw payload、task 和 ProviderCall 一年后删除，而 design §9.3 明确长期业务解释不能只依赖这些证据。

应先在 v2 指定成功 binding evidence 的长期落点，再由 tracer 引用；可扩充现有 identifier 的版本化证据字段或定义由 v2 拥有的长期 binding evidence，但不能在下游另建平行账号主档。验收应把 fake clock 推进一年以上，确认 identifier 仍可解释采用的 policy 与分布。

## 上一轮其余 finding 的回归结论

#1 的 v1 文首已有 archived、替代链接和禁止用途；#2 将长期 checkpoint 与一年期 page/call lineage 分开；#3 将 R9、design、task 与 v2 唯一键统一为一个 Discovery；#5 删除“返回最多 20 条”语义；#6 把详情/评论移到后续 Spec。#10 已把三次失败、平台错配、assignment conflict、清理和 redaction 分配到具体 task；#11 区分 evidence level、environment 与 production approval；#12 将 steering 登记为 derived，并把 legacy 位置限定为不可扩张例外；#13 在 Rule、Metrics、Access 和总纲中统一为 owner unresolved，Rule 权威链包含 Access；#14 的 Metrics build 只生成 candidate，由授权 actor 显式 activate；#15 的 Access 空 requirements 已删除。
