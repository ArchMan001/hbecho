# 域 E 用户与权限详细设计评审意见

> **文档状态**：`archived`  
> **当前相关设计**：[`access-control/design.md`](../../../.kiro/specs/access-control/design.md)  
> **归档说明**：评审建议已被选择性吸收进当前 Access Control 设计；未被当前 Spec 明确吸收的建议不生效。  
> **禁止用途**：不得单独作为需求、实现合同或验收依据。

---

> 评审对象：`HBECHO设计方案/archive/legacy/域E-用户与权限详细设计.md`  
> 评审目的：识别进入开发前需要修正或明确的设计问题，并给出可执行建议。  
> 评审原则：以本产品自身需求、用户规模和部署条件为准，不要求与其他产品统一，也不为了“安全完整”引入不必要的复杂基础设施。

---

## 1. 总体结论

原设计在短时 Access Token、可撤销 Session、Refresh Token 轮换、Cookie/CSRF 防护、一次性激活凭证、默认拒绝、最终数据出口复查以及 Agent 身份隔离方面考虑较完整，具备良好基础。

当前主要问题不是缺少安全机制，而是部分接口和规则的适用范围定义过宽，少数账号恢复、组织停用、异步任务和外部人员生命周期场景没有闭环。如果不在开发前澄清，可能出现以下后果：

1. 把“素材按品牌隔离”错误扩展为所有业务资源的统一规则。
2. 权限模块与 SQL、表别名和具体数据库绑定，后续难以覆盖 Agent、下载、向量检索等非 SQL 出口。
3. 用户恢复、组织停用或异步任务执行时继续沿用已经失效的授权。
4. `external` 角色长期承载多个不同身份，最终演变为难以解释的权限集合。
5. 用户管理大权限包使重置密码、查看手机号和普通资料修改无法独立控制。

建议将本文 P0 问题作为开发前置项，P1 问题在正式上线前闭环；P2 为可根据实际规模取舍的优化项。

### 优先级定义

| 优先级 | 含义 |
|---|---|
| P0 | 可能造成越权、失效授权继续生效或核心模型返工，开发前必须明确 |
| P1 | 不一定立即形成漏洞，但会影响安全边界、运维和后续演进，上线前应处理 |
| P2 | 可维护性、性能或未来扩展问题，可结合真实需求和压测结果决定 |

## 2. P0：开发前必须修正或明确

### 2.1 “品牌是唯一数据权限”不能成为全系统规则

**现状**

文档将 `material.brand_code` 定义为数据权限主字段，并明确组织、区域和职位不参与素材权限。对于素材浏览本身，这个结论可能正确；但文档同时将域 E 定义为跨域身份与授权契约，并在区域看板、用户管理、Agent、下载、打包和治理工作台等场景复用同一 `AuthCtx` 和授权门禁。

**问题**

“素材按品牌可见”不等于“所有资源都只按品牌可见”。不同资源可能存在不同范围语义：

- 素材：按品牌可见；
- 用户管理：还要限制目标角色、目标组织和授权边界；
- 区域看板：要同时限制品牌和区域；
- 个人收藏、反馈、任务：可能还要限制为本人；
- 审计记录：要按审计级别、操作者范围和敏感字段限制；
- 系统配置：可能只允许超级管理员，与品牌无关。

若所有 Repository 都直接复用品牌 SQL，容易出现同品牌跨区域查看、管理对象越级或审计数据暴露。

**建议**

将品牌规则明确命名为 `MaterialScopeStrategy`，只适用于素材及其文件；为其他资源显式声明各自范围策略。新增资源没有注册范围策略时默认拒绝，而不是自动套用品牌过滤。

可采用如下语义接口：

```ts
interface AuthorizationModule {
  authorize(request: AuthorizationRequest): Promise<AuthorizationDecision>;
  buildDataScope(request: DataScopeRequest): Promise<DataScope>;
}
```

`DataScope` 表达品牌、组织、区域、本人等语义，由各数据访问适配器转换为 SQL 或其他过滤条件。

**优先级：P0**

### 2.2 `AuthorizationGate` 混合认证、授权、SQL 和用户管理职责

**现状**

`AuthorizationGate` 同时包含：

- `authenticate()`：认证请求；
- `require()`：检查 Capability；
- `visibilityScope()`：生成 SQL；
- `assertCanManageUser()`：用户管理领域规则。

`visibilityScope()` 还直接返回 `SqlFragment`，并要求调用方传表别名。

**问题**

这个接口把四种变化原因绑在一起：

1. 登录与 Session 协议变化；
2. 权限矩阵变化；
3. 资源范围规则变化；
4. MySQL 查询实现变化。

它会导致授权模块知道数据库表别名，业务调用方知道授权 SQL；对 PostgreSQL、OSS 文件出口、Agent 工具和内存对象又需要额外旁路。长期看，权限规则会重新分散到多个出口。

**建议**

至少拆成两个模块：

```ts
interface SessionAuthenticator {
  authenticate(request: Request): Promise<AuthCtx>;
}

interface AuthorizationModule {
  authorize(request: AuthorizationRequest): Promise<AuthorizationDecision>;
  buildDataScope(request: DataScopeRequest): Promise<DataScope>;
}
```

- 认证模块负责“你是谁、会话是否有效”；
- 授权模块负责“能否执行动作、允许访问什么范围”；
- MySQL/PostgreSQL/OSS/Agent 各自使用适配器解释 `DataScope`；
- 用户管理的上下级与授权边界作为 `UserManagementScope` 或领域策略，不放在通用认证接口中。

**优先级：P0**

### 2.3 组织停用后，用户是否还能登录和访问数据没有闭环

**现状**

组织模型规定“禁用组织不自动禁用用户”；认证示例主要检查 Session 和 User 状态，没有检查用户所属组织状态。

**问题**

如果组织已停用，而其用户仍为 `active`：

- 用户可能继续登录；
- 原品牌授权可能继续生效；
- 已停止合作的外部机构人员可能继续下载素材；
- 管理端虽然显示影响人数，但实际访问并未收缩。

“不自动批量禁用用户”可以是合理的运维选择，但必须明确停用组织对认证和授权的影响，不能只停用组织记录而不改变任何访问行为。

**建议**

明确以下二选一策略，建议采用第一种：

1. **组织停用立即阻断访问**：用户记录保持原状态以便审计，但认证或授权阶段发现所属组织失效时拒绝访问；组织恢复后再按用户自身状态决定是否恢复。
2. **组织停用前强制完成人员迁移或禁用**：存在 active 用户时拒绝停用组织，管理员必须先处理人员。

同时补充组织停用、恢复和移动的事务规则、影响预览及验收用例。

**优先级：P0**

---

### 2.4 `undelete` 只清除 `deleted_at` 可能恢复过期授权

**现状**

用户状态机规定软删除只设置 `deleted_at`，`undelete` 只清除该字段并保留删除前状态。

**问题**

如果删除前用户是 `active`，简单清除字段可能同时恢复：

- 已经失效或停用的组织；
- 已经撤销的合作关系；
- 不再允许的角色；
- 过期品牌权限；
- 原有 Session/Token 之外的长期业务授权。

“保留原状态”有利于忠实恢复，但不能代替恢复时的不变量重检。

**建议**

将恢复设计为显式命令，而不是通用字段更新：

```ts
restoreUser({ userId, targetStatus, reason }, actor)
```

恢复事务中重新校验：

- 手机号唯一性；
- 组织存在且有效；
- 角色与组织类型是否匹配；
- 非超管品牌非空且仍可授权；
- 操作者当前仍有权管理该用户；
- 外部人员合作关系是否仍有效；
- 不恢复旧 Session、Refresh Token、激活码和临时权限。

默认可恢复到 `disabled`，由管理员确认授权后再启用，安全性更高。

**优先级：P0**

---

### 2.5 异步任务缺少统一的权限快照与撤权语义

**现状**

文档规定 Python worker 不复制用户鉴权，由 TypeScript 在任务提交前完成授权；打包 URL、向量文本等最终出口会再次复查当前权限。

**问题**

目前没有统一回答：

- 任务提交后用户新增权限，任务能否读到新增范围；
- 任务提交后用户被撤权，已排队任务是否继续；
- Worker 使用何种身份读取数据；
- 打包、导出、Agent 长任务、向量处理是否采用一致规则；
- 最终出口复查之前，Worker 是否已经处理了超范围数据。

仅依赖“提交时授权”可能让 Worker 使用系统权限扩大读取；仅依赖“交付时复查”又可能在内部处理阶段接触不应读取的数据。

**建议**

任务统一保存：

```json
{
  "requestedBy": 1024,
  "permission": "material.download",
  "scopeSnapshot": {"brandCodes":["hisense"],"version":7},
  "payloadHash": "...",
  "requestedAt": "..."
}
```

执行和交付时：

1. 检查用户仍为 active；
2. 重新计算当前范围；
3. 使用 `effectiveScope = scopeSnapshot ∩ currentScope`；
4. Worker 使用用途受限的 service actor，不伪造超级管理员；
5. 最终文件、文本或 URL 出口再对具体资源复查；
6. 用户已禁用或范围交集为空时，数据外发任务取消并写审计。

这样既不因后续扩权扩大旧任务，也不在撤权后继续交付数据。

**优先级：P0**

### 2.6 外部人员缺少有效期和退出机制

**现状**

`external` 可表示设计师、门店人员、经销商或外部机构人员，用户品牌授权表只有授予时间，没有有效期；用户生命周期主要依赖管理员手动禁用。

**问题**

外部人员通常具有合同到期、项目结束、临时协作或品牌授权到期等生命周期。仅依赖人工禁用容易形成长期遗留账号。由于 `external` 还可能拥有多个品牌，遗留授权影响更大。

**建议**

至少增加以下一种机制：

- 用户级 `access_expires_at`；或
- 品牌授权级 `valid_from/valid_to`；或
- 外部合作关系表，授权从有效合作关系派生。

第一期不必建设复杂合同系统，但应做到：

- 创建外部用户时可填写到期时间；
- 到期后认证或授权自动拒绝；
- 到期前在管理页面可查询；
- 延期需要有权限的管理员显式操作并留审计；
- 不依赖定时任务按时执行才能拒绝访问，在线鉴权也要检查有效期。

**优先级：P0**

## 3. P1：正式上线前应处理

### 3.1 `user.manage.all/scoped` 权限粒度过粗

**现状**

用户管理主要使用 `user.manage.all` 和 `user.manage.scoped` 两个 Capability。

**问题**

它把风险明显不同的动作合并在一起：

- 查看列表；
- 创建用户；
- 修改普通资料；
- 修改组织、角色、品牌；
- 禁用或恢复；
- 重置密码；
- 撤销会话；
- 查看或导出完整手机号。

一旦某角色拥有 `user.manage.scoped`，后续很容易在新增接口时默认放行所有用户管理动作。

**建议**

采用 `resource.action` 的动作级权限：

```text
user.list
user.create
user.update
user.grant.update
user.disable
user.restore
user.password.reset
user.session.revoke
user.pii.view
user.pii.export
```

角色矩阵仍可固定播种，不需要开放自定义角色 UI。细权限的意义是后端可精确校验和审计，不等于产品必须提供复杂配置界面。

**优先级：P1**

---

### 3.2 通用 `updateUser(patch)` 容易绕过敏感变更流程

**现状**

`IdentityDirectory` 暴露 `updateUser(userId, patch, actor)`，同时文档又规定角色、品牌、状态变化必须走 `UserGrantTransaction`。

**问题**

如果 `UserPatch` 包含 `role_code/org_id/status/brands`，调用方可能绕开授权事务；如果完全不包含，则接口契约需要明确。通用 PATCH 也容易把普通资料和高风险授权字段混在同一接口中。

**建议**

明确 `updateUserProfile()` 只能修改姓名、职位、头像等普通资料；敏感动作使用独立命令：

```text
changeUserGrant()
transferUserOrg()
disableUser()
restoreUser()
issuePasswordReset()
revokeUserSessions()
```

所有敏感命令统一进入授权事务和审计，不允许通用 Repository 直接修改相应字段。

**优先级：P1**

---

### 3.3 `external` 角色语义过宽

**现状**

`external` 同时覆盖设计师、门店人员、经销商和外部设计机构人员；职位不参与授权。

**问题**

如果这些人员当前 Capability 完全相同，统一角色可以降低复杂度；但文档没有明确证明其数据范围、上传下载能力、Agent 使用权和看板权限长期一致。未来出现差异时，团队可能被迫：

- 让职位偷偷参与授权；
- 在业务代码中判断组织类型；
- 为某些用户追加隐式特例；
- 把 `external` 变成含义不清的大角色。

**建议**

在文档中明确：

1. `external` 是权限角色，不是人员类别；
2. 设计师、经销商、门店人员是职位或合作方类型；
3. 一期合并的前提是 Capability 和数据范围相同；
4. 禁止用 `position_code` 在各业务模块散落判断权限；
5. 若未来确有稳定差异，应新增明确策略或角色，而不是不断给 `external` 加例外。

**优先级：P1**

---

### 3.4 单一 `auth_version` 混合了会话安全与授权缓存语义

**现状**

密码、角色、品牌、禁用等变化都递增同一个 `auth_version`，并撤销全部 Session。

**问题**

这一设计简单安全，但把两类含义混合：

- 会话安全版本：密码重置、账号禁用、凭证泄露；
- 授权版本：品牌、Capability、组织范围变化。

当前规模下全部重新登录可以接受，但后续任何低风险授权调整都会造成所有设备退出；缓存键和审计也难判断版本变化原因。

**建议**

第一期可以保留单版本，避免过早优化，但应在字段和文档中明确其行为：任何授权变化都会强制重新登录。如果后续用户体验或缓存需要，再拆为：

```text
session_version
authorization_version
```

不要现在同时保留多个含义不清的版本字段。

**优先级：P1（可先记录决策，按实际体验实施）**

---

### 3.5 手机号明文规范化列需要重新评估

**现状**

`app_user.phone_normalized` 保存完整规范化手机号并建立唯一索引，展示层做掩码。

**问题**

展示脱敏不能防止数据库备份、误查询或内部账号泄露导致完整手机号暴露。手机号又是该系统的登录标识，具有较高集中度。

**建议**

根据项目真实风险二选一：

1. **基础方案**：保持明文规范化列，但严格限制数据库账号、备份访问和导出；应用日志永不记录完整值。
2. **增强方案**：保存 `phone_ciphertext + phone_lookup_hmac`，使用带服务端 pepper 的稳定 HMAC 做唯一查询，完整值按需解密。

如果是小型内部系统且数据库权限受控，基础方案可以接受；但应在风险接受记录中明确，而不是把“页面掩码”描述为完整的隐私保护。

**优先级：P1**

---

### 3.6 业务审计缺少不可篡改约束

**现状**

文档对 `auth_event_log`、`audit_log` 的内容和保留周期定义较完整，但没有明确业务数据库账号是否可以 UPDATE/DELETE 审计记录。

**问题**

如果产生业务操作的同一数据库账号能够修改审计日志，误操作或被入侵后可能连同痕迹一起删除。仅规定“写审计”不等于审计可信。

**建议**

- 审计表只允许追加写；
- 业务运行账号不授予 UPDATE/DELETE；
- 清理使用独立受控任务和独立数据库权限；
- 高风险事件可同步到独立日志存储；
- before/after 只存变化字段，敏感字段脱敏；
- 审计写入失败时，高风险操作应失败关闭或进入明确的补偿队列。

小项目不必建设昂贵 SIEM，但至少要落实数据库权限隔离。

**优先级：P1**

---

### 3.7 超级管理员变更仍存在单人完全控制风险

**现状**

新增/禁用超级管理员要求 10 分钟内再次输入密码和填写 reason，一期不做复杂审批流。

**问题**

如果当前超级管理员的会话和密码同时被窃取，二次输入同一密码无法阻止攻击者新增另一个超级管理员。最后一名超管保护解决的是误删，不解决账号被接管。

**建议**

不必建设通用审批系统，但可以对极少数动作增加最小控制：

- 新增、降级、禁用超级管理员由另一名超级管理员确认；
- 若系统只有一名超管，先建立离线恢复流程或第二名受控超管；
- 超管可选启用 TOTP/WebAuthn；
- 其他一般敏感操作继续采用 re-auth + reason + 审计。

控制范围应严格限制在超级管理员生命周期、全量手机号导出和全局密钥变更等极高风险动作，避免过度设计。

**优先级：P1**

---

### 3.8 “超管无品牌行表示全部”属于隐式特殊值

**现状**

普通用户空品牌集合表示无数据，超级管理员空品牌集合表示全部数据。

**问题**

虽然代码已经显式区分角色，但同一个数据库状态“没有品牌行”存在两种完全相反的解释。导出脚本、报表任务或新 Repository 若只检查空集合，容易错误放行或错误拒绝。

**建议**

至少确保所有范围都由唯一 `buildDataScope()` 生成，禁止业务代码直接读取品牌行并自行解释。还可以返回显式结构：

```ts
{ mode: 'ALL' }
{ mode: 'LIMITED', brandCodes: [...] }
{ mode: 'NONE' }
```

不要求数据库增加伪造的“全部品牌”记录，但接口层不要继续用同一个空数组表达两种语义。

**优先级：P1**

---

### 3.9 预留但一期不使用的 visibility 字段可能成为未来旁路

**现状**

文档预留 `material.visibility` 和 `material_file.visibility`，一期明确不参与权限。

**问题**

提前落库但不执行的权限字段容易造成认知分裂：某些页面可能显示“仅总部”，而后端实际仍按品牌公开；后续某个 Repository 可能局部启用，形成不同出口行为不一致。

**建议**

二选一：

- 一期不建字段，等真实需求出现后统一设计和迁移；或
- 保留字段但不在页面暴露，代码扫描禁止业务读取；未来启用时必须作为新 `ScopeStrategy` 一次性覆盖列表、详情、下载、打包、Agent 和向量检索出口。

**优先级：P1**

---

## 4. P2：可结合真实规模决定

### 4.1 每请求查询 MySQL 的容量结论仍需压测验证

**现状**

文档基于约 5,000 用户、200 峰值在线，认为每请求查询 Session/User 的成本可接受，初版不使用 Redis。

**评审意见**

这个取舍合理，不应为了“大厂做法”提前引入 Redis。但“200 在线”不能直接推导每秒请求量，仍应使用真实接口并发和数据库连接池进行压测。

**建议**

上线前验证：

- 认证上下文 P95；
- 数据库连接池占用；
- 登录和 Refresh 峰值；
- MySQL 故障时 503 行为；
- `last_seen_at` 合并写是否产生锁竞争。

只有数据证明需要时，再增加 5～10 秒本地缓存或 Redis，并明确强退延迟上限。

**优先级：P2**

---

### 4.2 最大三层组织结构应记录为业务约束，而不是技术假设

**现状**

组织树最大三层，由领域逻辑强制校验。

**问题**

如果“总部—分公司—外部机构”确实是稳定业务事实，三层限制能降低复杂度；如果只是当前数据样例，则硬限制会在新增区域、事业部或集团层时导致模型迁移。

**建议**

补充产品决策记录：

- 为什么最多三层；
- 哪些组织类型允许作为父子；
- 区域与分公司是否永远同层；
- 总部直管外部机构如何统计。

若业务尚未确认，技术上可继续用 path，但不要在数据库和接口中写死只接受固定层数。

**优先级：P2**

---

### 4.3 `bcrypt_sha256_v1` 必须使用受审查实现和固定测试向量

**现状**

密码方案先做 SHA-256 预哈希，再使用 bcrypt，以规避 bcrypt 72 字节限制，并通过 `password_algo` 支持未来迁移。

**问题**

方案本身可以成立，但属于组合构造；若 Base64 编码、字符集或版本处理不一致，可能造成跨版本无法验证密码。团队也容易误以为是普通 bcrypt，使用不兼容实现。

**建议**

- 封装唯一 PasswordHasher 模块；
- 固定 UTF-8、Base64URL 是否带 padding 等细节；
- 提供固定输入输出测试向量；
- 禁止调用方自行拼装预哈希；
- 若技术栈已有成熟 Argon2id 支持，可在不违背产品约束时直接采用成熟算法；否则保留当前方案即可。

**优先级：P2**

---

### 4.4 认证失败关闭需要配套可用性预案

**现状**

MySQL 不可用时认证返回 503，不因 JWT 验签成功而放行。

**评审意见**

失败关闭是正确的安全选择，但也意味着数据库故障会让整个系统无法使用。

**建议**

不改变失败关闭原则，同时补充：

- 数据库备份和恢复演练；
- 连接池耗尽告警；
- 认证存储健康检查；
- 本机离线超管恢复 CLI 的权限和使用审计；
- 禁止公网万能密码或共享应急口令。

**优先级：P2**

---

## 5. 建议补充的验收用例

当前文档已有较完整的安全测试方向，建议再加入以下用例，确保上述问题真正闭环。

### 5.1 资源范围

1. 同品牌不同区域用户访问区域看板、用户管理和审计数据时，分别符合各自策略。
2. 新增资源未注册范围策略时，系统启动检查或 CI 失败，运行时默认拒绝。
3. 普通用户品牌集合为空时，MySQL、PostgreSQL、下载、Agent 四个出口均返回空或拒绝。
4. 超级管理员全量范围使用显式 `ALL`，业务代码不直接解释空品牌数组。

### 5.2 生命周期

5. 组织停用后，其 active 用户下一次请求按既定策略被拒绝或组织停用操作本身被阻止。
6. 恢复已删除用户时，组织失效、品牌越权或外部合作到期均导致恢复失败。
7. 外部用户授权到期后，即使 Session 尚未过期，也不能继续访问。
8. 授权变化、禁用和删除后，旧 Session、Refresh Token、激活码均不可继续使用。

### 5.3 异步任务

9. 用户提交打包后被移除品牌，任务不得交付已撤权品牌文件。
10. 用户提交任务后新增品牌，旧任务不得自动扩大到新增品牌。
11. 用户被禁用后，未交付的数据外发任务取消并写明原因。
12. Worker 不能以伪造超级管理员身份绕过范围。

### 5.4 管理边界

13. 总部管理员不能修改自己的角色、品牌、状态或组织范围。
14. 普通资料编辑接口不能修改角色、品牌、组织和状态字段。
15. 查看完整手机号、导出手机号、重置密码分别校验独立权限。
16. 两个并发请求不能同时禁用最后两名超级管理员。
17. 超级管理员新增、降级和禁用按确定的双人确认或应急流程执行。

### 5.5 审计

18. 高风险操作的审计写入失败时，操作不会静默成功。
19. 业务运行账号无法 UPDATE/DELETE 审计日志。
20. 审计、错误响应和普通日志中不出现密码、Token、Cookie、STS 或完整手机号。

## 6. 建议的整改顺序

### 第一批：开发前确认

1. 将品牌过滤限定为素材范围策略，建立按资源声明的范围机制。
2. 拆分认证与授权接口，取消通用授权接口对 `SqlFragment` 的直接依赖。
3. 明确组织停用对用户访问的影响。
4. 将用户恢复改为重新校验授权不变量的命令。
5. 定义异步任务的范围快照、当前范围交集和最终出口复查。
6. 为外部用户或外部品牌授权增加有效期。

### 第二批：用户管理开发时处理

7. 拆分 `user.manage.*` 为动作级权限。
8. 限制通用用户 PATCH，敏感字段使用独立命令。
9. 明确 `external` 的角色语义和未来拆分条件。
10. 明确单一 `auth_version` 的退出登录行为。

### 第三批：上线前验证

11. 落实手机号存储风险接受或加密查询方案。
12. 限制审计表修改权限。
13. 为超级管理员生命周期增加最小双人控制。
14. 完成范围、恢复、异步任务、并发超管和审计不可变性测试。
15. 使用真实流量模型验证每请求 MySQL Session 校验。

---

## 7. 不建议因本次评审引入的复杂度

为避免整改演变为过度设计，本次评审不建议仅因上述问题立即引入：

- OPA、Casbin、Zanzibar 等独立策略平台；
- 动态自定义角色和可视化策略编辑器；
- 所有操作通用化的审批流引擎；
- 全员强制 MFA；
- 未经压测证明必要的 Redis Session；
- 多组织成员关系；
- 微服务化的独立权限中心；
- 两个产品共享用户数据库或角色表。

当前规模下，优先把资源范围、生命周期、管理边界和最终出口这四件事做正确，再根据实际业务增长演进。
