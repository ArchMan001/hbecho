# ADR-0008 · 门店身份与门店编码分离

- **状态**：accepted
- **日期**：2026-11-02
- **决策人**：刘学奎
- **推翻**：v2 §7.6 的 `UQ(store_code)`；A 域 PRD §4.1 第 7 条「门店的经销商、品牌、板块不可变」

## 背景

门店编码来自 CRM 导出，历史上出现过三种会让「编码即身份」失效的情况：

1. **同一编码在多个品牌下各有一条记录**——一个物理门店同时经营日立与海信时，CRM 按「门店 × 主营业务」出行，同一编码出现两次（实测 5 组）；
2. **同一品牌下同一编码出现两条**——重复建档或商家变更留下的旧记录（实测 11 组）；
3. **编码本身会变**——升级换码、新旧系统迁移，实测一份导出里有 1,252 条带「升级前门店编码」。

如果拿编码当主键，任何一种情况都会让已发生的归属、快照、判定和看板结果挂到错误或消失的门店上，而且不会报错。

## 决定

### 1. 身份与属性分开

- **`store_id` 是唯一权威身份**，系统生成，永不改变；
- **`store_code` 是外部属性**，可以变、可以重复出现在不同品牌下；
- 所有业务引用只指向 `store_id`；门店改名、改码、换经销商都不迁移历史数据。

### 2. 唯一键是 `(brand_id, store_code)`

全公司共用一个门店编号池，但门店归属于品牌，因此唯一性只在品牌内成立。这同时解决了一店多品牌造成的重码。

### 3. 导入只做匹配，不做推断

- 按 `(brand_id, store_code)` 精确匹配；命中则更新属性，未命中则新建；
- **不按编码族自动合并**（`X` 与 `XB01` 可能是两家店）；
- **不因某行在导出中消失就自动停用**：消失只生成待确认项，由有权限的人确认撤店后才置 `closed`。

### 4. 编码变更由管理员承接

源系统若改码，由管理员把新编码写到原门店记录上，`store_id` 不变。不新建门店，不建别名表。

## 备选方案与不选原因

| 方案 | 不选原因 |
|---|---|
| 用 `store_code` 直接当主键 | 一店多品牌、重复建档、改码三种情况都会断链，且不报错 |
| 引入 CRM 稳定门店 ID | × 已与技术人员确认：CRM 没有不随编码变化的内部主键 |
| 按编码族（去 `Bxx` 后缀）自动合并 | 实测 8 组「基础码 + `Bxx`」并存，其中 7 组是**不同门店**（名称、商家、CRM 码都不同），自动合并会把两家并成一家 |
| 门店消失即自动停用 | 导出范围变化、改码都会表现为消失；自动停用会误伤整店账号 |

## 后果

- `stores` 的唯一键从 `UQ(store_code)` 改为 `UQ(brand_id, store_code)`；
- 门店的经销商与板块改为「以当前值保存、变更走受审计修正、不保留历史」，与名称、等级一致；
- 导入流程新增「待确认撤店」清单，不能省略——否则撤店门店会永远留在系统里继续采集；
- 门店编码不做任何规范化转换（`NO.0004105` 与 `NO0004105` 是两个不同编码），原文保存，另存只做去空格与大小写的匹配值。

## 现在谁在守

- DDL：`stores` 的唯一键与 `source_batch_id`；
- 导入服务：按 `(brand_id, store_code)` 匹配、不自动停用；
- 主数据修正：编码变更记审计，且只对超管开放；
- 验收：A 域 A1「同一品牌下同一门店编码不能创建两条门店」「导入中消失的门店不会自动停用」。
