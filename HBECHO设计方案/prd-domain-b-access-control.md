## 一、这个域管什么

### 1.1 四个问题

```
你是谁            → 账号从哪来、怎么激活、怎么登录
你能做什么        → 四类角色分别能操作什么
你能看到什么      → 组织范围 × 品牌
你什么时候被踢出  → 会话时长、强制下线、停用、离职
```

### 1.2 不管什么

| 事情 | 归谁 |
|---|---|
| 门店、专员、账号是什么 | A 数据底座 |
| 内容该不该被采 | A 数据底座 |
| 什么算达标 | D 规则与考核 |
| 指标怎么算 | E 指标与看板 |
| 页面长什么样 | F 业务应用 |
| 服务器与密钥怎么管 | I 运维与成本 |

### 1.3 一条主线

```
管理员开通账号 → 用户自己设密码 → 登录得到会话
→ 每个动作先问"能不能做" → 每个查询再问"能看哪些"
→ 所有出口（页面、导出、下载、Worker、AI）执行同一套判断
→ 停用或撤权后，会话失效、任务收窄、交付前再查一次
```

**B 的职责是"发许可"和"守出口"，不是"存业务数据"。**

## 二、用户与场景

### 2.1 四类角色

| RoleCode | 角色 | 典型人数 | 一句话 |
|---|---|---|---|
| `platform_admin` | 超级管理员（平台运营） | 1–3 | 管系统、管人、管全部配置 |
| `hq_manager` | 总部人员 | 20–50 | 管授权品牌的业务与配置 |
| `branch_manager` | 分公司人员 | 50–100 | 管本分公司的数据与人员 |
| `store_staff` | 经销商人员（门店专员本人） | 3,500+ | 看自己的数据、学课程、用 AI 辅助 |

> 人数是规模估算，用于判断"批量导入"与"管理范围"的设计重心，**不作为验收项**。

### 2.2 三条真实路径

| # | 场景 | 走哪条链路 |
|---|---|---|
| 1 | 新一年度名单下来，要一次开通几百个账号 | 批量导入 + 激活（第四章） |
| 2 | 用户每天登录看自己的数据 | 登录与会话（第五章） |
| 3 | 门店换人、分公司调整、人员离职 | 生命周期与授权变更（第六、九章） |

### 2.3 1.0 的边界

- 无公开注册、无经销商自助入驻；
- 无 SSO、无 MFA、无设备管理中心；
- 无动态角色设计器、无个人权限覆盖；
- 无高风险动作二次认证（可以 2.0 再加）；
- 认证基于 better-auth，授权自建（ADR-0005）。

## 三、概念

### 3.1 三类身份必须分开

| 概念 | 含义 | 谁能登录 |
|---|---|---|
| `User` | 登录主体 | ✅ |
| `MediaStaff` | 某人在某门店与品牌下的业务身份 | ❌ |
| `ExternalAccount` | 平台账号 | ❌ |

**`User` 与 `MediaStaff` 不是一回事。** 总部与分公司人员只有 `User`，没有 `MediaStaff`；门店专员本人两者都有。

### 3.2 Capability 与 DataScope 正交

| 维度 | 回答 | 例子 |
|---|---|---|
| **Capability** | 能不能执行这个动作 | "能不能触发手工同步" |
| **DataScope** | 能访问哪些对象 | "能同步哪些门店的账号" |

两者必须分开判断：有动作权限的人，数据范围可能很小；数据范围大的人，未必有写权限。

| 场景 | Capability | DataScope | 实际结果 |
|---|---|---|---|
| 分公司管理员 | 有 `data.sync.trigger` | 只能访问本分公司 | 能手工同步，但只能同步本区的账号 |
| 总部分析人员 | 只有 `data.account.read`，没有 `data.sync.trigger` | 授权品牌下全部组织 | 能看全品牌的数据，但不能触发同步 |
| 门店专员 | 有 `learning.read` 与 `ai.content.assist` | 仅本人 | 能看课、用 AI 辅助，但只看自己的账号 |
| 超管 | 全部 Capability | 全部 | 不受限，但仍走显式判断，没有隐藏旁路 |

### 3.3 管理范围

管理别人时多一个维度：

```
管理范围 = 角色 ∩ 组织范围 ∩ 品牌
```

且**不能授出超过自己**：不能给别人自己都没有的品牌、组织或能力。

### 3.4 数据出口

所有能把数据带出系统的地方，执行同一套判断。B 域负责定义出口清单与复查时机（第十章）。

## 四、B1 开户与激活

### 4.1 邀请制

- 平台运营或上级管理员创建用户，填写：姓名、角色、组织范围、品牌、手机号；
- **系统里不存在默认管理员账号和默认密码**；
- 首个超级管理员由一次性初始化操作创建，不通过界面导入。

### 4.2 激活

- 新用户处于"待激活"；
- 用户首次登录时**自己设置密码**；
- 运营人员在任何界面都不能设置、也不能查看用户密码；
- 激活凭证短期有效、一次性；重发使旧凭证失效。

**激活方式：短信验证码**（D-39）。用户输入手机号 → 收到验证码 → 验证通过后设置密码。与登录共用同一套短信能力，不预生成激活码、不导出文件。

**短信参数**（激活、登录、重置密码共用一套）：验证码有效期 **5 分钟**；同一手机号 **60 秒**后可重发；同一手机号每天最多 **10 条**；连续输错 **5 次**即作废，需重新获取。短信额度与费用归 I 域。

### 4.3 批量导入

- 格式 CSV（与 A 域一致）；
- 先预检再确认：阻断"操作者没有权限授予的角色、组织与品牌"；
- **只做新增**；已存在的手机号标为冲突，不静默改角色或范围；
- 失败行回流为同格式文件，每行带原因码与一句指引：
  - 角色 / 范围不符 → 到用户管理里单独修改；
  - 手机号已存在且是换号 → 停用旧用户后新建（D-43）；
  - **不提供"一键改成新增"**，避免绕过授权校验。

### 4.4 明确不做

- 公开注册；
- 自助找回未开通的手机号；
- 导入时直接把密码写进文件。

## 五、B2 登录与会话

### 5.1 登录方式

| 方式 | 1.0 | 说明 |
|---|---|---|
| 手机号 + 密码 | ✅ | 主方式 |
| 手机号 + 短信验证码 | ✅ | 与激活、找回密码共用同一套短信能力 |

### 5.2 会话

- 登录后获得可撤销的会话；
- **有效期 15 天，滑动续期**（D-40）：
  - 第 1 天登录，有效期到第 16 天；
  - 第 10 天再次登录，有效期刷新到第 25 天；
  - 连续 15 天不登录，会话到期失效，需要重新登录；
- 每次登录都重新检查用户状态与授权，停用用户无法续期；
- 支持"退出登录"与"管理员强制下线"。
- **不设绝对有效期，也不限制并发会话数**（2026-10-29 决定）：只要持续活跃，会话可以一直续期；撤销仍通过停用、改密、强制下线三条路径完成。

### 5.3 密码

- 由用户自己设置，管理员不能查看、也不能代设；
- **不强制字符组合、不强制定期改密、不做弱密码黑名单**（D-45）；
- 仅保留一条安全下限：**最短 8 位**；
- 忘记密码走短信自助重置；
- 修改密码后，该用户的其他会话全部失效。

### 5.4 登录保护

- 登录失败限流（IP + 账号双维度）：
  - **账号维度**：连续 5 次失败 → 该账号锁 15 分钟，期满自动解锁；锁定期间正确密码也不放行，不通知、不永久锁定；
  - **IP 维度**：同一 IP 10 分钟内 20 次失败 → 该 IP 限 15 分钟；
  - 锁定期满后失败计数清零；
- 连续失败不修改业务用户状态；
- 待激活账号走密码登录时，提示与"手机号或密码错误"一致，不暴露账号是否存在。

## 六、B3 用户生命周期

### 6.1 三个状态

| 状态 | 含义 | 能否登录 |
|---|---|---|
| 待激活 | 已创建，未设密码 | ❌ |
| 有效 | 正常 | ✅ |
| 停用 | 禁止登录，历史保留 | ❌ |

**不物理删除。** 离职、退出试点都用停用表达。

### 6.2 停用与恢复

- 停用：现有会话全部失效，不能新建会话；
- 恢复：重新检查角色、组织范围、品牌与关联业务身份；**已失效的项直接去掉（自动收窄），用户恢复为有效**。移除项在审计里记一条，不做单独的恢复结果页。
- 停用不影响 A 域的数据采集；采集只看业务状态与监控开关；
- **采集与登录激活完全解耦**（D-46）：门店专员从未首次登录、`User` 一直是"待激活"或根本没有 `User`，只要该专员的业务身份已导入、监控开着，A 域照常采集该门店的账号；
- 同理，`User` 停用也不会停止采集；停采只看 A 域的业务状态与监控开关。

### 6.3 人员变动

- 换门店或换品牌：调整组织范围或关联的 `MediaStaff`，记审计；
- 离职：停用 `User`；对应的 `MediaStaff` 按 A 域规则处理（账号停采、归属不变）；
- 手机号变更：**只做"删旧建新"**（D-43）——停用旧用户，用新手机号新建用户并重新授权；
- 系统不支持直接修改登录手机号；
- 理由：系统无法区分"换号"与"换人"，而两者正确的处置完全不同；改绑会让新人继承旧人的全部权限；
- 若将来确需改绑，必须同时满足：新号短信验证、旧号收到通知、填写原因并记审计。
- **不建立新旧用户之间的关联**（2026-10-30 决定）：审计按 `User` 维度记录，不按自然人；换号后新旧用户是两条独立记录，系统不提供"同一人"的追溯，也不要求填写原用户。

## 八、B5 数据范围

### 8.1 范围构成

```
DataScope = 组织范围（子树） × 品牌集合
            + 是否仅本人
```

### 8.2 按资源类型的规则

| 资源 | 范围规则 | 说明 |
|---|---|---|
| 账号 / 内容 / 主页 / 媒资 | 组织子树 × 品牌 | 门店专员只看本人 |
| 外部监控账号（竞品与官方号） | 默认只有平台级可见 | 无门店与专员，不落入组织范围；分公司看不到 |
| 报表 / 点检表 | 同一投影下按当前范围过滤 | 同一张配置，不同人看到不同行 |
| 规则与指标配置 | Capability + 适用品牌 | **配置的适用范围不是授权** |
| 用户管理 | 角色 ∩ 组织 ∩ 品牌 | 读写用同一条谓词 |
| 原始载荷 | 独立高敏 Capability + 业务范围 + 审计 | 普通读数据权不自动包含 |
| 手机号 | 随所在行的范围判断（B §8.1） | 不单设字段级 Capability：能看到行就能看到手机号 |
| 媒资下载 / 签名 URL | 继承源对象范围 | 每次短期签发 |
| 审计日志 | 按级别与操作者范围过滤 | 超管看全部 |

### 8.3 "本人"怎么绑定

- `store_staff` 的 User 与一个 `MediaStaff` 一对一绑定；
- 例：张三在"北京日立 001 店"是新媒体专员，他的登录账号绑定到这条 `MediaStaff` 记录；他能看到的账号与内容，就是归属到这条记录的那些；
- 如果没有绑定、绑定到已停用的 `MediaStaff`、或同时绑定多条：**拒绝本人范围**，不回退成"本门店"或"本品牌"；
- `hq_manager` 与 `branch_manager` 不使用"本人"范围——他们按组织范围看。

### 8.4 当前权限与历史事实

- 当前 Grant 决定"现在能看什么"；
- 历史事实（列表出现、快照）保存采集当时的归属快照，不因改绑或组织调整而改写；
- 授权收缩立即缩小查询结果，但不删除历史事实。

### 8.5 未注册默认拒绝

每个资源类型必须显式声明范围规则；**没有声明就拒绝**，不套用"品牌过滤"或"全量"。

## 九、B6 管理范围与授权

### 9.1 三维

管理范围 = 角色 ∩ 组织范围 ∩ 品牌。三类必须同时满足。

### 9.2 不能授出超过自己

- 不能给别人自己没有的角色等级、品牌、组织范围；
- 不能给别人自己没有的 Capability；
- 批量操作逐条判断；被拒的进"跳过"清单，不让整批失败。

### 9.3 读写同源

列表、详情、修改、停用、恢复、删除、批量操作使用**同一条范围判断**，杜绝"看不到但能改"。

### 9.4 最后一个管理员

系统必须始终至少有一个可用的超级管理员；禁用或删除最后一个超管必须被拒绝。

## 十、B7 数据出口

### 10.1 出口清单（1.0）

| # | 出口 | 检查内容 |
|---|---|---|
| 1 | 页面查询 | 动作权限 + 数据范围 |
| 2 | 手工同步 | 动作权限 + 目标账号在范围内 |
| 3 | 点检表 / 报表 | 动作权限 + 当前范围过滤 |
| 4 | 导出文件 | 提交时范围 + 执行时范围 + 交付前复查 |
| 5 | 媒资下载 / 签名 URL | 源对象范围 + 短期有效 |
| 6 | 原始载荷 | 高敏 Capability + 业务范围 + 审计 |
| 7 | 后台 Worker | 使用 §10.3 定义的服务身份，不伪造超级管理员 |
| 8 | AI 工具取数 | 继承调用者范围 + 行数上限 + 审计 |
| 9 | 通知 / 消息 | 只发与接收者范围相关的摘要 |
| 10 | 学习资料下载 | 动作权限 + 品牌范围 + **下载审计**（谁、何时、哪门课、文件标识、结果） |

**`data.export` 与 `report.export` 的边界**（2026-10-29 决定）：

- `data.export`：导出物以**原始对象**为主结构——账号、内容、媒资、名单；按 DataScope 过滤行，不做口径加工；
- `report.export`：导出物以**报表产物**为主结构——点检表、看板快照、明细表；绑定 `projectionId` + `outcomeSetId`，数值与页面一致；
- 点检表下钻后导出的明细仍算 `report.export`，明细行按 DataScope 过滤；
- 两者都走出口 4 的三次校验，不因"是报表"放宽。

### 10.2 交付前复查

导出、打包、媒资、AI 结果与签名链接，在**交付前**再查一次：

```
当前范围是否仍覆盖产物内容
→ 不覆盖：拒绝、删除或按新范围重建
```

只在提交时查，会在撤权后继续处理；只在交付时查，会让 Worker 内部接触到超范围数据。**两头都要查。**

### 10.3 Worker 身份

Worker 不是 `User`，没有 Grant，也不继承任何角色的默认能力。只有两种身份：

| 任务类型 | 身份 | 能做什么 | 不能做什么 |
|---|---|---|---|
| 计划任务（周期同步） | 固定服务身份 | 采集相关动作；范围覆盖全平台被监控账号 | 读原始载荷、导出、改授权、改配置 |
| 用户触发任务（`data.sync.trigger`） | 继承提交者 | 与提交者相同的 Capability | 超出提交者当前范围；交付前必须复查 |

计划任务之所以是平台级范围，是因为它要跑全量；这**不构成**越权，因为它没有任何"把数据交给某个人"的出口。用户触发任务反过来：范围来自提交者，撤权后交付前复查会拦住过期任务。

## 十一、B8 审计

### 11.1 记录什么

- 邀请、激活、登录成功/失败、强制下线、会话撤销；
- 用户创建、导入、停用、恢复、角色/范围/品牌变更；
- 敏感字段查看、原始载荷访问、手工同步；
- 规则发布与重算、指标与模板变更；
- **活动计划与监控判定计划的创建、删除、恢复、30 天期满清除**（2026-10-30 决定：计划是跨域消费入口，删除与恢复必须可追溯）；
- 导出提交、执行、取消、交付；
- 高成本操作的授权与拒绝。

每条至少包含：谁、对谁、什么动作、什么结果、什么时候、范围摘要、原因。

**手机号不脱敏**（2026-10-29 决定，2026-10-30 明确到日志）：审计与应用日志都可以记录完整手机号；密码、Token、Cookie 永不记录。

### 11.2 谁能看

1.0 **只有 `platform_admin` 能看审计**；其他角色一律不可见。审计入口由独立的 `audit.read` 控制，1.0 只授予 `platform_admin`（D-41）。

> 后续如果业务要求总部或分公司查看本范围的审计，再单独开一条规则，不在 1.0 默认放开。

### 11.3 保留

保留 **一年**（D-44）；敏感读取的审计同样至少一年。到期清理与业务数据分开执行。

**到期清理**（2026-10-30 决定）：按时间窗口批量删除超过 365 天的记录，删除动作以系统身份记一条审计；**不提供单条删除，也不提供界面删除**。"不可覆盖"约束的是不修改历史记录，不约束按保留期清理。
