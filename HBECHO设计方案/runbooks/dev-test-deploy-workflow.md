## 1. 目标流水线

```text
Mac：写代码 + 离线测试
  → push 分支 / 开 PR
  → GitHub Actions：verify（类型 / 测试 / 静态门禁 / 文档 / 密钥）
  → （需要时）构建应用镜像，标签 = git 短 sha，推 ACR
  → 测试 ECS：拉同一个 sha 标签，一次性库上跑迁移与端到端
  → 合并 main
  → 生产 ECS（**未购买；购买并登记前这一步不执行**）：拉同一个 sha 标签，按 备份 → 迁移 → 换标签 → 冒烟 → 记录 上线
  → 出问题：换回上一个标签；表结构按「扩展 → 部署 → 收缩」保证旧代码可跑
```

**构建一次，到处用同一个产物。** 测试机验证过的标签就是生产标签，不在生产机上重新构建。

## 2. 环境划分

### 2.1 本机（Mac）

- 写代码、跑离线测试、跑 `./scripts/verify.sh`。
- 需要数据库时，只连本机一次性容器；库名以 `_test` 结尾，用完即毁。
- 不放生产 `.env`，不连生产库。

### 2.2 测试 ECS（现有，当前唯一实例）

**当前这台就是测试机**：`i-2zef8qpi1d2mldntjgrv`，华北2（北京）F，`ecs.g9i.2xlarge`（8 vCPU / 32 GiB），Alibaba Cloud Linux 4，系统盘 100 GiB + 数据盘 100 GiB（`/data`）。资产与系统配置见 `server-operations-runbook.md` §1。

作为测试机，额外规则：

| 项 | 规则 |
|---|---|
| 测试数据库 | 只用一次性容器（独立 docker 网络、不映射宿主端口、库名以 `_test` 结尾、用完 `down -v`）；默认不连现有的 `hbecho` 库 |
| 凭证 | 不放生产凭证；AI Master 开关默认关闭或 mock |
| OSS | 只使用测试桶或 `test/` 前缀；不写正式媒资 |
| 清理 | 与测试相关的容器、镜像、临时文件可自行创建与清理；改安全组、改 RAM、动系统服务、释放实例仍要先说明并得到同意 |

**未来若再购一台**：先明确它是生产机还是替换现有测试机，写一份 ADR 并在本文件登记；在那之前，不要把现有测试机当生产机，也不要把生产凭证放进来。

### 2.3 生产 ECS（未购买）

当前没有生产 ECS。以下规则在购买并登记后生效：

- **永不跑测试**、`verify`、`pytest`、迁移演练。
- 应用代码只通过 `git pull` 或镜像部署，不用 `tar` / `scp` 覆盖。
- 所有业务端口绑 `127.0.0.1`，对外只经反代；80/443 在 `runbook §10.6` 条件满足前不开放。
- 生产凭证与测试凭证分开，不复用；测试机的 `.env`、数据库、OSS 对象不得直接复制过去。

## 3. 分支与推送

- `main` 永远处于「CI 绿 + 可部署」状态。
- **一个 spec 一条分支**，不按批次开新分支；修复用 `fix/<主题>`。
- **一个 spec 推两次**：① 建表/迁移那批完成后；② 收尾。中间不推。
- 不直接 push `main`。
- 合并前必须有一次已跑完且 `verify` 为绿的 run。

提交信息前缀沿用：`feat:` / `fix:` / `docs:` / `refactor:` / `chore:`。

## 4. 本机验证

**唯一入口**：

```bash
./scripts/verify.sh
```

当前包含四步：

| 步骤 | 检查 | 能否失败 |
|---|---|---|
| 1 | 工作区密钥特征与凭证文件名 | 能 |
| 2 | git 历史中的凭证文件名 | 能 |
| 3 | 所有 Markdown 的相对链接可达 | 能 |
| 4 | 必需文档存在且非空、归档有状态头、spec 结构完整、文档目录已登记 | 能 |

**边界要说清楚**：它现在**不检查类型、不跑测试、不验证 DDL、不验证领域规则**。在应用代码落地前，任何「验证通过」都只覆盖文档与密钥层。

应用代码落地后，`verify.sh` 扩展为：typecheck → 全部测试 → 静态门禁 → 文档与密钥。扩展时保持同一条命令，不要新增一个「差不多」的入口。

## 5. GitHub Actions

工作流：`.github/workflows/ci.yml`。

### 5.1 现在

- 触发：任意分支 push、到 `main` 的 PR、手动 `workflow_dispatch`。
- 单个 `verify` job：`checkout`（`fetch-depth: 0`，历史密钥扫描需要）→ 运行 `./scripts/verify.sh`。
- `permissions: contents: read`；无 secret、无数据库、无网络付费调用。
- `concurrency: cancel-in-progress`：同分支新 push 取消旧 run。

### 5.2 应用代码出现后要补的 job

| job | 触发条件 | 内容 |
|---|---|---|
| `app-verify` | 每次 push / PR | MySQL 8.4 服务容器 → 空库跑迁移 → typecheck → 测试 → 静态门禁 → 生产构建 |
| `image` | 仅在应用/worker 相关路径变化或手动触发 | 构建镜像 → 镜像内测试 → 推 ACR，标签 = git 短 sha |
| `deploy-test` | 手动触发 | 测试 ECS 拉同一标签、一次性库迁移、端到端 |
| `deploy-prod` | 手动触发 + 环境审批 | 生产 ECS 按 §7 顺序上线 |

**镜像仓库**：hbdam 的实测结论是北京机器从 ghcr 拉大镜像只有约 150 KB/s，**不能用于分发**。hbecho 若需要镜像分发，优先同地域 ACR 内网地址；开通前单独决定并记 ADR，不要默认 ghcr。

**迁移命令**：一旦有迁移工具，CI 只允许执行「版本化迁移命令」，**禁止 `db:push` 一类会猜结构的命令**。迁移必须能在空库上从头执行得到相同结构（`runbook §10.2` 部署契约第 6 条）。

## 6. 测试 ECS 上的隔离（五层）

任何一层单独生效都能挡住「测试清生产库」。这五层在应用代码落地时实现：

| 层 | 做法 | 挡住的场景 |
|---|---|---|
| L1 结构 | 生产镜像不带 `tests/`；生产 `.env` 在代码目录之外（`/data/app/.env`，root 600），只经 compose `env_file` 注入 | 在服务器上随手跑测试 |
| L2 正向识别 | 测试启动时确认目标实例存在哨兵库 `__hbecho_disposable__`，且当前库名以 `_test` 结尾，否则退出。哨兵只由 `db:test:prepare` 在本地或 CI 的一次性实例上创建 | 端口填错、`.env` 抄了生产值 |
| L3 共享函数自检 | 清表函数（`truncateAll()` 与 Python fixture）内部再查一次哨兵 | 有人绕过 setup 直接调 helper |
| L4 网络 | 服务器只走 Workbench，不存在 SSH 隧道；守卫拒绝 `NODE_ENV=production` 与非回环数据库地址 | 从本机经隧道连生产库 |
| L5 权限 | 应用账号只有 `SELECT/INSERT/UPDATE/DELETE`，没有 `DROP`（无 DROP 就执行不了 `TRUNCATE`）；迁移账号才有 DDL 权限 | 以上全部失效后的最后一道 |

**测试机上的 `.env`**：`NODE_ENV` 不是 `production`；AI Master 开关默认关闭；OSS 只指向测试桶或测试前缀。

## 7. 生产部署

> **当前不适用**：没有生产 ECS。本节描述生产机购买后的流程；现在所有部署与验证都在测试机上进行，测试机上的部署不要求生产级备份窗口，但迁移仍必须版本化、可在空库重放，不得手工 `ALTER`。

### 7.1 顺序（任何一步失败就停）

1. **确认目标**：打印环境、库名、当前标签；要求人工确认。
2. **备份**：MySQL 逻辑备份（`--single-transaction`），校验文件非空、`gzip -t` 通过；同步一份到备份桶。恢复演练未做过的备份不算备份（`runbook §11.5`）。
3. **迁移**：只执行版本化迁移；不使用会猜结构的命令。
4. **切换产物**：换成测试机已验证的同一个标签；或 `git pull` 到指定 SHA（无镜像阶段）。
5. **冒烟检查**：健康端点、端口只绑 `127.0.0.1`、OSS endpoint 自检、`AIMASTER_ENABLED` 仍是预期值、磁盘水位、关键表与约束存在。
6. **记录**：`runbook §17` 追加一行：标签、备份路径、迁移版本、冒烟结果、操作人。

### 7.2 回滚

- **应用**：换回上一个已知 good 的标签/SHA。
- **表结构**：迁移遵守「扩展 → 部署 → 收缩」——一个发布里只加列/加表；删列、改名放到下一个发布。这样回滚应用时不需要回滚结构。
- **数据**：从第 2 步备份恢复；会丢失备份后的写入，上线前可接受，上线后要在维护窗口做。

### 7.3 部署脚本

`deploy/deploy.sh`、`deploy/compose.prod.yml` 与 `.env.prod.example` **在第一份可运行代码合入时创建**。当前不创建空脚本，避免「看起来有部署流程、实际跑不起来」。

## 8. 密钥与配置

| 项 | 位置 | 规则 |
|---|---|---|
| 本机 `.env` | 仓库根，已被 gitignore | 只放开发探针需要的键；不进仓库 |
| 生产 `.env` | `/data/app/.env`，root 600 | 不在代码目录内，不随部署覆盖 |
| 测试 `.env` | 测试 ECS，root 600 | 不放生产凭证 |
| OSS | 实例 RAM 角色 | 机器上零长期 AccessKey |
| CI secrets | GitHub Secrets | 当前不需要；将来只放镜像推送密码，不放业务密钥 |
| SSH / 部署密钥 | 本机钥匙串 / 服务器 `~/.ssh` | 只读部署密钥；不进仓库 |

日志与错误上报不得出现 API Key、Authorization、Cookie、完整 ODS key、临时签名 URL。

## 9. 现在还不成立的部分

这一节是给后来者看的，防止把目标流程当成已运行的事实：

1. **没有生产 ECS**，也没有生产环境；现有唯一实例是测试环境，规则见 §0、§2.2。

3. **CI 只验证文档与密钥**，不验证代码、迁移或运行时。

6. **`server-access.md` 与 runbook §3.1 的 SSH 别名冲突**：按 2026-10-14 决定以 steering 为准；runbook 待同步。

## 10. 如何证明这条流水线有效

按顺序做，每一步都要留下证据：

1. 在分支上故意提交一个含假密钥的文件 → `verify.sh` 与 CI 必须变红。
2. 故意制造一个断链 → CI 必须变红。
3. 删除一个 spec 的 `requirements.md` → CI 必须变红。
4. 在干净环境下跑 `./scripts/verify.sh` → 必须变绿。
5. 应用代码出现后：在空库上从零执行迁移 → 结构与 v2 验收查询一致。
6. 首次真实部署：备份 → 迁移 → 换标签 → 冒烟；把耗时与结果记入 runbook §17。
7. 恢复演练：用逻辑备份恢复到临时库，核对行数与 CHECK 约束，记录耗时，删除临时库。

## 11. 与 hbdam 的差异与理由

| hbdam 做法 | hbecho 的取舍 | 理由 |
|---|---|---|
| Next.js + Drizzle + MySQL + PostgreSQL/pgvector | **不继承应用栈** | hbecho 的应用框架/ORM/队列未冻结（ADR-0004） |
| extract 镜像 + ACR + 测试机 devloop | **暂不建镜像链路** | 没有应用镜像；先建会制造空转的流水线 |
| 品牌数据隔离 + 6 个静态门禁 | **不继承具体门禁** | 领域不同；hbecho 的门禁应由 constitution 与第一个 spec 决定，不复制品牌规则 |
| hbdam 同账号一套测试 / 生产 ECS | **当前只有测试 ECS，生产待购** | 用户 2026-10-25 更正：现有唯一实例就是测试机；没有购买生产 ECS |
| Workbench only | **继承** | 2026-10-14 的决定明确适用于 hbecho |
| 一个 spec 一条分支、推两次 | **继承** | 单人项目、主干开发，规则与栈无关 |
| ACR 企业版分发 | **暂缓，按需决定** | 先有镜像再决定；不得默认 ghcr |
