## 2. 核心概念

| 术语 | 定义 |
|---|---|
| **指标 Metric** | 一个有唯一编码、明确口径、可聚合到多个粒度的度量。是报表列与看板卡片的唯一数据来源 |
| **维度 Dimension** | 指标的切分方式：组织维度（品牌/大区/分公司/板块/门店/专员）、内容维度（平台/形态）、时间维度（活动/周/月） |
| **粒度 Grain** | 一行数据代表的最小对象。点检表通常是"活动 × 组织节点" |
| **口径 Definition** | 指标的分子、分母、聚合方式、观测基准、过滤条件的完整说明 |
| **报表模板 ReportTemplate** | 一张报表的完整配置：列定义 + 分组 + 排序 + 表头层级 + 样式 + 导出配置 |
| **看板 Dashboard** | 卡片集合。卡片 = 指标 + 维度 + 图表类型 + 筛选器 + 阈值着色 + 下钻路径 |
| **视图 View** | 用户对明细表的个人化设置（显示哪些列、列序、筛选、排序），可私有或共享 |

## 3. 指标体系

### 3.1 三类指标来源

这是整个模块的骨架。

```
┌──────────────────────────────────────────────────────────────┐
│ 类型一：内置基础指标（系统预置，开箱可用）                        │
│   粉丝数 · 新增粉丝 · 点赞 · 评论 · 转发 · 收藏 · 互动总数        │
│   关注数 · 作品数 · 发布内容数 · 账号数 · 门店数 · 发布率 …        │
│   → 业务在 BI 报表中自行显示 / 隐藏                              │
├──────────────────────────────────────────────────────────────┤
│ 类型二：考核项派生指标（业务配考核项时自动产生）                    │
│   每个考核项自动派生 3 个指标：                                  │
│     {别名}_完成人数 · {别名}_完成率 · {别名}_命中内容数            │
│   → 业务配完考核项，报表配置里立刻能选到                          │
├──────────────────────────────────────────────────────────────┤
│ 类型三：自定义指标（业务基于前两类做二元运算）                      │
│   如：人均互动数 = 互动总数 / 参与专员数                          │
│       人均发布数 = 发布内容数 / 参与专员数                        │
│   → 受限表达式，只支持二元运算与常数，不支持嵌套                    │
└──────────────────────────────────────────────────────────────┘
```

**类型二是"配了啥才能看见啥"的实现机制**。业务不需要理解指标字典——他配完活动考核项，去报表配置里就能直接看到对应的可选列。这避免了"配一次考核要在规则、达标定义、指标、报表四个地方各配一遍"。

### 3.2 内置基础指标清单

#### 账号与粉丝

| 指标编码 | 名称 | 计算 | 粒度 | 注意 |
|---|---|---|---|---|
| `account_count` | 账号数 | COUNT(DISTINCT account) | 任意组织粒度 | 受公共条件的平台/形态限定 |
| `account_active_count` | 正常账号数 | 同步状态正常的账号数 | 同上 | 用于剔除采集异常干扰 |
| `follower_total` | 总粉丝数 | SUM(最后观测粉丝数) | 同上 | **最后观测值**，非实时 |
| `follower_delta` | 新增粉丝数 | SUM(区间末快照 − 区间初快照) | 同上 | ⚠️ 见下方说明 |
| `following_total` | 总关注数 | SUM(该账号关注他人数) | 同上 | 与粉丝数是两个不同概念 |
| `favorited_total` | 总获赞数 | SUM(账号累计获赞) | 同上 | 平台提供的账号级累计值 |
| `post_total_platform` | 平台作品总数 | SUM(平台显示的作品数) | 同上 | 用于与已采集数对比查漏 |
| `post_collected_count` | 已采集内容数 | COUNT(contents) | 同上 | |

**`follower_delta`（新增粉丝数）的口径说明** —— 这个指标有三个陷阱，必须在定义里写死：

1. **依赖 `account_snapshots` 的区间首尾差值**，不是任何单一字段。
2. **最小粒度是周**。因为每周同步一次，快照是周级的。业务想看"618 期间新增粉丝"，实际是"最接近活动开始的那次快照 → 最接近活动结束的那次快照"的差值，边界有最多 6 天误差。报表上要标注实际取用的两个快照日期。
3. **可能为负**（掉粉）。汇总时不能简单当正数处理，人均值与占比要考虑负数。

#### 内容与互动

| 指标编码 | 名称 | 计算 | 观测基准 |
|---|---|---|---|
| `content_published_count` | 发布内容数 | COUNT(contents in window) | — |
| `likes_total` | 点赞总数 | SUM(like_count) | 需声明 |
| `comments_total` | 评论总数 | SUM(comment_count) | 需声明 |
| `shares_total` | 转发总数 | SUM(share_count) | 需声明 |
| `collects_total` | 收藏总数 | SUM(collect_count) | 需声明 |
| `interactions_total` | 互动总数 | SUM(赞+评+转+收) | 需声明 |
| `interactions_avg_per_content` | 篇均互动 | interactions_total / content_published_count | 需声明 |
| `best_content_url` | 最佳作品链接 | 组织内点赞最高的内容 | 需声明 |

**所有互动类指标必须声明观测基准**（`last_observed` / `n_day`），见 §3.6。

#### 组织与覆盖

| 指标编码 | 名称 | 计算 |
|---|---|---|
| `dealer_count` | 门店数 | COUNT(DISTINCT dealer) |
| `staff_count` | 专员数 | COUNT(DISTINCT staff) |
| `participant_count` | **参与专员数** | 活动公共条件圈定的专员数 ← **这是完成率的统一分母** |
| `posted_staff_count` | 有发布的专员数 | 窗口内至少发 1 条的专员数 |
| `post_rate` | 发布率 | posted_staff_count / participant_count |
| `silent_staff_count` | 停更专员数 | participant_count − posted_staff_count |

#### 数据质量

| 指标编码 | 名称 | 用途 |
|---|---|---|
| `sync_success_rate` | 同步成功率 | 数据可信度的前置判断 |
| `data_freshness` | 数据鲜度 | 最后成功同步时间 |
| `asset_completeness` | 素材归档完整率 | 封面/背景图缺失比例 |
| `window_overflow_count` | 窗口溢出账号数 | 可能漏采的账号数（见大纲 §0.4） |

**这四个指标要出现在每张报表的页脚或看板角落。** 数据质量不透明时，业务会用错数据而不自知。旧系统的"全量明细 Excel"里已经有类似信息（链接一致性校验、最近爬取时间），但没产品化。

### 3.3 考核项派生指标的自动派生规则

业务在活动下创建考核项时，系统自动向指标字典注册三个指标：

| 派生指标 | 编码模式 | 计算 | 说明 |
|---|---|---|---|
| 完成人数 | `item_{itemId}_achieved` | COUNT(达标的专员) | 分子 |
| 完成率 | `item_{itemId}_rate` | `item_{itemId}_achieved / participant_count` | 分子分母同源 |
| 命中内容数 | `item_{itemId}_hits` | COUNT(命中的内容) | 用于分析"是集中在少数人还是普遍发" |
| 待定人数 | `item_{itemId}_pending` | COUNT(因信号缺失待定的专员) | 数据透明，见规则引擎 §8.5 |

**显示名 = 考核项别名 + 指标后缀**：考核项别名「国庆营销视频」→ 指标显示名「国庆营销视频 · 完成人数」、「国庆营销视频 · 完成率」。

**改别名只改显示名**，指标编码基于 `itemId` 不变，报表列绑定不断。

**综合完成**：`counts_toward_final = 1` 的考核项自动组合成一个 composite 考核项，同样派生三个指标。这替代旧系统硬编码的 `final_complete`。

### 3.4 自定义指标

业务可基于内置与派生指标做**受限的二元运算**：

```json
{
  "code": "custom_interactions_per_staff",
  "name": "人均互动数",
  "expression": {
    "op": "divide",
    "left":  { "metric": "interactions_total" },
    "right": { "metric": "participant_count" }
  },
  "format": "number",
  "decimals": 1
}
```

**刻意限制**：只支持 `add / subtract / multiply / divide` 四则二元运算，操作数只能是「已有指标」或「常数」，**不支持嵌套**。理由：无限表达能力会让指标字典退化成另一个 DSL，出错方式隐蔽且无法校验。真需要复杂计算时，走"新增内置指标"（研发实现，可测试可校验）。

除零处理：分母为 0 时返回 `null`（显示为 `—`），不返回 0。这个区分很重要——"0%" 和"无数据"是不同的业务含义。

### 3.5 指标定义模型

```sql
CREATE TABLE metric_definitions (
  code            VARCHAR(64)  NOT NULL PRIMARY KEY,
  name            VARCHAR(128) NOT NULL,
  source_type     ENUM('builtin','item_derived','custom') NOT NULL,
  -- item_derived 时的来源
  assessment_item_id INT       DEFAULT NULL,
  derived_kind    ENUM('achieved','rate','hits','pending') DEFAULT NULL,
  -- 口径
  numerator_def   JSON         DEFAULT NULL,  -- 分子定义
  denominator_def JSON         DEFAULT NULL,  -- 分母定义（比率类必填）
  aggregation     ENUM('sum','count','count_distinct','avg','max','min','ratio','custom') NOT NULL,
  metrics_basis   ENUM('last_observed','n_day','not_applicable') NOT NULL DEFAULT 'not_applicable',
  n_day           INT          DEFAULT NULL,  -- metrics_basis='n_day' 时的 N
  -- 支持粒度
  supported_grains JSON        NOT NULL,      -- ["region","branch","sector","dealer","staff"]
  -- 展示
  unit            VARCHAR(16)  DEFAULT NULL,  -- '%' / '人' / '条'
  format          ENUM('integer','decimal','percent','text','url') NOT NULL,
  decimals        TINYINT      DEFAULT 0,
  higher_is_better TINYINT(1)  DEFAULT 1,     -- 阈值着色方向
  -- 治理
  definition_note TEXT,                        -- 业务口径说明，展示在列悬浮提示
  owner_user_id   INT          DEFAULT NULL,
  status          ENUM('active','deprecated') NOT NULL DEFAULT 'active',
  created_at      DATETIME     NOT NULL
);
```

### 3.6 两条强制校验

**校验一：分子分母同源**

比率类指标保存时校验「分子人群 ⊆ 分母人群」。旧系统有一个真实缺陷：`final_complete` 的分子条件不要求"认证通过"，但分母是"认证通过专员数"，导致比率理论上可超过 100%。

实现：分子与分母的人群定义都归约为一组过滤条件，校验分子条件集 ⊇ 分母条件集（条件越多人群越小）。不满足则拒绝保存并提示具体冲突项。

**统一分母**：所有考核项完成率的分母都是 `participant_count`（活动公共条件圈定的专员数），不再用"认证通过数"（业务已确认该字段将剔除）。

**校验二：观测基准必须显式声明**

所有互动类指标必须声明 `metrics_basis`：

| 基准 | 含义 | 适用 |
|---|---|---|
| `last_observed` | 最近一次同步观测到的值（内容滑出 API 窗口后冻结） | 展示、当期总量汇总 |
| `n_day` | 内容发布满 N 天时的观测值 | 排名、跨期对比、优秀内容筛选 |

**为什么必须显式声明**：API 每次只返回最近 ~20 条内容，一条内容在窗口内会被反复观测，滑出后数值冻结。所以早发的内容天然积累更久、数字更大。同一张报表混用两种基准会让新旧内容不可比，也会让"早发"而非"发得好"的人占优。

报表列必须在悬浮提示里显示基准与观测时点（如"最后观测：2026-10-08"）。否则业务质疑"我明明有 150 赞怎么显示 80"时无法回答。

**N 的取值待业务确认**（建议 7 天，按每周同步的观测节奏覆盖率最高）。

## 4. 三张核心表

这是本模块最重要的交付物。三张表对应旧系统已验证的三个导出（`full-detail` / `video-detail` / `checklist`），但全部改为配置驱动。

### 4.1 产出链路与关系

```
【活动级公共条件】时间 · 平台 · 形态 · 板块 · 参与范围
        ↓ 规则引擎 §8.2 圈定
┌──────────────────────────────────────────────────────────┐
│ 表1 全量数据表                                             │
│ 一行 = 一条内容（含未命中任何考核项的）                        │
│ 规模 ≈ 4~7 万行/活动                                       │
│ 用途：分母核查 · 数据完整性 · 未命中原因分析                    │
└──────────────────────────────────────────────────────────┘
        ↓ 筛出命中任一考核项的
┌──────────────────────────────────────────────────────────┐
│ 表2 业务明细表                                             │
│ 一行 = 一条命中内容 + 命中的考核项别名 + 证据                  │
│ 规模 ≈ 表1 的 10~30%                                       │
│ 用途：业务核对达标内容 · 证据下钻 · 优秀内容筛选                 │
└──────────────────────────────────────────────────────────┘
        ↓ 达标聚合 + 组织归集（按 org_snapshot）+ 预聚合
┌──────────────────────────────────────────────────────────┐
│ 表3 点检表                                                 │
│ 一行 = 一个组织节点（大区 / 分公司 / 可下钻门店）               │
│ 列 = 参与专员数 + 各考核项（完成人数 / 完成率）+ 基础指标          │
│ 用途：考核 · 通报 · 催办                                      │
└──────────────────────────────────────────────────────────┘

三张表互相下钻：表3 某格 → 表2 该组织的命中内容 → 表1 该专员的全部内容
```

**表1 存在的核心价值**：它是表3 分母的可核查依据。业务质疑"为什么我们分公司完成率只有 40%"时，能一路下钻到"这 60% 的人到底发了什么"。旧系统的这个能力藏在一个手工触发的 Excel 导出里，新设计把它做成一等报表。

### 4.2 表1 全量数据表

| 项 | 设计 |
|---|---|
| 数据源 | `queryCampaignFullContents(campaignId, filters, pagination)` |
| 配置方式 | **明细表模式：全字段自选显示/隐藏 + 拖拽列序 + 保存视图** |
| 默认列 | 大区 · 分公司 · 板块 · 门店名称 · 专员姓名 · 平台 · 账号昵称 · 内容标题 · 发布时间 · 时长 · 话题 · 点赞 · 评论 · 转发 · 收藏 · 互动数 · 各考核项命中标记 |
| 可选列 | 门店编码 · 经销商名称 · 联系方式 · 主页链接 · 粉丝数 · 账号作品总数 · 已采集数 · 封面链接 · 内容链接 · 最后同步时间 · 同步状态 · 数据来源（供应商/legacy） |
| 考核项命中标记列 | 每个考核项一列，值为 `✓命中` / `✗未命中` / `⏳待定` / `—不适用`，可点击展开证据 |
| 附加视图 | **账号维度汇总**（一行 = 一个专员账号：发布数、命中数、最近发布日、最后同步时间、平台作品数 vs 已采集数） |
| 筛选 | 组织维度 · 平台 · 形态 · 考核项命中状态 · 发布时间段 · 是否有互动 |
| 行内着色 | 命中任一考核项 → 浅绿；未命中 → 无色；待定 → 浅黄；同步异常 → 浅红 |

**账号维度汇总视图的价值**：它直接回答"谁没发""谁的数据没同步上"。旧系统 `full-detail.xlsx` 的第三个 sheet 就是这个，且带"链接一致性"校验（`home_url` 的 sec_uid 与 `account_identifier` 是否一致），这个校验要保留并升级为数据质量指标。

### 4.3 表2 业务明细表

| 项 | 设计 |
|---|---|
| 数据源 | `queryCampaignMatchedContents(campaignId, { itemIds?, ...filters }, pagination)` |
| 配置方式 | 明细表模式（全字段自选） |
| 独有列 | **命中考核项**（多个别名的标签列）· 证据摘要 · 命中时间 |
| 独有筛选 | 按考核项筛选（多选）· 按证据类型筛选（靠文案命中 / 靠画面命中） |
| 可选嵌入 | 封面图缩略图列（导出时嵌入 Excel，走 §8 异步导出） |
| 排序 | 默认组织序，可切互动量降序（用于挑优秀内容） |

**"按证据类型筛选"是个有价值的能力**：当业务配了 composite 考核项（文案版 OR 画面版）时，能看出"靠文案达标的多还是靠画面达标的多"，这直接指导下次活动的规则设计。

### 4.4 表3 点检表

这是考核的主表，也是列结构最需要动态生成的表。

**列结构（三层表头，与旧系统一致但动态生成）**

```
┌────────────────────────────────────────────────────────────────────────┐
│                26年海信新媒体专员国庆活动点检表（水机）                      │  ← 第1行 总标题
├──────┬───────┬────────┬──────────────┬──────────────┬─────┬─────┬──────┤

```

| 项 | 设计 |
|---|---|
| 数据源 | 预聚合表 `ads_campaign_org_metrics`（§5） |
| 配置方式 | **汇总表模式：从指标选择器挑指标 → 拖成列** |
| 固定列 | 大区 · 分公司（分组维度）· 参与专员数（分母） |
| 动态列 | **每个考核项 2 列**（完成人数 / 完成率），列序由考核项 `sort_order` 决定 |
| 可选列 | 命中内容数 · 待定人数 · 总点赞 · 总互动 · 篇均互动 · 发布率 · 新增粉丝 · 最佳作品链接 · 任意自定义指标 |
| 分组维度 | 大区 → 分公司（默认）；可切换为 大区 → 分公司 → 门店，或 板块 → 分公司 |
| 排序 | 组织主档的 `sort_order`（默认）或按某指标排序 |
| 阈值着色 | 每列可配（如完成率 < 60% 红、≥ 90% 绿），方向由指标的 `higher_is_better` 决定 |
| 空行策略 | 可配：显示所有组织节点（含无数据的，值为 `—`）/ 只显示有数据的 |
| 页脚 | 数据截至时间 · 基于哪版考核项 · 待定内容数 · 同步成功率 |

**"空行策略"是旧系统的一个隐含行为**：旧系统按硬编码的 42 个分公司名单输出，没数据的分公司也出一行（值为 null）。这个行为对通报有意义（能看出谁完全没参与），但要做成可配置而不是写死。

**页脚的数据质量信息是新增的**。旧系统的点检表只有数字，业务无法判断"这个 40% 是真的差，还是有一半账号没同步上"。

## 5. 预聚合引擎

### 5.1 ADS 宽表

```sql
CREATE TABLE ads_campaign_org_metrics (
  id             BIGINT PRIMARY KEY AUTO_INCREMENT,
  campaign_id    INT          NOT NULL,
  -- 组织粒度：用 grain + key 表达任意层级
  grain          ENUM('brand','region','branch','sector','dealer','staff') NOT NULL,
  org_key        VARCHAR(64)  NOT NULL,   -- region_id / branch_id / dealer_id / staff_id
  region_id      INT          DEFAULT NULL,   -- 冗余，便于筛选与下钻
  branch_id      INT          DEFAULT NULL,
  sector         VARCHAR(20)  DEFAULT NULL,
  -- 指标值：稀疏存储
  metric_code    VARCHAR(64)  NOT NULL,
  metric_value   DECIMAL(20,4) DEFAULT NULL,   -- NULL = 无数据（区别于 0）
  metric_text    VARCHAR(500) DEFAULT NULL,    -- 文本型指标（最佳作品链接）
  -- 溯源
  computed_at    DATETIME     NOT NULL,
  source_run_ids JSON         DEFAULT NULL,    -- 依据哪些判定批次
  UNIQUE KEY uq_metric (campaign_id, grain, org_key, metric_code),
  KEY idx_lookup (campaign_id, grain, metric_code)
);
```

**为什么用稀疏行存（metric_code + value）而不是宽列**：考核项数量由业务决定，无法预先定列。稀疏行存让新增考核项零 DDL。代价是查询要 PIVOT，但数据量很小（一个活动 × 43 个分公司 × 20 个指标 ≈ 860 行），性能无压力。

规模估算：`活动数(6/年) × 组织节点(约 1,400) × 指标数(约 30) ≈ 25 万行/年`。完全可控。

### 5.2 触发链路

```
周末数据同步完成
      ↓
增量判定（规则引擎，各考核项）
      ↓
达标聚合（专员级达标结论）
      ↓
composite 考核项聚合
      ↓
预聚合：按 staff → dealer → branch → region → brand 逐级上卷
      ↓
写 ads_campaign_org_metrics（幂等 upsert）
      ↓
失效报表与看板缓存
```

**幂等 upsert**：同一 `(campaign_id, grain, org_key, metric_code)` 覆盖写。重算安全。

**逐级上卷的注意点**：完成率不能上卷（分公司完成率的平均 ≠ 大区完成率）。必须**分子分母分别上卷，再在目标粒度上做除法**。这是聚合类指标最常见的错误来源，要在实现里强制：比率类指标不提供 `sum` 上卷，只提供"分子上卷 / 分母上卷"。

### 5.3 重算与范围收窄

| 场景 | 重算范围 |
|---|---|
| 某考核项判定完成 | 该考核项相关的全部指标 × 该活动全部组织节点 |
| 指标定义变更 | 该指标 × 引用它的全部活动（需确认，可能量大） |
| 组织结构调整 | 受影响组织节点的全部指标 |
| 手工触发 | 用户指定活动与粒度 |

**指标定义变更要有影响面提示**：改一个内置指标的口径会影响所有历史报表。UI 上必须展示"该指标被 N 张报表、M 个看板引用，影响 K 个历史活动"，并要求确认。

## 6. 报表配置

### 6.1 两种报表模式（这是回答"全字段自选"的关键）

| | 明细表模式 | 汇总表模式 |
|---|---|---|
| 适用 | 表1 全量数据表、表2 业务明细表、账号台账 | 表3 点检表、组织汇总表 |
| 一行 | 一个对象（内容 / 账号 / 专员） | 一个组织节点 |
| 一列 | **字段**（对象的直接属性） | **指标**（分子/分母/聚合的组合） |
| 配置方式 | ✅ **全字段自选显示/隐藏 + 拖拽列序 + 保存视图** | ❌ 不能选字段，要从**指标选择器**挑指标 |
| 谁能配 | 所有角色（个人视图） | 仅超管 + 总部（模板） |
| 实现成本 | 低，可先做 | 依赖指标字典 |

**明细表可以按"全字段自选"来做**，因为每一列都是对象的直接属性，没有口径问题。这正是你说的做法，对这类表是对的。

**汇总表不能这样做**，因为"国庆营销视频完成率"不是任何一张表的字段，它是 `达标专员数 / 参与专员数` 的计算结果。它的配置方式是从指标选择器里挑——而指标选择器里的内容正是 §3.1 的三类指标。

### 6.2 明细表的字段自选

```sql
CREATE TABLE report_views (
  id            INT PRIMARY KEY AUTO_INCREMENT,
  report_key    VARCHAR(64)  NOT NULL,   -- 'campaign_full_contents' / 'campaign_matched_contents'
  name          VARCHAR(64)  NOT NULL,
  owner_user_id INT          NOT NULL,
  visibility    ENUM('private','shared') NOT NULL DEFAULT 'private',
  column_config JSON         NOT NULL,   -- [{field:"branch", visible:true, order:1, width:100}, ...]
  filter_config JSON         DEFAULT NULL,
  sort_config   JSON         DEFAULT NULL,
  is_default    TINYINT(1)   NOT NULL DEFAULT 0,
  created_at    DATETIME     NOT NULL,
  KEY idx_report_owner (report_key, owner_user_id)
);
```

交互要点：

- 列设置面板：全字段列表 + 复选框 + 拖拽排序 + 搜索字段
- 字段分组展示（组织字段 / 专员字段 / 账号字段 / 内容字段 / 互动字段 / 考核项 / 数据质量）
- 「另存为视图」+「设为我的默认」
- 共享视图：总部可把视图共享给分公司（只共享配置，数据仍按各自范围过滤）
- 系统预置几个常用视图：「精简版」「含互动数据」「含数据质量」「导出用完整版」

### 6.3 汇总表的报表模板

```sql
CREATE TABLE report_templates (
  id            INT PRIMARY KEY AUTO_INCREMENT,
  code          VARCHAR(64)  NOT NULL UNIQUE,
  name          VARCHAR(128) NOT NULL,       -- '标准点检表'
  report_type   ENUM('checklist','org_summary') NOT NULL,
  brand_scope   JSON         DEFAULT NULL,
  -- 分组与排序
  group_dims    JSON         NOT NULL,       -- ["region","branch"]
  sort_config   JSON         NOT NULL,       -- {"by":"org_order"} 或 {"by":"metric","code":"..."}
  empty_row_policy ENUM('show_all','only_with_data') NOT NULL DEFAULT 'show_all',
  -- 标题（支持变量）
  title_template VARCHAR(200) DEFAULT NULL,  -- '{yy}年{brand}新媒体专员{campaign}点检表（{sector}）'
  -- 样式与导出
  style_config  JSON         DEFAULT NULL,   -- 表头层级、隔行底色、冻结行列
  export_config JSON         DEFAULT NULL,   -- 是否嵌入图片、文件命名模板
  version_no    INT          NOT NULL DEFAULT 1,
  created_by    INT          NOT NULL,
  created_at    DATETIME     NOT NULL
);

CREATE TABLE report_template_columns (
  id            INT PRIMARY KEY AUTO_INCREMENT,
  template_id   INT          NOT NULL,
  -- 列引用：三种之一
  ref_type      ENUM('dimension','metric','assessment_item_group') NOT NULL,
  ref_key       VARCHAR(64)  DEFAULT NULL,   -- dimension:'branch' / metric:'likes_total'
  assessment_item_id INT     DEFAULT NULL,   -- assessment_item_group 时
  item_sub_metrics JSON      DEFAULT NULL,   -- ["achieved","rate"] 该考核项要展开哪几个子列
  -- 展示
  display_name  VARCHAR(64)  DEFAULT NULL,   -- 覆盖默认名（默认取指标名或考核项别名）
  width         INT          DEFAULT NULL,
  align         ENUM('left','center','right') DEFAULT 'center',
  number_format VARCHAR(32)  DEFAULT NULL,
  -- 阈值着色
  color_rules   JSON         DEFAULT NULL,   -- [{op:"lt",value:60,bg:"#FFCDD2"},{op:"gte",value:90,bg:"#C8E6C9"}]
  sort_order    INT          NOT NULL,
  KEY idx_template (template_id, sort_order)
);
```

**`ref_type = 'assessment_item_group'` 是关键设计**：一个列定义引用一个考核项，展开成 2~4 个子列（完成人数 / 完成率 / 命中内容数 / 待定人数）。这样：

- 考核项别名自动成为主表头（跨列合并）
- 子指标名自动成为子表头
- 业务改别名，表头跟随
- 加一个考核项，模板里加一个列定义即可（或配置"自动包含全部考核项"）

**模板可配"自动包含全部考核项"**：这样业务加考核项后点检表自动多列，完全零配置。这应该是默认行为。

### 6.4 多层表头的生成

表头层级由列定义结构自动推导，不需要业务手工画：

| 列的 ref_type | 表头行为 |
|---|---|
| `dimension` | 跨第 2~3 行合并（如"大区""分公司"） |
| `metric`（单指标） | 跨第 2~3 行合并（如"总点赞"） |
| `assessment_item_group` | 第 2 行 = 考核项别名（跨子列合并），第 3 行 = 各子指标名 |
| 总标题 | 第 1 行，跨全部列合并，内容由 `title_template` 渲染 |

`title_template` 支持变量：`{yy}` `{yyyy}` `{brand}` `{campaign}` `{sector}` `{date_range}`。旧系统的标题是字符串拼接写死的（`${shortYear}年${brand}新媒体专员${campaignName}点检表`），这里改为模板。

### 6.5 模板复制

业务最实际的诉求：**去年 618 的点检表模板复制一份，换个活动就能用**。

复制时的处理：

| 引用类型 | 复制行为 |
|---|---|
| `dimension` | 直接复制 |
| `metric`（内置 / 自定义） | 直接复制 |
| `assessment_item_group` | ⚠️ 考核项属于旧活动，需**映射到新活动的考核项**。UI 提供映射向导：按别名相似度推荐（"5G荣耀家产品视频" → "5G荣耀家新品视频"），业务确认 |
| 若配了"自动包含全部考核项" | 无需映射，直接适用新活动 |

**这是"自动包含全部考核项"应该做默认行为的另一个理由**——它让模板复制无需映射。

### 7.2 四角色的默认看板

看板配置由超管+总部维护，但每个角色有各自的默认首页：

| 角色 | 默认看板内容 |
|---|---|
| 超级管理员 | 四品牌横向对比 · 各品牌进行中活动进度 · 系统健康度（同步成功率 / 配额用量 / 队列积压） |
| 总部人员 | 本品牌大盘 · 进行中活动的各考核项完成率 · 大区对比（柱图）· 分公司完成率明细表 · 数据质量 |
| 分公司人员 | 本分公司完成率 · 门店完成率明细表 · 未达标专员名单（可直接催办）· 本区优秀内容 |
| 经销商个人 | 我的达标情况（各考核项）· 我的内容表现 · 待办任务 · 推荐学习内容 |

**排行榜类卡片首版不做**（业务已确认）。总部与分公司的对比需求用「明细表卡片 + 按指标排序」满足——功能上等价，但避免了排行榜特有的可见范围争议（下属能否看到同级排名）与激励副作用。

**经销商看板的"我的达标情况"要能下钻到证据**——这是他理解"为什么我没达标"的唯一途径，直接减少申诉成本。

### 7.3 配置权限与数据范围严格分离

| | 谁能改 | 数据范围 |
|---|---|---|
| 看板配置 / 报表模板 | 仅超管 + 总部 | — |
| 看板/报表的数据 | — | **按查看者的 DataScope 过滤** |

**同一张看板配置，不同角色打开看到不同数据**。总部配的"分公司完成率明细表"，分公司人员打开只看到本分公司那一行及其下属门店，经销商只看到自己。这由 DataScope 在查询层强制注入，不依赖前端隐藏。

**明细表的个人视图**所有角色都能存，因为它只是列显示配置，不涉及数据范围。

## 8. 导出中心

### 8.1 全部导出异步化

旧系统的导出是同步生成、全量进内存（`LIMIT 100000` + 30 并发图片 buffer），单个请求就能吃掉数百 MB。新设计：

```
用户点导出 → 创建导出任务（记录模板/视图/筛选/范围）→ 入队 → 立即返回任务号
      ↓
Worker：流式查询 → 分批写 Excel（ExcelJS streaming）→ 图片按需下载嵌入
      ↓
上传 OSS → 更新任务状态
      ↓
下载中心：任务列表、进度、下载链接（签名 URL）、7 天生命周期
```

```sql
CREATE TABLE export_jobs (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id       INT          NOT NULL,
  export_type   ENUM('full_contents','matched_contents','checklist','org_summary','account_ledger') NOT NULL,
  campaign_id   INT          DEFAULT NULL,
  template_id   INT          DEFAULT NULL,
  view_id       INT          DEFAULT NULL,
  params        JSON         NOT NULL,   -- 筛选条件、是否嵌图、范围快照
  status        ENUM('queued','running','done','failed','expired') NOT NULL,
  progress      TINYINT      DEFAULT 0,
  row_count     INT          DEFAULT NULL,
  file_key      VARCHAR(300) DEFAULT NULL,
  file_size     BIGINT       DEFAULT NULL,
  error_msg     TEXT,
  created_at    DATETIME     NOT NULL,
  finished_at   DATETIME     DEFAULT NULL,
  expires_at    DATETIME     DEFAULT NULL
);
```

### 8.2 Excel 渲染要保留的旧系统能力

旧系统的 Excel 导出有几处业务已经习惯的细节，要在模板化后保留：

| 能力 | 实现 |
|---|---|
| 三层表头 + 单元格合并 | 由 §6.4 的表头推导生成 |
| 冻结行列 | `style_config.freeze` |
| 隔行底色 | `style_config.row_stripe` |
| 条件着色（命中整行标绿、异常标红） | 列的 `color_rules` + 行级规则 |
| 嵌入封面图 / 背景图 | `export_config.embed_images`，Worker 按内容指纹批量拉取 OSS 后 `addImage` |
| 超链接列（主页链接、内容链接） | 列的 `format = 'url'` |
| 文件名模板 | `export_config.filename_template`，支持同 §6.4 的变量 |
| 页脚口径说明 | 自动生成：活动名、时间范围、数据截至、考核项版本、待定数、同步成功率 |

**图片嵌入必须限流**。旧系统是 30 并发拉图 + 全量进内存。新设计：流式分批（每 200 行一批）、限并发、单文件图片数上限（超限提示改用"仅链接"模式）。

## 9. 数据范围与权限

| 对象 | 配置权限 | 数据范围 |
|---|---|---|
| 指标定义（内置） | 仅超管 | — |
| 指标定义（自定义） | 超管 + 总部 | 按品牌 |
| 报表模板 | 超管 + 总部 | 按品牌 |
| 明细表个人视图 | **所有角色** | — |
| 看板 | 超管 + 总部 | 按品牌 + 按角色可见性 |

### 9.1 分公司的报表权限（业务已确认）

**分公司人员对点检表为「只读、限本区」**：

| 能力 | 分公司人员 |
|---|---|
| 查看表3 点检表 | ✅ 可看，数据限本分公司及其下属门店 |
| 配置报表模板 / 增删列 / 改指标 | ❌ 不可 |
| 查看表1 / 表2 明细表 | ✅ 可看，限本区 |

理由：分公司要管下属门店，不给点检表无法工作。但模板配置权保留在超管+总部，保证全体系口径一致。

## 10. 与自助分析、取数 Agent 的边界

三者容易混淆，明确分工：

| | 报表与看板（本模块） | 自助分析（E5） | 取数 Agent（H7） |
|---|---|---|---|
| 定位 | **预定义模板 + 配置化** | 即席查询 | 自然语言问数 |
| 谁配 | 超管 + 总部配模板，全员使用 | 业务自己拖维度指标 | 任何人打字提问 |
| 数据源 | 预聚合 ADS 表 | 语义层（可查明细） | 语义层 + 只读网关 |
| 口径 | 指标字典（唯一） | 指标字典（唯一） | 指标字典（唯一） |
| 输出 | 固定结构，可导出，进考核 | 临时结果，可存为看板 | 一次性结果表/图 |
| 适用 | 周期性、结构固定、要对外通报 | 探索性、维度组合不定 | 长尾问题、临时核查 |
| 性能 | 秒级（预聚合） | 有行数与超时上限 | 有行数与超时上限 |

**三者共用同一套指标字典**，所以数值必然一致。这是"口径唯一"原则的落地方式。

**明确的分界**：**进考核、要通报的数据必须走报表模板（预聚合）**，不走自助分析或 Agent。后两者是给人看的探索工具，结果不进考核链路。

| 14 | 配置与范围分离 | 总部配的看板，分公司账号打开只看到本区数据 |

## 12. 遗留问题

### 12.1 已确认

| # | 事项 | 结论 |
|---|---|---|
| 1 | 分公司的报表权限 | **点检表与明细表可只读查看，限本区；不可配置模板**。见 §9.1 |
| 2 | 排行榜卡片 | **首版不做**。对比需求用「明细表卡片 + 按指标排序」满足，避免可见范围争议 |
