## 一、这个域管什么

### 1.1 四个问题

```
看到什么字     → 标题、正文里的话题、@ 提及、POI、链接
图长什么样     → 主页背景 / 头像 / 封面与标准图像不像
算过没有       → 哪条内容、哪一版能力、什么时候算的
算不出来怎么办 → 没这个字段、本来不适用、算失败了、算得太旧
```

### 1.2 不管什么

| 事情 | 归谁 |
|---|---|
| 内容、主页、评论、媒资怎么采、怎么存 | A 数据底座 |
| 这个信号算不算命中、阈值定多少 | D 规则与考核 |
| 完成率怎么算、点检表怎么排 | E 指标与看板 |
| 谁能触发重算、谁能看证据 | B 访问控制 |
| 标准图从哪来、选哪张、跟哪个活动绑定 | D（规则参数，随规则版本冻结） |
| OCR、口播转写、视觉大模型、以图搜图 | 2.0 |
| 页面长什么样 | F 业务应用 |

### 1.3 一条主线

```
A 把内容和图片存成不可变的事实
→ C 从中抽出可判定的测量值，同时记下用的是哪一版能力、什么时候算的
→ D 的规则只读测量值做判定，绝不自己调识别
→ 信号不够时 D 提需求，C 只对规则圈定的候选补算
→ 能力升级后只重算受影响的信号，不重判全部历史
```

**C 的职责到「可判定的测量值」为止。** 它不回答「这条内容有没有达标」，只回答「这条内容的封面与这张标准图的匹配度是 0.83」。

## 二、用户与场景

### 2.1 谁在用

| 使用者 | 来这个域做什么 | 频率 |
|---|---|---|
| 平台运营 | 查某条内容有哪些信号、哪一版、什么时候算的 | 每周 |
| 总部/分公司运营 | 看到「这条内容为什么没命中」时，顺着证据追到信号 | 每月 |
| D 规则与考核（系统） | 按规则声明的依赖信号读取测量值；缺信号时提需求 | 持续 |
| 研发 | 注册新信号、升能力版本、触发受控重算 | 按发版 |

**业务用户不直接操作 C。** 他们看到的是规则判定与证据；C 只在证据下钻时露出。

### 2.2 三条真实路径

| # | 场景 | 走哪条链路 |
|---|---|---|
| 1 | 每周同步后，新内容入库，0 档信号自动就位 | 文本信号抽取（第四章） |
| 2 | 某活动要求「主页背景与标准图一致」，规则圈定候选后跑比对 | 模板匹配（第五章） |
| 3 | 模板匹配算法升级，要知道哪些历史结果过期、要不要重算 | 能力版本与重算（第七章） |

### 2.3 规模

| 参数 | 数值 | 状态 |
|---|---|---|
| 被监控账号 | 6,000 | 已确认（D-02、D-30） |
| 支持平台（1.0） | 抖音、小红书 | 已确认 |
| 内容增量假设 | 每账号每天 1 条 → 约 218 万条/年 | **沿用旧总纲假设，待实测** |
| 特征表规模 | 一条内容一行 → 与内容表同量级 | 估算 |
| 模板匹配调用量 | 进入第 2 层时对该活动圈定范围全量执行，按候选约占 10% 估算 → 约 22 万次/年 | 估算，取决于活动与规则 |

> 旧总纲的容量测算是按 3,000 账号算的；D-30 把被监控账号改为 6,000 后，内容与特征表的年增量大约翻倍。**这不是精确预算，只用来判断「不需要大数据栈、需要按候选集控制识别调用」这个结论仍然成立。**

### 2.4 1.0 的边界

- 1.0 只做 **C1 文本信号、C2 模板匹配（图片是否一致）、C4 特征存储**（§7.1）；
- 2.0 增加 **C2 的 OCR**（图中文字）与 **C3 的音频 / 图片 / 视频理解**（§5.9）；
- **不做** pHash、向量检索（§7.1）；pHash 同时不得作为媒资判同依据（不继承清单第 7 条）；
- **不做** 分镜、机型识别等独立能力——它们由视频理解的标准化输出覆盖，不单列模块；
- **C5 向量与相似检索、C2 档 4 图像向量化明确不做**——1.0 与 2.0 都不做（2026-10-28 决策，见第十三章 13.8）；
- **不做** 任何「业务判定」——阈值、命中、达标都在 D；
- 只覆盖抖音与小红书；视频号、快手 2.0。

## 三、概念

### 3.1 什么算信号

**信号是从原始事实或素材中抽出的、可被规则直接比较的测量值。**

它不是原始字段的复制。原始字段归 A（标题、正文、时长、互动数都在内容快照里）；信号是经过解析与归一化、能被规则稳定引用的那一层。

| 例子 | 是信号吗 | 原因 |
|---|---|---|
| `published_at` | 否（是 A 的事实） | 平台返回的时间原样存着 |
| `hashtags = [#618, #海信中央空调]` | 是 | 从正文里解析、去重、归一化后得到 |
| `cover_template_score = 0.83` | 是 | 一次比对算出的测量值 |
| `is_618_campaign = true` | 否 | 这是判定，归 D |

### 3.2 两类信号：结构化与派生

| 类别 | 从哪来 | 存储 | 成本 | 1.0 例子 |
|---|---|---|---|---|
| **结构化信号** | 从 A 的字段解析 | 能走索引的列或 JSON 列 | 0 档 | 话题、@ 提及、POI、外链、正文归一化文本 |
| **派生信号** | 需要算法计算 | 特征表的信号 JSON | 档 1（本地算法） | 模板匹配得分 |

分工的理由：结构化信号要作为 0 档算子做 SQL 预过滤（把几千条剪到几百条），必须能走索引；派生信号只在候选集内存中比较，候选集已经很小。

> 结构化信号存在哪张表、用列还是 JSON，由 C 域 spec 决定；本文只要求「0 档信号必须可索引、可下推」。

### 3.3 一个信号的五态

规则只看到「命中 / 不命中 / 不知道」三值；C 内部必须把「不知道」拆细，否则运营无法判断该补采、该重算还是该改规则。

| 状态 | 含义 | 典型原因 | 规则看到 |
|---|---|---|---|
| `valid` | 算出来了 | — | 参与比较 |
| `missing` | 该有但还没有 | 还没跑、依赖的素材没归档 | unknown |
| `not_applicable` | 本来就不适用 | 图文笔记没有时长；无封面 | not_applicable |
| `failed` | 算了但失败 | 图片损坏、算法异常、超时 | unknown |
| `stale` | 有旧值，但能力已升级 | 算法版本落后于当前版本 | unknown（可回退使用旧值，须显式） |

**`missing` 与 `failed` 不能合并成 null**，`not_applicable` 不能当成 `missing`——后者会触发无意义的识别任务。

### 3.4 信号版本与时间

每个信号值必须同时带着三件事：

```
value        测量值本身
capability   产出它的能力标识与版本（如 template-match@1）
produced_at  实际产出的时间（UTC），不是内容发布时间
```

**版本要精确到单个信号，不是整张特征表。** 升级模板匹配不应让文本信号一起失效。

### 3.5 信号不是判定

- 模板匹配返回**匹配度**（0–1 的得分 + 证据），不返回「算不算达标」；
- **阈值是规则参数**，写在 D 的算子实例里，随规则版本冻结（待确认，见 13.2）；
- 因此同一次匹配结果可以被两条规则用不同阈值复用，不需要重算。

### 3.6 缓存与复用

一次识别结果的复用键是四元组：

```
素材指纹（SHA-256）+ 能力标识 + 能力版本 + 参数指纹
```

- 参数指纹包含算法参数与标准图指纹；**标准图换了就是新的参数指纹**，必须重算；
- 只按素材指纹缓存会让不同标准图读到彼此的结果（设计大纲 C2 注意点 1）；
- 复用键一旦上线再改等于历史缓存全部作废，必须在 C 域 spec 开工前定稿。

### 3.7 信号目录（2026-10-28）

信号分两类来源，**写法不同**：

- **事实信号**：A 直接提供，C 不加工（发布时间、互动数、作者 ID 等）。C 只读，不重新计算；
- **派生信号**：C 产出，带能力版本与产出时间。

> **命名规范**：`<对象>.<语义>`，如 `content.published_at`。带参数的信号按维度分开存（`image.template_score[target]`、`image.element_score[element_id][target]`）。

## 四、C1 文本信号

### 4.1 抽什么

| 信号 | 从哪抽 | 1.0 |
|---|---|---|
| 话题标签 | 正文与标题中的 `#话题` | ✅ |
| @ 提及 | `@昵称` | ✅ |
| POI / 位置 | 平台返回的地点或正文中的位置标记 | ✅ |
| 外链 | 正文中的 URL | ✅ |
| 归一化标题与正文 | 全半角、空白、不可见字符、平台专有占位符 | ✅ |
| 分词与关键短语 | 正文分词、短语抽取 | **待确认（见 13.1）** |

**不做情感、不做实体识别、不做摘要。** 这些是 2.0 或 H 域的事。

### 4.2 归一化规则

同一活动的话题，业务和专员写法不会一致；不归一化就会出现「配了 #618 却漏掉 #618大促」的假阴性。

| 情况 | 处理 |
|---|---|
| 全角 `＃` 与半角 `#` | 统一为半角 |
| 话题大小写 | 英文统一小写，中文不受影响 |
| 前后空白、连续空白 | 去除 / 合并为单个 |
| 中文标点与英文标点 | 统一为中文标点（用于文本匹配） |
| emoji 与不可见字符 | 保留原文，另存归一化副本 |
| 平台专有占位（@好友、话题跳转符） | 按平台适配器剥离，不进入正文 |

**原文永远保留。** 归一化只产生「用于匹配的那一份」，不覆盖 A 存的原始字段。

### 4.3 何时抽

- 内容快照 **finalized 之后立即抽**，0 档、免费、不阻塞同步落库；
- 抽取失败不回滚内容入库——内容事实已经成立，信号状态记为 `failed`；
- 同一内容重复入库不重复抽（按 content + snapshot + capability 幂等）。

### 4.4 抽不出来怎么办

| 情况 | 表现 |
|---|---|
| 平台没返回位置字段 | POI 为 `not_applicable`，不是空字符串 |
| 正文为空 | 归一化文本为 `valid` 的空值，话题为空数组 |
| 解析器遇到未识别格式 | 该信号 `failed`，记录原始片段，其余信号照常 |

### 4.5 平台差异

抖音与小红书的话题、@、位置在返回结构里位置不同，**解析规则按平台版本化**，不写成一个 if 分支堆。两平台的表现差异必须能在信号目录里看出来（哪个平台支持哪类信号）。

## 五、C2 素材比对与 C3 理解能力

### 5.1 三个业务问法（不区分图像对象）

2026-10-28 决策（刘学奎）：素材比对按**业务问法**定义能力，不按图像对象（主页背景 / 头像 / 封面 / 图文图片）拆分。同一能力可用于任一图像，由调用方指定对象。

| 业务问法 | 输入 | 技术手段 | 成本档 | 1.0 |
|---|---|---|---|---|
| 这张图和标准图是不是同一张 | 标准图 | 特征匹配（pHash 预筛 + SIFT / ORB 精匹配） | 1 | ✅ |
| 图里有没有某个元素 | 元素图（业务提供） | 局部特征匹配（SIFT / ORB + 单应性校验） | 1 | ✅ |
| 图里有没有某些字 | 要求出现的文字 | OCR + 字符串匹配 | 2 | ❌ 2.0 |

**三种做法统一输出 0–10 分与 11 个整数档**，每档配一张真实被测评图，供业务判断阈值。

**不做类别识别**（2026-10-28 决策）：业务不会说"要有空调外机"这种没有具体图的要求；所有元素判断都走"提供元素图 + 特征匹配"。因此视觉大模型不用于第 2 层的元素判断，只用于第 3 层的图片/视频理解。

**元素图匹配的适用边界**：它找的是"这一张具体的图"——同一设计稿、同一素材、外形基本一致时才找得到。元素要有足够纹理、在画面中不能太小、不能被大面积遮挡；纯色 logo、文字类元素特征点少，匹配不稳定，这类需求应改用文字识别。

**四类做法的成本差异很大**，实施与计费必须分开看：模板匹配是本地算法（~0），OCR 是低额外部调用，视觉大模型是中高额调用。

### 5.2 技术档位映射

| 档 | 能力 | 对应业务问法 | 1.0 |
|---|---|---|---|
| 0 | 感知哈希 pHash / dHash | 同图判定与快速预筛 | ✅ |
| **1** | **特征匹配 SIFT / ORB** | **图片是否一致、元素图是否出现** | ✅ |
| 2 | OCR | **图中是否包含指定文字** | ❌ 2.0 |
| 3 | 视觉大模型 | 第 3 层的图片理解与视频理解 | ❌ 2.0 |
| 4 | 图像向量化 | — | ❌ 明确不做（13.8） |
| 5 | 组合判定 | 由多条规则组合表达 | ❌ 不做 |

### 5.3 分数标准化与阈值选择

- C 把原始相似度**标准化为 0.0–10.0 分**，原始值与算法参数保留在证据里；
- 0–10 共 11 个整数分值，每档对应一张真实被测评图与测评结果，由 D 的界面展示，业务据此判断阈值；
- **不同做法的 0–10 分含义不同**（整图匹配分 / 元素图匹配分 / 文字命中度），阈值不可互换，也不能跨做法复用同一套分数；
- **文字检测的分数定义**：要求出现 N 个字或词，识别到 M 个，得分 `round(M ÷ N × 10)`；全部命中为 10 分。要求只有一个词时，命中即 10、未命中即 0；
- 阈值本身属于 D 的规则参数，C 只提供分值。

### 5.4 模板匹配做什么

输入两张图：**标准图**与**待比对图**。输出：

| 输出 | 说明 |
|---|---|
| 标准化得分 | 0.0–10.0 |
| 证据 | 原始相似度、匹配点数量、内点率、预处理尺寸、耗时 |
| 能力版本 | 算法与参数版本 |
| 状态 | `valid` / `failed` / `not_applicable`（无图） |

**不输出「匹配 / 不匹配」。** 阈值由 D 的算子实例决定。

**1.0 的适用范围**：同一张标准图与同一张待比对图的整体相似度。不做局部区域匹配、不做多标准图选优、不做旋转/透视校正之外的复杂变换。

### 5.5 输入从哪来

```
标准图  ← 每个活动一张，随规则版本冻结（D-05），C 只读不拥有
元素图  ← 业务为「图里有没有某元素」提供的那张图，同样随规则版本冻结
待比对图 ← A 的正式媒资（verified + archived），C 只读不下载
```

- **每个活动只允许一张标准图**，不做标准图组（2026-10-28 决策）；
- 标准图的存储与版本化方式未定（T-02），在 ADR 或 D 域 spec 关闭前，C 只按「一张可从 OSS 读取的图 + 稳定指纹」对待；
- 标准图变更 = 参数指纹变更 = 必须重算，不复用旧结果；
- **不允许使用 `carried_forward` 素材做「当前图匹配」**：它证明不了本轮当前图没变（规则引擎 design §8.2 第 8 条）。

### 5.6 什么时候跑

2026-10-28 决策（刘学奎）：业务进入第 2 层筛定时上传标准图或元素图，后台对**该活动圈定范围内的全量对象**执行比对，不等到规则发布。

1. **进入第 2 层时**：对圈定范围全量跑，产出每个对象的分值，供业务看分值分布并定阈值；
2. **受控重算**：能力升级或标准图变更后，由有权限的人指定范围补算。

**仍没有「入库即全量算」。** 比对范围是「该活动圈定的候选」，不是全部历史内容。

### 5.7 输出什么

一次比对的结果落到特征表，带五态、得分、证据、能力版本、产出时间。**同一 (素材, 能力, 版本, 参数) 只算一次**；再请求直接复用。

### 5.8 陈旧素材

待比对图是上一轮 `carried_forward` 的，或素材文件已不可读时：

- 状态记 `stale` 或 `missing`，不返回得分；
- 业务侧统一展示为「未获取成功」，不等待、也不判不达标（D 域 §1.4）。

### 5.9 C3 理解能力：三类

2026-10-28 决策（刘学奎）：C3 按输入形态分三类，不再按「语音与视频」笼统定义。

| 类型 | 输入 | 处理 | 输出 |
|---|---|---|---|
| **音频理解** | 视频音轨 | ASR | 转写文本（带时间点） |
| **图片理解** | 封面、主页背景、图文图片 | 视觉大模型 + 系统提示词 | 标准化结构化描述 |
| **视频理解** | 视频（关键帧或整段） | 视觉大模型 + 系统提示词 | 标准化结构化描述 |

音频最直接：调 ASR 拿到文本即可。图片与视频需要**系统提示词约束输出格式**，不允许自由文本。

### 5.10 标准化输出与落库

- 每个理解能力有一套固定的**系统提示词与输出 schema**；
- 输出必须是结构化 JSON（不是散文），落到特征表，带能力版本与产出时间；
- 下游的对话大模型读取这些结构化结果做判断，**不重新读原始素材**；
- schema 变更 = 能力版本变更，旧结果标 `stale`。

### 5.11 业务与对话大模型协作定标准

2026-10-28 方向（细节待 D 域设计）：业务不再只靠表单配阈值，可以与大模型对话描述标准（如「封面里要有活动主视觉，且不能出现竞品」），由大模型把标准转成可执行的判定条件。

约束：**对话产生的标准必须落成可复核的结构化条件**，不能只存在于对话历史里；否则无法解释、无法重算、无法审计。

## 六、C4 特征存储

### 6.1 一个对象一行

一条内容 / 一个账号只保留**一行**特征记录，信号放在结构化字段或 JSON 里，每个信号自带版本与时间。

理由：按信号拆行会让行数上一个数量级（约 218 万内容 × 十来个信号），而查询永远是「读这个对象的全部信号」。

### 6.2 每个信号自带版本与时间

```text
{
  "hashtags":       { "v": ["618", "海信中央空调"], "cap": "text@1",     "at": "..." },
  "cover_template": { "v": 0.83, "ev": {...},          "cap": "template@1", "at": "..." }
}
```

升某一个能力时只重算该信号的条目，不动其他条目。

### 6.3 复用键

见 §3.6。特征表按复用键判重，**重复请求不产生第二次计算**。

### 6.4 保留与失效

| 项 | 规则 |
|---|---|
| 判定结果（达标 / 不达标 / 未获取成功） | **长期保留**，作为成绩档案 |
| 判定证据与被判定引用过的特征 | **3 个月**（申诉期，2026-10-28 决策） |
| 未被任何判定引用的特征 | **1 年**，随 ODS 一起清理 |
| 旧能力版本的特征 | 确认无判定引用后清理 |
| 失败的记录 | 3 个月，供运营判断是否补采素材 |
| 重算的可行性 | 重算读的是 A 的正式媒资（长期保留），不读 ODS；证据删除后可通过重算重建（OCR 与视觉有费用，模板匹配免费） |

> **可解释性的取舍**：申诉期定为 3 个月。期内判定可完整下钻到证据；超过 3 个月只保留结论，不再能解释"为什么"。这个取舍由业务接受（刘学奎，2026-10-28），不是技术默认值。

## 七、能力版本与重算

### 7.1 什么时候算「能力升级」

以下任一变化都算升级，必须是新版本：

- 抽取/匹配算法或参数变化；
- 归一化规则变化（例如话题大小写策略调整）；
- 平台解析规则变化；
- 依赖的预处理变化（图像尺寸、去水印）。

**升级不自动重算历史。** 旧结果保留并标 `stale`。

### 7.2 重算是显式操作

重算不是界面上一个「重新识别」按钮。任何重算必须：

1. 指定范围（时间 / 品牌 / 活动 / 账号 / 内容）；
2. 展示预估条数与预估费用（1.0 档 1 免费，仍展示条数）；
3. 由有权限的人触发，记录操作者、范围、时间、能力版本；
4. 只重算该范围，不越界。

这样设计的原因：新增一个能力后，业务的第一反应必然是「把历史全部重跑」，而全量重算在 2.0 接入付费识别后就是百万级调用。

### 7.3 重算不阻塞判定

重算期间，D 可以用旧值继续判定（带 `stale` 标记）；也可以等待。**这是规则侧的策略，C 不替它决定默认行为。**

### 7.4 旧结果不删除

新版本结果写入后，旧版本记录保留供对账：同一范围内两版得分差异、翻转的对象清单。

## 八、失败与未知

### 8.1 识别失败 ≠ 未命中

技术失败（图片损坏、算法异常、超时、依赖未就绪）一律记 `failed`，规则看到 unknown。**绝不能把失败写成 0 分或空数组**——那会让「没算」和「算出来是零」混为一谈。

### 8.2 素材缺失

需要比对图但 A 还没有 verified 媒资时，状态是 `missing`，并向 D 暴露「需要素材」这件事（由 D 通过 A 的媒资需求链路补下载），C 不直写同步任务。

### 8.3 不适用

图文没有视频时长、内容没有封面、账号没有自定义背景图 → `not_applicable`，不是失败，也不触发识别任务。

### 8.4 过期与不可重算

媒资文件缺失、损坏或从未归档 → 标记不可重算，保留原结果与原因。**ODS 过期不影响重算**，因为重算读的是长期保留的正式媒资。

## 九、谁能做什么

C 没有独立界面。它的操作入口都在相邻域，权限由 B 统一发放：

| 动作 | 典型 Capability | 说明 |
|---|---|---|
| 查看某对象的信号与证据 | 随对象的读取权限（内容/账号） | 没有内容读权限就看不到证据 |
| 触发受控重算 | 独立的写能力，默认只给平台运营 | 必须带范围与预估 |
| 注册新能力 / 升版本 | 研发发版，不走业务界面 | 记录变更 |
| 查看信号目录与覆盖率 | 平台运营 | 哪个信号在哪个平台可用、覆盖率多少 |

**未注册的信号默认不可用**；规则引用一个未注册或未启用的信号时，保存即拒绝，而不是运行时返回空。

| 不做 | 原因 | 何时再做 |
|---|---|---|
| pHash 作为判同或变更检测 | 媒资判同已由 SHA-256 承担（D-11） | 需要「近似重复」时，作为信号而非判同 |

| 自己调供应商 API 取内容 | 采集属于 A | 永不 |
| 全量自动重算 | 成本不可控 | 永不 |

| 对方 | C 要什么 | C 给什么 |
|---|---|---|
