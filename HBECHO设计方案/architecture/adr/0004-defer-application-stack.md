# ADR-0004 · 暂不冻结应用框架、ORM/迁移工具与队列

- **状态**：superseded（2026-11-04）—— 框架、ORM/迁移工具与队列由 [ADR-0005](0005-application-stack-and-auth.md) 决定，目录约定由 [ADR-0013](0013-repository-layout.md) 决定；本 ADR 只保留延迟决定的历史背景，不再约束实现
- **日期**：2026-09-02
- **决策人**：刘学奎
- **替代**：旧项目沉淀中的 NestJS / Prisma / BullMQ / Redis 选型

## 背景

2026-09 的文档重组把「应用框架、ORM/迁移工具、队列实现」明确列为未决项。原因不是没有偏好，而是这些决定难以逆转，且会被脚手架悄悄固化：一旦 `create-app` 跑过，技术栈就变成了事实，而不是一个可以被评审的选择。

与此同时，数据底座的 tracer 可以被完整规格化，不依赖任何框架选择。

## 决定

1. **不预选、不预装、不生成脚手架**。服务器上不装 Redis、不装 ORM 工具链、不装应用框架。
2. 运维手册 §1.3 的目录规划与 §5 的安装清单**不得**用「已经装了什么」来代替技术决策。
3. 需要开工时，单独提出决定，写一份新的 ADR，至少说明：
   - 框架 / ORM / 迁移工具 / 队列各自的选择与版本；
   - 备选方案及不选原因；
   - 「不用它做什么」——哪些职责仍然自建；
   - 对 v2 的事务边界、受限写入过程、CHECK 约束、迁移可重放性的影响；
   - 迁移脚本能否在空库上从头执行得到相同结构。
4. 在该 ADR 合入前，`a-data-foundation-tracer` 只能做离线 fixture、合同锁定与纯领域逻辑，**不得**引入框架特有的运行时或目录约定。

## 备选与不选原因

| 方案 | 不选原因 |
|---|---|
| 直接沿用旧项目的 NestJS + Prisma + BullMQ + Redis | 与 hbecho 的基线冲突：v2 的任务语义依赖 MySQL 的 `FOR UPDATE SKIP LOCKED`、受限写入过程与 lease/fencing；引入 Redis 队列会新增一套基础设施并把任务状态分处两库 |
| 先搭脚手架再补设计 | 脚手架会把未决项变成既成事实，后续评审只能追认 |

## 后果

- 实现线暂时没有代码；这是有意为之，不是停滞。
- 第一份可运行代码出现前，不购买测试 ECS（沿用 hbdam 2026-10-14 的决定）。
- 服务器上已装的 Docker 是运行时，不是框架选择；不要把它当成已选型的证据。
