## 1. 三个固定位置

| 位置 | 是什么 | 怎么用 |
|---|---|---|
| 主目录 `~/Documents/hbecho` | GitHub `main` 的**只读镜像**，对话和阅读的地方 | 不在里面改文件；每次合并后由 AI 拉取到最新 |
| 预览工作树 `~/Documents/hbecho-preview` | 界面和代码的工作区，自带依赖 | **它当前所在的分支，决定 4100（原型）/ 4400（完整应用）展示什么**；一次只做一件事；4100 / 4400 常驻，不要关 |

**对话始终在主目录进行，不需要换目录、不需要新开对话。** 分支和工作树由 AI 用命令创建；IDE 文件树只显示主目录，未合并的草稿请 AI 展示内容，或到 GitHub 分支上看，或把对应工作树用「Add Folder to Workspace」加进来。

## 2. 三类工作怎么走

**A · 小修改**（已有页面的按钮、筛选、文案、布局）
需求 → AI 判断是小改并建议「一批还是几批」→ 预览工作树切到 `fix/<主题>-<日期>`（从最新 `origin/main`）→ 改完在 **4400** 看、截图 → 你说「确认」→ **本地提交**（可以多个）→ 本机 verify 一次 → 你说「推送到 GitHub」→ **推一次** → CI 绿 → 合并 `main` → 经你同意部署 → 运维记录 → 清理分支。

**B · 新 spec**
需求 → AI 调研，建 spec 分支，写 requirements / design → 带页面的先在 **4100** 做原型，**你明确说「确认」后**才写页面任务和代码 → 实现、4400 验收，期间都是本地提交；建表 / 迁移后在本机跑一次 verify → 你说「推送」→ **推一次，CI 一次** → 合并 → 经你同意部署 → 运维记录 → 清理。

**C · 纯文档 / 规则**
临时工作树 → 本机文档检查 → 本地提交，**附在下一批里一起推**（紧急修复除外）。

## 3. 提交、推送与 CI（CI 额度有限）

- **「提交」= 只在本机 `git commit`，不花 CI。「推送到 GitHub」只有你明确说才做。**
- **每次推送前，AI 先盘点**：所有本地分支上已提交未推送的提交、各分支领先 `main` 的数量；能合成一批就合成一批（几条分支在本机合进一个批次分支，只推它），报给你确认后再推。
- **一批小修改、一个 spec，都是只推一次、CI 一次。**
- 需要异地备份时：备份推送的最新提交说明里写 `[skip ci]`，GitHub 不跑 CI；要合并的那一次不写。
- 合并进 `main` 时分支必须已含最新 `main`（树一致）。`main` 上只跑「文档与密钥门禁 + 构建镜像」，**不重跑 verify**；所以每批通常是 1 次完整验证 + 1 次轻量运行，而不是 2 次完整验证。
- 推送后、合并前不要再推同一分支（新的推送会取消上一次 CI）。
- 失败先 `gh run rerun <run-id> --failed`，不为重跑再 push。`scale.perf.db.test.ts`（2,000 行名单并发解析）有已知偶发失败，先重跑一次再查。
- 2026-11-18 一天跑了约 26 次、墙钟约 7 小时，原因是逐任务推送、逐次合并，所以**攒批**是第一优先。

## 4. 谁做什么、需要你说什么

| 事项 | 谁 |
|---|---|
| 提需求和范围；界面「确认」；**「推送到 GitHub」**；「同意部署」 | **你** |
| 建分支、写代码和文档、本地提交、本机检查、推送前盘点、（你说推送后）推送、等 CI、合并、拉取主目录、清理 | AI |
| 部署到 ECS（Workbench）、写运维记录 | AI 做，**你同意后**才做 |

「没有反对」不等于确认；超出已确认范围要重新确认。

## 5. 每次新会话，AI 先报告

主目录是否在 `main` 且干净；落后 `origin/main` 几个提交；有无未推送的分支或遗留工作树；预览工作树在哪个分支；ECS 线上版本与 `main` 是否一致。
