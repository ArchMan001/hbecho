## 1. 背景与证据
同一个判定计划连续执行 4 次，「未获取成功」从 368 → 311 → 151 → 39（测试机 2026-11-20 的执行 9–13）。原因不是判定逻辑，而是**每次执行时各账号的视频列表还没采完**：D 只读已落库的数据，零内容的专员需要「窗口内有一次完整的列表同步」，没有已终态的列表任务就记 `sync_failed`。名单导入后补采列表要几十分钟（解析约 4 秒 / 账号、列表约 4 秒 / 页，同步并发有限），在这段时间里点「执行」，结果里全是误报。

最后剩下的 39 个才是真问题：25 个身份校验误报（已另行修复）、14 个旧批次预算拦截（已重开监控）。

## 2. 需求
| # | 需求 |
|---|---|
| WC-1 | **执行前自动等待（刘学奎选 C）**：点「执行」后，若本次参与账号里还有账号处于「采集中」，执行先进入「等待列表采集」，全部采完（或等待超时）再继续判定，使结果基于最新数据。 |
| WC-2 | **「采集中」的定义**：参与账号存在未终态的 `fetch_content_list` / `fetch_profile` / `resolve_account` 任务（`pending` / `running` / `retry_wait`，任何批次、任何 purpose），或其名单项来自仍在 `resolving` 的导入批次。**已经终态失败的账号不算**（例如身份校验失败、预算被拦），它们不阻塞执行，只在结果里提示。 |
| WC-3 | **等待有上限**：默认 60 分钟（配置项，不写死）。超时后继续执行，仍在采集中的账号记「采集中，未完成」（见 WC-4），页面顶部说明「执行时仍有 N 个账号在采集」。 |
| WC-4 | **「未获取成功」拆成两种原因**：`sync_pending`（还在采集 / 等待超时时仍在采集）与 `sync_failed`（采集失败）。点检表与执行详情分别显示「采集中」「采集失败」。 |
| WC-5 | 等待期间**可取消**；取消语义与现有 `waiting` 状态一致。 |
| WC-6 | 没有「采集中」账号时**不增加任何等待**（直接进入下一阶段）。 |
| WC-7 | 等待阶段**不发起任何供应商调用、不花点数**；它只读 A 的任务表。 |

## 3. 非目标
- 不主动给账号补采（补采由名单导入的收尾与周一全量负责；本 spec 只等待，不触发采集）；
- 不阻止「建立 / 保存」判定计划，只影响「执行」；
- 不改变判定语义（三值逻辑、数量要求、零内容规则）。

## 4. 未决项（等刘学奎答复）
| # | 问题 | 建议 |
|---|---|---|
| U1 | 等待上限默认多久？ | 60 分钟；一次名单导入全部补采约 20–30 分钟 |
| U2 | 等待超时后是否继续执行？ | 继续执行并标明数量（不继续的话用户会一直卡住） |
| U3 | 页面文案与展示（见 design §界面） | 沿用现有「等待」状态，新增「等待列表采集」 |

## 5. 失败语义与验收边界
- 等待阶段崩溃 / 重启：按现有阶段续跑（阶段详情里记 `waiting_on = "collection"` 与截止时间，重放安全）；
- 读 A 的任务表失败：整次执行失败并留原因，不当作「没有采集中」；
- 验收见 [tasks.md](tasks.md) 的 T1–T4；离线测试，不发真实调用。
